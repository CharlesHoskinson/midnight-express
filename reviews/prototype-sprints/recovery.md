# Sprint 2: durable RFQ processing and measured SQL recovery

Status: proposed implementation and acceptance plan, 2026-10-03. This document adds no runtime implementation and reports no new test passes. It expands [Sprint 2](sequence.md) using the [UmbraDB recovery foundation](../../docs/product-requirements/umbradb-recovery.md) and [event-contract rules](../data-model/event-contracts.md).

## Scope and baseline

Deliver one trusted Node >=24 workflow host backed by PostgreSQL, handling the Sprint 1 buyer/two-dealer RFQ fixture. Accepted terms, event/action replay guards, acknowledgement outbox, checkpoint and processing cursor must recover as one committed local outcome. Keep application policy and semantic validation above the storage primitives. Genuine admission continues on its separate track; a stand-in can support an explicitly labeled local recovery experiment but cannot establish anonymous admission.

The inspected UmbraDB baseline is 0.9.5, commit `3c0c68b3d0397ee2e8344b77e9ed715132fef6ca`; PostgreSQL 17 is the reviewed test baseline. Its public `withTransaction` handle can be shared by TemporalKV, checkpoint `save` and watermark operations. This is verified API/source composition, not an executed MPE recovery test. The future MPE atomic-effect helper is unimplemented. `saveAndAdvance(deps, walletId, networkId, data, cursor, opts)` covers checkpoint/cursor only and opens its own transaction; do not nest it or use private SQL-resolver imports.

Run one writer, one host and one trust domain. Umbra leases are cooperative and use a different connection from the effect transaction. They do not fence stale commits or prove safe HA failover. Exclude replicated retention, independently signed storage receipts, shared plaintext multitenancy, mobile retrieval, settlement and production availability from this sprint. SQLite on standalone Rust clients remains a separately verified adapter; PostgreSQL evidence does not transfer to it.

## Entry and immutable recovery model

Entry requires the Sprint 1 RFQ flow, closed installed contract bundles, signature/role policy, offer revision and competing-acceptance rules, transport expiry behavior and source adapter mapping. Record the admission result separately. Assign implementation and review owners before starting the proposed two-week timebox; dates and capacity remain unset.

Persist these components within the host's application/network/authority domain. Names below describe logical records, not new Umbra API methods or an approved SQL schema.

| Component | Required contents and invariant |
|---|---|
| Authenticated inbox | Original envelope/event bytes or protected references; EID, authenticated `(source,id)`, occurrence digest, contract/profile/schema digests, verification provenance, causation/correlation, occurrence time, separate transport/authority expiry, source version/finality and inventory position. Preserve originals; never recreate wire evidence from a migrated object. |
| Source projection | Application-owned adapter identity/version, authenticated source scope, sequence/version, snapshot base or delta predecessor, finality evidence and explicit gap state. Arrival order or occurrence time alone never defines source freshness. |
| RFQ acceptance | Request ID, exact offer ID/revision, immutable signed terms/digest, quantity and asset/scale, price convention, conditions, buyer/dealer role evidence, authority domain, acceptance action ID and durable result. A single request's selected offer is changed only by the pinned state machine. |
| Event guard | Scope includes consumer/application/network and authenticated `(source,id)`; binds original occurrence digest and its processing disposition. Same identity plus different content is a conflict. |
| Action guard | Scope includes application/network, destination and replay policy domain plus `actionId`; binds canonical authorized action digest and prior result. Its durable scope survives profile upgrades; profile digest is retained in the assertion, not used to reset action consumption. |
| Outbox | Stable output identity, destination idempotency key, signed acknowledgement assertion/bytes, correlation/causation, expiry and dispatch/reconciliation status. An acknowledgement states the exact committed acceptance; transmission alone does not prove receiver processing. |
| Checkpoint | Projection bytes and digest, domain/network, exact semantic bundle identities, source versions/finality, source/inventory cursor and replay-guard generation/reference. Secret-bearing bytes are encrypted before raw storage. Hash integrity alone establishes neither provenance nor freshness. |
| Cursor | Separate opaque retention/inventory position from application processing position. Application progress is a contiguous prefix of committed effects or explicit policy dispositions; never a maximum observed source number or last-arriving EID. |

All source/type/profile/role/correlation selectors stay inside encryption; store lookup metadata is private to this trusted host. Protect local quarantine, database/WAL/backups and key access according to the declared threat model. Umbra supplies no built-in at-rest encryption or secure erasure. Do not retain retired session secrets in historical snapshots and then claim erasure.

For duplicate detection compare a pinned occurrence assertion digest and the canonical action assertion digest, not EID alone. A resealed envelope can have a new EID for the same event/action. A new event can legitimately carry an already-consumed action: authenticate it, return the prior result on a matching action digest, and record its disposition without another acceptance or new semantic acknowledgement. An action ID with changed terms, destination, constraints or contract-bound meaning fails as a conflict.

## Processing transaction and recovery procedure

1. Authenticate/recognize and persist the inbox before handler execution. Bounded parsing and exact installed-contract validation precede actionable dispatch. Invalid/unknown contracts enter protected quarantine; no acceptance or acceptance acknowledgement is created. An ingress retention cursor can advance after durable capture, but that does not advance business progress.
2. Open `withTransaction`; pass the same public handle to every participating TemporalKV read/write, checkpoint `save`, and watermark read/write. Recheck current authorization, expiry, RFQ/source versions and relevant gap policy inside the serialized/CAS transition. Prevalidation alone must not authorize a stale acceptance.
3. Resolve existing event/action guards before effect creation. An identical committed duplicate returns its persisted result; it does not repeat the transition, regress the cursor or allocate a fresh output action. A conflict leaves business progress unchanged and creates separately durable diagnostic/quarantine evidence after rollback. An unsupported or unresolved gap must remain visible until policy resolution.
4. For a new valid action, atomically create guards, CAS the request/offer state, retain exact accepted terms/result, stage the explicit signed acknowledgement, save the configured checkpoint and monotonically advance only the contiguous processing prefix. If any part fails, roll back all these records. A racing create-only/CAS failure is not proof of a matching duplicate: roll back and compare the winner's content in a fresh transaction.
5. Commit before exposing business acceptance or dispatching the outbox. A lost commit response means outcome unknown; reconnect to authoritative local storage and query event/action/result records. Retry with the same identities only after reconciliation. No absence judgment is safe while PostgreSQL recovery/querying remains unavailable, and no external side effect belongs inside the callback.
6. Dispatch committed outbox entries separately. Preserve EID and expiry for retransmitting the same envelope; persist sealed bytes before sending if envelope sealing happens after acceptance. Resealing is an explicitly different envelope, never a new business action. Persist dispatch/reconciliation transitions with CAS and never send an expired pending envelope merely to complete the demo.
7. Restart by reconciling authoritative committed records and unfinished inbox/outbox work. Use a checkpoint as a projection optimization; never overwrite newer action guards, accepted terms or progress with older snapshot contents. If a database backup itself is older than trusted progress/guard evidence, refuse automatic effectful recovery and expose a recovery gap. A snapshot hash cannot solve rollback of the entire database.

Permanent rejection/quarantine may close a processing position only through an explicit durable policy disposition; that means inspected/rejected, not accepted. Unresolved source gaps/conflicts block that source's contiguous business progress while unrelated workflows can continue. Record the disposition with its position transactionally. Watermarks are last-write-wins primitives: the caller must enforce monotonicity and contiguity using guarded records/CAS in the same transaction; do not assume built-in ordering protection.

## Crash and fault matrix

Every row inspects the complete vector: inbox, original-byte/provenance references, RFQ terms/result, event/action guards, outbox, checkpoint, processing cursor, source versions/gaps and receiver result. Merely restoring checkpoint bytes does not pass. `old` means the last committed prefix; `new` means all components of the tested processing transaction committed together.

| ID | Fault/fixture | Required observed outcome |
|---|---|---|
| F01 | Kill before inbox persistence, then replay retained input | No business effect/cursor advance; input is recovered from available history or a missing-history gap is explicit. |
| F02 | Kill after inbox commit, before handler | Inbox pending survives; replay yields one authorized acceptance. |
| F03 | Inject failure after each guard/effect/outbox/checkpoint/cursor write, before COMMIT | Vector remains old with pending inbox; no outbox sends; replay commits new once. |
| F04 | Kill client or sever connection while COMMIT is in flight | Recovered vector is entirely old or new. Caller first reconciles uncertainty and returns persisted result or safely retries identical intent. |
| F05 | Kill after confirmed commit, before dispatch | New terms/guards/checkpoint/cursor survive; original outbox entry is dispatched without another local acceptance. |
| F06 | Receiver commits acknowledgement, response is lost; kill before local confirmation | Destination key yields prior receiver result, or entry remains uncertain for reconciliation. No fabricated completion or second receiver effect. |
| F07 | Crash during dispatch status/retry write | Pending/in-flight/uncertain state recovers via destination query or stable-key retry; no new business identity. |
| F08 | Repeated input and concurrent identical action; same action in new event/new EID | Exactly one local accepted result and semantic outbox output; later occurrences record matching duplicate disposition. |
| F09 | Same event ID with conflicting content; same action ID with changed digest; competing offers for one request | Conflicts are preserved without cursor skipping; one request acceptance wins under CAS/state-machine rule. No silent discard of conflicting authority. |
| F10 | Abrupt PostgreSQL termination/restart after acknowledged COMMIT | New vector survives under declared local WAL policy. A graceful restart alone cannot satisfy this row; storage/power-loss guarantees remain outside measured coverage. |
| F11 | Unsafe durability at startup, on a new pool connection and reconnect | Writer refuses processing before acceptance/dispatch claims. Evidence shows actual effect-session policy, not only a migration connection warning. |
| F12 | Disconnect; out-of-order deltas, missing predecessor, duplicate snapshot, stale/provisional source evidence | No false contiguous progress or promoted finality. Valid base/snapshot repair is adapter-authorized; unavailable/expired history yields typed gap. |
| F13 | Older checkpoint with newer durable guards; wrong domain/network/profile/key; corrupt bytes; full backup rollback | Older projection cannot resurrect consumed actions. Mismatched/corrupt restore refuses; missing trusted freshness exposes a blocker/gap, not a successful secure restore. |
| F14 | Profile upgrade and replay of A under B; B adds approval restriction or changes units | Retain exact A evidence/validator and stable guard scope. Unsupported/changed authority refuses; no latest-schema reinterpretation, default permission or action reset. |
| F15 | Poison event, failing handler, cancellation, explicitly authorized redrive | Bounded protected quarantine/retry; unrelated handlers continue. Cancellation is local; redrive rechecks authorization/expiry and preserves identities. `once` never promises business exactly-once. |
| F16 | Expire offer/authority between validation and commit; expire retry/outbox before dispatch | Recheck fails before new acceptance, or expired dispatch is refused. Prior valid acceptance stays committed with explicit undelivered/expired status; fresh authorization is needed for changed intent. |
| F17 | Restart while a second writer or an old cooperative lease holder remains alive | Stop/refuse the unsupported overlap and report violated single-writer precondition. This exercise cannot demonstrate fenced HA safety. |
| F18 | Prune history/checkpoint/guard dependencies inside declared replay horizon | GC is refused or horizon narrowed explicitly with unavailable recovery reported. Live checkpoint manifests and referenced guard/output evidence survive; deleting guards cannot enable replay. |

For F06 also run a receiver without durable idempotency/query support: automatic resend after an ambiguous success must stop for manual resolution. A SQL transaction cannot make arbitrary remote execution exactly once. The receiver fixture proves only its declared destination contract.

## Profile evolution and restore gate

Retain a digest-pinned bundle and validation/adapter version for every actionable contract still within inbox, replay, backup and restore horizons. Keep original signatures/bytes and explicit derived-projection provenance alongside any materialized new representation. Compatibility records name old/new semantic digests, direction, preserved restrictions, source/finality mapping, expiry rules and signer treatment. Changing signed meaning requires fresh authorization; a migration is not that authorization.

Test an accepted A action replayed after deployment of B under the same event, a different event and a resealed EID. All return the same local result only when the original authorized action digest matches; no replay guard is recreated in a B-only namespace. An old signed event never gains B defaults or loses A conditions. A genuinely new contract-bound intent reusing a consumed action ID conflicts. Negotiate only installed allowlisted contracts above local minimum policy; retain dual-read support until replay/restore horizons close.

Secure restore requires reviewed trusted freshness/anti-rollback evidence, context binding and key custody. Where that evidence is unavailable, report this production gate as unresolved and constrain the internal demo to the current authoritative database. Do not claim protection against total backup rollback, historical-key disclosure or secure erasure from the single-host fixture.

## Evidence and exit decision

Produce one run manifest containing baseline commits, exact dependency/contract digests, runtime/host/OS, PostgreSQL settings, signing/expiry policy, single-writer assumptions, source/receiver fixture labels, clock setup, data size/concurrency and admission real/stand-in status. Store encrypted/private fixture details separately from redacted shareable logs; packet/topic evidence must not expose business selectors or secrets.

Each F-row records command/seed, injection point, expected vector, observed durable before/after records, receiver ledger where relevant, run count, timestamps, outcome and artifact hashes. Include non-skipping executable commands in the eventual prototype's evidence bundle. Database crash tests blocked by Docker/socket or other host access are **blocked**, not passed; the reviewed Umbra baseline crash suite was not rerun locally. Synthetic crash durations, replay counts, event age and retry attempts are distributions under that manifest, not SLAs or customer savings.

The demo starts with a valid signed offer, commits acceptance, kills the host at F03/F05/F06, replays on reconnect and shows identical accepted terms/result plus explicit acknowledgement status. Then show conflicting identities, expired retry, a source-history gap, poison-handler isolation and profile-upgrade replay protection. Separate transport receipt from business acceptance and receiver confirmation in the UI/logs.

Sprint 2 passes for bounded local reuse only when the public transaction integration, concurrent acceptance, F01–F16 and retention behavior have non-skipping evidence; F17 documents/enforces the single-writer boundary rather than HA. Any test requiring unavailable freshness evidence is explicitly blocked for the stronger restore claim, with the narrower authoritative-database demo stated. Carry failed core transaction/duplicate/durability cases into Sprint 3 before invoice or agent breadth. Admission progress is reviewed independently. Production adoption still requires the fourteen future recovery requirements, hardened restore/key/erasure policy, retention/availability evidence and ledger authority/replay/anchored-message gates.
