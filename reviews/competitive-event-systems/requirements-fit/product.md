# MIDNIGHT EXPRESS: REQUIREMENTS FIT OF GOSSIPSUB + SIGNAL AND OPEN-SOURCE COMPONENTS
Independent reviewer: design_review_product. Checked2026-10-03 America/Denver.
Status: Documentary architecture/product assessment; no installs, integration tests or production acceptance performed.

ANSWER
GossipSub plus a Signal-derived session protocol is a useful two-layer foundation, not a complete implementation of the original requirements. The missing work is several independent systems: private admission, durable recovery, recipient recognition/retrieval, Midnight proof/ledger integration, operations and verification. There is no single third protocol that closes all those gaps.

If selecting one additional PROTOCOL investment for production, prioritize real anonymous quota/admission proofs (RLN-style). Signal encrypts messages but does not establish authorized network publishing allowances; GossipSub peer scoring is not private, chain-backed admission. For private mobile reception, separately investigate PIR/OMR. For forward-secure groups, separately investigate MLS. For hiding client IP from a connection endpoint, separately investigate Tor. These are contextual modules, not substitutes for each other.

## OPEN-SOURCE CANDIDATE STUDIES
Each item was reviewed against its primary current repository/documentation. License labels summarize primary project notices, not legal clearance for every dependency or combined distribution. No tool is selected merely because its README describes useful functionality.

rust-libp2p — https://github.com/libp2p/rust-libp2p ; https://github.com/libp2p/specs/blob/master/pubsub/gossipsub/gossipsub-v1.2.md
Rust networking engine, MIT project notice; baseline reuse candidate. Need exact release/profile1.2 behavior and MPE-specific scoring/validation. Not a managed delivery network, store or recipient-private service. Go: wire/interoperability/admission-cache tests pass. No-go: default config accepted as production privacy/security evidence.

libsignal — https://github.com/signalapp/libsignal ; https://github.com/signalapp/libsignal/blob/main/LICENSE
Rust session implementation with Java/Swift/TypeScript interfaces, AGPLv3; external use explicitly unsupported and API changes require maintenance. Candidate backend experiment if license/distribution and exact profile decisions permit; no automatic Apache2 relicensing. Independent business signatures remain required. Need packet/KEM/header compatibility and crash-safe supplied stores before normative conformance.

Waku RLN and Zerokit — https://docs.waku.org/learn/concepts/protocols ; https://github.com/vacp2p/zerokit ; https://github.com/waku-org/nwaku
Current Zerokit describes Rust RLNv2 implementation using Circom/Groth16, FFI/WASM interfaces and multiple-message-ID burn; project offers MIT/Apache2. Waku nwaku URL currently redirects to logos-messaging/logos-delivery; that node project also exposes MIT/Apache2 licenses. Zerokit engine may support MPE admission research, while adopting the full node stack adds transport/storage conventions that require separate review. MPE requires exact genesis/registry/window/class/credit/content binding, membership-root lifecycle, nullifier replay handling and maximum encoded proof cost. No claim upstream RLN proof matches those fields already. Gate: show selected circuit/proof statement compatibility, setup/prover-key provenance and performance/security acceptance. Waku filtering is not default MPE recipient privacy.

OpenMLS — https://github.com/openmls/openmls ; https://github.com/openmls/openmls/blob/main/LICENSE
MIT Rust MLS implementation with pluggable crypto and storage providers, including repository SQLite storage modules. Candidate group engine after group application policy is decided. Does not give identity discovery, operator delivery, private topology, archival policy or Midnight authority. Need epoch-ordering/revocation/recovery, complete sealed control framing and encrypted packet-size tests. No new blanket audit/maturity claim inferred from code/repository existence.

mls-rs — https://github.com/awslabs/mls-rs
MIT/Apache2 Rust MLS library with configurable credentials/state and memory/SQLite providers. README claims RFC9420 conformance but explicitly states it has not received a full third-party security audit; some crypto providers are experimental. Candidate comparison with OpenMLS, not production-approved alternative. Gate: chosen provider/features audited for selected deployment, cross-library vectors and application membership/recovery invariants pass. Groups are contextual, not necessary for a two-party pilot.

Microsoft SEAL — https://github.com/microsoft/SEAL
MIT C++ homomorphic-encryption library; useful computational substrate, not PIR protocol or routing service. Current README recommends4.4.0+ critical fixes for untrusted input/memory/interoperability. Need safe parameter choices, bounded parser/computation and chosen PIR composition. Do not conflate Microsoft SEAL with Sui's Seal key-management service.

SealPIR — https://github.com/microsoft/SealPIR
MIT computational-PIR example/research library; README explicitly says not to use it in production and documents SEAL4.0.0 dependency. Benchmark/reference only until maintained secure implementation selected. The old documented pin conflicts with current SEAL upgrade guidance; version/API migration and security validation are real work. Hidden database index does not by itself hide query occurrence, schema/tenant choice, database-update patterns or selective failure.

Google private-retrieval — https://github.com/google/private-retrieval
Apache2 C++17/Bazel private retrieval library. README explicitly says not an officially supported Google product, provided as-is. Candidate research engine, not managed Google confidential delivery. Gate: exact retrieval construction, mutable-database/update model, response integrity/completeness, query timing and mobile/server cost evaluated. No assumption of audited production readiness.

SimplePIR / DoublePIR — https://github.com/ahenzinger/simplepir
MIT reference Go implementation accompanying USENIX2023 research, explicitly research prototype. Candidate bandwidth/CPU/hint-preprocessing comparison. Client hints/database churn matter for a constantly changing48-hour event store; paper throughput is not a validated MPE mobile/server figure. Gate: full recurring hint/update/network/energy cost and malicious-server behavior, not only per-query payload.

Tor / Arti — https://arti.torproject.org/about/ ; https://docs.rs/arti-client/latest/arti_client/ ; https://docs.rs/crate/arti-client/latest
Arti is the Tor Project's embeddable Rust client, MIT/Apache2 crate. Current arti-client docs state APIs are pre1.x, ongoing updates are necessary and give process-exit-on-obsolete-consensus caveat. For non-Rust integration documentation suggests CLI SOCKS subprocess. Tor can hide a client's direct source address from destination under its threat model; not a mix-network substitute for global timing/volume/relationship resistance. Candidate optional TCP connection profile, not universal GossipSub/UDP anonymization. Gate: no DNS/direct fallback leaks, circuit isolation/lifecycle and observable overhead tested; failures must not silently downgrade declared privacy. Running client through Tor does not fund MPE operator service.

RocksDB — https://github.com/facebook/rocksdb ; https://github.com/facebook/rocksdb/blob/main/LICENSE.Apache
Embedded persistent C++ key-value store, dual GPLv2/Apache2 choice. Candidate node storage where measured write/read workload benefits; explicit license choice recorded. Implement transactions/write batches, WAL/sync recovery, retention pruning, indexes and encryption-at-rest policy. It is not replicated archival protocol and atomic local state is not a remote-side-effect guarantee. Gate: crash/restart/replay/receipt-after-persistence tests with selected bindings/configuration.

SQLite — https://www.sqlite.org/copyright.html ; https://www.sqlite.org/atomiccommit.html ; https://www.sqlite.org/security.html
Core SQLite public domain, embedded transactional SQL engine. Strong initial candidate for client cursor/dedup/ratchet state and modest pilot stores. Atomic commit depends on configuration/OS assumptions; ordinary core is not transparent encrypted storage or remote replication. Encryption needs selected additional layer/engine with separate license and review; encrypted payloads do not hide all index metadata. Gate: atomic effect+cursor+dedup and ratchet-store tests under crash, backup rollback and fsync/fault model. No need to add both RocksDB and SQLite everywhere.

## MINIMAL BACKEND COORDINATION PILOT
Use rust-libp2p GossipSub with specified profile, existing MPE envelope/recognition, authenticated invitations, one-device pairwise crypto adapter if compatible, and a selected SQLite or RocksDB durable state layer. Add application SDK plus complete-shard retention/backfill, typed status, gap reporting and local effect idempotency. Stage0 may use mock Ledger Adapter and explicitly labeled stand-in admission per MPE-OPS-045; that cannot claim production admission unlinkability. A simpler default symmetric-profile pilot can precede any Signal integration; optional ratchets are not needed to prove basic workflow value.

Pilot business scenario: buyer and dealer exchange private RFQ/offer/accept messages; users explicitly authorize replies. Keep it coordination-only until genuine Midnight signature/replay/expiry and anchored-envelope binding proof acceptance passes. Production still requires selected real admission proof; proof generation/verification must satisfy MPE-ECO-048 rather than assumed millisecond placeholders.

## FULL PROFILE / MOBILE / PRODUCTION EXTENSIONS
Required for ordinary production regardless of optional advanced crypto: real private quota/admission, Bus Registry and finalized ledger adapter, durable replay/window state, replicated retention/repair, operator funding/governance, verified release gates, complete privacy observation inventory and actual workload/security evidence.
Required if those advertised features are selected: MLS or another reviewed group protocol for scalable forward-secure groups; PIR/OMR and recognition-independent scheduling for resource-limited private mobile clients; Tor/Arti for optional connection-origin protection; carefully reviewed key-history/backup composition; nested-crypto-compatible application authority proofs for message-triggered effects. None supplies the other layers by itself.

## PRODUCT GO/NO-GO
Go now for measured component experiments and backend coordination reference application, not universal privacy/service promises. Adopt components only after: (1) exact live requirement-owner mapping; (2) license/API/maintenance owner; (3) actual serialization and cost; (4) state/chaos/backup recovery; (5) observer-leakage trace tests including lookup/repair/confirmation; (6) independent security/composition review; (7) consumer workflow/customer evidence; (8) funded operator and verified ledger capability gates where production is claimed.

The practical third building block is therefore an admission-proof layer plus durable product infrastructure, not another all-purpose messaging brand. Prioritize useful backend workflows first; separate proof admission, group crypto and mobile private retrieval experiments so each result can be assessed against the original requirement scope.

## MOBILE DISCOVERY COST ILLUSTRATION — NOT A SELECTED DESIGN
A proposed public discovery inventory with only16-byte salt plus16-byte recognition tag would carry32 bytes per envelope. At the design ceiling10 envelopes/s,864,000/day means27.648 MB/day before inventory framing, authenticity/completeness verification, retransmission or PIR. Adding a32-byte envelope identifier gives55.296 MB/day, already near the design56–60 MB/day mobile budget before payload retrieval, hints and updates. This is derived arithmetic for an evaluation idea, not evidence the inventory is sufficient, a production performance result or a new requirement. PIR still needs private discovery of indices and a dynamic update/completeness model.

## GROUP-FIRST CRYPTO CHOICE
If the initial product emphasizes organizational groups, compare an MLS-only session layer (including two-member groups for pairwise conversations) against the Signal-derived pairwise layer. Do not adopt both by default. One session engine can reduce duplicated key/session stores, lifecycle logic, codec APIs, license decisions and audit surface. MLS credential validation, epoch ordering, delivery/recovery and application authority still need MPE integration. Signal-derived pairwise crypto may remain attractive for a specifically pairwise product, but the choice should follow measured profile fit and workflow needs. Run separate comparative experiments before choosing; do not infer complete interoperability, private discovery or Midnight proof compatibility from either engine.

## GOSSIPSUB IMPLEMENTATION BOUNDARY
The original expiry requirements also cover messages queued for IWANT responses and cached payloads: an application validation result alone may not prevent later stale sends from implementation queues/cache. Inspect the chosen rust-libp2p hooks and, where needed, maintain a narrowly scoped adapter or upstream patch with expiry/cache tests. This is component integration work, not evidence another protocol is required. Any modification retains reviewed message-ID, score and recognition-independent behavior.
