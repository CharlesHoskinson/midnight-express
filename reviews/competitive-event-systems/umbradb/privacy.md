# UmbraDB: independent privacy and recovery review

Reviewed 2026-10-03, read-only, against CharlesHoskinson/UmbraDB commit `3c0c68b3d0397ee2e8344b77e9ed715132fef6ca` at `/home/hoskinson/Projects/UmbraDB`. This is the Apache-2.0 TypeScript/PostgreSQL library, not the unrelated TUM Umbra database. Reviewed AGENTS.md, SECURITY.md, durability contract, transaction/lease, checkpoint, watermark, envelope, client and migration implementations, package API, and relevant canonical MPE requirements. No UmbraDB changes or executable tests were performed by this reviewer.

**Verdict: PASS for an isolated, nonsecret SQL recovery integration prototype. BLOCK unconditional production adoption for secret state, mutually distrusting tenants, or Store Node durable receipts until the gates below are implemented and tested.** Recommend an optional application/SDK backend recovery tier; do not replace the transport/admission hot path or local SQLite default on the strength of this audit.

## What the implementation provides

`saveAndAdvance` opens one transaction and passes its handle to both checkpoint save and watermark set (`src/postgres/save-and-advance.ts:58–70`). Checkpoint save joins a supplied transaction instead of opening another (`src/postgres/checkpoint-store.ts:291–303`). This is a useful foundation for recovery without a cursor committed ahead of its corresponding snapshot.

Checkpoint load reads under REPEATABLE READ and checks dense chunk positions, per-chunk SHA-256, and ordered manifest hash (`src/postgres/checkpoint-store.ts:348–392`). These detect accidental corruption and inconsistent chunk reconstruction. They do not authenticate data against a malicious database operator who can change payloads and recompute hashes, or detect restoration of an older, internally valid backup.

The package is currently version **0.9.5**, Node >=24 and ESM-only (`package.json`; `README.md:45–50`). PostgreSQL 17 is tested; 15/16 are described as untested. Apache-2.0 is confirmed by LICENSE and package.json. SECURITY.md's references to the 1.0.0 contract must not be presented as a released 1.0 or a current compatibility guarantee.

## Adoption blockers and exact boundaries

1. **High: no secret-state encryption is shipped.** The envelope encoder serializes ordinary UTF-8 JSON (`src/interfaces/wallet-state-envelope.ts:133–144`), and `PgWalletStateEnvelopeStore.save` writes those bytes directly (`src/postgres/wallet-state-envelope.ts:38–53`). SECURITY.md:107–144 expressly documents plaintext storage and secret-bearing wallet state. An MPE application must encrypt ratchet keys, recognition keys, wallet secrets and confidential workflow snapshots before raw `CheckpointStore.save`, or provide and audit a caller-owned encrypting CheckpointStore decorator. The existing envelope constructor permits such a decorator, but UmbraDB ships no cipher implementation. Bind ciphertext with AEAD associated data to principal, network, state format, key generation and application-controlled checkpoint identity. Keep decryption keys inside the Subscriber's trusted endpoint boundary (MPE-PRV-007); outsourcing encrypted backup storage must not silently outsource recognition/decryption. Disk/backup encryption protects stolen media under its key assumptions, not a DBA with access to a running database.

2. **High: the migration warning callback is not a rejection gate.** `synchronous_commit=off` returns a lost-tail warning (`src/postgres/durability-probe.ts:101–116`). `runMigrations` swallows both synchronous throws and asynchronous callback rejections (`src/postgres/migrate.ts:162–173`). Throwing from `onDurabilityWarning` therefore does not fail startup. Capture warnings synchronously, await migrations, then explicitly refuse adapter startup before any publication/receipt/effect if a lost-tail warning occurred. Alternatively perform adapter-owned SQL configuration checks. `probeDurability` is internal, not exported by the supported package root (`src/index.ts:72–74`; README.md:42–43), so do not prescribe a supported deep import. Enforce a flush-before-ack commit policy on every relevant transaction/session, not merely the one reserved connection probed at startup (`src/postgres/durability-probe.ts:194–205`). fsync and full_page_writes must remain enabled; avoid the opt-out. MPE-STO-011 explicitly concerns process-restart recovery; a stronger power-loss durable receipt profile must additionally exclude acknowledged lost tails. No claim of replica/failover durability follows from local-primary durability.

3. **High: principal isolation is a deployment obligation.** SECURITY.md:17–55 requires one trusted writer/trust domain, trusted database/backups/operator, and says schema names are not authorization. The global chunk pool and GC disclose known-content existence and cross-wallet references (SECURITY.md:57–105; `src/postgres/checkpoint-store.ts:233,518–532`). Mutually distrusting principals on one store are explicitly unsupported. Give each principal a separately secured store, role and connection boundary; namespace/wallet identifiers alone do not suffice. Caller-side randomized encryption reduces plaintext equality leakage but does not turn the library into an authorized multitenant service or hide identifiers, snapshot sizes, timing and retention metadata.

4. **High for ratcheted recovery: snapshots are not anti-rollback or erasure.** Checkpoint history intentionally preserves old snapshots. `prune` retains at least one manifest, deletes older manifests by count, and reclaims unreferenced chunks after a 15-minute grace period (`src/postgres/checkpoint-store.ts:472–524`). SQL deletion does not establish removal from WAL, replicas, backups or prior snapshots. MPE-CRY-011 requires refusal to publish when restored state cannot establish nonce uniqueness/ratchet freshness; MPE-CRY-029 requires superseded secret erasure outside skipped-key policy. Define restore/re-establishment and key-retention policies separately. Per-generation wrapping keys with an audited destruction policy may support cryptographic erasure, but this is additional design, not an UmbraDB capability. A whole-history backup of usable obsolete secrets would undermine the intended forward secrecy.

5. **Medium: checkpoint+cursor is not complete processOnce.** `saveAndAdvance` does not also commit arbitrary application effects and replay/dedup rows. It acquires no writer lease (`src/postgres/save-and-advance.ts:66–69`), and watermark set is an unconditional upsert (`src/postgres/watermarks.ts:77–82`), not monotonic compare-and-set. The application must compose effect, dedup and cursor in the same database transaction to meet MPE-CON-033, enforce its single-writer ordering, and reconcile uncertain commit outcomes. External payments, chain transactions and other remote effects still need destination idempotency/reconciliation. Session advisory locks coordinate cooperative writers; they do not fence a hostile or stale writer (SECURITY.md:26–30). A lease-loss callback after a successful effect is not proof that concurrency could not occur during the callback.

## Prototype and production acceptance gates

- Safe immediate prototype: synthetic nonsecret state; dedicated local PostgreSQL 17; one trusted writer; direct/session-mode connection; fsync/full_page_writes enabled; synchronous_commit=on; pinned commit; no production keys or receipts.
- Demonstrate rollback of checkpoint+cursor together, restart recovery, corruption rejection, duplicate-event suppression with an application effect in the same transaction, and reconciliation of an ambiguous commit result.
- Demonstrate explicit startup refusal for synchronous_commit=off, including the callback-throw regression; verify the actual writer connection policy, and reject unsupported transaction pooling.
- Before secret use, inspect database/WAL/backup payloads for ciphertext-only secret state, test wrong-key/wrong-principal tamper rejection, and document key custody, restores, rollback refusal, skipped-key budgets and obsolete-secret destruction. Do not commit secret-bearing fixtures.
- Before Store Node deployment, separately implement envelope/EID/expiry/verification-material schema, retention scheduling and receipt-after-commit ordering. Snapshot pruning is not the MPE envelope-retention contract. Benchmark the actual message workload and resource ceilings; this review supplies no evidence of transport hot-path suitability.

UmbraDB can make business workflow recovery concrete by supplying a real atomic SQL substrate. Its trust assumptions are compatible with a backend operated as the application's trusted endpoint. They are not automatically compatible with an untrusted shared provider, private reception outsourced to an indexer, or a claim that historical secret snapshots preserve ratchet forward secrecy.
