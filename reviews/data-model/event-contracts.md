# Event contracts, evolution, and canonical signed meaning

Research date: 2026-10-03. Scope: the private semantic payload and SDK contract in the selected Midnight Express stack. This is a design recommendation, not a claim of implemented conformance. The selected [stack](../../docs/product-requirements/recommended-stack-and-use-cases.md) already places structured CloudEvents-compatible events inside authenticated encryption and separates transport security from signed business authority. Eleven primary specifications/documentation pages plus an additional Protobuf canonicalization page were fetched in full with Scrapling; [manifest, timestamps, and SHA-256 hashes](../../catalog/data-model/event-contracts/manifest.json) identify the exact evidence inspected.

## Recommendation

Use a compact common event core plus separately governed, narrow domain profiles. Standardize how a consumer discovers an exact contract, verifies who asserted it, distinguishes event delivery from business execution, and rejects unknown actionable meaning. Do not require an RFQ, invoice, revocation, and agent approval to share a universal business object. Each profile should define its own fields, units, identity domains, state transitions, evidence requirements, and authorized effects.

Use CloudEvents 1.0 structured JSON as the private event wrapper, JSON Schema 2020-12 for closed structural validation, a separately pinned semantic contract/state machine, RFC 8785 JCS for an explicitly defined business-signature input, and AsyncAPI for operation documentation. Default actionable consumption to an exact allowlisted contract digest. Permit a compatibility transition only through a reviewed named adapter or an authenticated negotiation that selects an exact installed contract; negotiation must not enable arbitrary sender-selected schemas or silent downgrade.

These standards solve distinct problems. CloudEvents describes occurrence context; JSON Schema constrains data shape; a domain profile specifies business meaning; a signature authenticates an assertion; application policy decides whether an effect is allowed. None alone makes an AI interpretation safe.

The strong common result is that syntactic compatibility and business compatibility differ. The rejection/allowlisting recommendations above are MPE design judgments drawn from those behaviors, rather than requirements imposed by CloudEvents on all implementations.

## Concrete private contract shape

The common core should require `specversion`, `id`, `source`, `type`, `time`, `datacontenttype`, `dataschema`, and `data`. Add a small fixed set of CloudEvents-compatible, lowercase alphanumeric extensions such as `mpeprofile` and `mpecontract` only when needed to identify the semantic profile and its immutable manifest digest. Define exact lengths, allowed values, and dependencies. A contract manifest binds the schema closure, semantic profile text/state machine version, canonicalization policy, authority grammar, and conformance vectors. `dataschema` identifies an immutable data schema; the manifest digest also captures rules a schema cannot express.

The common core does not need optional fields for every use case. A quote profile might use `requestId`, `offerId`, asset identifiers, quantity, price convention, expiry, and conditions. An invoice profile needs invoice/issuer/payment-reference identity and payment-evidence/finality semantics. An agent approval profile needs exact operation, destination, permitted resource identifiers, budget/units, validity interval, approval evidence, and policy version. Reuse bounded primitives where semantics actually match. State their meaning explicitly: an `amount` without asset, scale, and direction is insufficient.

Use distinct event types for facts, proposals, approvals, accepted/rejected decisions, and final outcomes. A signed quote observation or payment notice must not be interpreted as an instruction to settle or post an invoice. Use explicit tagged alternatives and `oneOf` only where branches are provably disjoint. Avoid a freeform `kind` plus arbitrary payload and avoid open parameter maps for executable tools.

All these fields remain inside encryption, including source/type/correlation/schema/profile references and signer/role data. AsyncAPI logical operation descriptions must not become visible GossipSub business topics, upstream selectors, or plaintext routing headers. Adapter source claims need authenticated provenance and explicit finality/gap semantics; decryption merely establishes access to contents.

### Validation implementation

1. Apply MPE size/class limits, authentication/decryption, and bounded parsing. Reject duplicate decoded keys, invalid UTF-8/Unicode, excessive nesting, overlong strings, oversized arrays, and prohibited numeric forms before they reach an ordinary deserializer.
2. Check the closed event core and allowlisted `(type, mpeprofile, mpecontract, dataschema)` mapping. Load schema resources only from an installed local bundle whose transitive `$ref` closure is digest-pinned. Do not fetch event-supplied references at runtime; this prevents drift, availability dependencies, and schema-fetch access leaks.
3. Validate with the exact 2020-12 dialect, asserted required vocabularies, verified format behavior, and no coercion/default insertion/unknown-field stripping. For composed objects use `unevaluatedProperties: false` after evaluated branches; for simple closed objects `additionalProperties: false` is often easier to inspect. Close nested objects independently. Reject unknown authority-relevant fields and enum values.
4. Run deterministic domain checks: asset/issuer identity, units/scales, bounds, relationships, source sequence/finality, quote/request correlation, allowed state transition, destination, expiry, and current authorization policy. JSON Schema alone cannot prove balances, a credential's freshness, external finality, or permission to execute.
5. Verify the canonical signed assertion and signer-to-role policy. Record exact original event/envelope bytes and verification provenance. Unknown/unsupported contracts enter encrypted local quarantine with a bounded reason code and no business effect. They may be retained/forwarded as opaque envelopes according to transport policy.
6. Dispatch a generated typed value to the handler or AI. AI sees verified fields and may propose an effect; the effect executor rechecks a typed action and current capability/approval policy. Narrative strings, descriptions, attachments, and documentation are untrusted content, never capability grants.

No automatic conversion, stripping, or inferred default should change the assertion used to verify business authority. Rendering may show a projection, but authorization must use the exact signed semantics.

## Event identity, business action identity, and transport identity

| Identity | Meaning and scope | Deduplication obligation |
|---|---|---|
| CloudEvents `(source, id)` | An asserted occurrence, scoped to an authenticated source domain; retries may retain it. | Same identity with conflicting authenticated content is a conflict, not a harmless duplicate. Multiple consumers can process the same occurrence differently. |
| Business `actionId` | A particular authorized effect at a named destination/policy domain. Profile-specific; not every event authorizes an action. | Commit action identity, canonical action digest, result, and replay consumption atomically. Same action ID plus different digest must fail. New event IDs or envelope IDs must not permit repeat execution. |
| MPE EID | Existing MPE envelope identity, distinct from both the semantic occurrence and an executable effect. The original design excludes the Admission Slot from EID. | Preserve the original byte definition and vectors. Changing admission serialization can preserve EID; resealing an event can create a different EID while preserving event/action identities. |
| GossipSub message ID | The original draft's hash of the complete immutable envelope including Admission Slot under its specified domain. | Do not replace it with semantic event identity: cache/suppression and corrupted-admission defenses have different requirements. |

The EID/message-ID distinction is established in the local [experiment design](../../docs/design-document/draft-final/09-experiments.md), especially the Q6 full-envelope identifier discussion. This recommendation does not redefine either wire hash. Semantic contracts remain inside existing MPE sealing/recognition, and an event signature alone does not satisfy the selected stack's anchored-message binding or applied-phase/replay proof gates.

## Canonical business signatures

Specify a separate assertion object with fields such as signature-profile version, network/application authority domain, exact contract digest, operation/destination, action ID, canonical event/payload digest as required, signer/role binding, constraints, expiry, and replay scope. The enclosing signature field is excluded from its own preimage. Select the cryptographic algorithm/key encoding through an allowlisted authority profile; a sender cannot select an arbitrary algorithm or downgrade it. Define domain separation and preimage framing unambiguously, for example a fixed protocol label plus length-framed JCS UTF-8 assertion bytes. This is a proposed grammar, not an existing MPE wire format.

Require implementations to sign the same typed assertion that executors authorize. Bind the contract manifest digest into the assertion: the same field bytes can have different meanings under changed units or policy versions. Treat an immutable schema URI as useful identification, not cryptographic pinning. A signature verifies who asserted bytes; independently checked issuer/role membership and scoped authority determine permission.

Keep three commitments separate: original envelope bytes/EID for transport and anchoring, a canonical semantic assertion for business signatures, and exact schema/profile bundle bytes for contract identity. Never recompute original wire evidence from a migrated JSON object. If a migration changes signed intent, the new authoritative assertion needs fresh authorization; otherwise preserve the original signature with an explicit derived projection and named transformation evidence.

### Exact values and time

Use exact decimal strings with a pinned grammar for financial quantities, paired with an explicit asset and scale (or fixed profile scale). Reject whitespace, exponent syntax, leading zeros, negative zero, and out-of-range coefficients if the profile disallows them. Whether trailing zero precision is meaningful must be fixed by the domain profile; JCS leaves these strings unchanged. For bounded counters, restrict JSON integers to the agreed safe range; wider identifiers/counters use constrained strings. Avoid floating-point business money and assume neither a JSON Schema `number` nor JCS provides arbitrary precision.

Choose one UTC instant format, for example fixed milliseconds `YYYY-MM-DDTHH:mm:ss.sssZ`, and require a real calendar/instant parser in addition to lexical constraints. Choose whether leap-second values are rejected or handled through a specified conversion. An offset equivalent, a different number of fractional digits, or a date string is not the same signed representation. `time` records occurrence time; authority expiry and transport expiry are separate constraints and cannot substitute for one another. Do not claim trusted clocks merely because a field passed validation.

JCS preserves Unicode strings rather than normalizing them. For protocol identifiers prefer a bounded ASCII grammar or define and enforce normalization before issuing/signing identifiers. Do not normalize strings during verification. Cross-language vectors must cover supplementary characters because JCS sorting uses UTF-16 code units, not UTF-8 bytes or implementation-native character ordering.

## Evolution without a universal committee

A small core steward can own identity/canonicalization/validation mechanics while domain owners own RFQ, invoice, and agent-approval semantics. Every profile release has an immutable manifest, accountable owner, change rationale, migration evidence, negative vectors, and explicit adoption/revocation policy. A global registry can index profiles without endorsing every profile or requiring one enormous common business schema.

For executable profiles, exact pinning is the initial default. Any authority-field addition, removal, unit change, enum/state transition change, default, restriction, or evidence requirement produces a new semantic contract digest. Even an optional added field is not automatically compatible: if old consumers reject unknown fields, shape acceptance changes; if they ignore it, new constraints may be lost. Separate benign documentation changes from executable rules, while still preserving archival versions.

For advisory/read-only events, a reviewed forward-compatible projection can be acceptable when its losses are declared and no restriction is represented as honored. This must be distinct from executable authority. For effectful consumers, a compatibility record should name exact old/new digests, direction, validator/adapter version, state-machine guarantees, signer treatment, and expiry/finality handling. Test semantic counterexamples, not just sample parsing success. An authenticated capability exchange can negotiate a supported contract before publication; it must bind session/participants and forbid selecting below local policy's minimum version. Retain dual-read deployments until recovery/replay windows close; never transform old stored events using whatever schema happens to be latest.

Avro or binary Protobuf remain viable internal encodings after measured size/performance needs justify them. Use their writer/reader evolution rules intentionally, but require a separate semantic contract and signature grammar. Avro's schema parsing fingerprint omits semantics such as logical-type metadata; Protobuf deterministic output is not portable canonicalization. Neither is a reason to weaken closed authority validation.

## Counterexamples and acceptance gates

| Counterexample | Failure without the profile rule | Required outcome |
|---|---|---|
| New RFQ offer adds `requiresHumanApproval: true`; old reader ignores unknown fields. | Old software accepts and settles a conditionally approved offer. | Unknown actionable contract/field prevents effect; explicit adapter may not erase the restriction. |
| Invoice `amount` changes from currency units to minor units with identical JSON shape. | Validators parse successfully while posting 100 times the intended amount. | Changed semantic manifest digest and units; old handler refuses. |
| JSON contains both `budget` and an escaped spelling decoding to the same name. | Signer, UI, and executor may select different values. | Duplicate-key rejection before deserialization/signature interpretation. |
| AI tool action references a document whose narrative says to bypass the approved budget. | Schema-valid content becomes an instruction channel. | Documents remain untrusted data; typed executor enforces signed bounds. |
| Same `actionId` appears under a new event ID and resealed EID. | Transport/event dedup misses a duplicate payment. | Destination action dedup/replay rejects or returns prior result atomically. |
| Two authenticated events share `(source,id)` but disagree on destination/amount. | Dedup silently discards evidence or chooses an arbitrary assertion. | Conflict recorded and no new effect permitted. |
| A sender supplies a mutable `dataschema` URL or remote `$ref`. | Same signed URI validates against changed rules; fetching exposes interest. | Installed digest-pinned schema closure only. |
| AsyncAPI native Draft-07 tool ignores `unevaluatedProperties`. | Documentation appears closed while executable fields remain open. | Separate authoritative 2020-12 validation; tool support proven with a negative extra-property case. |
| Large integer `9007199254740993` passes a generic JSON parser as a number. | Binary64 rounds it before signing or execution. | Exact string representation or lexical numeric rejection; Rust/TypeScript agreement. |
| Equivalent instants use different offsets/fractions; code string-compares expiry. | Ordering or signature interpretation diverges. | Fixed timestamp representation and actual instant comparisons. |
| A schema specifies `default: true` for missing approval. | A mutating validator manufactures an unsigned permission. | Defaults never generate authority; missing required approval fails. |
| A signed event is old, revoked, provisional, or from the wrong authority domain. | Authentic bytes are mistaken for present permission. | Independent freshness, finality, domain, and role checks. |

Before an effectful pilot, run cross-language fixtures in the actual Rust and TypeScript stack for duplicate escaped keys, precision bounds, NaN/Infinity, Unicode/lone surrogates, JCS UTF-16 property order, enum additions, nested closure/composed schemas, unsupported vocabularies, format/default behavior, timestamp policy, contract-ref pinning, identical and conflicting event/action identities, and crash-safe action dedup. These are integration acceptance gates; this review does not claim they have been implemented or passed.

The practical endpoint is a typed private coordination interface with a shared event spine and explicit domain authority. It reduces ambiguous AI inputs without making schema validation a substitute for business policy or forcing a universal cross-industry data model.
