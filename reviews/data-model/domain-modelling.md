# Midnight Express: bounded semantic core and governed workflow profiles

Research date: 2026-10-03. Scope: domain modelling, enterprise standards, constrained extensibility, governance and adapters. This is a design recommendation, not an implemented protocol or a claim of standards conformance. Product baseline: [recommended stack and use cases](../../docs/product-requirements/recommended-stack-and-use-cases.md). Source archive: [manifest](../../catalog/data-model/domain-modelling/manifest.json), containing fetched URLs, timestamps, HTTP results and SHA-256 hashes of raw and extracted documents. All successful source archives below were fetched with Scrapling `Fetcher.get(url, timeout=25)` and read as full text; search snippets were discovery aids only.

## Decision

Use **one small coordination contract, reusable value types, and separate immutable domain/workflow profiles**. Keep organizations' internal ERP, trading, identity and agent models behind application-owned adapters. Agreement covers the meaning of each field and action, the participant roles, state transitions, evidence and constraints, rather than merely a JSON shape. Start with the three prioritized pilots: RFQ coordination, invoice reconciliation, bounded human-approved agent work. Do not build a universal Customer/Transaction/Status record spanning all ten use cases.

A free-form `payload: object` contract shifts unresolved ambiguity into runtime interpretation; a universal enterprise schema shifts it into an expanding shared governance problem. The middle course is strict within each negotiated profile and composable across profiles. JSON is a physical representation. A shared JSON validator cannot determine whether a payment is final, whether a quote is binding, or whether a particular signature authorizes spending.

## What the primary sources establish

**Eric Evans, DDD Reference, pp. 28–36.** Models apply within bounded contexts; a context map documents translations and relationships. A shared kernel is a deliberately small, jointly maintained model/code subset, whereas an anticorruption layer expresses an external system through the receiving system's own model. A published language can provide the interchange contract without exporting an internal model. An open host service reserves one-off translators for unusual needs rather than expanding the common protocol for every client. These are architectural patterns, not a universal-schema requirement. Midnight's interchange kernel follows those constraints; independent organizations need a published language and conformance fixtures rather than a shared database. [Author's PDF](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf), [reference and license](https://www.domainlanguage.com/ddd/reference/).

**Gregor Hohpe and Bobby Woolf, Enterprise Integration Patterns.** The canonical model pattern lowers coupling by translating each application's messages through an independent representation. Its translator-count comparison assumes all-to-all exchange: direct translation grows as n(n−1), versus 2n canonical translators. It does not prove lower total semantic or governance cost; two applications require fewer direct translators. The separate Format Indicator pattern supports explicit interpretation/version identification. Use canonical forms where participants actually share a workflow, and direct adapters where they do not. [Canonical Data Model](https://www.enterpriseintegrationpatterns.com/patterns/messaging/CanonicalDataModel.html), [Format Indicator](https://www.enterpriseintegrationpatterns.com/patterns/messaging/FormatIndicator.html).

**UN/CEFACT CCTS 2.01, §4.6.2 and dictionary/registry rules.** Context-neutral core components become business information entities in specific business circumstances; the distinction is semantic context, not a different serializer. A component can be basic, aggregate or an association, with defined value sets and dictionary information. This supports a common primitive vocabulary plus context-specific assemblies. UBL explicitly builds on this version; CCTS 3.0 also exists, so 2.01 is the UBL methodology reference, not an assertion that it is newest. [Original specification hosted by OASIS](https://www.oasis-open.org/committees/download.php/6232/CEFACT-CCTS-Version-2pt01.zip). The direct UNECE PDF returned 403 and is separately recorded as a failed capture.

**OASIS UBL customization, §§1.4.4–1.4.6, 3.1.4 and 4.** A customization must preserve common meanings. Standard-schema validation alone cannot catch semantic drift. UBL distinguishes base version, implementation customization and business-process profile. Extensions can preserve base schema validity while their internal structure remains unchecked by the base schema. Structural validation, code lists and other constraints therefore need separate checks. This supplies the central lesson: an extensible standard needs explicit, independently validated profiles. [UBL 2 Guidelines for Customization](https://docs.oasis-open.org/ubl/guidelines/UBL2-Customization1.0cs01.html).

**OASIS Business Document Naming and Design Rules 1.0, §§2–4.** Abstract semantic bundles are distinct from generated XML structure and data-value validators. Reusable aggregates and top-level document assemblies are distinct; extension metadata identifies supplementary content. Midnight should borrow that separation rather than inherit the entire UBL library as mandatory runtime state. [OASIS Standard](https://docs.oasis-open.org/ubl/Business-Document-NDR/v1.0/os/Business-Document-NDR-v1.0-os.html).

**ISO 20022 Registration Authority.** The methodology separates syntax-independent financial concepts and message flows from physical schema generation. Its dictionary defines contextual elements, types, constraints, traceability and registration status; its business model feeds concrete message definitions. These are useful patterns for a semantic registry. Financial message conformance is a separate obligation from using selected definitions in an internal profile. [Methodology](https://www.iso20022.org/about-iso-20022), [dictionary](https://www.iso20022.org/understanding-data-dictionary), [business model](https://www.iso20022.org/iso20022-repository/business-model). Avoid importing ISO's entire centralized registration process into private experimental workflows.

## Proposed type boundary

Everything in the following table is a Midnight design proposal. An implementation must reconcile exact fields with the existing CloudEvents-compatible encrypted payload contract and MPE byte limits; the table does not change the outer wire format.

| Layer / proposed type | Minimum semantics and constraints | Excluded from this layer |
|---|---|---|
| Mandatory `EventIdentity` | CloudEvents `(source,id)` uniqueness; immutable event type, event schema identifier/digest and content representation; retry preserves identity and authenticated content | Invoice number, RFQ number and effect idempotency are distinct identifiers |
| Mandatory `ContractRef` | Immutable core/profile/workflow version references and digests, exact selected feature set; locally trusted manifest publisher | Live remote schema lookup or a server deciding semantics from untrusted bytes |
| Optional core `WorkflowRef` | Scoped workflow instance ID, definition digest, causation references; where required, authoritative revision/base revision | A globally ordered bus or universal business lifecycle |
| Reusable `ScopedIdentifier` / `EntityRef` | Issuer/namespace + scheme + value; reference can pin revision; equality defined by scope | Automatic merging of legal party, wallet, installation, role or admission identity |
| Reusable `EvidenceRef` | Evidence kind, digest algorithm/content digest, provenance issuer, subject binding, timestamp/finality semantics defined by profile | A Boolean `verified` that authorizes all actions |
| Reusable `AuthorizationRef` | Authority issuer, principal/role, allowed action and targets, expiry, policy/capability reference; verification is consumer policy | Membership proof, encryption key possession or relay admission as business authority |
| Optional `ArtifactRef` | Digest, media type, size limit, access policy and encrypted/object-store locator; explicit retrieval permission | Public attachment URLs, implicit fetch permission or inline multi-megabyte UBL documents |
| Optional `ExtensionValue` | Qualified ID + immutable schema digest + bounded typed value; impact class and recognized-feature requirements | Unbounded free-form maps, scripts, parser plugins or arbitrary executable validators |

The mandatory envelope remains very small: identity plus contract interpretation. Workflow, evidence and authority become mandatory where a selected event profile requires them. Support value types such as `Decimal`, `Amount`, `AssetQuantity`, `Instant`, `LocalDate`, `Code` and `Digest` in an optional library, with pinned definitions. They should not force every event to carry money, addresses or a party graph.

An `Amount` requires a currency identifier, decimal representation/precision, sign semantics and rounding rules. An `AssetQuantity` requires an asset namespace/identifier and unit/scale; a ticker alone is insufficient. A `Code` requires its vocabulary version or digest. An `Instant` is distinct from a local accounting date. Omission is distinct from explicit null, unknown, withheld and not applicable; a profile selects permitted cases. These distinctions prevent AI systems from silently filling absent evidence or interpreting a day as an expiry instant.

## Three initial profiles

**RFQ coordination (`rfq.offchain.v1`).** Define `RfqRequested`, `QuoteIssued`, `QuoteWithdrawn`, `QuoteAccepted` and `RfqClosed` as separate typed messages. A quote pins the RFQ, instrument/asset identifiers, side from a named party's perspective, quantity/unit, executable versus indicative status, price convention, issuer authority, expiry instant and terms digest. Acceptance pins exact quote revision/bytes and is permitted only by the named accepter while the quote is valid; concurrent acceptance needs an application-owned authority decision. Quote acceptance means off-chain business acceptance under this profile. Settlement requires a separately defined capability, proof and ledger finality profile, matching the repository's explicit gates. Transport receipt never implies either acceptance or settlement.

**Invoice reconciliation (`invoice.reconcile.v1`).** Carry `InvoiceNotice`, `PaymentStatusObserved`, `AllocationProposed` and `AllocationConfirmed`. Invoice identity is supplier/issuer scoped; document reference preserves the original UBL or other ERP document digest. Payment evidence includes the source's status scheme, account/rail reference, observed amount/currency, as-of instant, provenance and finality interpretation. Preserve partial payments, reversals, credits, tax jurisdiction and accounting dates; omit tax fields from the kernel. Matching an invoice to a payment is its own allocation decision with destination idempotency. Map UBL invoice fields and the customer's exact payment-message version only when the adapter has verified the required correspondence. Do not rename a bank's pending status to `Paid`.

**Bounded agent work (`agent.approval.v1`).** Define `ActionProposed`, `ApprovalGranted`, `ApprovalDenied`, `ApprovalRevoked`, `ExecutionStarted` and `ExecutionReported`. A proposal has a closed action schema, target identifiers, maximum budget/unit, environment, exact input/artifact digests and expiry. An approval binds that proposal digest, policy/capability digest, human or threshold authority and maximum effect count. Changing a target, amount or tool argument requires a new proposal/approval. Narratives remain bounded advisory text, never executable instructions. Execution reports preserve actual outcomes/evidence without implying that an approval proved execution or that an execution report is independently authentic.

These profiles reuse primitives and recovery semantics while preserving distinct authority and business meanings. An insurance claim or credential revocation profile can be published later without expanding RFQ lifecycle states.

## Workflow definitions and versioning

A profile manifest must pin: semantic glossary; schemas and field constraints; code-set versions; event roles; state machine and transition guards; correlation/causation rules; authoritative revision policy; evidence/finality requirements; retry/expiry/redrive rules; acknowledgement meanings; allowed extensions; size/depth limits; external-effect policy; supported core versions; migration identifiers; owners and trust/signature metadata. Documentation and executable fixtures must agree.

Maintain four independent version axes: outer MPE wire/security profile, event envelope/core, domain schema/profile, and workflow/policy definition. Pin exact digests for deterministic handling; a semantic version label is a convenience, not sufficient evidence of compatibility. A workflow instance stays on its starting definition unless an authorized, explicit migration creates a recorded transition. Upgrade SDK readers independently of old workflow semantics. Keep previous schemas/validators for the actual retention, recovery and audit horizon.

A “minor” schema change is accepted only after consumer compatibility testing. Adding a supposedly optional field is breaking if old receivers would ignore a fee, change approval scope or reject unknown members. Changing defaults, units, rounding, authority, finality interpretation, enum meaning, transition guards, required evidence or maximum effects is a new semantic contract even if the JSON structure is identical. Unknown states or required capabilities produce an explicit unsupported result/quarantine, never a guessed closest state. An arbitrary version interval does not establish compatibility.

## Constrained extension policy

Use one typed extension container per profile, with bounds derived from the MPE class budget. Qualified extension IDs avoid collisions; schema and vocabulary digests are mandatory. A manifest distinguishes **advisory** extensions, which cannot affect authorization/accounting/lifecycle, from **effect-bearing** extensions, which require recognized handling and negotiated support. Senders cannot self-declare a fee or approval restriction advisory: the consumer's trusted manifest decides impact. Reject undeclared members in operational event bodies; preserve opaque unfamiliar data only in explicit relay/archive-only modes. An endpoint cannot claim actionable interoperability in archive-only mode.

Extension slots must never override a core meaning, masquerade as an alternate signature/authority field, redefine amounts or silently change workflow transitions. Promote widely reused semantics through a profile revision after demonstrated reuse, rather than add every customer field to the shared kernel. An extension that changes an action's meaning belongs in a new profile or effect-bearing feature. The generic UBL extension mechanism is more permissive than this proposed Midnight policy; base UBL schema validity must not be treated as validating application extensions.

## Governance and local capability agreement

Use three ownership scopes. Core maintainers govern the small envelope, primitive invariants and compatibility process. Named domain owners govern their profiles with downstream consumer fixtures. Organizations govern private, namespace-scoped extensions and adapter releases within the kernel invariants. Private experimental profiles can proceed without a network-wide committee; public shared profiles require an accountable owner, review, examples and a compatibility report. A signed registry entry is evidence of publication, not automatic trust or automatic installation.

Profile changes move through `draft → experimental → stable → deprecated`; historic stable artifacts remain immutable and content-addressed. A proposal for kernel promotion should demonstrate the same semantics in at least two independently implemented profiles and show that an adapter/library cannot solve it. That threshold is a project policy recommendation, not an enterprise-standard requirement. Keep release decisions with named maintainers and affected consumers; avoid requiring all participants to approve unrelated domain changes.

Before starting a workflow, authenticated participants exchange encrypted capabilities: exact supported profile/workflow digests, handled effect-bearing features, permitted size limits, authority policies and expiry. Their locally selected intersection becomes the instance contract, bound into signed intent where applicable. No overlap produces `unsupported-profile`; a signed compatible adapter may be explicitly selected. Do not let senders negotiate away a receiver's minimum authority or proof requirements. Pin the selection and detect downgrade/replay by binding counterparties, nonce/instance, expiry and profile digest. Carry capability updates through the same private local-recognition design; a public global capability directory or business-specific transport topic would leak subscription interests.

## Adapter and migration rules

1. **Adapters translate claims, not grant authority.** Pin source system, source schema/version, adapter version/digest and source evidence. The target application still verifies permissions. Legacy status meanings are documented in the source context and mapped only when the target predicate holds.
2. **Separate transport/event/effect identities.** `(source,id)` deduplicates events; workflow ID correlates a process; source object/revision identifies business records; destination plus action plus authorized intent identifies an external effect. Generating a new adapted event cannot bypass effect deduplication.
3. **Make mappings deterministic and loss-aware.** Preserve source bytes/digest, explicit field transformations, units/timezone/code-set conversions and declared loss. Missing facts become a typed insufficient-evidence result. An AI may propose an adapter, but approval, fixture validation and deployment pin a deterministic artifact; no opportunistic per-message semantic invention for effects.
4. **Preserve finality, causality and freshness.** Map provisional/final/retracted evidence as distinct states. A delta records authoritative base revision; a gap triggers a source-approved snapshot/reconciliation, never synthetic state interpolation. Source order is scoped to its authority, not guessed from GossipSub arrival time.
5. **Derived data keeps provenance.** A migrated event has a new identity plus original event/digest and transformation record. Never attach the original signature to changed bytes as if the original issuer signed them. Signed business intents and anchored byte bindings remain verifiable against original bytes; conversion may require a new signature/approval.
6. **Dual-read by explicit dispatch.** Dispatch old and new schemas by pinned contract rather than trial parsing. Compare shadow projections before activating a migration. Do not dual-write external business effects merely because two profile versions are active; share destination idempotency and reconcile ambiguous timeouts.
7. **Migrate instances explicitly.** An upgrade records previous state/version, target state/version, authority, migration function/digest and invariants. Unmappable open cases remain on the old version or enter supervised resolution. Retire old readers only after retention/replay commitments and open instances have been handled.

## Counterexamples and acceptance cases

| Tempting design | Failure | Required boundary/test |
|---|---|---|
| `Customer` is a shared legal party, wallet and installation | Revoking an installation revokes the wrong business principal | Scoped identity refs; explicit verified mappings and role authority |
| `status: completed` is universal | Payment submitted becomes final settlement; quote accepted becomes ledger execution | Domain-qualified lifecycle predicates and distinct evidence |
| Common `amount: 100` | USD major units, token minor units and a percentage become interchangeable | Asset/currency scheme, scale, convention and rounding pinned |
| UBL-valid invoice extension adds a handling fee | An old processor validates the base invoice and ignores the fee | Negotiated effect-bearing extension; old receiver refuses |
| An AI repairs unknown enums or supplies missing account fields | Plausible syntax invents a business fact or target | Unknown value/insufficient evidence; quarantine and explicit resolution |
| Add `requiresApproval: false` as an optional field | An old reader uses a more permissive default | Contract change and compatibility review; no implicit privilege change |
| Every company publishes its own “stable” `Paid` meaning | Schema registry grows while interoperability disappears | Shared profile glossary, authority/finality predicates and cross-implementation fixtures |
| All ten use cases use a universal workflow object | Every profile change touches unrelated consumers | Separate profiles with a small shared kernel |

Minimum pilot fixtures should cover: two independent implementations accepting exactly the same RFQ terms; rejecting mismatched unit/side conventions; refusing unknown required extensions; expired or revoked approval; duplicate delivery after crash; provisional payment followed by reversal; replay of old capability agreement; a delta with a missing base; changed proposal digest; old workflow replay after a profile upgrade; lossful mapping into an operational contract; and inability to infer business completion from retention/anchor/transport evidence. Measure profile size, adapter effort and integration defects before expanding the kernel.

## Standards reuse and licensing boundaries

- **Evans:** the author's reference page marks DDD Reference CC BY 4.0; earlier book pattern summaries are separately CC BY 3.0. Preserve attribution and indicate adaptations. This does not grant rights to reproduce the full commercial book.
- **EIP:** the authors permit specified pattern elements (icon/name, bold problem/solution, sketch) under Creative Commons Attribution; the remainder is copyright protected. These fetched pages are research captures, not a blanket license to republish site/book text. Prefer original paraphrase and links.
- **UN/CEFACT CCTS 2.01:** p.113 allows copying/translations and explanatory/implementation derivative works with its copyright and permission paragraph, but prohibits modification of the specification itself except translation. Preserve those notices in copies; do not present Midnight definitions as an altered official CCTS standard.
- **OASIS UBL/NDR:** published notices permit explanatory/implementation derivatives with notices but restrict modification of the specification itself; customization guidance calls for acknowledging derivation and avoiding misleading conformance claims. Schema/model artifacts and referenced code sets must be checked against their actual notices and TC IPR terms. A JSON projection is not automatically a UBL-conformant XML document, and using a few UBL concepts does not make an invoice processor compliant. [Customization notices and §1.3](https://docs.oasis-open.org/ubl/guidelines/UBL2-Customization1.0cs01.html).
- **ISO 20022:** published Repository information carries a non-exclusive royalty-free use license under the contribution policy. The site's terms require unofficial replicas to identify the official up-to-date source. This is distinct from purchasing/licensing the multipart ISO standard text, and third-party code-set or contribution notices can impose separate constraints. Semantic reuse or a JSON mapping does not by itself establish registered ISO 20022 message compliance. [IPR policy](https://www.iso20022.org/intellectual-property-rights), [terms](https://www.iso20022.org/terms-use).

The archive is a dated research snapshot, not an official standards replica. The authoritative up-to-date ISO 20022 materials are at [ISO20022.org](https://www.iso20022.org/).
