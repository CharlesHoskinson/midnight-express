# Solana application domain — inventory and proposed bounded profiles

Status: researched design, 2026-10-03; no runtime, SDK, production schema, decoder or finality verifier is implemented here. This extends the [unified model](unified-data-model.md) with an inventory of common Solana application traffic. It does not make the three [reference profiles](../../model/README.md) capable of handling blockchain messages. The profile families below are original MPE design recommendations inferred from the cited interfaces; RPC availability and program formats must be pinned per deployment.

## Coverage and separation

Common coverage means a reviewed adapter can preserve every supported source message and normalize known meanings. It cannot mean a universal decoder for every deployed program. Keep transport/RPC exchanges, account-state observations, transaction lifecycle observations, deterministic instruction decoding, business intents, wallet approvals and program-specific economics in separate closed contracts. Arbitrary instruction bytes, program logs or an indexer's label never authorize an effect.

Solana does not expose an Ethereum-style universal contract event ABI. Its applications observe accounts, transactions, instruction execution, CPI traces, return data, logs and program-defined state; each program needs a pinned decoder. Solana's account model and [CPI semantics](https://solana.com/docs/core/cpi) determine what a translation can establish. Ethereum receipt logs, transaction nonce sequencing and `safe`/`finalized` tags must retain their own domain rules; a shared display label is insufficient to equate them with Solana commitment.

## Common RPC messages

Use a closed request/response pair for each admitted method, or a closed union generated from an installed method dictionary. Preserve JSON-RPC request ID separately from MPE occurrence, workflow and logical action IDs. Record method, exact parameter bytes/digest, requested commitment, encoding, endpoint identity, response context, node version and adapter contract. A batch needs independent item outcomes. Distinguish a valid `result:null`, method-level JSON-RPC error, transport failure, timeout, unsupported version, rate limit and unavailable historical data. A node's successful HTTP response is not proof of chain truth.

| Application need | Current HTTP inventory | Required preservation |
| --- | --- | --- |
| Account and program state | `getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts`, `getBalance`, `getLargestAccounts`, `getMinimumBalanceForRentExemption` | Address, program owner, data encoding and bytes, lamports, executable flag, space/data slicing, filters, context slot; explicit missing account |
| Token holdings and supply | `getTokenAccountBalance`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getTokenLargestAccounts`, `getTokenSupply` | Token program, mint, token-account address, token authority, canonical raw amount and decimals; context and filter scope |
| Transaction building | `getLatestBlockhash`, `isBlockhashValid`, `getFeeForMessage`, `getRecentPrioritizationFees`, `simulateTransaction` | Blockhash, last valid block height, context, unsigned/signed input distinction, fee samples, simulation settings/result |
| Submission and reconciliation | `sendTransaction`, `getSignatureStatuses`, `getTransaction`, `getSignaturesForAddress`, `getTransactionCount`, test-only `requestAirdrop` | Exact signed bytes digest and first signature, send settings, status/error, history search settings, pagination anchors, account-reference scope |
| Blocks and chain progress | `getBlock`, `getBlocks`, `getBlocksWithLimit`, `getBlockTime`, `getBlockHeight`, `getBlockCommitment`, `getBlockProduction`, `getSlot`, `getSlotLeader`, `getSlotLeaders`, `getLeaderSchedule` | Slot versus height, parent slot and hashes when supplied, requested transaction detail/version, skipped/unavailable distinctions, nullable block time |
| Network, epochs and operation | `getGenesisHash`, `getAgGenesisCert`, `getVersion`, `getIdentity`, `getHealth`, `getClusterNodes`, `getEpochInfo`, `getEpochSchedule`, `getVoteAccounts`, `getStakeMinimumDelegation`, `getSupply`, `getInflationGovernor`, `getInflationRate`, `getInflationReward`, `getRecentPerformanceSamples`, `getMaxRetransmitSlot`, `getMaxShredInsertSlot`, `getHighestSnapshotSlot`, `getFirstAvailableBlock`, `minimumLedgerSlot` | Chain identity/capability observations; epoch, stake/reward units and signedness; retention boundary; no business authorization |

The live [HTTP method index](https://solana.com/docs/rpc/http) is the inventory authority; the archived copy records this snapshot, including `getAgGenesisCert`. Do not infer that every provider implements every listed method. Fetching a documentation URL with HTTP 200 is not a capability test. For example [getStakeActivation](https://solana.com/docs/rpc/deprecated/getstakeactivation) was removed in Agave v2.0; activation requires decoding stake and StakeHistory state with epoch-aware warmup/cooldown rules. Removed legacy `getConfirmed*`, `confirmTransaction`, `getRecentBlockhash` and fee methods belong to explicit legacy adapters, never silently current contracts.

## Websocket and streaming messages

Subscriptions require request, accepted/rejected, notification, unsubscribe and connection/gap/resume events. Subscription IDs are scoped to the connection/endpoint; they are not global occurrence IDs. Persist filter and commitment configuration and establish a snapshot/backfill boundary. Reconnects may lose notifications or repeat them; neither subscription acceptance nor a quiet stream proves complete coverage. Provider webhooks, Geyser/gRPC and vendor transaction streams require separate reviewed adapters and sequence/cursor semantics.

| Subscription → notification | Source meaning and mapping boundary |
| --- | --- |
| `accountSubscribe` → `accountNotification` | One account update with context slot and account payload; retain encoding/configuration. This alone does not identify the transaction that changed it. |
| `programSubscribe` → `programNotification` | Account changes for the owning program under configured filters. Program owner differs from token authority; filter changes need new coverage boundaries. |
| `logsSubscribe` → `logsNotification` | Signature, `err`, log strings and context; `all`, `allWithVotes`, or a `mentions` filter. The documented mentions list supports one address. Logs are execution evidence requiring program-specific decoding, not ABI events. |
| `signatureSubscribe` → `signatureNotification` | A transaction's requested commitment status with error, or optional `receivedSignature` receipt notification. Receipt proves node receipt only; the terminal commitment notification automatically ends the subscription. |
| `slotSubscribe` → `slotNotification` | Validator slot progression with slot, parent and root. Slot progression alone does not prove application transaction success. |
| `rootSubscribe` → `rootNotification` | Node-observed root slot; retain the source/node identity. A root number alone does not prove that an arbitrary account revision or transaction belongs to that rooted branch. |
| `blockSubscribe` → `blockNotification` | Blocks reaching confirmed/finalized, with configurable full/accounts/signatures/none transaction detail, encoding, versions and rewards; unstable and opt-in. Requires `--rpc-pubsub-enable-block-subscription` and transaction history. |
| `slotsUpdatesSubscribe` → `slotsUpdatesNotification` | Unstable tagged lifecycle variants: `firstShredReceived`, `completed`, `createdBank`, `frozen`, `dead`, `optimisticConfirmation`, `root`; variant fields differ and timestamp is milliseconds. `dead` is branch evidence, not a generic failed transaction. |
| `voteSubscribe` → `voteNotification` | Unstable, opt-in `--rpc-pubsub-enable-vote-subscription`; gossip votes are pre-consensus and may never enter the ledger. Do not count them as inclusion/finality evidence. |

Each documented subscription has an unsubscribe method. Install closed variants for [standard subscriptions](https://solana.com/docs/rpc/websocket), [signature receipt/status](https://solana.com/docs/rpc/websocket/signaturesubscribe), [block availability](https://solana.com/docs/rpc/websocket/blocksubscribe), [slot lifecycle](https://solana.com/docs/rpc/websocket/slotsupdatessubscribe) and [gossip vote limitations](https://solana.com/docs/rpc/websocket/votesubscribe). Pin unstable formats and disable them when the provider cannot attest capability; a fallback poll must carry its own observation provenance.

## Exact Solana primitives

These are proposed domain primitives, deliberately broader than the pilot's positive-only 18-digit decimal:

- `SolanaAddress`: canonical base58 encoding of exactly 32 decoded bytes, case-sensitive, with no whitespace or Unicode normalization. Addresses include public keys and PDAs; do not require every valid address to be on the Ed25519 curve. Program IDs, mint addresses, account addresses and authority addresses have separate field roles.
- `SolanaSignature`: canonical base58 encoding of exactly 64 decoded bytes. Transaction identity commonly uses the first signature; retain all required signatures and the exact serialized message/transaction commitment for verification. A syntactically valid signature does not establish a principal's role.
- `SolanaHash`: canonical base58 encoding of exactly 32 bytes for the applicable blockhash/genesis/nonce role, with distinct typed fields. Do not substitute Ethereum hexadecimal hashes.
- `U64Decimal`: `0` or a nonzero leading digit followed by digits, range `0..18446744073709551615`; JSON string, no sign/exponent/leading zeros/floating-point conversion. Use for lamports, raw token amounts and relevant unsigned counters. Preserve signed reward lamport deltas with a distinct signed primitive and field-specific range; do not force every numeric RPC field to u64.
- SOL amounts use integer lamports (10^9 lamports per SOL). Token quantities use `{program,mint,rawAmount,decimals}` with validated mint decimals (u8) and exact base-unit meaning. Treat `uiAmount` floats as presentation only; do not reconstruct raw quantity from rounded UI values. Token-2022 scaled/interest-bearing display rules need an explicit display conversion contract rather than assuming every UI number equals raw/10^decimals.
- Chain identity binds the observed `getGenesisHash` to a locally approved cluster configuration. `mainnet`, `devnet`, `testnet`, `localnet`, wallet chain strings and endpoint URLs are useful labels, not sufficient identity. Never assume an address or signature identifies the same object on every cluster.
- Distinguish slot, block height, epoch and transaction index. Their numeric values are not interchangeable. Context slot is a node's observation context, not an automatic exact transaction inclusion locator. Preserve unavailable/null block time and source millisecond timestamps without inventing precision or a trusted wall clock.

The [account documentation](https://solana.com/docs/core/accounts), [RPC transaction structures](https://solana.com/docs/rpc/json-structures), [token balance response](https://solana.com/docs/rpc/http/gettokenaccountbalance) and [genesis RPC](https://solana.com/docs/rpc/http/getgenesishash) support these source distinctions. Canonical strings, role separation and local chain binding are MPE recommendations. Account RPC `owner` is the program permitted to modify account data/debit lamports, whereas a decoded token-account `owner` is its transfer authority. Neither is a legal beneficial-owner claim. Account creation/deletion, executable programs, sysvars, rent/storage reserve and state data need separate account-state variants.

## Transaction lifecycle, failures and expiry

A closed lifecycle should represent `intent-proposed`, `wallet-signing-requested`, `wallet-signed`, `simulation-observed`, `submission-requested`, `rpc-accepted`, `receipt-observed`, `execution-observed`, `commitment-observed`, `expiry-observed`, `branch-invalidated`, and `outcome-unresolved` as distinct event types. They are not a single monotonic status ladder: simulation can precede signing, multiple observations can disagree, receipt may be absent, and signing does not submit. Correlate attempts to the stable authorized business action; replacing blockhash/instructions or signatures yields a new transaction and requires policy review of the changed proposal.

[sendTransaction](https://solana.com/docs/rpc/http/sendtransaction) returns an accepted transaction's first signature without waiting for confirmation. Preserve preflight commitment, `skipPreflight`, retry limits, encoding and `minContextSlot`. A timeout is uncertain delivery, not rejection; reconcile before creating another economically equivalent transaction. Retry of the exact bytes is distinct from rebuilding and resigning.

[simulateTransaction](https://solana.com/docs/rpc/http/simulatetransaction) supplies execution diagnostics without committing changes. Preserve `sigVerify`, replacement-blockhash setting/result, commitment, account snapshots, logs, return data, inner instructions, compute usage and `err`. Success with signature verification disabled is not a valid signed authorization; success with a replaced blockhash is not evidence that the original signed bytes are sendable. Simulation cannot prove future execution under changed account state.

[getTransaction](https://solana.com/docs/rpc/http/gettransaction) and [transaction JSON structures](https://solana.com/docs/rpc/json-structures) supply message/accounts/instructions, version, execution metadata, fees, pre/post lamports and tokens, inner instructions, logs, return data, rewards and address-table resolution when available. Preserve absent versus null versus empty fields. `err:null` establishes successful execution in that observation, subject to source authenticity/branch evidence. Execution failure can still charge fees; do not translate it into a zero-cost/no-state-effect blanket claim. For ordinary failed instruction execution, business state changes revert. Durable nonce failure has special runtime behavior.

[getSignatureStatuses](https://solana.com/docs/rpc/http/getsignaturestatuses) distinguishes unknown/null from present status and supports a history-search option; an empty recent cache result does not establish nonexistence. A missing transaction can mean insufficient commitment, retention limits, node lag, fork loss or unsupported version. Record the evidence and keep the result unresolved until the policy's reconciliation criteria are met.

Recent-blockhash attempts preserve the [getLatestBlockhash](https://solana.com/docs/rpc/http/getlatestblockhash) blockhash, context and `lastValidBlockHeight`; establish expiry using height and status evidence from the same approved chain/commitment policy. The [confirmation guide](https://solana.com/developers/cookbook/transactions/confirmation) explains processing-age checks and RPC lag/fork hazards. Do not expire by wall-clock timeout or treat slots as produced block height. Live pages contain shorthand slot-age descriptions; use explicit RPC validity bounds and pinned runtime rules instead of hard-coding a universal 150-slot timer.

[Durable nonces](https://solana.com/docs/core/transactions/durable-nonces) replace recent-blockhash lifetime with nonce-account state and an advance instruction. Preserve nonce-account address, stored nonce, authority, exact observed revision and advance placement. Lifecycle includes initialize, advance, authority change and withdrawal; ordinary `lastValidBlockHeight` expiry is inapplicable. Advancing a nonce invalidates other attempts using that stored nonce, and accepted durable-nonce execution may retain nonce advancement/fees after later instruction failure. A changed nonce alone does not prove which competing transaction executed. Reconcile signatures and account state before replacing an unresolved action.

## Commitment, branch lineage and evidence

Solana `processed`, `confirmed` and `finalized` are chain-specific commitments. A processed observation may be on an abandoned fork; confirmed represents the cluster's confirmation rules; finalized represents rooted finality under those rules. Store requested commitment separately from returned evidence and observed commitment. Preserve slot, blockhash, parent slot/previous hash and signature inclusion where available. An RPC claim remains a source claim until an approved evidence verifier/trust policy establishes its reliability. Do not promote `receivedSignature`, gossip votes, a log line, elapsed time or an indexer's `success` flag into finality.

Design policy may permit reversible UI updates at processed/confirmed while reserving irreversible settlement effects for verified finalized evidence. This is a product policy recommendation, not a universal requirement imposed by RPC. Chain observations and authorized actions remain different contracts even after finality.

A branch-invalidated event must reference exact prior observation IDs and source-object versions, old inclusion/branch evidence, replacement evidence where known, and reason/verifier contract. Roll back derived account/token/protocol projections, invalidate dependent candidate actions and emit explicit correction/compensation requests when an external effect already occurred. Never erase the audit trail or claim an external payment was undone because a local projection rolled back. Solana RPC does not provide a universal Ethereum-style `removed:true` for every subscription; dead-slot information, roots, block lineage and reconciliation must support adapter-specific invalidation. A provider correction and a verified fork invalidation have different authority.

## Native SOL, token and account events

| Closed semantic family | Common intents/observations | Field-specific constraints |
| --- | --- | --- |
| System/native account | Create/allocate/assign account; native SOL transfer; account close/reclaim where applicable; nonce operations | Separate payer, source, destination, program owner, authority and lamport amount; rent reserve/fees are not transfer amount |
| Token mint/account lifecycle | Initialize mint/account/multisig; ATA creation; close account; sync native/wrapped SOL | Bind token program and mint; preserve payer/close authority and native reserve; creating an ATA is not receipt of tokens |
| Token quantity | Transfer/TransferChecked; mint/MintToChecked; burn/BurnChecked; balance/supply observed | Source/destination are token accounts; owners/authorities separate; raw amount, mint, decimals, execution location, fees and extension effects |
| Delegation/authority | Approve/ApproveChecked, revoke, SetAuthority | Delegate allowance versus owner balance; authority kind, previous/new authority; multisig threshold/signers; null authority revocation explicit |
| Account restrictions | Freeze/thaw; frozen/default state; nontransferable/pausable restrictions where supported | Authorized freezer/pauser, affected account/mint, observed state, extension/version; no general inference of transferability |
| Token-2022 extension lifecycle | Transfer fees/withheld amounts/withdrawal; transfer hooks; permanent delegates; confidential balances; interest/scaled UI; metadata/group pointers and authorities | Each extension has a closed profile and pinned supported combinations; preserve additional accounts, policies and hidden/unavailable amounts |

The [Token Program](https://www.solana-program.com/docs/token), [ATA Program](https://www.solana-program.com/docs/associated-token-account) and [Token-2022 documentation](https://www.solana-program.com/docs/token-2022) establish the interfaces. ATA derivation includes wallet authority, token program and mint; validate the correct derivation rather than assume every token account is an ATA. Token-2022 shares base instruction layouts but extension semantics alter required accounts and effects. The [extension guide](https://www.solana-program.com/docs/token-2022/extensions) covers features such as transfer fees, hooks, delegates and confidential transfers; unknown extensions are preserved as opaque source data and block automatic semantic actions.

An observed balance delta is not automatically a transfer. Fees, wrapping/unwrapping, mint/burn, withheld fees, account closure, rebasing/display conversions, swaps and multiple instructions can contribute. A transaction can contain several transfers of the same mint; use instruction/CPI locations for operation identity rather than one record per transaction signature. Confidential amounts remain encrypted/unknown unless an authorized proof/decryption workflow establishes them; never fill them with zero.

## Instructions, CPI and decoding provenance

An instruction profile preserves program ID, ordered account addresses/indices, signer/writable flags, raw bytes and top-level index. A CPI observation also preserves parent instruction index, inner-instruction order and stack height when supplied. Resolve versioned account tables under a pinned transaction-version adapter, retaining table IDs, indices and resolved addresses. Unknown versions reject actionable decoding. Current overview documentation mentions newer formats beyond legacy/v0; cluster activation and adapter support require explicit evidence rather than a global version assumption.

A decoded program event references its raw transaction/account evidence digest, signature, slot/branch, instruction path, program ID, program deployment/code identity when established, decoder schema/IDL digest, decoder version and loss flags. Logs may contain program-defined text, truncated output and nested invocation traces. Anchor/IDL event decoding is a program-specific mapping; log text matching alone is not a validated business event. Account diffs can support state transitions but lack causal transaction identity unless the adapter supplies evidence. Upgradeable programs require deployment/version-aware decoding even when the address remains stable. Provider parser updates require new adapter commitments.

## Wallet and application intent

Support closed request/result/error/cancel variants for connect/disconnect/account changes, `solana:signMessage`, `solana:signTransaction`, `solana:signAndSendTransaction` and `solana:signIn`; adapter APIs may additionally expose `signAllTransactions`. The [Wallet Standard Solana extensions](https://github.com/wallet-standard/wallet-standard/blob/master/extensions/solana.md) and [wallet-adapter signer interfaces](https://github.com/anza-xyz/wallet-adapter/blob/master/packages/core/base/src/signer.ts) define these distinct capabilities; feature-detect them and negotiate supported chains/versions.

Bind each request to requesting application/origin, selected account, approved genesis/chain, method, exact message or transaction bytes/digest, complete human-readable proposal, correlation/action key and expiry. Preserve returned signed bytes, signer identity, signature, and any wallet modifications; verify exact bytes and recheck the authorized proposal. `signMessage` authenticates a byte string only under a verified key binding. It is not permission to send a transaction. Sign-in requires a pinned challenge, domain, nonce, issuance/expiry and replay policy. A wallet connection is neither signature nor standing spending approval. Cancellation and unsupported feature are different from RPC execution error.

## Common DeFi, NFTs and cross-chain applications

These are proposed workflow vocabularies, not claims that Solana RPC already emits standardized business events. Every admitted program needs its own installed closed profiles and exact authority/evidence rules.

| Workflow | Common intent/result families | Meaning that must remain explicit |
| --- | --- | --- |
| DEX/aggregator | Quote, route, swap intent, simulation, submitted swap, executed fill, failed/expired quote | Input/output mint and program, exact-in/exact-out, raw amounts, limit/slippage, deadline/context, route programs, price impact, platform/transfer fees and actual execution; quote is not a fill |
| AMM/liquidity | Pool creation, deposit/withdraw liquidity, position open/close, liquidity increase/decrease, fee/reward collect | Pool/position identity, assets, tick/range/share units, fees and settlement; balance delta alone is insufficient |
| Lending/perpetuals | Supply/withdraw collateral, borrow/repay, liquidation, position/order/fill/funding | Market/obligation, oracle source/revision, collateral/debt units, rates/rounding, signed exposure, margin and liquidation policy |
| Staking/governance | Stake delegation/deactivation/withdrawal/reward; vote/proposal/execute | Authority and stake account separate; epoch-dependent activation, protocol staking distinct from native stake; governance approval is not execution |
| NFT/assets | Create/mint/burn/transfer, list/cancel/buy, escrow, metadata/update/plugin changes | Token Metadata, compressed assets and Metaplex Core are different representations; collection verification and mutable off-chain metadata require explicit provenance |
| Bridge/messaging | Source lock/burn/message publication, guardian/relayer attestation, destination redeem/mint/release, timeout/refund | Source and destination genesis/network, emitter/program, sequence/message digest, asset mapping/decimal normalization, replay protection and independent destination execution evidence |
| Oracle/indexer notifications | Price/state update, risk trigger, webhook correction | Provider/feed identity, signed value/unit/exponent, publish time/confidence/staleness, source revision; data publication does not authorize a trade |

[Jupiter legacy Swap V1 documentation](https://developers.jup.ag/docs/swap/v1) provides a concrete historical aggregator boundary; its live page marks V1 superseded by Swap V2. A new adapter must pin its actually supported API/program version and current migration requirements, rather than treating this V1 example as the current interface. [Metaplex Core](https://www.metaplex.com/docs/smart-contracts/core) provides a distinct asset/account/plugin model; do not represent all NFTs as a token mint plus amount one. [Wormhole's Solana Core contract](https://docs.wormhole.com/products/messaging/reference/core-contract-solana/) provides message publication/verification interfaces; source publication or a valid bridge attestation alone does not establish destination delivery or economic settlement. Other protocols must contribute their own reviewed profiles rather than borrow these semantics by name.

## Proposed minimum profile catalog and actionability

Use versioned exact types under the existing private CloudEvents core. Each row represents a family whose concrete messages have closed schemas and variants; it is not one unrestricted `data` dictionary.

| Family | Concrete variants to install | Default effect classification |
| --- | --- | --- |
| `solana.rpc` | Per-method requested/responded/rejected; transport failed/timeout | Observation or technical request; read capability only where explicitly approved |
| `solana.subscription` | Requested/accepted/rejected/unsubscribed; connected/disconnected/gap/backfilled | Coverage/control evidence |
| `solana.account` | Snapshot/update/closed; lamport balance; decoded state revision | Source state observation |
| `solana.token` | Mint/account/balance/supply; transfer/mint/burn; delegation/authority/freeze/extension variants | Operation observation; matching intents require separate spending capability |
| `solana.transaction` | Proposed/signed/simulated/submission-requested/RPC-accepted/receipt/executed/failed/expired/unresolved | Submission is effect-bearing; other source outcomes are evidence |
| `solana.chain` | Block/slot/root/commitment/vote; branch invalidation | Chain evidence with source-specific strength |
| `solana.instruction` | Raw top-level/CPI; decoded operation/log/event; decoder failure | Derived observation; no arbitrary program dispatch |
| `solana.wallet` | Feature/account session; sign-message/sign-in/sign-transaction/sign-and-send request/result/cancel/error | Signing/submission requires exact account/app/action capability |
| Program-owned profiles | Swap/LP/lending/NFT/bridge/governance/oracle exact variants | Dedicated state machine, policy and authorization |

A production effect requires authenticated source/principal/role, installed contract and adapter, exact chain/account/program binding, current permission and revocation, freshness, approved complete proposal, bounded lamport/token/fee spend, required evidence strength, replay protection and durable atomic action state. An observation never grants spending power. An outer MPE sender authentication cannot turn a node/indexer claim into validator consensus proof or prove that the sender controls the wallet. Preserve source authenticity, execution validity, chain finality and application authorization as independent checks.

Large blocks, account data, CPI traces and token extensions exceed the pilot's 3,926-byte body and 16-item arrays. Future profiles require reviewed bounds and transport-compatible attachment/evidence references with exact digest, size, media type, authorization and retention policy; no live arbitrary URL fetch or hidden truncation. A bounded summary must disclose omitted data and cannot claim complete execution semantics without the required evidence.

## Acceptance evidence required before runtime adoption

Verify lossless large-integer handling across Rust/TypeScript, base58 decoded lengths/PDA handling, genesis mismatch rejection, failed/successful transaction metadata, null/absent history, token authority versus program owner, Token/Token-2022 ATA separation, fee-bearing failures, nonce advancement on failure, repeated CPI transfer identity, unsupported version/extension refusal, wallet-returned-byte mismatch, reconnect/backfill gaps, dead-branch projection rollback and source/destination bridge independence. Use two independent adapters and canonical-intent comparison. Documentation inventory and source archives do not substitute for these conformance tests.

Primary evidence is stored in [the Scrapling manifest](../../catalog/data-model/solana/manifest.json), with raw/text files, SHA-256 hashes, retrieval time, original/resolved URL, HTTP status and fetch errors. The initially guessed Wormhole shim URL returned 404 and is not evidence; the replacement Core-contract source is separately archived. Successful removed-method pages are explanatory evidence, not supported methods. Archive redistribution/license review is still required before importing vendor SDKs, IDLs or generated protocol schemas.
