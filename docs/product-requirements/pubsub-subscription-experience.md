# Private subscriptions and consumer experience

Midnight Express should let a person, wallet, DApp or agent follow a business workflow without publishing its interests to delivery operators. A buyer can follow quotes, a finance application can follow invoice evidence, and an agent can collect approval requests for human review. Receiving an update must remain separate from deciding that it is trustworthy and authorized to cause an action.

## Discover and organize feeds

The user selected a feed directory as the subscription page’s default workflow. It must make hundreds of feeds searchable and let people retain organization between visits. Inbox reading and delivery operations support that directory. The [council recommendation](../../design/subscriptions/directory-workspace.md) specifies directory, preview, inbox and delivery workflows; the [research record](../../wiki-llm/subscription-design-council/README.md) preserves evidence and disagreements. The target experience requires distinct, explicitly scoped feed identities and retained information, not hundreds of aliases for the same category. Persisted synthetic inbox and read markers may be retained as labeled historical information, but cannot restore current authority, wallet connection or active delivery without a fresh check. A metadata-only scale harness is useful verification and does not substitute for independently selectable feeds. This requirement does not claim that the current tab-memory demo provides those capabilities.

## From connection to a useful inbox

A host receives its selected whole shard and performs recognition and authenticated decryption locally. An authorized consumer then creates a private watch over exact supported profiles and contract commitments. Browse categories are navigation aids; they are neither network topics nor new data-model types. The local service binds each watch to its principal, revision, allowed source scope, expiry, start position and bounded delivery policy.

| Consumer | Subscription experience | Authority boundary |
|---|---|---|
| Human | Browse descriptions, inspect an example, choose a scope, see permission and recovery state, review an inbox item. | Display and review do not execute an effect. Permission expiry blocks further delivery. |
| Wallet | Explicitly connect the wallet, then separately request a local watch over supported quote or payment evidence. | Wallet origin access, shard membership, source authentication and transaction approval are separate grants. |
| DApp | A typed local SDK creates the watch and pulls bounded batches; its UI renders provenance and pending/final/reversed observations. | Application policy and authenticated evidence determine permissible actions. A displayed Final label cannot supply missing finality. |
| Agent | Discover schemas and capabilities, use a human-provisioned scoped watch, read bounded batches, commit dispositions and ask for approval through a separate action contract. | Notifications cannot authorize tools. Scheduling and autonomous wake-up depend on the host. |

Pause stops consumer delivery. Whole-shard intake and resource scheduling must remain independent of which messages match; local queue pressure never propagates into recognition-dependent network timing. Resume rechecks permissions and reports any coverage gap. Close records a tombstone and does not erase effect deduplication. Scope edits create revisions; old deliveries retain the revision under which they were selected. Revocation stops queued callbacks as well as fresh delivery. Already disclosed information cannot be recalled. Real selectors, revision history and processing dispositions reveal interests; exports and diagnostics require deliberate disclosure. The demo export contains mock data only.

A host journal high-water records intake separately from each watch. A delivery cursor records receipt into the consumer inbox. A processing cursor records contiguous decided dispositions, including explicit quarantine. These positions describe local progress; ledger finality and business execution require their own evidence. Retention and backpressure must never silently advance either cursor. An unavailable interval requires an explicit gap and a choice between authorized archive recovery and accepting a new start.

## Components to build

The existing transport, recognition, admission, Registry and database choices provide a foundation. They do not yet implement this consumer experience. Add a private local consumer service and typed SDK with principal-bound handles, closed selectors, capability checks, bounded pulls, cancellation, revision history and a durable consumer journal. Use Umbra/PostgreSQL for the backend composition and SQLite for the standalone tier; their integration must atomically preserve inbox dispositions, cursors and effect-related state. The browser demonstration clears on reload and supplies no database durability evidence.

The proposed application operations are `watch.create`, `watch.list`, `watch.read`, `watch.pause`, `watch.resume`, `watch.close`, `consumer.commit` and a separately authorized `action.prepare`. These are application operations exposed through an adapter. MCP supplies the surrounding protocol methods. [The proposed local contract](../../design/subscriptions/README.md) records the schema and integration gates.

Keep optional interoperability adapters above that service. Current [MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog) uses `server/discover` and `subscriptions/listen`; legacy resource-subscription methods require a separately negotiated compatibility adapter. Notifications invalidate a local watch resource, after which the client reads the journal. MCP notification connections are not the durable watch itself. Read on startup and reconnect as well as on notifications; host-scheduled bounded polling can cover missed hints. Private watch responses use private cache scope and no cache lifetime, with authorization checked on every request. Sender text is capped and explicitly untrusted; it cannot add tools, widen a grant or become a tool description. Agents may use a human-provisioned watch grant by default; expanding scope requires human approval. A2A provides commissioned remote agent tasks, MCP Apps is a candidate for supervision inside an agent host, AG-UI renders custom agent frontends, and Agent Client Protocol serves editor integration. Keep these adapters optional. The [standards inventory](../../wiki-llm/pubsub/standards.md) distinguishes current versions, historical interfaces, drafts and frameworks.

No added broker is selected for the default private transport. Kafka and NATS offer useful recovery and credit patterns to study, but remote interest routing would change the privacy profile. A hosted gateway that sees selectors requires its own explicit disclosure and authorization model.

## Data-model usefulness and limits

The existing v0.2 model provides exact quote, invoice-observation and sandbox-approval contracts suitable for selecting and interpreting bounded workflows. [Actual validation results](../../wiki-llm/pubsub/data-model-fit.json) bind events and synthetic trusted contexts to a fixed test clock. Accepted results retain `executes:false`. Changed authority, unsupported fields and expired contexts are refused. This evidence supports the reference fixtures; it does not establish live source authenticity, finality or customer adoption.

Subscriptions, cursors, queue state and connection events belong to the local control plane. Do not add them to the sealed business envelope. Contract renewals and credential expiry need separate reviewed payload contracts, evidence rules and conformance vectors before promotion from mock examples. Ethereum and Solana vocabularies remain bounded observation domains, not blanket support for every chain application or signing operation.

## Moth and the website demonstration

[The subscription page](../../website/dist/subscriptions.html) exposes mock categories, local watches, bounded delivery, review, duplicates, gaps and permission changes. Quote, payment and approval examples carry actual fixed-context validator results bound to the event and context hashes. Contract, credential and operations examples remain explicitly mock-only. All journal state is in memory and clears on reload or reset; no transport, protocol admission or transaction execution runs in the page.

The Moth adapter targets the verified experimental reference implementation, API 4.0.1 and `preprod`. It discovers `window.midnight.moth`, connects only after an explicit user gesture, and calls only connection and status methods. Moth's grant applies to the origin and includes capabilities beyond those calls. Local disconnect clears the adapter handle; it cannot revoke that grant. The public Pages site shares its owner origin with other project sites; connection therefore requires explicit acknowledgement of that origin-wide exposure. Production wallet integration should use a dedicated origin and no third-party scripts. Status checks are explicit, since Moth connector activity refreshes auto-lock. The beta connector API is not silently accepted. [Wallet research](../../wiki-llm/pubsub/wallet-consumers.md) records the source commit and limitations.

## Acceptance evidence

Require real transport integration without business selectors leaving the host; permission expiry and revocation before every callback; cross-principal watch isolation; bounded queues and explicit retained-range recovery; immutable scope revisions; restart-safe contiguous checkpoints; and idempotent conflict handling by source and occurrence identity. Exercise subscription recovery separately from uncertain external effects.

Validate exact MCP version negotiation and reconnect behavior, unsupported wallet versions, wallet rejection, provider disappearance and network mismatch. A real Moth extension session remains a manual integration gate. Promote new business profiles only after economic meaning, units, lifecycle, source evidence and action authority are explicit and independent interpreters agree on conformance examples. Collect customer workflow baselines before claiming business savings. Measure whole-shard recognition cost and real sealed payload sizes; JSON example sizes alone do not establish fixed-class wire fit. Store repair, finalized root freshness and RLN per-class credit compatibility remain original protocol gates.


## Directory replacement acceptance

The replacement must resolve each stable feed through trusted local metadata to an explicit principal/shard/profile/contract/source/predicate scope. Multiple same-category subscriptions work independently; renamed descriptors cannot silently revise installed scopes. Folders, channels and saved views organize information and do not create network topics or broaden permissions. Keep the closed local intent and sealed business envelope unchanged unless a separately reviewed extension is required.

Preserve bounded synthetic history, read/saved markers and requested intent through reload, with current authority unchecked and no automatic Moth calls. Validate browser records, handle migrations, quota failure and stale-tab writes, and atomically preserve dispositions and checkpoints before reporting durable progress. Real private history belongs to an authenticated service and dedicated origin. A metadata-only catalog or retained bookmarks alone does not fulfill stateful independent subscriptions.

Search and results must be usable in the first viewport. Use stable native result rows, local facets, clear empty/error states and reliable focus/back behavior. Reading leaves processing unchanged; review/quarantine targets the selected receipt. Credits-full is behind, distinct from lost history; recovery and explicit new-start acceptance preserve pause. Intake and repair stay independent of follow/match state. Exercise independent mock-source scope isolation and hundreds-watch resource bounds separately from catalog rendering and production transport measurements. Detailed acceptance scenarios are in the workspace recommendation.
