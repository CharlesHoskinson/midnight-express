# Ethereum applications — proposed bounded domain

Status: researched inventory and proposed contract families, **no implemented Ethereum profile or adapter**. The [Python reference](../../model/README.md) accepts only RFQ, invoice and sandbox approval; its positive 18-digit decimals and 3926-byte event bound cannot represent general uint256 values, receipts, ABIs or blocks. These require separate closed contracts and bounded pagination/evidence objects. This study extends the [unified model](unified-data-model.md) without changing the encrypted transport or authorizing execution. Source captures and hashes are in [the Ethereum catalog](../../catalog/data-model/ethereum/manifest.json).

“Common” means the application-facing RPC, wallet and contract surfaces inventoried below. It does not mean every Ethereum client extension, every EVM chain, every protocol ABI, or every future fork is supported. Source specifications describe APIs; the proposed MPE types are original mappings. An inventory row is a design requirement, not a working adapter.

## Common RPC messages

Preserve JSON-RPC `jsonrpc`, method, request ID type/value, parameter order, endpoint/session, chain binding and response result/error as distinct typed records. A request ID correlates within a connection/request scope; it is not an occurrence ID or transaction ID. Results can be `null`; errors have integer code, message and bounded opaque data. Batch entries correlate by ID, not array position. Notifications have no response ID. Requests, observations and execution intents must never share an ambiguous `transaction` event type. The [RPC reference](https://ethereum.org/developers/docs/apis/json-rpc/) and [EIP-1474](https://eips.ethereum.org/EIPS/eip-1474) provide the baseline; client support is discovered and pinned per adapter.

| Family | Common requests / responses | Proposed private profile and boundary |
| --- | --- | --- |
| Endpoint/network | `web3_clientVersion`, `net_version`, `net_listening`, `net_peerCount`, `eth_chainId`, `eth_syncing`, `eth_blockNumber`, `eth_accounts` | `ethereum.endpoint-observed`; distinguish network ID from signing chain ID, syncing false from progress object, node accounts from wallet exposure |
| Block/header | `eth_getBlockByHash`, `eth_getBlockByNumber`, transaction counts by hash/number, `eth_getBlockReceipts` where supported | `ethereum.block-observed`; header projection or bounded transaction-hash pages; preserve block hash/parent hash, height, timestamp and fork fields, never silently omit unknown effect-bearing fields |
| Transaction lookup | `eth_getTransactionByHash`, `eth_getTransactionByBlockHashAndIndex`, `eth_getTransactionByBlockNumberAndIndex`, `eth_getTransactionReceipt` | `ethereum.transaction-observed` / `ethereum.receipt-observed`; explicit null/not-found observation, pending nullable location, included receipt and execution status |
| Account/state | `eth_getBalance`, `eth_getTransactionCount`, `eth_getCode`, `eth_getStorageAt`, `eth_getProof` | `ethereum.state-observed`; chain, subject and exact state block/hash; proof bytes require a separate bounded proof reference and a specified trusted root/verifier |
| Simulation/fees | `eth_call`, `eth_estimateGas`, `eth_gasPrice`, `eth_maxPriorityFeePerGas`, `eth_feeHistory`, `eth_createAccessList` where supported | `ethereum.simulation-observed` / `ethereum.fee-observed`; retain call inputs, state, revert bytes, gas and override provenance; simulation is neither mined success nor execution permission |
| Broadcast/sign | `eth_sendRawTransaction`, `eth_sendTransaction`, `eth_sign`, wallet signing methods | `ethereum.broadcast-requested/result`, `ethereum.transaction-proposed`, `ethereum.signature-requested/result`; admission/hash return proves no inclusion; sending and signing are separately authorized capabilities |
| Log filters | `eth_getLogs`, `eth_newFilter`, `eth_newBlockFilter`, `eth_newPendingTransactionFilter`, `eth_getFilterChanges`, `eth_getFilterLogs`, `eth_uninstallFilter` | `ethereum.log-observed` plus filter/session lifecycle; bounded ranges/pages and gap accounting; filter IDs are endpoint-local and expiring |
| Subscriptions | `eth_subscribe`, `eth_unsubscribe`, `eth_subscription` for `newHeads`, `logs`, `newPendingTransactions`, `syncing` | `ethereum.subscription-state` plus observations; subscription IDs scope to endpoint/connection, delivery is not a durable complete ledger feed |

The baseline also inventories uncle queries, legacy mining/work APIs and `web3_sha3`; defer them rather than confuse them with modern application finality. `debug_*`, `trace_*`, `txpool_*`, `admin_*`, `personal_*`, Engine API, historical archive availability and vendor webhooks/indexer pagination are separate client-specific profiles. Transaction traces are needed to describe internal native-value movements; ordinary logs do not enumerate them. `eth_getBlockReceipts` and optional methods must be capability checked, never assumed portable.

## Blocks, receipts, log ordering and transaction lifecycle

A block observation records the network's genesis/checkpoint identity as well as chain ID, block hash, parent hash, number and source/observation time. Chain ID alone does not distinguish a private fork. `latest`, `pending`, `safe`, `finalized` and `earliest` are query selectors, not immutable evidence identities. Resolve a returned observation to a concrete hash/height when available. Pending state has no committed block hash. [EIP-1898](https://eips.ethereum.org/EIPS/eip-1898) allows hash-based selectors and `requireCanonical` on specified state methods; support must be checked.

[Geth subscriptions](https://geth.ethereum.org/docs/interacting-with-geth/rpc/pubsub) are live connection streams: reconnect requires replay/reconciliation from a durable cursor, and a subscriber may receive multiple headers at the same height. Catch-up may emit only the last head. A log can be re-emitted with `removed:true` when its old block is reorganized out, then reappear in a different block. Preserve `(network,blockHash,transactionHash,logIndex)` as the physical log location, order with block/transaction/log indexes, and emit an explicit removal/reorg observation rather than overwrite history. A missing removal notification does not establish canonicality. Block ancestry, backfill and canonical hash checks detect gaps and invalidate dependent observations.

| State/observation | Evidence and exact interpretation |
| --- | --- |
| Proposed | Local complete transaction intent; no signature or broadcast implied |
| Signed | Exact signed bytes and hash under a pinned transaction codec; signature result alone is not a broadcast |
| Broadcast accepted / rejected / outcome unknown | Endpoint result, RPC error or transport timeout; acceptance/hash return is not mempool-wide acceptance or settlement; unknown outcome needs reconciliation |
| Pending observed | Endpoint pending transaction notification or lookup with null block location; mempools are local and incomplete |
| Included succeeded / reverted | Receipt `status` 0x1 / 0x0 at a concrete block; pre-Byzantium root-based receipts need a separate historical profile; status is EVM execution outcome, not application economic success |
| Canonical / safe / finalized observed | Independently recorded chain-head relation and source finality view for that receipt's block; confirmation count alone is not protocol finality |
| Orphaned | Canonical ancestry check or removed log/block evidence; prior effects require workflow compensation/reconciliation |
| Replacement suspected / confirmed under policy | Two different signed transaction hashes for the same recovered sender, chain and nonce; observing one does not prove the other was globally dropped; canonical inclusion determines which nonce consumption occurred |
| Dropped suspected / unavailable | Explicit adapter inference with endpoint coverage, observation interval and policy; null lookup or elapsed time proves neither cancellation nor global drop |

There is **no universal Ethereum JSON-RPC replaced/dropped notification**. A same-nonce “cancel” is another transaction intent and may lose the race; label wallet/indexer assertions separately. No receipt for an unseen transaction means unknown/pending/unavailable, not failed. Receipt records retain transaction/block identity, sender/destination or contract creation address, transaction index, gas used, cumulative gas used, effective gas price, logs and applicable type/blob-gas fields. A reverted transaction can still pay fees. For blob transactions, execution and blob fee quantities remain distinct. [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) and [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) require versioned transaction fields; unknown types reject actionable decoding.

Ethereum proof-of-stake finality is a consensus checkpoint property, not a synonym for “N blocks old”; the [consensus overview](https://ethereum.org/developers/docs/consensus-mechanisms/pos/) explains finalization. Record head hash/height and the assertion source for safe/finalized observations. Do not silently promote a provider claim to a locally verified consensus proof. Finality delay, contradictory providers, a stale endpoint and L2 settlement/challenge semantics require explicit network policy and a halt/reconcile path.

## Exact values and decode provenance

RPC `QUANTITY` is minimal unsigned `0x` hexadecimal (`0x0` for zero; no leading zero digits); `DATA` is even-length hexadecimal bytes (`0x` is empty). Normalize validated quantities to canonical unsigned decimal strings with range checks, retaining original response digest and conversion contract. Reject floats, exponential notation, odd-length byte hex, ambiguous zeros and truncation. Use lowercase normalized hex internally after validating a source address/checksum convention; addresses are exactly 20 bytes and hashes exactly 32 bytes. EIP-55 checksum spelling, ENS names and symbols are presentation/resolution data, not independent wallet identities. Chain IDs are exact bounded integers encoded as strings, never JavaScript numbers; bind them to approved network configuration.

ETH native amounts and gas prices use integer **wei** (10^18 wei per ETH); gas is an independent integer unit, gas price is wei/gas, and total fees require actual receipt inputs and fork rules. Token amounts are integer base units tagged with chain, contract and standard; ERC-20 `decimals` is optional metadata, not permission to assume 18. ERC-721 IDs are uint256 identifiers, not amounts; ERC-1155 has uint256 IDs and uint256 quantities. Zero native/token transfers and zero approvals are valid. ABI signed integers, fixed bytes, booleans and arrays preserve exact Solidity widths/types; do not coerce signed swap deltas into positive quantities.

Raw log evidence includes emitting address, topics (at most four under the EVM log instruction), data, block/transaction locations and removed flag. ABI decoding is a **separate attestation**: raw digest, decoder/version/contract digest, ABI artifact digest, event signature including canonical parameter types, indexed layout, contract deployment identity and proxy implementation/code binding at the observed block. [Solidity ABI rules](https://github.com/ethereum/solidity/blob/develop/docs/abi-spec.rst) explain that indexed dynamic values are hashes, not recoverable plaintext, and anonymous events omit the signature topic. A familiar topic does not prove token compliance or protocol identity. Unknown/ambiguous ABI, unverified proxy upgrades or malformed data remain opaque evidence; no guessed decoding drives an effect.

UserOperation hash, transaction hash and wallet batch ID are different identities. A token approval or signed permit can create spending authority and is never classified as an inert notification merely because it transfers no tokens immediately.

## Bounded mapping and actionability

Proposed families reuse only occurrence/source/time/contract and evidence provenance; chain and wallet primitives live in this domain. Each exact event type gets its own closed schema, explicit numeric bounds, enum state machine, adapter commitment and authority model. The [machine inventory](../../catalog/data-model/ethereum/inventory.json) records the boundary. Large results use bounded projections/pages plus locally installed evidence-reference contracts; sender URLs never trigger automatic retrieval. Preserve complete raw response digests and loss fields; a projected object is not a full signed receipt or block.

All above events are informational unless a separately reviewed action contract matches a current authenticated capability. Before signing/broadcasting: recheck selected account/chain, full destination/calldata/value, nonce, gas/fee cap, wallet permission, expiry and proposal digest; require approved ABI/code/proxy binding where decoding affects policy. Bind approvals to a stable action key, not a new event ID. Recheck revocation and use durable atomic replay/effect state; unknown broadcast outcome stops automatic resubmission until reconciled. Before a balance/payment/bridge-triggered effect: independently establish source authenticity, canonical block identity, required finality, current state and exact application meaning. Never interpret token symbols, logs, wallet connectivity, RPC success or an LLM narrative as authorization.

Implementation acceptance must cover two independent source adapters, cross-language uint256/ABI agreement, chain switch and wallet rejection, duplicate/out-of-order/reorg logs, reconnect gaps, failed receipts, replacements as inference, decimal metadata changes, proxy upgrades, bounded batches and stale/contradictory finality. No such implementation or test result is claimed here.
