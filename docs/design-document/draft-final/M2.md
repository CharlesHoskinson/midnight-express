## Specification

This specification defines the MPE Envelope bytes, the cryptographic bindings and the endpoint checks for delivering Confidential Messages over the GossipSub overlay and the ledger lane, including carried events. It changes nothing in the Midnight node. Nor does it define a contract event type: contract events, public or private, keep the meaning that MIP-0002 and MPS-0005 give them [@midnight-mip-0002; @midnight-mps-0005].

A Publisher and its Subscribers share a stream secret through an authenticated invitation. The Publisher seals each Message under keys derived from that secret into a fixed-size MPE Envelope, attaches admission, and either sends the Envelope to a Bus Node or puts its Sealed Body on the ledger lane. Bus Nodes relay it unopened. A Subscriber opens only the Envelopes whose Recognition Tag matches.

### Terminology and conventions

The terms fall into four groups: the Foundation's event terms, and this proposal's application objects, transport objects and infrastructure roles.

| Term | Meaning |
|---|---|
| event | The Foundation's term: a contract event that a Compact circuit emits with `emit`. The transaction transcript records it and the Indexer serves it [@midnight-mip-0002; @midnight-coip-0003]. |
| private event | The Foundation's term: a contract event some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment that the proof checks. MPS-0005 Part 2 plans it, and that text is unpublished [@midnight-mps-0005]. This specification does not redefine it. |
| Indexer | "A service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]. |
| Message | The application message a Publisher seals and delivers. A Message is not a contract event. |
| Confidential Message | A Message sealed into an MPE Envelope for which the four properties defined in Chapter 4 hold: content confidentiality, sealed labels, conditional interest privacy and no silent change. Its Publisher's signature authenticates it and an Anchor commits it. No contract execution does either. |
| Carried event | A Confidential Message whose payload is the unchanged bytes of a contract event, public or private, together with the transaction hash and position that let a Consumer verify it against the chain. |
| stream | An application channel set up by an authenticated invitation and identified only inside the Sealed Body. It is also called a private stream, and it is distinct from a Shard. |
| consumption nullifier | The value a consuming contract records so that it refuses a second reaction to the same Message (Consumer interface). |
| MPE Envelope | The fixed-size wire object that carries one Message across the overlay. On the ledger lane only its Sealed Body travels. Ledger records such as `VersionedLogItem` are never called envelopes in this specification. |
| pubsub message | GossipSub's message object. Its protobuf `data` field carries exactly one MPE Envelope. |
| Shard | One partition of the overlay, carried as one GossipSub topic. The word "topic" appears only in "GossipSub topic" and in the names of MPS-0005's planned `@topic` annotation and topic-based filtering, to which a Shard is unrelated. |
| Recognition Tag | A salted, keyed 16 B value in each MPE Envelope that lets a Subscriber recognise candidate Envelopes locally. |
| carrier | The route that delivers a Message: the GossipSub overlay or the ledger lane. |
| ledger lane | The explicitly selected carrier that puts a class 0, 1 or 2 Sealed Body on Midnight as 1, 4 or 16 `Misc` events named `mip-xxxx:envelope[v1]`, all in one phase of one intent [@midnight-mip-0019]. The per-block `bytes_written` budget of 50,000 B bounds its capacity, as does `block_usage` (Ledger interface). |
| Admission Proof | The proof or ticket in the Admission Slot that authorises one publication under the applicable rate limit. It is not a Midnight transaction proof. |
| admission window | The 60 s interval, numbered `floor(Unix time / 60)`, to which the per-class publication limits apply. |
| admission nullifier | The class-bound value in the Admission Slot that identifies one use of a publication allowance. |
| Anchor | A Bus Registry state record that commits to the Envelope Identifiers accepted in one 60 s window across all Shards. Its `Misc` copy, named `mip-xxxx:anchor[v1]`, is only a notification. Verification uses Bus Registry state. |
| Bus Node | A sidecar process that runs beside the Midnight node, not inside it, joins the GossipSub overlay and relays MPE Envelopes. |
| Store Node | A Bus Node that also retains MPE Envelopes for back-fill. It stores no chain history. |
| Publisher | The client role that creates, seals and submits Messages. On the ledger lane it is also a MIP-0019 publisher [@midnight-mip-0019]. |
| Subscriber | The client role that receives MPE Envelopes and recognises Messages locally. On the ledger lane it acts as a MIP-0019 reader. |
| Consumer | A party that acts on a Message: an autonomous agent, wallet, application or smart contract. A contract consumes a Message only through a later transaction (DEC-022). The Foundation's consumer of events also includes indexers and explorers [@midnight-mip-0002; @midnight-mip-0018]. |
| Bus Operator | A party that runs a Bus Node, a Store Node or an anchoring service. An Indexer operator is not a Bus Operator unless it also runs one of these. |
| Bus Registry | The Compact contract that holds memberships, parameters, the relay list and Anchors (Ledger interface). |
| Ledger Adapter | The interface through which clients and Bus Nodes read Midnight ledger information and submit transactions. It acts only on finalized blocks. |
| Visible Header | The 8 B fixed header and the Admission Slot that precede the Sealed Body. |
| Admission Slot | The fixed-width region that holds the admission fields and zero fill. |
| Sealed Body | A fixed-length body made of a clear recognition prefix and authenticated ciphertext. |
| Sealed Prefix | The fixed 40 B prefix inside the encrypted plaintext. |
| Logical Message Identifier | A random 16 B identifier that stays the same across retransmissions and carriers of one Message. |
| Envelope Identifier | The content commitment that excludes the Admission Slot, abbreviated EID. |
| Network Identifier | The 32 B genesis block hash of the Midnight network, abbreviated `N`. |
| Cryptographic profile | The algorithms, encodings, domains, key lifecycle and one-byte suite identifier that an MPE Envelope version selects. |

The capitalised words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY have the meanings defined by BCP 14, RFC 2119 and RFC 8174, and only when they appear in capitals. Parenthesised identifiers refer to Appendix A, and parameter identifiers refer to Appendix A.1.

Offsets are zero-based, and byte ranges are half-open: `[a:b]` includes byte `a` and excludes byte `b`. `||` denotes byte concatenation, and quoted domain strings are ASCII bytes without a terminating zero. All multi-byte integers MUST use unsigned big-endian encoding (`MPE-FMT-002`, `MPE-CRY-006`).

The initial parameters are the version-1 values that the proof of concept will implement. A production change that needs different offsets or a different cryptographic interpretation selects a new MPE Envelope version.

### MPE Envelope and sealing

**Wire layout and size classes.** Each MPE Envelope version MUST select exactly one cryptographic profile. Version 1 MUST select profile `mpe-v1-sym`, suite identifier `01`: HKDF-SHA-256, HMAC-SHA-256, ChaCha20-Poly1305 and plain Ed25519 (`MPE-CRY-001`, `MPE-FMT-053`). The suite identifier names the profile in invitations and in the label table below, in the manner of the suite byte of MIP-0012's `InboxEntry` [@midnight-mip-0012], but it is not a wire field. Because a version binds exactly one suite, a new suite takes a new version, just as a new `InboxEntry` suite takes a revision of MIP-0012.

ChaCha20-Poly1305 is an AEAD scheme: it encrypts a plaintext and authenticates it together with associated data that travels in clear. The profile assumes that HKDF-SHA-256 and HMAC-SHA-256 are pseudorandom functions, that SHA-256 is collision resistant, that ChaCha20-Poly1305 is confidential and unforgeable while no key-nonce pair repeats, and that Ed25519 signatures cannot be forged.

A Bus Node reads the header without opening the Envelope. An MPE Envelope therefore MUST contain the following fixed fields, and it MUST NOT contain optional fields, external extension fields, variable-length integers or self-describing wrappers (`MPE-FMT-001`, `MPE-FMT-003`).

| Wire offset | Length | Field | Interpretation |
|---:|---:|---|---|
| 0 | 1 B | `version` | `01` |
| 1 | 1 B | `size_class` | Class 0, 1, 2 or 3 |
| 2 | 1 B | `shard` | Shard index |
| 3 | 1 B | `reserved` | `00` |
| 4 | 4 B | `expiry` | Unix time in seconds |
| 8 | 512 B | Admission Slot | Admission fields followed by zero fill |
| 520 | `B` B | Sealed Body | Length selected by `size_class` |

The Sealed Body MUST have exactly the selected length. The client MUST choose the smallest class that holds the payload unless the application asks for a larger class, and it MUST refuse a payload that exceeds the selected class's capacity, without truncating it and without silently fragmenting it (`MPE-FMT-013` to `MPE-FMT-015`).

Every body spends 170 B before any payload. Sixty bytes lie outside the encrypted plaintext, namely the 44 B clear prefix (salt, nonce and Recognition Tag) and the 16 B Poly1305 authenticator, so the plaintext is `B − 60` bytes. Inside the plaintext, the 40 B Sealed Prefix and the 70 B Publisher authentication block take 110 B more, which leaves a payload capacity of `B − 170` bytes. Capacities and wire lengths per class follow from these two subtractions.

| Class | Body `B` | Clear prefix | Plaintext `B − 60` | Maximum payload `B − 170` | Wire `8 + 512 + B` |
|---:|---:|---:|---:|---:|---:|
| 0 | 256 B | 44 B | 196 B | 86 B | 776 B |
| 1 | 1,024 B | 44 B | 964 B | 854 B | 1,544 B |
| 2 | 4,096 B | 44 B | 4,036 B | 3,926 B | 4,616 B |
| 3 | 16,384 B | 44 B | 16,324 B | 16,214 B | 16,904 B |

These wire lengths are complete MPE Envelopes; they exclude the pubsub protobuf framing and the transport framing (Noise and Yamux). The encoded GossipSub RPC limit MUST be 65,536 B (`MPE-FMT-010`, `MPE-NET-014`), and every encoded RPC, including batched messages and control fields, MUST fit that limit. A single class-3 Envelope of 16,904 B leaves room for framing, but several valid Envelopes batched into one RPC can exceed it: four take `4 × 16,904 = 67,616 B` before framing.

A Bus Node built on go-libp2p-pubsub MUST set the limit explicitly instead of using the library's 1 MiB default.^[libp2p/go-libp2p-pubsub, pubsub.go, constant DefaultMaxMessageSize; accessed 2 October 2026.] Rejecting an MPE Envelope for its length and rejecting a transport frame for its size are separate checks.

**Admission Slot.** Admission caps how many Envelopes of each size class a member publishes per admission window, through the rate-limit relation of RLN-v2 [@2024-vac-rln-v2-spec]. Each publication spends one allowance, fixed by the window, the class and an allowance index. That allowance defines a line `y = a0 + a1 × x` whose intercept `a0` is the member's admission secret and whose slope `a1` is a hash of the secret, window, class and index. The abscissa `x` is a hash of the EID, and the slot carries the share `y` and the admission nullifier, a hash of `a1`. A member who spends one allowance on two different EIDs therefore publishes two points on one line under one admission nullifier, and two points fix the line and expose `a0`. How admission is built and validated is specified in "Overlay protocol". The initial slot is laid out as follows.

| Wire offset | Slot offset | Length | Field | Meaning |
|---:|---:|---:|---|---|
| 8 | 0 | 8 B | `window` | Admission window, `floor(Unix time / 60)` |
| 16 | 8 | 32 B | Membership root | Bus Registry membership root used for admission |
| 48 | 40 | 32 B | Admission nullifier | Class-bound identifier of one publication allowance |
| 80 | 72 | 32 B | Share `y` | Admission share bound to the EID |
| 112 | 104 | 256 B | Proof | Input to the selected admission verifier |
| 368 | 360 | 152 B | Fill | All zero bytes |

The client MUST keep this fixed layout and zero-fill the unused slot bytes. The slot MUST NOT contain a persistent label specific to a Publisher (`MPE-FMT-003`, `MPE-FMT-005`, `MPE-FMT-050`; `MPE-ECO-052`, `MPE-ECO-053`).

The admission mechanism specified for the proof of concept is a stand-in whose membership secrets Bus Nodes can see. Those Bus Nodes can link publications to memberships and forge admission, so the stand-in provides no admission unlinkability and no admission privacy. It is suitable only for devnet and testnet. A production zero-knowledge admission proof system remains a profile to be selected separately, and its binding and operating cost are unknown until that selection is made. Whatever the system, the admission secret MUST NOT be sent to a prover outside the client's trust boundary unless that prover is attested, because a remote prover receives the private witness [@midnight-mps-0004].

In production, the slot width `W` is the measured length of the proof fields, rounded up to a multiple of 64 B, capped at 4,096 B and fixed per version. The body then begins at `8 + W`, and the wire length becomes `8 + W + B`. A wider slot weighs most on class 0. With the 512 B version-1 slot, header and slot take 520 of its 776 wire bytes (67 percent); at `W = 1,024 B` they would take 1,032 of 1,288 B (80 percent), against 1,032 of 2,056 B (50 percent) in class 1. All four body classes therefore remain available when `W ≤ 1,024 B`. Otherwise the production table keeps classes 1 to 3 (DEC-013). The width MUST be measured before that version's class table is frozen (`MPE-FMT-007`, `MPE-FMT-048`, `MPE-FMT-053`; `MPE-ECO-048`).

No production admission proof exists, so `W` can only be estimated from proofs on the same proof system. The cost model gives 4,368 B for every Bus Registry, ledger-lane and consumer circuit compiled for the ledger interface, a figure derived, not measured on a network. An admission proof of that size plus the 104 B of other slot fields needs `104 + 4,368 = 4,472 B`, which rounds up to `W = 4,480 B`, above the 4,096 B cap (P-ECO-11). Since the cap bounds the slot of every class, no class has a valid layout at that width. The production profile therefore needs either a smaller proof or a revised cap.

**Body and plaintext.** The body MUST begin with the salt, the nonce and the Recognition Tag, in that order (`MPE-FMT-051`).

| Body offset | Wire offset | Length | Field |
|---:|---:|---:|---|
| 0 | 520 | 16 B | MPE Envelope salt |
| 16 | 536 | 12 B | AEAD nonce |
| 28 | 548 | 16 B | Recognition Tag |
| 44 | 564 | `B − 60` B | Encrypted plaintext |
| `B − 16` | `520 + B − 16` | 16 B | Poly1305 authenticator |

The Recognition Tag and the Poly1305 authenticator are different fields. The salt, nonce and Recognition Tag are observable, and the plaintext fields after them are encrypted. Sealing protects content under the profile's assumptions, and equal wire lengths hide payload length only within a size class. An observer still sees the class, Shard, visible expiry, message timing, volume and the full transport transcript, and the GossipSub topic name also reveals the network prefix, the major version and Shard membership.

The client MUST encode the plaintext as the fixed binary structure below, including the 70 B Publisher authentication block (`MPE-FMT-034`, `MPE-CRY-041`).

| Plaintext offset | Length | Field | Version-1 meaning |
|---:|---:|---|---|
| 0 | 1 B | `pt_version` | `01` |
| 1 | 1 B | `kind` | `01`, application Message |
| 2 | 2 B | `flags` | `0001`, authentication block present |
| 4 | 2 B | `payload_len` | Actual payload length |
| 6 | 2 B | `schema_version` | Application schema version |
| 8 | 8 B | `seq` | Sequence number per Publisher and stream |
| 16 | 16 B | Logical Message Identifier | Random identity of the Message |
| 32 | 8 B | Schema identifier | Registered decoder identifier |
| 40 | 2 B | Authorised-key index | Index into the invitation's list of Publisher keys |
| 42 | 4 B | `creation` | Unix time in seconds |
| 46 | 64 B | Publisher signature | Plain Ed25519 signature |
| 110 | `payload_len` B | Payload | Schema-defined bytes |
| `110 + payload_len` | Remaining bytes | Padding | All zero bytes |

Sequence numbers advance by one per Message (`MPE-PUB-019`), and recognition does not depend on a sequence lookahead. The Logical Message Identifier MUST stay identical across retransmissions and carriers of one Message (`MPE-FMT-022`).

Neither the stream identifier nor the Publisher identity needs a cleartext field: the first comes from subscription state, and the encrypted key index selects the second. Application labels, timestamps, the signature and the payload MUST stay protected. Private reception MUST keep recognition and decryption secrets inside the Subscriber's trusted endpoint boundary (`MPE-CRY-002`, `MPE-PRV-003`, `MPE-PRV-007`).

Padding MUST lie inside the authenticated encryption and MUST contain only zero bytes. The client MUST check the payload boundary before it reads the payload or the padding (`MPE-FMT-016`, `MPE-FMT-017`, `MPE-CRY-022`). The lengths therefore add up to the class body:

```text
padding length = B − 170 − payload_len
body length   = 44 + 40 + 70 + payload_len + padding length + 16
              = B
```

The payload encoding belongs to its registered schema, and canonical CBOR is the default schema encoding. Decoder selection MUST use the application's fixed registration table. An unknown schema MUST produce an authenticated, opaque Message marked undecodable (`MPE-FMT-026`, `MPE-FMT-027`).

**Carried events.** A carried event delivers a contract event's bytes through a stream, before finality and without an Indexer query that would show the Subscribers' interest. Schema identifier `6d70653a63657674` (ASCII `mpe:cevt`) with `schema_version = 1` is reserved for carried events, and applications MUST NOT register it for any other schema. A carried event's payload MUST use the following layout.

| Payload offset | Length | Field | Meaning |
|---:|---:|---|---|
| 0 | 32 B | Transaction hash | Hash of the final transaction that contains the event |
| 32 | 4 B | Position | Zero-based index of the event among the events the ledger applies for that transaction, in application order |
| 36 | 2 B | `log_len` | Length of the event bytes |
| 38 | `log_len` B | Event bytes | The event exactly as the ledger records it: the `VersionedLogItem`, or its successor for private events |

The Publisher MUST copy the event bytes unchanged, MUST NOT re-type, reorder, truncate or re-encode them, and MUST NOT carry several events in one Message. A Consumer MUST decode the event bytes only with the Foundation's decoder for the event's `LogEventType` and `version`, never with an application schema decoder [@midnight-mip-0002]. Every field of a carried event, including any value that MPS-0005 would mark `@topic`, travels only inside the Sealed Body (`MPE-FMT-003`).

The client delivers every Message with a finality label, `gossip` or `final` (`MPE-CON-015`; Consumer interface), and `gossip` means not yet verified against finalized chain data. A carried event stays `gossip` until its transaction is finalized and its bytes match the transcript when checked against authenticated on-chain data [@midnight-mip-0018]. An event from a fallible phase counts only if that phase succeeded [@midnight-mip-0019]. "Consumer interface" specifies these checks.

The event's authority remains "the contract author's claim" [@midnight-mip-0002]. The Publisher's signature adds only who forwarded it. On chain the event pays `Log` gas, plus any future encryption fee; carriage adds no protocol fee.

A single event is at most 1 KB serialized [@midnight-mip-0002]. With the 38 B carried-event header, event bytes up to 816 B fit class 1 (`854 − 38 = 816 B`) and larger ones need class 2. A `Misc` event has 288 B of struct data, about 328 B serialized with MIP-0002's overhead of about 40 B, so it fits class 1. Class 0 leaves `86 − 38 = 48 B` for event bytes, and no carried event fits class 0.

MPS-0005 Part 2 is unpublished, so two things about private events are unknown: whether the client holds a private event's bytes before submission, and whether the transcript keeps its ciphertext or only a commitment to it. This layout carries whatever bytes the ledger records.

**Keys, Recognition Tags and recognition.** Let `S` be the 32 B stream secret, `P` the ASCII profile identifier `mpe-v1-sym` and `s` the 16 B MPE Envelope salt. The client MUST obtain `S`, fresh salts and fresh nonces from cryptographic randomness. If randomness is unavailable, it MUST refuse the affected operation (`MPE-CRY-008`, `MPE-CRY-009`, `MPE-CRY-010`, `MPE-CRY-013`). Stream secrets MUST NOT be derived from a wallet seed. Invitation identity keys and the admission secret MAY be derived with the wallet's `deriveSecret` method under the domains `mpe:invitation:v1` and `mpe:admission:v1`, with the membership period as context, so that memberships survive device loss [@midnight-mip-0015]. That method is Proposed and optional per wallet, so clients MUST check that it is available. Neither value is ever derived from spending or encryption keys (`MPE-CRY-027`).

`N` enters both keys, the Recognition Tag and the Message secret, so under the pseudorandom-function assumption one `S` on two Midnight networks yields unrelated values. The salt in `K_enc` gives each MPE Envelope its own key. The profile MUST use the derivations below. Each HKDF operation performs extraction and expansion to 32 B (`MPE-CRY-006`, `MPE-CRY-007`, `MPE-CRY-013`; `MPE-PUB-002`).

| Value | Derivation |
|---|---|
| Recognition key `K_rec` | `HKDF-SHA-256(salt=N, IKM=S, info="mpe/v1/rec" || P)` |
| Encryption key `K_enc` | `HKDF-SHA-256(salt=s, IKM=S, info="mpe/v1/enc" || N || P)` |
| Recognition Tag | First 16 B of `HMAC-SHA-256(K_rec, "mpe/v1/tag" || N || s)` |
| Stream identifier `I` | `SHA-256("mpe/v1/stream" || S)` |
| Shard | `u64be(SHA-256("mpe/v1/shard" || S)[0:8]) mod` the Bus Registry Shard count |
| Message secret | `HKDF-SHA-256(salt=N, IKM=S, info="mpe/v1/event" || Logical Message Identifier)` |

The Message secret feeds the consumption nullifier specified in "Consumer interface" (`MPE-CRY-025`). Of the visible values derived from `S`, only the Shard stays fixed across a stream's Envelopes; the salt changes the Recognition Tag in each one (`MPE-FMT-004`). With one Shard at launch, the Shard separates no streams.

Before installation, an authenticated invitation MUST bind the network, the profile and its suite identifier, the stream setup material and the authorised Publisher keys (`MPE-CRY-018`). First contact uses authenticated invitations only (DEC-020). A profile that encrypts to a recipient's Midnight shielded encryption public key, resolved through the name service's `epk` field [@midnight-mip-0007], is deferred so that it can follow `encrypt_for` once MPS-0005 Part 2 specifies it [@midnight-mps-0005]. Until then this specification standardises no public-key profile.

Giving a stream secret to a third party, such as an auditor, grants a coarse viewing capability over every Message of that stream that remains in retention or an archive. The grant cannot be revoked. It resembles the viewing delegation of MIP-0012 [@midnight-mip-0012].

For each received MPE Envelope, the Subscriber MUST test the salted Recognition Tag locally under its installed recognition keys and treat every match only as a candidate for complete authentication. Installing more than 256 distinct recognition keys MUST fail locally (`MPE-CRY-014` to `MPE-CRY-016`). At that cap (P-CRY-4) recognition costs 256 HMAC-SHA-256 evaluations per Envelope, and the proof of concept will measure that cost on its target client hardware. Recognition Tag comparison uses constant-time equality, and every matching candidate goes through opening and signature verification. The client MUST refuse delivery if distinct streams authenticate the same Envelope (`MPE-CRY-017`). Non-committing AEAD constructions, ChaCha20-Poly1305 among them, can let one ciphertext authenticate under several keys [@2021-len-partitioningoracle], so authentication outcomes stay inside the client and the ambiguous case ends in refusal.

Recognition MUST NOT trigger an automatic acknowledgement, a selective retrieval request or a remotely exported recognition result (`MPE-PRV-008` to `MPE-PRV-010`, `MPE-PRV-014`). Interest privacy is therefore conditional. It holds only within a fixed set of received Shards, and only while recognition changes no subscription, request, acknowledgement, retry, error, repair, receipt or diagnostic. GossipSub itself does not provide it. Under the selected assumptions the Recognition Tag avoids a stable cleartext label, but it does not stop grouping by Shard, ingress, admission metadata, timing or outside observation.

The Recognition Tag does the work of MPS-0005's planned topic-based filtering by other means: it is fresh for each MPE Envelope, and only the Subscriber evaluates it. Filtering at the Indexer per wallet, as MPS-0005 plans, and MIP-0002's prefix filters correspond to reduced-privacy selective profiles that an application must opt into explicitly (`MPE-PUB-016`, `MPE-PRV-013`). They are not the default [@midnight-mps-0005; @midnight-mip-0002].

Version 1 has no fuzzy message detection. Because first contact uses authenticated invitations only (DEC-020), the client generates no clue and registers no detection key, which satisfies `MPE-CRY-037` by construction. Fuzzy detection would supply first-contact candidates with false positives, and its detection ambiguity does not give interest privacy against an observer who uses traffic counts or other context [@2022-penumbra-fmd]. A clue construction would need its own profile, version and measurements (`MPE-FMT-053`, `MPE-CRY-039`), and its delegation would export only that construction's first-contact detection capability (`MPE-CRY-038`).

**Sealing and signatures.** Public-context authentication (`MPE-CRY-004`) requires that the Network Identifier, Visible Header bytes 0 to 7 and the body's salt, nonce and Recognition Tag be AEAD associated data, so that changing any byte sent in clear stops the Envelope from opening. A ledger-lane reader, however, receives only the Sealed Body and must reconstruct every associated byte itself. It reconstructs header bytes 0 to 3 from four sources: the version in the `Misc` name, the body class implied by the part count (1, 4 or 16 parts for classes 0, 1 or 2), the Shard derived from `S`, and the zero reserved byte. The visible expiry in bytes 4 to 7 it cannot reconstruct before it opens the body.

Define `H4 = wire[0:4]` and `C = salt || nonce || Recognition Tag`. The carrier-compatible profile binds the public context that both carriers can reconstruct. It MUST use ChaCha20-Poly1305 with `K_enc`, the transmitted 12 B nonce and the following 90 B associated-data string (`MPE-CRY-001`, `MPE-CRY-004`, `MPE-FMT-037`, `MPE-FMT-051`):

```text
AAD = "mpe/v1/aad" || N || H4 || C
```

The profile thus departs from `MPE-CRY-004`: of the eight header bytes it places only bytes 0 to 3 in the associated data, so that a ledger-lane body still opens from its own bytes, and changing any of them stops the Envelope from opening. Bytes 4 to 7 are protected instead by fixing their value. Version 1 therefore MUST set `expiry = creation + 172,800 s` and MUST reject arithmetic overflow, and the signed statement below covers both creation and expiry. A changed expiry then fails at two points. At a Bus Node it changes the EID, to which admission is bound, so admission fails. At a Subscriber, the client MUST check the visible expiry of an overlay copy against the value reconstructed from the sealed creation time and discard the copy if they differ (`MPE-FMT-028`, `MPE-FMT-037`, `MPE-CRY-021`, `MPE-CRY-022`).

Variable lifetimes need a new body format that contains a sealed expiry. And because expiry is fixed at creation plus 172,800 s, the visible expiry tells every Bus Node the creation second.

The signed statement names a destination contract and an action, so that a signature given for one effect cannot authorise a reaction elsewhere (`MPE-CON-043`; Consumer interface). Let `D` and `A` be the configured 32 B destination-contract and action values, each zero when absent. The Publisher MUST sign this exact 244 B statement with plain Ed25519 and no additional prehash (`MPE-CRY-020`, `MPE-CRY-021`):

```text
"mpe/v1/sig" || N ||
SHA-256(N || H4 || C) ||
I || Logical Message Identifier ||
u64be(seq) || schema_identifier || u16be(schema_version) ||
u32be(creation) || u32be(expiry) ||
SHA-256(payload) || D || A
```

The authorised-key index selects the verifying key from authenticated invitation state, so holding the stream secret alone gives no authority to sign as a Publisher. GossipSub's StrictNoSign mode ("Overlay protocol") removes the pubsub author stamp. It authenticates no Publisher and gives no application replay protection. Publisher authentication exists only inside the Sealed Body.

A consuming contract that grants authority from a Message MUST verify this signature, or the equivalent under its profile, in circuit (`MPE-CON-043`; Consumer interface). Anchor inclusion alone proves only that some anchored EID exists. It binds no consumption nullifier to the Message, so a Consumer holding one inclusion proof could react more than once. The binding can come from the Publisher's signature or from recomputing the EID from the Sealed Body inside the circuit.

Whether a consuming circuit can afford the signature route depends on two costs: hashing the statement's fields, which has been estimated, and verifying the signature, which has not. The estimate comes from exploratory Bus Registry, ledger-lane and consumer contracts compiled with Compact 0.35.0 (language 0.27.0) against a ledger-9 release candidate; circuit sizes come from the compiler and fees from the ledger cost model, none of the contracts was run on any network, and the design does not depend on them being final. `persistentHash` over byte fields equals plain SHA-256 of their concatenation (checked in the Compact simulator), so a circuit can reproduce the statement's digests. What they cost depends on how the preimage is written: three chained SHA-256 Merkle node hashes need 133,922 rows with a preimage assembled byte by byte and 12,674 rows with a struct of fixed-width fields, for identical digests. Every field of the signed statement has a fixed width. The recomputation route is unpriced, because the compiled consumer takes the EID as a private witness and recomputing it means hashing the whole Sealed Body, up to 16,384 B, at a cost that has not been measured. `ed25519Verify` exists in the Compact standard library but needs the ZKIR v3 backend.

MIP-0013 rejects Ed25519 for in-circuit authorisation because the emulated field arithmetic costs "hundreds of constraints per field operation" [@midnight-mip-0013]. The signature circuit has been neither written nor compiled, so its size is unknown. The candidate alternative is a JubJub Schnorr publisher-signature profile using `jubjubSchnorrVerify`, which would be a new cryptographic profile and therefore a new version. The choice between the two will follow measurement of rows, proving time and prover-key size for each.

A contract's block-time comparison reveals its operand, here the creation second. A consuming circuit therefore reveals only a coarse bound that the prover chooses, such as the expiry rounded down to the hour, and checks the real expiry privately (`MPE-CON-046`, `MPE-CON-061`; Consumer interface).

Each AEAD key-nonce pair MUST be used for at most one encryption. A retransmission MUST reuse the original serialised bytes instead of encrypting again. Restored state that cannot establish safe nonce use MUST refuse publication under the affected key generation (`MPE-CRY-010` to `MPE-CRY-012`).

**Identifiers and construction order.** Deduplication, admission binding and Anchors ask whether two copies carry the same sealed content; GossipSub's duplicate cache asks whether they are the same bytes. Both identifiers are 32 B SHA-256 outputs. The client and the Bus Node MUST compute them from the received bytes as follows (`MPE-FMT-018`, `MPE-FMT-019`; `MPE-NET-010`):

```text
EID = SHA-256("midnight-pe/id/v1" || N || wire[0:8] || wire[520:])
GossipSub message identifier = SHA-256("mpe/v1/msgid" || wire)
```

In version 1, `wire[520:]` is the Sealed Body; a version with slot width `W` hashes `wire[8 + W:]`. In the second formula, `wire` is the complete, immutable MPE Envelope carried in the pubsub message's `data` field, Admission Slot included. The input excludes the GossipSub protobuf framing, the GossipSub topic, RPC batching and the Noise and Yamux framing. Every client and Bus Node MUST hash identical bytes and encode the output identically, and the transport MUST NOT apply a data transform that changes this input.

The EID binds expiry and the protected content but excludes admission. It is used for admission binding, inventories, application deduplication and Anchors. Changing only the Admission Slot therefore keeps the EID but changes the GossipSub identifier.

GossipSub's duplicate cache records identifiers before application validation.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, Behaviour::handle_received_message, accessed 2 October 2026.] Because the slot is hashed, a copy with a corrupted admission slot cannot suppress the honest copy through that cache, subject to the collision resistance of SHA-256 (`MPE-SEC-042`). Delivery against other attacks is not guaranteed: other identifier collisions, handling across GossipSub topics, software defects or a configured transform can still poison state recorded before validation. Reject and Ignore do not remove a seen-cache entry, so an identical copy ignored during overload stays suppressed at that Bus Node while its identifier remains cached. The rust-libp2p default caches it for 60 s, and the go-libp2p-pubsub default is 120 s.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, Config::default, field duplicate_cache_time; libp2p/go-libp2p-pubsub, pubsub.go, variable TimeCacheDuration; accessed 2 October 2026.]

Application deduplication is separate from that cache. The Bus Node keeps each accepted EID until the Envelope's expiry plus 60 s (P-FMT-4) and treats a copy that carries another valid admission for the same EID as a duplicate (`MPE-PUB-027`, `MPE-SEC-014`).

The client MUST build the immutable header and the recognition prefix, sign the plaintext, encrypt it, compute the EID, attach admission and then compute the GossipSub identifier. Admission MUST NOT enter the AEAD associated data or the signed statement (`MPE-FMT-020`, `MPE-CRY-005`).

**Worked byte examples.** These sealing-stage fixtures use `N = 4d` repeated 32 times, `S = 03` repeated 32 times, signing seed `04` repeated 32 times, authorised-key index 0, Shard 0, sequence 1, Logical Message Identifier `06` repeated 16 times, schema bytes `736368656d613031` (`schema01`), schema version 1 and zero destination and action values. Creation is 100 s, so expiry is `100 + 172,800 = 172,900 s`, encoded `0002a364`. The Admission Slots stay zero until admission is attached, and the fixtures alone therefore do not authorise relay acceptance. Attaching admission changes each MsgID below but not the EID.

The `Misc` names follow the MIP-0018 convention: lowercase, colon-separated, namespaced by the proposal number, with the layout version in brackets [@midnight-mip-0018]. The editors' assigned number replaces `xxxx` before the names are frozen. A later version MAY move every cryptographic label to one colon-separated form such as `mpe:<purpose>[v2]`. Labels enter derivations, so such a move is a new cryptographic profile and needs a new MPE Envelope version (`MPE-FMT-053`).

**Versioning, expiry and rejection.** A new field, a changed offset, a different slot width or a different cryptographic profile MUST use a new MPE Envelope version, and reserved bytes MUST NOT act as extensions. Version 1 accepts only `pt_version = 1`, `kind = 1` and `flags = 0001`. Control kind 2 remains reserved, and there is no receipt kind (`MPE-FMT-001`, `MPE-FMT-006`, `MPE-FMT-025`, `MPE-FMT-034`, `MPE-FMT-036`, `MPE-FMT-053`). Production Bus Nodes that support two active versions MUST relay the GossipSub topics of both for at least 34 days, which is `2 × 172,800 s + 30 days` (`MPE-FMT-024`).

On the ledger lane the `Misc` name carries the layout version: version-1 bodies use `mip-xxxx:envelope[v1]` and Anchors use `mip-xxxx:anchor[v1]`. A new MPE Envelope version or a new Anchor layout takes a new name [@midnight-mip-0018].

Bus Nodes MUST finish the structural and expiry checks before any admission cryptography, and MUST decide relay outcomes without decrypting the body (`MPE-FMT-009`, `MPE-FMT-011`). Reject suppresses delivery and forwarding, and it applies the P4 invalid-message penalty to the forwarding peer, which need not be the Publisher. Ignore suppresses delivery and forwarding without P4 ("Overlay protocol"). Reject is for bytes that no peer following this specification would forward; Ignore is for bytes an honest peer could still forward, such as an Envelope that expired in transit.

A Bus Node checks expiry against its local clock. Its Ledger Adapter marks the view stale when that clock and the latest finalized block timestamp differ by more than 60 s (P-NET-13; `MPE-NET-019`). With a stale view the Bus Node cannot tell a far-future expiry from an error in its own clock, so checks that depend on the clock or on chain state return Ignore, never Reject (`MPE-NET-018`, DEC-009). The following outcomes are mandatory.

| Condition | Outcome | Requirement |
|---|---|---|
| Fewer than 8 B; truncated or extra bytes; class-length mismatch | Reject | `MPE-FMT-007` |
| `version` differs from the version of the supported GossipSub topic it arrived on, including an unknown value | Reject | `MPE-FMT-023` |
| Arrival in a protocol context the Bus Node does not support | Ignore; Bus Nodes MUST NOT subscribe to GossipSub topics of unsupported versions | `MPE-FMT-023` |
| Class outside the version's table | Reject | `MPE-FMT-008` |
| Non-zero reserved byte | Reject | `MPE-FMT-006` |
| Shard differs from the GossipSub topic it arrived on or lies outside the configured range | Reject | `MPE-FMT-052`; `MPE-PUB-002` |
| Non-zero unused Admission Slot byte | Reject | `MPE-FMT-050` |
| Invalid admission encoding, proof or network binding | Reject | `MPE-FMT-021`; `MPE-ECO-012` |
| Expiry later than `now + 172,800 s + 60 s` | Reject; Ignore when the ledger view is stale | `MPE-FMT-029`, `MPE-FMT-031` |
| Expiry earlier than `now − 60 s` | Ignore | `MPE-FMT-030` |
| EID already accepted | Ignore | `MPE-PUB-027`, `MPE-SEC-014`; `MPE-NET-017` |
| Structure passes | Continue to admission validation | `MPE-FMT-009`, `MPE-FMT-011` |

Version checks MUST NOT penalise valid traffic from a future profile that the Bus Node does not support. GossipSub topic names are routing labels, and their eight-byte genesis prefix does not guarantee that networks stay separate. Network separation comes from the full Network Identifier in the EID, the associated data, the signed statement and the admission binding (`MPE-FMT-021`).

Passing a Bus Node's tolerance check does not extend application validity. Bus Nodes MUST stop sending expired MPE Envelopes, including in IWANT responses and queued sends (`MPE-FMT-032`). GossipSub does not interpret the expiry field, and the stock rust-libp2p and Go IWANT handlers serve validated cached messages without an MPE expiry check.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, Behaviour::handle_iwant; libp2p/go-libp2p-pubsub, gossipsub.go, GossipSubRouter.handleIWant; accessed 2 October 2026.] Meeting this requirement therefore needs cache and send handling that is aware of expiry, with a recorded conformance test. The proof of concept must implement that handling and pass that test.

Expiry MUST be described as a retention rule for honest services, with no claim of deletion from adversarial archives (`MPE-PRV-028`). An adversary can keep recorded ciphertext and metadata indefinitely, and under a profile without forward secrecy, a later compromise of the stream secret exposes the archived content.

Subscribers MUST apply the following local outcomes and MUST commit cryptographic state only after complete authentication (`MPE-CRY-022`, `MPE-CRY-023`).

| Condition | Local outcome | Requirement |
|---|---|---|
| No matching Recognition Tag | Discard, with no traffic that depends on recognition | `MPE-CRY-014`, `MPE-PRV-009` |
| AEAD opening fails, or stream or Shard context is wrong | Discard | `MPE-CRY-022` |
| Unknown plaintext version or kind | Unsupported-format error | `MPE-FMT-025` |
| Unsupported flags, missing authentication block or non-canonical inner layout | Discard as malformed | `MPE-FMT-034`, `MPE-CRY-022`, `MPE-CRY-041` |
| Payload boundary outside the plaintext, or non-zero padding | Discard as malformed | `MPE-FMT-017`, `MPE-CRY-022` |
| Invalid key index, unauthorised Publisher or invalid signature | Discard | `MPE-CRY-018`, `MPE-CRY-022` |
| Creation plus lifetime overflows, or visible and signed expiry differ | Discard | `MPE-FMT-028`, `MPE-CRY-021`, `MPE-CRY-022` |
| Current time later than the authenticated expiry | Discard as expired | `MPE-CRY-022` |
| Complete authentication under distinct streams | Refuse ambiguous delivery | `MPE-CRY-017` |
| Authenticated logical replay | Suppress repeat delivery | `MPE-CRY-024` |
| Unknown schema after authentication | Deliver raw payload marked undecodable | `MPE-FMT-026` |
| Reserved carried-event schema | Decode with the Foundation's decoder only; label `gossip` until verified against the chain | Carried-event rule above |

A holder of the stream secret without an authorised Publisher key can seal an Envelope that opens but fails signature verification. Suppose its Logical Message Identifier were recorded before the signature check: a forgery that copied a genuine Message's identifier would then make the genuine Message look like a replay.

A malformed ledger group is discarded locally under the reassembly rules in "Ledger interface" (`MPE-FMT-046`). Local opening failures never become GossipSub Reject outcomes, and a Bus Node relays validly admitted ciphertext whose body never opens. A random Recognition Tag or an invalid sealed signature leads to a discard by the Subscriber, not to a relay outcome (`MPE-FMT-011`).

The launch profile MUST declare the following properties unclaimed: content forward secrecy, metadata forward secrecy, post-compromise security and post-quantum confidentiality. It MUST also declare timing privacy, relationship privacy and general Message unlinkability unclaimed (`MPE-PRV-024`, `MPE-PRV-026`, `MPE-PRV-027`).

Two measurements remain before a production version can be fixed. The size of a zero-knowledge admission proof sets `W` and decides whether class 0 and the 4,096 B cap survive. The in-circuit cost of a Publisher signature decides between plain Ed25519 and a JubJub Schnorr profile.
