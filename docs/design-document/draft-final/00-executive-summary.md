# Executive summary

Midnight keeps contract state private and proves facts about it in zero knowledge, but when a contract tells anyone that something happened, it does so in public. In the ledger-9 generation that the Midnight node's code pins, a Compact circuit can `emit` a contract event whose fields must all be disclosed. The one custom event, `Misc`, carries a 32-byte name and a 256-byte payload. Readers see it only after finality, about 18 s, through an Indexer that learns which contract each client watches [@midnight-mip-0002]. In the Foundation's terms, a private event is a contract event some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment the proof checks. It is planned for Phase 2 of MPS-0005, in a Part 2 that is unpublished [@midnight-mps-0005]. Unless Part 2 adds a mechanism that hides them, a chain observer will still see a private event's contract, entry point, time and size. Midnight Express is the proposed system for Confidential Message and private event delivery on Midnight, and it redefines neither term. It complements private events and, under stated conditions, transports them. It does not replace MPS-0005 Part 2.

A Message is an application message that a Publisher seals and delivers. A Confidential Message is a Message sealed into a fixed-size MPE Envelope and delivered through Midnight Express so that four properties hold as Chapter 4 states them: content confidentiality, sealed labels, conditional interest privacy and no silent change. The size classes show where the definition stops. A 100-byte Message and an 800-byte Message both travel as 1,544-byte MPE Envelopes, but a 900-byte Message travels as a 4,616-byte class-2 MPE Envelope, and every relay sees the change. A carried event is a Confidential Message whose payload is the unchanged bytes of a contract event, public or private, with its transaction hash and position. The carried bytes count for nothing until a Consumer has checked them, byte for byte, against what the chain records. What Midnight Express adds to a carried event is early delivery and interest-hiding.

Five architectures were compared against criteria fixed before the requirements were written: the ledger and Indexer alone (Option 1), a GossipSub sidecar overlay with ledger anchoring (Option 2), a protocol inside the Midnight node (Option 3), mix or private-retrieval delivery (Option 4) and an external publish/subscribe service (Option 5). The recommendation is Option 2. Bus Nodes run beside the Midnight node and relay MPE Envelopes of four fixed sizes with GossipSub v1.2 behaviour, on one Shard at launch. Store Nodes keep the MPE Envelopes for 48 hours. Subscribers receive the whole Shard and recognise their own Messages by a salted 16-byte Recognition Tag. A Bus Registry contract holds memberships, quota roots, the relay list and one Anchor per 60-second window, and Message bodies never enter contract state. Option 1 remains only as the ledger lane, a last resort that the application must select. Option 3 would couple Message traffic to consensus, Option 5 would hand admission to another chain, and Option 4 needs a mix or server set that nothing funds.

The ledger interface contracts were written in Compact and compiled with toolchain 0.35.0 (language 0.27.0) against a ledger-9 release candidate. They are exploratory code, and the design does not depend on them being final. None of them ran on a network, and every fee below is derived from the cost model at genesis prices. All three compile, and `emit` is the Bus Registry's only ledger-9 dependency. Proofs are at most 4,368 B and verifying keys at most 2,119 B. One `Misc` part built from a 256-byte argument needs 166,241 rows (k = 18), and sixteen parts need about k = 22. An Anchor post costs 0.195 DUST, so one Anchor every 60 s costs about 1,440 × 0.195 = 280 DUST per day. MIP-0002 counts events against the `bytes_written` limit of 50,000 B per block, and a ledger-lane part takes about 328 B. A 6 s block therefore holds about 38 four-part class-1 Messages (50,000 / 1,312), or about 6.3 per second for the whole chain, against the limit of 10 per second for one Shard. A Midnight transaction has no signer, and a contract cannot read block time. Authority is therefore a hash preimage proved in circuit, and Bus Nodes enforce the 3,600 s root window.

Throwaway exploratory runs guided the design, but nothing here rests on them. The next step is the proof of concept, a single reference implementation with a deterministic simulator, which Part III specifies and which has not been built. No admission proof system has been selected. The admission check specified for the proof of concept is a stand-in whose secrets every Bus Node can read, so it gives no admission unlinkability. The live `block_usage` limit (200,000 B or 1,000,000 B), proving times and behaviour on wide-area networks are unknown. Interoperation with the Go implementation is not established, because Go requires `Dout < D/2` and so rejects D_out = 4 at D = 8.^[libp2p/go-libp2p-pubsub, gossipsub.go, parameter validation of `Dout`; master branch, accessed 1 October 2026.] The cost of an in-circuit signature is unknown, and without one a contract reaction has no authority. Mainnet ran ledger 8.0 on 4 August 2026 and had not reached ledger 9 by 28 September. Carrying a private event depends on MPS-0005 Part 2. The privacy claim stays limited: there is no claim against a global observer, and no timing or relationship privacy at launch.

The Foundation is asked to take two documents into its process, and its editors assign both numbers. The first is the problem statement MPS-xxxx, "Confidential Message and Private Event Delivery for Contracts, Agents and Wallets", which closes Chapter 4. MPS-0043 assigns the question of how confidential data travels to a pending statement, Confidential Contract Notifications (PR #271) [@midnight-mps-0043]. The editors must decide whether MPS-xxxx is that statement, a replacement for it or a companion to it. The second is the proposal MIP-xxxx, "Midnight Express: Confidential Message and Private Event Delivery over a GossipSub Overlay with Ledger Anchoring". It requires MIP-0002. It also follows MIP-0019, which is Proposed and counts as a prerequisite only if the editors accept a Proposed prerequisite. Three conditions decide whether Option 2 can launch, and each can be tested before launch. Delivery must reach at least 99 percent with p99 at most 6 s at 200 Bus Nodes on real networks. An Admission Proof must fit within 4,096 B and verify in 10 ms. And 8 organisations must commit in writing to fund Bus Operator roles for 12 months, since DUST cannot pay Bus Operators (`DEC-001`). If those commitments cannot be found, Option 2 cannot launch, and the ledger lane becomes the only carrier.
