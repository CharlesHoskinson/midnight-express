# Introduction {#ch1}

Midnight is a blockchain built for data protection. Its ledger keeps shielded state, and its contracts, written in Compact, prove facts about private inputs in zero knowledge. The Indexer is the service that reads chain data and serves it to wallets and DApps [@midnight-mps-0028]. However, the way a contract tells the outside world that something happened is still public. Midnight's ledger rules come in numbered generations, and contract events exist only from ledger 9. In the ledger-9 generation a Compact circuit can `emit` a contract event, which the transaction records and the Indexer serves [@midnight-mip-0002; @midnight-coip-0003]. The Foundation's documents cited here are Midnight Improvement Proposals (MIP), Midnight Problem Statements (MPS) and Compact Improvement Proposals (CoIP). Only one standard event carries custom data: `Misc`, with a 32-byte name and a 256-byte payload. `emit` is a disclosure site, where a value may leave the private computation only if the contract has marked it with `disclose`. Every field of an event is therefore already disclosed, and any client can subscribe to a contract's events through the Indexer. The virtual machine drops an event above 1 KiB without reporting an error.

The Foundation plans to go further. MPS-0005 announces private events for its Phase 2: contract events whose fields are encrypted for chosen recipients, bound to the transaction by a commitment (a value that fixes data without revealing it) that the proof checks, and filterable by topic [@midnight-mps-0005]. Part 2, which is to specify them, is unpublished. A private event will still travel inside a transaction. Unless MPS-0005 Part 2 adds a mechanism that hides it, a chain observer will see that a contract emitted something, from which entry point, when and at what size [@midnight-mip-0019; @midnight-mps-0043]. Its readers on the Indexer will also wait for finality, about 18 s after inclusion, and it will share the chain's per-block budgets with all other traffic. Agents acting for their owners generate a large volume of messages (Chapter 3). Nothing in the current stack lets one party tell another something within seconds at that volume without a transaction that everyone can see.

Midnight Express is the proposed system for Confidential Message and private event delivery on Midnight. Its main use is to carry Confidential Messages between parties off the chain. Under the conditions stated below, it can also deliver contract events, public or private, to their recipients early and without revealing to infrastructure who wanted them. It complements the Foundation's private events and can transport them. It is not an alternative to them, and it does not replace MPS-0005 Part 2.

## Purpose

The document sets out what Midnight Express must deliver and how, recommends one design, and plans the proof of concept that will test it. It is written for people who develop on, operate, check or decide about Midnight, and it makes four commitments. First, it adopts the Foundation's definitions of event and private event unchanged, defines Confidential Messages and carried events against them, and names the adversaries they are measured against (Chapter 4). Second, it recommends a GossipSub sidecar overlay anchored on the ledger. Option 1, the ledger and Indexer alone, stays only as the ledger lane, a last resort that a Publisher must select and that cannot carry the overlay's rate; if the overlay fails its tests or its Bus Operators go unfunded, the ledger and Indexer path is all that remains (Chapters 6 and 11). Third, it sets out a requirement set, a decision register and reconciled parameter values for prototype and production (Chapter 7 and Appendix A). Fourth, it specifies the system under test and the experimental design for the proof of concept (Chapters 8 to 11). The proof of concept is a single reference implementation with a deterministic simulator. Throwaway exploratory runs guided the design but nothing in it rests on them, and the proof of concept, which has not been built, is the next step.

Chapter 4 closes with a Midnight Problem Statement, "Confidential Message and Private Event Delivery for Contracts, Agents and Wallets" (MPS-xxxx). The document ends with a Midnight Improvement Proposal, "Midnight Express: Confidential Message and Private Event Delivery over a GossipSub Overlay with Ledger Anchoring" (MIP-xxxx). The Foundation's editors assign both numbers.

## Scope

The subject is a message overlay that runs beside Midnight. A Publisher seals each Message into a fixed-size MPE Envelope (MPE for Midnight Private Events). There are four size classes, numbered 0 to 3, with sealed bodies of 256 B, 1,024 B, 4,096 B and 16,384 B. Bus Nodes are sidecar relays, separate from the Midnight node, that carry MPE Envelopes over GossipSub, the libp2p publish/subscribe protocol [@2020-vyzovitis-gossipsub]. In GossipSub each relay forwards messages to a small set of peers per topic, its mesh. A Shard is one GossipSub topic partition of the overlay, and one Shard operates at launch. The transport profile requires GossipSub v1.2 behaviour: the v1.1 peer-scoring and mesh rules [@2020-gossipsub-v11-spec] plus IDONTWANT, the v1.2 control message by which a relay asks its mesh peers not to send it a duplicate. The v1.2 specification is still a Working Draft.^[libp2p/specs, pubsub/gossipsub/gossipsub-v1.2.md, lifecycle table (Working Draft, revision r2, 2026-08-30); master branch, accessed 1 October 2026.]

A Subscriber receives every MPE Envelope of each Shard it follows and recognises its own Messages locally by their Recognition Tags. Each MPE Envelope carries a fresh salt and a 16-byte Recognition Tag. A stream is an application channel named only inside the sealed body, and an MPE Envelope belongs to a stream when a keyed hash of the salt under that stream's key equals the Recognition Tag. Because the salt is new each time, a relay without the key sees unrelated Recognition Tags on two MPE Envelopes of one stream.

A root is one hash over a tree of entries, and a short path proves that an entry is in the tree. The ledger carries what must be agreed in a Compact contract, the Bus Registry, which holds two kinds of root. The first is for admission. A membership is a Publisher's registration, which allows it a limited number of MPE Envelopes per size class in each 60-second admission window. Each membership is an entry committing its member's identity and per-class limits. The root over these entries, the membership root, is also the overlay's quota root. An MPE Envelope names a membership root and carries an Admission Proof that its Publisher holds an entry under it and stays within that entry's limit. A Bus Node checks the proof if the Bus Registry holds that root or replaced it recently.

The second kind of root is the batch Anchor. Once per 60-second window an authorized anchorer commits on the chain one root over the identifiers of the MPE Envelopes it accepted in that window, so that anyone holding an MPE Envelope and its path can later check that it was anchored. The window and the root's contents are the anchorer's assertions; the chain establishes only that the commitment existed at the finalized block that includes it. When the overlay is not used, a second delivery path, the ledger lane, carries sealed bodies on the chain as `Misc` events. Message bodies are never stored in contract state.

GossipSub moves opaque bytes. On its own it provides no publisher anonymity, private subscriptions, durable delivery, application replay protection or network-wide admission quota. Retention, receipts, Anchors, replay protection, whole-Shard feeds and repair are Midnight Express application mechanisms. Chapter 8 specifies them, and Chapter 9 sets out how the proof of concept will test them. Store Nodes provide retention and sign receipts for the MPE Envelopes they hold. Repair refetches a 60-second window whose copy differs from a second source's.

A Message is not a contract event. No contract executes it, its Publisher's signature authenticates it, and only an Anchor over MPE Envelope identifiers commits it to the chain. Nothing in Midnight Express can therefore stand for "this contract emitted this field", and a Message has none of a contract event's authority. Midnight Express transports a contract's event only as a carried event: the unchanged event bytes, with the transaction hash, the event's position in it and the emitting contract's address and entry point. A Consumer, the party that acts on a Message, can then check the event against the chain. The event's authority stays with its transaction. Midnight Express adds early delivery, before finality (about 18 s after inclusion), and interest-hiding.

Two facts about Midnight transactions bear on this. A client constructs its transaction locally, including the transcript, which is the record of public effects that the proof checks, events among them. And a transaction has a guaranteed segment, which pays the fees and cannot fail, and fallible segments, which can fail one at a time and discard their effects, events included. MIP-0019 calls these segments phases. An intent is a sealed group of contract calls that share them. Early delivery works only under seven conditions:

- When the client constructs the transaction, it holds the event bytes exactly as the ledger will record them.
- The chain keeps the binding between the delivered bytes and the transaction, either through the ciphertext itself or through a commitment to it.
- The event fits a size class: class 1 carries 854 B of payload (1,024 B of sealed body less 170 B of fixed sealing and signature fields), and with the 73 + `e` byte carried-event header (`e` the entry-point name length) a logged item of up to 781 − `e` B fits it; larger ones need class 2.
- The recipient can recognise it.
- Consumers treat it as unconfirmed until the transaction is finalized and the bytes match the transcript, and they count an event from a fallible phase only if that phase succeeded [@midnight-mip-0018; @midnight-mip-0019].
- Midnight Express never re-types, re-orders or truncates it.
- The event pays its ledger fee once, on chain, and carriage adds no protocol fee.

Whether Phase 2 private events can meet the first two conditions depends on the unpublished MPS-0005 Part 2. The first condition turns on where the ciphertext is formed. A client that forms it while constructing the transaction holds the exact bytes, and otherwise it does not. The second condition turns on what the transcript keeps, since a Consumer can check delivered bytes only against something the chain recorded. If the transcript keeps the ciphertext, the check is the byte comparison of the fifth condition. If a committed field may be left out of the transcript, the chain keeps only the commitment. A Consumer must then check the delivered ciphertext against that commitment instead. MPS-0005 Part 2 must answer both.

The Foundation's own proposals ask for an off-chain channel of this kind. MIP-0011 tells callers to deliver the coin information of contract-minted coins out of band [@midnight-mip-0011]. MPS-0025 asks whether provenance evidence for shielded transfers should be encrypted to the recipient or provided out of band [@midnight-mps-0025]. MIP-0012 shows where such a channel must not be used: custody discovery and recovery must work from chain data alone, so Midnight Express is no substitute there [@midnight-mip-0012]. MPS-0043 assigns the transport and discovery of confidential data to a pending problem statement, Confidential Contract Notifications (PR #271), whose text is unpublished [@midnight-mps-0043]. The Foundation's editors will decide whether the problem statement that closes Chapter 4 becomes that statement, replaces it or accompanies it.

The privacy offered is limited on purpose. Infrastructure must not learn what a Message says, nor which Messages a Subscriber is interested in. The second property is conditional. It hides which MPE Envelopes a Subscriber recognised among those of the Shards it receives in full. It does not hide which Shards it receives. It holds only if recognition changes no subscription, request, retry, error, repair or receipt. A Subscriber that asks a Store Node for a receipt on the one MPE Envelope it recognised in a whole Shard tells the Store Node which one mattered.

The design makes no claim against a global passive observer. At launch it does not provide timing privacy, which would hide when and how often Messages are sent; there is no cover traffic or batching. Nor does it provide relationship privacy, which would hide that a Publisher and a Consumer interact when their activity can be correlated in time or through the ledger. Some things stay visible to the transport. The ingress Bus Node sees the connection that submits an MPE Envelope. GossipSub topic names reveal the network prefix, the protocol version and Shard membership. Size class, timing and volume remain observable. The admission mechanism specified for the prototype is a stand-in whose secrets the relays can see, so it gives no admission unlinkability: relays can tell which membership published an MPE Envelope.

These limits follow from the literature as well as from cost. Bitmessage hid recipients by flooding every message to every user, each of whom tried to decrypt all of them [@2012-warren-bitmessage-whitepaper]. Whole-Shard recognition is that pattern bounded to one Shard. At the baseline mix of Chapter 9 it costs about 1.86 GB per day (derived: a mean wire length of 0.60 × 776 + 0.25 × 1,544 + 0.10 × 4,616 + 0.05 × 16,904 = 2,158.4 B, times 10 MPE Envelopes per second, times 86,400 s). The anonymity trilemma shows that strong anonymity cannot be had together with low bandwidth and low latency overhead [@2017-das-trilemma]. Midnight Express bounds both overheads, so it gives up strong anonymity. The Foundation's planned topic filtering at the Indexer gives up part of interest privacy for a smaller scan [@midnight-mps-0005]. Midnight Express treats such filtering as a reduced-privacy profile and does not use it by default.

Changes to Midnight consensus, the ledger rules or the node are out of scope, except that Option 3 in Chapter 6 weighs forking the node and rejects it. Midnight Express adds Compact contracts, Bus Nodes, Store Nodes and client software, changes nothing in the node, and reads the Indexer through its existing schema. Where Midnight's published documentation and its code disagree, the text names the generation it relies on. The published documentation describes the earlier ledger generation, and the node code pins ledger 9. On 4 August 2026 mainnet ran ledger 8.0 [@midnight-coip-0005], so no contract could `emit` there. Neither the ledger lane nor carriage of contract events could run on mainnet, though MIP-0002 events were live on Stagenet [@midnight-mip-0018]. Whether mainnet has moved to ledger 9 since then is unknown.

Of the Foundation's event documents, only MIP-0002 is Accepted. MPS-0005, MPS-0007, MPS-0043, MIP-0018 and MIP-0019 are Proposed, and CoIP-0003 is a Draft. Where MPS-0005 and the implemented texts differ on Phase 1 events, MIP-0002 and CoIP-0003 govern, because they match the shipped compiler and Indexer.

## First results and open questions

The ledger interface was compiled and costed apart from the overlay. It consists of the Bus Registry, a ledger-lane contract and a consuming contract, compiled with Compact toolchain 0.35.0 (language 0.27.0) against a ledger-9 release candidate. Circuit sizes come from the compiler's circuit model, and fees are derived from the ledger cost model at genesis mainnet prices. None of this ran on a Midnight network: no proof was generated, no transaction was submitted and no fee was observed. The contracts are exploratory code, and the design does not depend on them being final.

The Bus Registry, the ledger-lane contract and the consuming contract all compile. `emit` is the only ledger-9 dependency of the Bus Registry and the ledger-lane contract (toolchain 0.33 or later); the consuming contract also needs ledger 9's cross-contract model (Chapter 2). A circuit with size parameter k has at most 2^k rows, and its proving key, memory and time grow with k. Most of the proving cost comes from turning circuit values into bytes. A `Misc` part carries 256 B, so a class-2 sealed body is 4,096 / 256 = 16 parts. Emitting one part from a 256-byte circuit argument needs 166,241 rows (k = 18). Four parts in one call need k = 20, and sixteen parts about k = 22. Yet proof size does not grow with k: the compiler's cost model gives proofs of 2,800 B or 4,368 B and verifying keys of 1,351 B or 2,119 B, 2,800 B for `activateParams`, `anchorRootValid`, `prunePeriod` and the four ledger-lane circuits, 4,368 B for the other Bus Registry circuits and the consumer's `react`.

The recurring cost is the Anchor. Fees are paid in DUST, a non-transferable resource generated by registered NIGHT, Midnight's native token. A registration transaction is about 8.7 KB and costs 0.246 DUST (0.308 DUST with the wallet's fee margin). An Anchor post costs 0.195 DUST (0.244 DUST with margin). One Anchor per 60 s therefore costs about 280 DUST per day (1,440 × 0.195 = 280.8), whatever the traffic. The 0.195 DUST per Anchor assumes no net state growth; each retained Anchor-tree root adds about 32 B, about 0.006 DUST per Anchor or about 9 DUST per day (derived: 32 × 0.0002; 1,440 × 0.0064), until a reset rule bounds the tree. On the ledger lane, sixteen parts cost 0.188 DUST in one call and 0.866 DUST as sixteen separate calls. These fees are derived with 4,368 B for every contract proof, an upper bound for the ledger lane; with the modelled 2,800 B the sixteen-call shape is about 55,170 B and 0.62 DUST instead of 80,260 B and 0.866 DUST, and the one-call shapes keep their compute-bound fees.

Writing the contracts also exposed ledger limits that the requirement set must respect (Chapters 8 and 10). A Midnight transaction has no signer. The authority of the Bus Registry's steward (the holder of its governance secret) and of an anchorer (a Bus Node that posts Anchors) is therefore a hash preimage proved in circuit. A contract can compare the block time with a value but cannot read it, and so cannot record when it published a root. Nor can the contract enforce the 3,600 s root window (`P-ECO-5`), which is how long a replaced membership root stays usable; Bus Nodes enforce it. DUST cannot be paid to a contract, so a registration price above the network fee would need NIGHT or another token.

Large transcripts land in the fallible segment. The parts of one ledger-lane MPE Envelope therefore share one phase of one intent, which MIP-0019 allows, but that phase is not necessarily the guaranteed phase. A phase keeps all its events or none, so an MPE Envelope arrives whole or not at all.

The decision register holds 28 decisions, `DEC-001` to `DEC-028`. Each has a prototype default, a production default and a statement of the evidence that would settle it. The requirement set has 625 entries: 510 live requirements, 113 that restate an obligation owned by another entry, and 2 withdrawn. Of the live requirements, 169 depend on a decision that is still open.

Six decisions matter most. The first is the production admission instrument (`DEC-007`). The stand-in specified for the prototype exercises the protocol flow at an assumed cost and gives no unlinkability. The next four are whether relaying stays permissioned and what test would justify opening it (`DEC-006`), who pays Bus Operators, since DUST cannot be transferred to them (`DEC-001`), who governs the Bus Registry (`DEC-019`), and how light and mobile clients receive Messages without downloading a whole Shard (`DEC-021`).

The sixth is how a contract acts on a Message (`DEC-022`). The compiled consuming circuit proves that an MPE Envelope identifier is covered by an Anchor. Nothing in that circuit binds the consumption nullifier to the Message, so inclusion alone gives no authority. Version 1 specifies signed-instruction consumption, in which the circuit verifies the Publisher's signature and derives every effect input from the signed payload, and that circuit has not been written. It proves who authorized the instruction, not that the overlay admitted or anchored the Message: proving that to a contract needs a binding between the signed statement and the anchored Envelope that version 1 does not specify.

Three further questions sit outside the decision register. First, carried private events depend on MPS-0005 Part 2. Second, it is unknown which value of the ledger's `block_usage` limit is live: 200,000 B or 1,000,000 B per block. It is also unknown which budget binds the ledger lane: MIP-0002 sizes event capacity against the 50,000 B per-block `bytes_written` budget, while the ledger-9 code books event bytes as churn and leaves `block_usage` to bind. `MPE-PRF-040` requires both ceilings to be measured on a ledger-9 network.

Third, interoperability between GossipSub implementations under the selected profile is untested. The transport profile, and the proof of concept, negotiate the standard identifier `/meshsub/1.2.0`, which rust-libp2p's gossipsub crate offers by default, and apply `MPE-NET-058` to what each connection negotiates. That crate pins a custom protocol identifier only to v1.0 or v1.1 behaviour, and it sends IDONTWANT only to peers whose negotiated kind is v1.2 or later.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, method `ConfigBuilder::protocol_id`; protocols/gossipsub/src/behaviour.rs, method `Behaviour::send_message`; master branch, accessed 1 October 2026.] A network-specific identifier with v1.2 behaviour would therefore need a source change that adds `Version::V1_2`, and a Bus Node built that way would not interoperate with peers that offer only `/meshsub/1.2.0`. The proof of concept is a single implementation on rust-libp2p, so it will test no other GossipSub implementation. The Go implementation's parameter check rejects the selected mesh setting (D = 8, D_out = 4), although the specification allows it.^[libp2p/go-libp2p-pubsub, gossipsub.go, method `GossipSubParams.validate`; master branch, accessed 1 October 2026.] Here D is the target mesh size per topic and D_out the minimum number of mesh peers a Bus Node dials itself. D_low = 6 is the size below which it adds peers. The specification requires D_out < D_low and D_out ≤ D/2, both true here; the Go check requires D_out < D/2, which 4 < 4 fails.

One more question follows from the design itself, because independent validators cannot enforce a network-wide admission quota. Each Bus Node checks a membership's limit only against the MPE Envelopes it has itself seen. A membership that spends one allowance at several ingress Bus Nodes at once can therefore have a conflicting MPE Envelope accepted at each of them before their admission nullifiers meet. This follows from the design: each Bus Node accepts against its own admission-nullifier state, and two Bus Nodes that have not yet seen each other's MPE Envelope both accept. The proof of concept must measure how many conflicting MPE Envelopes its spam scenario gets accepted and how far they spread (Chapter 9), and Chapter 11 sets out what each outcome would change. The first milestone's simulator and harness run on one machine, so they will say nothing about behaviour on a wide-area network.

Chapter 11 lists two more risks with the evidence each one needs. Whatever is decided, neighbouring Bus Nodes see forwarding paths and when they receive each MPE Envelope, and no GossipSub configuration removes these observations. It is unknown whether the peer-scoring profile stays safe with several Shards. GossipSub sums a peer's per-topic score contributions before applying the topic cap, the ceiling on what all topics together contribute, so good scores on some Shards can offset invalid-message penalties on another.

## Conventions

### Requirement identifiers

Each requirement has an identifier of the form `MPE-AREA-NNN`, where the area is one of twelve three-letter codes. `FMT` covers the MPE Envelope format, `CRY` cryptography, `PUB` publish and subscribe, `CON` consumers, `ECO` admission and the sustainable model, `NET` the network, `PRF` performance, `STO` storage, `OPS` operations, `PRV` privacy, `SEC` security and `VER` verification. Each live requirement carries a scope (prototype or production), a priority (MUST, SHOULD or MAY) and a status (settled, or open with a reference to the decision it waits on). A restating entry points to the entry that owns its obligation. Parameters are named by area and number, as in `P-FMT-4`, and the requirement text uses the name in place of the value. Chapter 7 maps the ten decision areas onto the twelve requirement areas, and Appendix A lists every requirement.

### EARS syntax

Each requirement is one sentence in the Easy Approach to Requirements Syntax (EARS), with exactly one "shall" and one of five patterns or a combination of them:

- ubiquitous ("The ... shall ...")
- state-driven ("While ..., the ... shall ...")
- event-driven ("When ..., the ... shall ...")
- optional feature ("Where ..., the ... shall ...")
- unwanted behaviour ("If ..., then the ... shall ...")

In the "event-driven" pattern an event is any trigger condition, not a contract event. Sentences have at most 60 words and leave out vague words such as "fast" or "secure", so that a third party can write a pass/fail test from the sentence alone. The word "shall" marks an obligation, and the priority attribute says how strong it is. An unwanted-behaviour requirement reads:

> `MPE-FMT-030` Expired on arrival. If a received MPE Envelope's `expiry` is earlier than the Bus Node's clock minus `P-FMT-4`, then the Bus Node shall return Ignore.

`P-FMT-4` is 60 s, a tolerance for disagreement between clocks. In GossipSub validation, Ignore means the message is neither delivered nor forwarded. The router applies no invalid-message penalty (P4) to the peer that forwarded it [@2020-gossipsub-v11-spec].^[libp2p/specs, pubsub/gossipsub/gossipsub-v1.1.md, section "Extended Validators"; master branch, accessed 1 October 2026.] A late MPE Envelope is thus treated as a network condition, not as misbehaviour. Ignore still has a scoring effect, because it also earns the forwarding peer no delivery credit (Chapter 8).

### Measured, derived and assumed

Every number given here is one of three kinds, and the text says which.

A measured number comes from running a tool or a system, and the text states what was run and with which settings. Apart from figures cited from the literature, the measured numbers in this document are those the Compact compiler's circuit model reports for the ledger interface contracts, such as circuit rows and proof sizes. Part III specifies how the proof of concept will measure the rest. Figures from the exploratory runs that preceded the design are not measurements in this sense. They appear only in Chapter 10, each labelled as an unreplicated exploratory observation, and no claim, threshold or choice rests on them.

A derived number is arithmetic on stated inputs, and the arithmetic is shown. The smallest MPE Envelope on the wire is 8 B of header + 512 B of admission slot + 256 B of sealed body = 776 B. The ledger lane carries only the sealed body, so a class-1 MPE Envelope (1,024 B sealed body) is four `Misc` parts. Each part has 288 bytes of struct data and is about 328 B with MIP-0002's 40-byte overhead. MIP-0002 sizes event capacity against the 50,000 B per-block `bytes_written` budget, so under its sizing the Envelope counts about 4 × 328 = 1,312 B, a block admits about 50,000 / 1,312 ≈ 38 such Envelopes, and at 6 s blocks that is about 6.3 class-1 Messages per second for the whole chain with no other writers (3.5 if `block_usage` is 200,000 B and binds, as the ledger-9 code's churn accounting implies). The fees of the ledger interface are also derived: they apply the ledger cost model to the circuit sizes the compiler reports and to the transcript gas from Compact's simulator.

An assumed number is an input that has not been measured, and it is named as an assumption wherever it appears. The proof of concept will charge 4.5 ms for each admission-proof verification. This is a synthetic stand-in and not the cost of a real proof system. The block bytes per transaction in the fee estimates, about 700 to 900 B besides proofs, are also assumed.

Hypotheses written before an experiment are called expected results, and each has a pass condition. A design choice that only the exploratory runs prompted is stated as such a hypothesis, with the test and threshold that the proof of concept must meet (Chapters 9 and 11).

### Terms

Three terms need full definitions:

> **Private event.** A contract event, emitted by a Compact circuit during transaction execution, some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment that the proof checks, as planned for Phase 2 of MPS-0005 [@midnight-mps-0005]. A private event is Midnight's term, and Midnight Express does not redefine it.
>
> **Confidential Message.** A Message that a Publisher seals into a fixed-size MPE Envelope and delivers through Midnight Express, such that content confidentiality, sealed labels, conditional interest privacy and no silent change hold as stated in Chapter 4. A Confidential Message is not a contract event. It is authenticated by its Publisher's signature and committed by an Anchor, not by contract execution.
>
> **Carried event.** A Confidential Message whose payload is the unchanged bytes of a contract event, public or private, together with the transaction hash and position that let a Consumer verify it against the chain.

Sealed labels means that no stream name, recipient address or session identifier appears in clear. No silent change means that no fallback, overload path or application reaction changes what leaks without the application's explicit choice. The other terms keep the short meanings listed below throughout, and Chapter 4 gives their precise definitions.

| Term | Meaning |
|---|---|
| Event (contract event) | A structured record that a Compact circuit emits with `emit` during execution, recorded in the transaction and served by the Indexer [@midnight-mip-0002]; the Foundation's term |

| MPE Envelope | The fixed-size sealed wire object that carries one Message; MPE stands for Midnight Private Events |
| Shard | One GossipSub topic partition of the overlay; one Shard operates at launch |
| Stream | The audience or channel an application cares about; it travels only inside the sealed body |
| Recognition Tag | A salted 16-byte value in an MPE Envelope that lets a Subscriber recognise its Messages locally; it serves the purpose of MPS-0005 topic filtering, but differs for every MPE Envelope and only the Subscriber evaluates it |
| Bus Node | A sidecar process, separate from the Midnight node, that validates and relays MPE Envelopes |
| Store Node | A Bus Node that also keeps MPE Envelopes, 48 hours by default, so that clients can fetch missed ones later; it stores no chain history |
| Publisher | A client that seals Messages and submits them; on the ledger lane it is also a MIP-0019 publisher |
| Subscriber | A client that receives a Shard and recognises its Messages; on the ledger lane it acts as a MIP-0019 reader |
| Consumer | A party that acts on a Message: an agent, wallet, application or smart contract; a contract acts only through a later transaction |
| Admission Proof | The proof in the admission slot that authorises one publication and enforces a rate limit |
| Admission window | The 60-second period over which a membership's publication limit applies |
| Admission nullifier | The value that each MPE Envelope's admission reveals, so that Bus Nodes can count publications against a membership's limit |
| Consumption nullifier | The value that a consuming contract records, so that one Message takes effect at most once |
| Bus Registry | The Compact contract that holds memberships, parameters, the relay list and Anchors |
| Anchor | An authorized anchorer's commitment, kept as a Bus Registry state record, to the identifiers of the MPE Envelopes it accepted in one 60-second window, for all Shards; the Bus Registry checks its authority, timing and form, not its contents; the `Misc` event that echoes it is a notification, not the record |
| Ledger lane | The path that carries an MPE Envelope on the ledger as `Misc` parts in one intent, read through the Indexer |
| Ledger Adapter | The interface from a client or Bus Node to Midnight state and transaction submission; a mock in the prototype |
| Indexer | "A service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]; Midnight Express uses it as a read path and as the carrier of the ledger lane |
| Bus Operator | A party that runs a Bus Node, a Store Node or an anchorer; an Indexer operator is an operator in the Foundation's sense, not a Bus Operator |
