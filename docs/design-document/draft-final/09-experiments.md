# Experimental design {#ch9}

The proof of concept specified in Chapter 8 is to settle questions that argument cannot. Seventeen decisions in the decision register depend on a number that only a running overlay produces: CPU per MPE Envelope, bytes per Bus Node, delivery under attack, or the latency tail under churn (the slowest deliveries, read here at the 99th percentile). Eight more questions concern the ledger interface. These depend on a Compact compiler, a ledger-9 network, the public Indexer or wallet tooling, and a mock cannot answer them. For each question the design below fixes four things before any run: what is measured, the hypothesis and its pass condition, the scenario or instrument that tests it, and the result that would change the design. The order matters. A threshold chosen after the result is known can always be chosen so that the result passes. A threshold fixed in advance can fail, and only a run that could have failed tells the reader something about the design. The proof of concept has not been built, and none of the overlay questions has been answered. Exploratory runs that guided the design are described in Chapter 10 as unreplicated observations, and nothing in this chapter rests on them. Of the ledger interface experiments, one has been carried out in a limited form, the compiling and costing of the contracts (experiment L1), and seven have not run.

## The harness

The first milestone of the proof of concept (Chapter 11) delivers two instruments that read the same scenarios and write the same result schema. The first is a deterministic simulator. It drives the Bus Node, Store Node and client code on a single-threaded executor with a simulated clock and the in-memory transport, so that the seed fixes the order of every event as well as the workload, and a failing run replays exactly, step for step. The second is a runnable harness that executes the same code as real libp2p swarms on a multi-threaded runtime, and so measures what the simulator cannot: CPU, queueing and timing on a real host. Every overlay experiment will run through one binary with a fixed command line:

```
mpe-sim run --scenario <NAME> --nodes <N> --seed <U64> --duration-secs <T> --out <FILE.json>
```

Optional flags choose variants, such as a different mesh profile or a different emission threshold for IDONTWANT, the GossipSub notice by which a Bus Node asks its mesh peers not to send it a message it already holds. They never change the meaning of the fixed arguments, so every variant can be set against its standard run.

**Real swarms in one process.** In the runnable harness, one tokio multi-thread runtime will run one worker per core. In libp2p a `Swarm` is the object that holds one peer's identity, its connections and the protocols it speaks. Each Bus Node and each client will be such a `Swarm`, driven by its own task, so every simulated Bus Node is a complete libp2p peer. The overlay code under test is the library itself, rust-libp2p 0.57 with gossipsub 0.50, and not a model of it: mesh maintenance, peer scoring, IHAVE and IWANT gossip, IDONTWANT and the seen cache all run the library's own code. Each Bus Node keeps a small set of peers per GossipSub topic, its mesh, to which it forwards full messages. The mesh has a target size D and is kept between D_low and D_high peers, and at least D_out of them are peers the Bus Node dialled itself. To peers outside the mesh a Bus Node announces the identifiers of recent messages with IHAVE, and a peer that lacks one asks for it with IWANT. Once per heartbeat, a periodic step of 1 s here, the Bus Node repairs its mesh and updates the score it keeps for every peer. That peer score is the sum of terms the specification names P1 to P7: time in the mesh (P1), first deliveries (P2), the mesh delivery rate and its failures (P3 and P3b), invalid messages (P4), a score the application assigns (P5), peers sharing one IP address (P6) and behavioural penalties (P7). The seen cache is the library's record of the messages a Bus Node has handled recently, and a copy whose identifier is still in it is dropped. The runs will have no link latency, no bandwidth limit, no address diversity and no real failures, so they will not reproduce the timing and peer mix of a deployment (see "Threats to validity").

Two properties of gossipsub 0.50 constrain the proof of concept. The first is version selection. The stock library reaches v1.2 behaviour on the standard identifier `/meshsub/1.2.0` without change, but on a custom protocol identifier only through a vendored `Version::V1_2` member (Q5 gives the source). The proof of concept therefore negotiates the standard identifier, which the transport profile requires, and applies `MPE-NET-058` to what each connection negotiates. The second is a decoder gap. StrictNoSign is the GossipSub mode in which a message must carry no author, sequence number or signature, so that the pubsub layer says nothing about who created it. Under StrictNoSign the 0.50 decoder rejects messages that carry `from`, `seqno` or `signature`, but it does not reject a message that carries only `key`, the field meant for the author's public key. The library's 0.51.0 source adds that check.^[libp2p/rust-libp2p, protocols/gossipsub/CHANGELOG.md, entry for 0.51.0; master branch, accessed 1 October 2026.] A proof of concept pinned to 0.50 inherits the gap, and the `malformed` scenario tests for it.

The harness simulates three things: the network, the ledger together with its Indexer and the contracts it hosts, and the cost of the Admission Proof. The transport is either the in-memory transport or TCP on 127.0.0.1. Both are upgraded with Noise, the handshake that authenticates and encrypts each libp2p connection, and Yamux, which carries several protocol streams over one connection. The in-memory transport is the default, and the TCP variant checks that no result depends on the transport. A byte-counting adapter will wrap each Bus Node's connections below the upgrade, once per direction, so the counters include Noise framing, Yamux, GossipSub control traffic and every client and Store Node protocol. Proof verification will run on a blocking thread behind two semaphores: one per Bus Node, with one permit, and one global, with one permit fewer than the core count. The mock ledger, the mock Indexer and the metrics registry are shared objects in the same process.

**Topology.** With N Bus Nodes the harness will create 2 bootstrappers, 3 Store Nodes (one per Bus Operator), 1 anchorer, and N − 6 relays: 44 relays at 50 Bus Nodes and 194 at 200. A relay in this count is a Bus Node with no other role; it validates and forwards. Bus Nodes are assigned round-robin to three mock Bus Operator organisations and listed in the mock relay list. Each Bus Node dials 10 random listed peers plus both bootstrappers, and the bootstrappers also relay. The harness will not exercise the zero-degree bootstrapper profile with Peer Exchange (PX) that the requirement set describes. In that profile a bootstrapper keeps no mesh of its own and, when it prunes a newcomer, hands it a list of other peers to dial. The Rust PX implementation exchanges peer identifiers only and does not process signed peer records, so every dial address will come from the mock relay list. There are 10 Publisher swarms, each hosting 4 memberships (40 in total), and 10 Subscriber swarms. Each Subscriber holds the keys of 4 of the 20 private streams plus 28 decoy keys, which gives the 32 keys per Subscriber that `P-PRF-19` assumes. A decoy key matches no stream, so it costs the Subscriber recognition work on every MPE Envelope without adding a delivery to count.

A Bus Node that has just started Ignores new admissions for a 140 s restart barrier, because it cannot know which admission nullifiers it accepted before it stopped (Q8 derives the rule), and it uses a membership root only once its block is final. The first membership root is in the genesis block of the mock ledger. That block is final by definition and is created 1 s after every initial Bus Node has started. No admission existed before it, so no initial Bus Node has forgotten an admission nullifier, and the initial cohort clears the 140 s restart barrier at once, without waiting for finality.

**Seeded schedule.** One seed, through `ChaCha20Rng::seed_from_u64`, will derive every random choice:

- Bus Node and client identity keys, so peer identifiers repeat across runs with the same seed;
- memberships, streams and the assignment of Publishers to streams (two memberships per stream);
- Subscriber keys and attacker placement;
- the full publish schedule.

The schedule will be generated before the run starts, as a Poisson process at 10 MPE Envelopes per second on the one operating Shard, each Envelope carrying one Message. In a Poisson process each publication is independent of the one before, so the gaps between publications are random with a mean of 0.1 s, and bursts and lulls occur as they would among many Publishers acting independently. Each Envelope's class is drawn 60/25/10/5 by count across classes 0 to 3. Its Publisher is drawn among the memberships that still have credit in that class and admission window, and its payload length is uniform within the class capacity. Each payload begins with a 16-byte random canary, which the leakage scanner looks for.

The mean wire size of this mix is derived as 0.60 × 776 + 0.25 × 1,544 + 0.10 × 4,616 + 0.05 × 16,904 = 2,158.4 B. At 10 MPE Envelopes per second the mix carries 21,584 B/s, or 21.1 KiB/s, about a third of the 64 KiB/s byte cap, so the count cap of 10 per second binds first.

Two alternative loads are defined. `--load bytecap` publishes class 3 only, at 65,536 / 16,904 = 3.88 MPE Envelopes per second. `--load rate50` publishes 50 per second with the `P-PRF-28` class weights of 70/25/5/0.1.

In the runnable harness the schedule is deterministic and network timing is not. The tokio runtime decides which task runs on which core and in which order, and that order changes from run to run. A repeated seed therefore replays the same workload against the same identities and gives slightly different measurements, so one run is one sample of timing noise: every gated result takes five seeds, and no two runs share the host (see "How results are checked"). The deterministic simulator removes that noise, and with it the CPU and timing measurements. A gate on latency or CPU is therefore read from the harness, and a failure is diagnosed in the simulator.

The unit of delivery is a pair. A Message on stream s and a Subscriber that holds the key of s form one eligible pair, and the pair counts as delivered when that Subscriber authenticates the Message. A Message whose stream two Subscribers follow contributes two pairs, and if it reaches one of them and not the other, one pair is delivered and one is lost. Each Subscriber follows 4 of the 20 streams, so on average 10 × 4 / 20 = 2 Subscribers can recognise each Message. A 60 s publish window at 10 per second holds about 600 Messages and therefore about 1,200 eligible Message and Subscriber pairs.

**Run periods.** A run has three periods:

1. A 10 s warm-up.
2. Publishing for `--duration-secs`, 60 s in the standard runs.
3. A drain, in which no new Message is published while delivery, repair and anchoring continue.

T0 is the moment publishing starts, at the end of the warm-up, and T is the length of the publishing period, the value of `--duration-secs`. Times such as T0 + 62 s or T/2 in the scenarios below count from these. The drain depends on what the scenario waits for: 15 s for baseline, spam, malformed, replay, eclipse and leakage; 30 s for back-fill; 40 s for the ledger lane; 60 s for anchor; and 125 s for churn, which is two reconciliation intervals plus 5 s. The longest standard run is 10 + 60 + 125 = 195 s. Latency counts from the publish call, so a Message repaired during the drain enters the tail with its whole delay.

Five windows of time recur below. The publish window runs from T0 to T0 + T; byte counters are read over it, and the eligible pairs are those of the Messages published in it. An admission window is a 60 s period over which a membership's per-class limits apply, and an admission stays acceptable for a 20 s tolerance after its admission window ends (`P-ECO-6`). An Anchor window is a 60 s period whose accepted EIDs, on all Shards, one Anchor commits to. A Shard window is an Anchor window on one Shard, the unit of inventory and repair. The root window is the 3,600 s after a membership root is superseded during which Bus Nodes still accept admissions under it (`P-ECO-5`).

The swarms produce counters, the counters become one result file per run, and a checker tests each file against a fixed set of thresholds. Verdicts come only from the result file, so the same checker reads the output of the deterministic simulator and of the runnable harness without change.

## The ten standard scenarios

Each scenario adds one stress to the baseline. All ten draw the honest schedule from the same seed, so for a given seed the honest Messages, their Publishers and their Subscribers are identical across scenarios. Every scenario keeps the baseline set-up and adds what its row lists.

| Scenario | Set-up beyond the baseline |
|---|---|
| `baseline` | 10 MPE Envelopes per second on 1 Shard, 10 Subscribers |
| `spam` | One attacker membership. Part A: 100 class-0 MPE Envelopes per second through one ingress Bus Node, with credit indices 0 to 63 valid and the rest either over the limit or reusing an index with a new body. Part B: the same membership injects conflicting MPE Envelopes into 5 Bus Nodes at once |
| `malformed` | 5 attacker gossip peers, each injecting 20 MPE Envelopes per second that are garbage, truncated, overlength, wrong-version, reserved, unknown-class, Shard-mismatched, corrupted-proof, wrong-network, far-future or expired. Also oversize RPCs above the 65,536 B frame limit, and pubsub messages that carry only a `key` field. Validly admitted MPE Envelopes with a random Recognition Tag, and MPE Envelopes with an invalid sealed signature from an insider who holds a stream secret. Honest load continues |
| `replay` | 200 MPE Envelopes recorded in the first 2 s are re-injected byte for byte once the seen cache has expired (about T0 + 62 s, see below). 50 already-published bodies are re-admitted under new credit indices (same EID, new wire bytes). 200 MPE Envelopes are injected whose expiry is 61 s in the past. Corrupted-slot copies are sent ahead of honest MPE Envelopes, and so are unchanged copies on an unsubscribed GossipSub topic and, with eight Shards, on another Shard's topic |
| `eclipse` | Allow-list off. 20 percent of N are withholding attackers that dial the victim, accept GRAFT, never forward, and send IHAVE without answering IWANT. In the `poisoned` variant the victim's dial list is attacker-heavy |
| `churn` | Every 10 s, 10 percent of relays leave and the same number of fresh relays join, are listed and wait out the restart barrier. Subscribers attached to a departed Bus Node fail over |
| `backfill` | An 11th Subscriber joins at T/2 and back-fills from T0 from one Store Node. That Store Node stops at 0.75 T, and back-fill completes from another Bus Operator's Store Node |
| `anchor` | The anchorer is active. 2 Subscribers verify the `final` label, one Consumer reacts with an inclusion proof, and 100 reactors race on one Message |
| `leakage` | The baseline plus wire capture and a scanner over every frame and log line |
| `ledgerlane` | The ledger lane. The overlay is off for 3 Subscribers that opted in. Publishers use the ledger lane at 2 Messages per second, classes 0 to 2, plus a burst of 200 at T0 + 20 s, plus class-3 attempts, which must be refused |

In `replay`, the re-injection is timed to the seen cache on purpose. A copy re-sent while its identifier is still in the seen cache would be dropped by the library before the application ever saw it, and the run would then test the seen cache of rust-libp2p, not the application seen-set that `MPE-PUB-027` requires. The Rust seen cache lasts 60 s by default; the Go implementation's default is 120 s.^[libp2p/go-libp2p-pubsub, pubsub.go, variable `TimeCacheDuration`; master branch, accessed 1 October 2026.] T0 + 62 s therefore bypasses the Rust cache only if every honest Bus Node first received the copy more than 60 s earlier. The fixture will record the cache lifetime and each Bus Node's first-receipt time, and it will delay any copy whose cache entry could still be live by at least a 1 s margin. Take one recorded MPE Envelope that the last honest Bus Node first received at T0 + 1.5 s. Its cache entry there expires at T0 + 61.5 s, and with the 1 s margin the fixture re-injects it no earlier than T0 + 62.5 s, half a second after the nominal time. The 120 s variant repeats the scenario with the Go default. The scenario also checks expiry on the send path. GossipSub does not read the MPE Envelope's expiry field, and the stock IWANT handlers serve cached messages without an expiry check. The harness will therefore count every expired MPE Envelope that an honest Bus Node sends, including forwards after Accept, IWANT responses and queued sends. The fixture adds three cases: a validly admitted MPE Envelope whose expiry is 1 s in the past, one whose expiry is the current second, and one whose expiry passes while it waits for verification or in a send queue. The 60 s tolerance of step 9 (Table 8.4) decides acceptance only; none of these may be sent once its expiry has passed (`MPE-FMT-032`). Until that count is zero in a recorded run, the proof of concept is not known to meet the expiry requirement.

In `malformed`, two kinds of injection are accepted by design. The validator never opens the sealed body, so a validly admitted MPE Envelope with a random Recognition Tag passes it, and every Subscriber then discards it. An invalid sealed signature fails only at the Subscriber that opens the body. These cases are counted in the result notes and are not treated as failures. The `key`-only messages test the decoder gap of gossipsub 0.50. A run that accepts them records a StrictNoSign compliance failure of the dependency, not a failure of the application validator.

In `eclipse`, the attackers withhold messages but stay protocol-correct in every other respect. An eclipse attack fills a victim's connections with attacker peers, so that everything the victim receives passes through the attacker, who can then delay or withhold it. GRAFT is the GossipSub message by which a peer joins another peer's mesh. An attacker that accepts GRAFT therefore takes a place in the victim's mesh, and one that sends IHAVE without answering IWANT advertises messages it never serves. GossipSub v1.1 peer scoring was designed against this attack [@2020-gossipsub-v11-spec].

In `ledgerlane`, the ledger lane sends each sealed body as `Misc` parts in one transaction. The mock ledger checks the per-block limits that apply to those transactions (see Q16).

## Metrics and how each is measured

Every run writes one result file with a fixed schema, in which every key is always present, with `null` where a metric does not apply. Each key is measured in one fixed way.

| Key | How it is measured |
|---|---|
| `published` | Messages the honest schedule submitted, each counted once regardless of retries. In `replay`, the 450 injections. For the ledger lane, see `ledgerlane.*` |
| `delivered.expected` | Eligible pairs: a Message and a Subscriber that holds that stream's key and was present for the whole publish window. In `churn` and `backfill` this includes Subscribers that join or move |
| `delivered.received`, `ratio`, `per_subscriber_min_ratio` | Pairs the Subscriber authenticated before the drain ended; `ratio` is received over expected; `per_subscriber_min_ratio` is the lowest of the per-Subscriber ratios |
| `latency_ms` (p50, p95, p99, max) | From the publish call to authentication at the Subscriber, on one monotonic clock, over received pairs only. Missing pairs are counted separately in the notes |
| `duplicates` | Deliveries to the application beyond the first per Subscriber and EID. Network duplicates are amplification, not duplicates, and are reported in the notes |
| `rejected.*` | Adversarial injections only, each counted once by the outcome at the first honest Bus Node that received it, under seven reasons: malformed, oversize, bad admission, over quota, replay, expired, bad signature |
| `panics` | A panic hook counter plus every task that ended in a panic |
| `expired_sends` | MPE Envelopes an honest Bus Node sent after their expiry, by path: forward after Accept, IWANT response, queued send |
| `wire.envelope_sizes`, `distinct_sizes` | Length histogram of every GossipSub payload received by any Bus Node and every MPE Envelope inside a client protocol frame |
| `wire.plaintext_leaks` | Captured frames that contain 8 or more bytes of any secret the harness knows |
| `bandwidth.*` | Counting-transport bytes per Bus Node over the publish window: median over Bus Nodes per direction, and the maximum per direction |
| `cpu_ms_per_node_p50` | Per Bus Node: the summed duration of every poll of its swarm task plus its blocking verification time; median over Bus Nodes |
| `store.max_bytes` | Maximum over Store Nodes of retained MPE Envelope bytes plus 72 B per index entry |
| `store.backfill_expected`, `backfill_recovered` | EIDs accepted on the Shard before the late Subscriber joined, and how many of them that Subscriber obtained through back-fill |
| `anchor.*` | Anchors final on the mock ledger; every `final` determination by a Subscriber and every inclusion proof a mock contract checked, and how many were valid |
| `eclipse.*` | The victim's attacker and honest peer counts at the end of warm-up; the fraction of honest MPE Envelopes the victim accepted within 10 s |
| `spam.*` | Attacker MPE Envelopes submitted; distinct attacker EIDs accepted by at least one honest Bus Node in part A; the quota, which is 64 times the number of admission windows part A spans |
| `ledgerlane.*` | Messages submitted through the ledger lane; Messages authenticated through the mock Indexer; total size of included transactions; log items or transactions dropped by a ledger limit |
| `notes` | Drain used, verification cost used, honest outcome counts by reason, variant results, mock limits hit, the configuration echo |

The capture in `leakage` is the view of a relay after Noise decryption; Noise ciphertext itself is not analysed. A zero leak count means that no secret the harness knows appears as a contiguous byte string in the captured frames. It says nothing about values derived from a secret (an admission proof keyed by `a0`, a Recognition Tag), about the creation second that `expiry` carries, or about timing and volume, and it is not evidence for the Content Game or the Selection Game. The scanner will search for every payload canary, Logical Message Identifier, stream secret, stream identifier, recognition key, encryption key, admission secret, identity commitment, Publisher public key and schema identifier. The same scenario compares byte distributions offset by offset outside the `shard` and `expiry` fields (`MPE-FMT-004`). Within each size class it sets 1,000 MPE Envelopes from one Publisher and stream against 1,000 from distinct ones. If a Publisher's MPE Envelopes always carried, say, the same byte at offset 40, the first sample would concentrate on one value where the second spreads over all 256. Two properties of the samples shape the test. With 1,000 values over 256 byte values the expected count per value is about 4, too few for the asymptotic chi-square, and a test at p > 0.01 repeated over hundreds of offsets fails somewhere by chance: even 256 independent offsets all pass with probability 0.99^256, about 7.6 percent. The statistic is therefore the largest per-offset chi-square in the class, and its p-value comes from 1,000 random relabellings of the two samples (a permutation test), which holds the chance of any false alarm across the class at 1 percent. A positive control plants a constant byte at one offset of the single-Publisher sample, and the test must flag it. A pass means that no single offset differs at that level. It is evidence, not proof, that a relay cannot group MPE Envelopes by their bytes: a grouping visible only in a combination of offsets, such as two bytes whose XOR is constant, passes the test, and the `shard` and `expiry` fields, lengths and timing are outside it.

The questions also use metrics derived from these keys. The formulas are fixed here so that every result applies them the same way:

- Rate in Mbit/s: bytes × 8 / window length in seconds / 10^6, over the publish window.
- Ingress amplification: median per-Bus-Node ingress divided by the unique MPE Envelope bytes published in the window (`MPE-PRF-005`).
- Subscriber download per day: feed, reconciliation and receipt bytes per Subscriber in the window × 86,400 / window length (`MPE-PRF-021`).
- Repair share: received pairs whose first authenticated copy came by reconciliation or back-fill, divided by all received pairs.
- Within 10 s: received pairs with latency of at most 10 s, divided by expected pairs.

Two of these formulas, worked once, show the scale. At the baseline mix a 60 s window carries 60 × 21,584 = 1,295,040 B of unique MPE Envelope bytes. A Bus Node that receives 3,885,120 B in that window has an ingress amplification of 3,885,120 / 1,295,040 = 3: on average each byte reaches it three times. Its ingress rate is 3,885,120 × 8 / 60 / 10^6 = 0.52 Mbit/s. The amplification of 3 is illustrative.

The p99 latency is taken over received pairs only, so a run that loses 20 percent of its pairs can still report a short p99. Latency is therefore always read together with the delivery ratio.

## Pass criteria

The thresholds turn the prototype parameters of the requirement set into numbers. They are acceptance targets for Midnight Express, not GossipSub guarantees, because GossipSub specifies no latency, throughput, CPU or bandwidth service level. Ratios are taken after the drain. Each scenario has one gate, and each gate value comes from a parameter or a requirement.

| Scenario | Gate | Source |
|---|---|---|
| `baseline` | within 10 s ≥ 0.999 of expected pairs, missing and late pairs counted against it; every Subscriber ≥ 0.99; p99 ≤ 10 s; no duplicates; ≤ 4 distinct sizes; no plaintext leak; no panic | `P-VER-7`, `P-VER-6`, `MPE-VER-014`, `P-FMT-1` |
| `spam` | part A accepted ≤ quota; no panic | `MPE-ECO-016`, `MPE-FMT-030` |
| `malformed` | honest delivery ≥ 0.999; no panic | `P-VER-7` |
| `replay` | every injection Ignored as a replay or as expired; no expired MPE Envelope sent by an honest Bus Node; no panic | `MPE-PUB-028`, `MPE-FMT-032` |
| `eclipse` | victim delivery by the gossip path ≥ 0.99; no panic | `P-PRF-23`, `P-VER-25` |
| `churn` | delivery ≥ 0.99 after the drain; no panic | `P-PRF-23` |
| `backfill` | recovered = expected | `MPE-PUB-031` |
| `anchor` | ≥ 1 final batch; every checked proof valid | `MPE-CON-016` |
| `leakage` | 0 plaintext leaks; ≤ 4 distinct sizes | `MPE-FMT-004` |
| `ledgerlane` (ledger lane) | delivered = published; nothing dropped over a ledger limit | `MPE-PUB-035` |

Two gates can be read off the design directly. The size gate allows at most 4 distinct sizes because the format has four size classes and gives each one wire length (776, 1,544, 4,616 and 16,904 B). A fifth length on the wire would mean that something about a Message's content or origin shows in its size. The spam gate is the per-membership limit in a second form. Part A offers 100 class-0 MPE Envelopes per second, which over one 60 s admission window is 100 × 60 = 6,000 attempts against 64 valid credit indices, so at most 64 may be accepted. If part A spans two admission windows the quota is 128.

The checker will fail closed. A missing or null value of a metric that a gate reads counts as a failure: a missing panic count reads as one panic, a missing leak count as one leak, and a missing duplicate or expired-send count as one duplicate or one expired send. A missing scenario, a missing seed, or a result file whose configuration echo differs from the configuration under test fails the whole set.

The checker evaluates each run on its own: it reads every result file, one per scenario and seed. A gate counts as passed for a configuration only if all five seeds pass it. Seeds are combined only for the question metrics of the next section, which use the median over the five seeds and report the range beside it.

The gates are a floor. Each one tests the property its requirement names and nothing more, so two of them can pass while the property they stand for goes untested. The `backfill` gate counts recovered identifiers, so a harness that also credits pages retrieved by other Subscribers still passes. The `eclipse` gate counts MPE Envelopes the victim accepted, so a Store Node repair that pushes Envelopes into the victim's validator raises the ratio without any help from the mesh. Each received pair therefore records the path that first delivered it, and each of the two gates counts only its own path (see "Attribution of delivery").

## The seventeen questions

Each question addresses a decision in the decision register or a requirement whose value is uncertain, and its hypothesis states what the design currently assumes, with a pass condition. Each question also names the result that would change a decision. Where the design supplies an expected value, that value is derived arithmetic, shown in the prose below the table, and the measurement will replace it.

### Recognition and validation cost

Q1 weighs two ways for a Subscriber to recognise its Messages. Both answer the same question, "is this MPE Envelope for one of my streams", and both must be asked of every Envelope on the Shard, because a Subscriber that downloaded only its own would reveal its interest. The Recognition Tag path computes one HMAC per installed key. An HMAC is a keyed hash, and with its pad states precomputed for each key one evaluation over the 58-byte tag input costs three SHA-256 compressions (Chapter 8). Trial decryption performs one key derivation plus one authentication pass over the whole sealed body per key, so its cost grows with the body size, and the Recognition Tag's does not. The Recognition Tag serves the purpose that MPS-0005 assigns to topic-based filtering of planned private events: it spares the recipient a trial decryption of everything [@midnight-mps-0005]. It differs in where the work happens. It is computed fresh for each MPE Envelope, it cannot be linked across Envelopes, and only the Subscriber evaluates it.

The decision rule has two triggers, and they can disagree. At the 32-key fixture both paths are cheap. The Recognition Tag path costs 32 × 100 × 0.5 µs = 1.6 ms of CPU per second even at an upper per-key cost, which is 0.16 percent of a core, and trial decryption at class 2 is also likely to stay under 5 percent at 32 keys. Read at 32 keys, the "both under 5 percent" trigger would move the default to trial decryption. Yet at 256 keys trial decryption scales eight times higher, while the Recognition Tag stays near 1 percent: 256 × 100 × 0.5 µs = 12.8 ms of CPU per second, or 1.28 percent of a core. The rule is therefore evaluated at the 256-key cap, the largest key set a Subscriber may install, and the 32-key result is reported alongside it. The cost that matters most is on a phone, so the benchmark also runs on phone hardware before `DEC-003` is closed.

Q2 separates proof cost from everything else. With 4.5 ms per verification, 10 MPE Envelopes per second cost 10 × 4.5 ms = 45 ms of CPU per second, or 0.045 core per Shard. That leaves most of the 0.30-core edge budget of `P-PRF-14` for polling, hashing and protocol work. The three proof costs (1,000, 4,500 and 10,000 µs) show whether the remainder is constant, as the budget assumes, or grows with proof time through queueing.

The 50-per-second arm has a host limit that the experiment must respect. Fifty Bus Nodes each verifying 50 proofs per second at 4.5 ms need 50 × 50 × 4.5 ms = 11.25 cores of proof work, and the planned host has 6. A 50-per-second run with the whole swarm on one host would measure the host, not a Bus Node. The per-Bus-Node ceiling needs one Bus Node pinned to its own cores, with the rest of the swarm on other cores at a reduced synthetic cost, or a run with one Bus Node per machine. Overload also has effects beyond local refusal. GossipSub holds a message that awaits the application's verdict in its message cache, and if validation is late, the pending message can leave the message cache. Queue bounds and temporary Ignore decisions can then interrupt propagation. The run will therefore record every failed `report_message_validation_result` call and every publish-queue failure, and it counts neither as propagation.

### Overlay behaviour

Q3 tests the claim that GossipSub v1.1 scoring, together with an outbound quota, keeps a surrounded Bus Node connected. The score terms that matter here are P1, P3, P4, P5 and P6. The outbound quota D_out is the number of mesh places reserved for peers that the Bus Node dialled itself. An attacker that connects inbound cannot fill those places, so with D_out = 4 at least four of the victim's mesh peers are of its own choosing, provided its dial list is honest. A Sybil attacker is one party that runs many identities. The published evaluation of v1.1 used 1,000 honest peers and 4,000 Sybils with a 20:1 Sybil-to-honest connection ratio on a cloud test platform [@2020-vyzovitis-gossipsub]. Its authors found no attack that degraded a warm network. Under one network-wide eclipse attack on a warm network they report a p99 propagation latency of 141 ms, a figure that describes that experiment and is not a latency guarantee. Attacks during network formation, the cold boot case, had some effect, and the network recovered [@2020-vyzovitis-gossipsub-v11-evaluation]. The defences work in combination. Scoring alone neither limits identity creation nor guarantees Sybil resistance. Outbound quotas resist capture by inbound connections only when honest dial sources exist, and poisoned discovery or colluding outbound peers remain a risk [@2020-gossipsub-v11-spec; @2020-leastauthority-gossipsub-audit].

The harness differs from that set-up in a way that changes what the scenario can show. Links have no latency, so a victim with a single honest mesh or gossip path receives each MPE Envelope almost as soon as it exists, and withholding then gains the attacker nothing. The eclipse scenario can show that the mesh keeps an honest path. It cannot show how long the victim waits when paths are slow.

Three refinements follow. First, the `poisoned` variant must poison every dial source, including both bootstrappers, because a victim that keeps even two honest outbound peers is not eclipsed by construction. Second, the scenario must run long enough for scoring to act. With P3 off, the specified system evicts a withholder through an application rule: a mesh peer that makes no first delivery in 90 consecutive loaded heartbeats (heartbeats in which the Shard carried traffic) is pruned from that Shard's mesh and receives a P5 of −33 for the 60 s backoff. That takes 90 s at the 1 s heartbeat, longer than the 60 s window, so the eclipse runs that test eviction last at least 180 s. Third, eviction must remove the peer, not only lower its score. The score sums one contribution per Shard, the profile caps their positive sum at 32 (the topic cap), and one Shard contributes at most +30 (+10 from P1, +20 from P2). P5 is added after the cap, so with −33 a peer at the cap of +32 totals −1, negative whenever P6 and P7 are not positive. With −20 it would total +12, and a peer at +30 would total +10, above the gossip, publish and graylist thresholds of −10, −50 and −80, so the peer would stay; that is why the specification prunes an evicted peer directly, whatever its score. The run will therefore record whether each evicted withholder actually left the victim's mesh and when. The eviction rule itself is an approximation. The Rust message events expose first deliveries only. A delivery-time callback exists, but it carries no message identifier and can run before acceptance. Honest forwarding also does not guarantee an equal share of first deliveries. The eviction test therefore includes asymmetric latency and topology, slow honest peers and every supported Shard.

Eclipse attacks on deployed networks have succeeded by monopolising a victim's connections from few addresses [@2015-heilman-eclipse; @2018-marcus-ethereumeclipse]. The in-process harness has no IP diversity at all, so address-based defences such as the GossipSub P6 score will be tested only in a separate TCP test with distinct loopback addresses. P6 also has a cost that this test cannot price: honest peers behind one NAT, hosting provider or proxy share an address and are penalised together.

Q4 tests the bandwidth planning model of the requirement set: egress = 1.25 × D × the unique byte rate. This is a planning assumption, not a bound that GossipSub specifies. At the byte cap and D = 8 the model gives 1.25 × 8 × 65,536 B/s × 8 bit/B = 5.24 Mbit/s. At D = 6 it gives 3.93 Mbit/s. Both are inside the 6 Mbit/s budget of `P-PRF-12`.

The model assumes that each Bus Node forwards each message to most of its mesh. Average egress over all Bus Nodes must equal average ingress, because every byte sent is a byte received. The equality holds only if both sides count the same endpoints, the same traffic categories and the same interval, so client feeds, Store Node traffic and repair are counted at both ends or excluded at both ends. Average ingress is the unique byte rate times the amplification, which means that the measured amplification tests the model directly. The maximum per direction is reported beside the median, because the busiest Bus Node may be busy for a reason other than the mesh, such as serving Subscriber feeds.

Q5 isolates IDONTWANT. Take one class-3 MPE Envelope of 16,904 B arriving at a Bus Node with eight mesh peers. The first copy arrives from one peer. Without IDONTWANT, any of the other seven that have the Envelope and have not yet sent it will send another 16,904 B copy. With IDONTWANT, the Bus Node immediately sends those seven a control message naming the 32-byte identifier, and a peer that receives it before sending skips the copy. The saving per avoided copy is the Envelope size, and the cost is a control message of a few dozen bytes per peer, so the trade is good for class 3 and doubtful for class 0. Four properties of the libraries bound what Q5 can show.

The first is the size predicate. Rust sends IDONTWANT only when the serialized pubsub message is strictly longer than the threshold, 1,000 B by default. Go tests the payload length instead, sends at equality, and defaults to 1,024 B.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, function `handle_received_message` (`raw_protobuf_len() >` threshold); libp2p/go-libp2p-pubsub, gossipsub.go, function `Preprocess` and constant `GossipSubIDontWantMessageThreshold`; master branches, accessed 1 October 2026.] Class 0, at 776 B wire size, stays below 1,000 B after pubsub framing and is unaffected by construction, so the effect is reported per class. The 700 B arm brings class 0 in, which can reduce data bytes or add control bytes. Thresholds below the class-0 length remain experimental until Q5 has measured both costs.

The second is what "off" disables. The off arm sets the emission threshold to 65,537 B, so no frame under the 65,536 B cap triggers a notice. That stops emission only, because the receiving side still honours any notice it gets. Every on and off result states that emission was the behaviour switched off.

The third is the version profile. The transport profile requires GossipSub v1.2 behaviour and negotiation of the standard identifier `/meshsub/1.2.0`; a default offer list does not establish that, because the libraries also offer v1.3 and older versions. The GossipSub topics for Shards and the request-response protocols are named under `/mpe/<g>/1`, where g is the first eight bytes of the genesis hash in lowercase hexadecimal. Stock rust-libp2p gossipsub 0.50 reaches v1.2 only through its standard identifiers. For a custom identifier it sets the internal protocol version through an enumeration that accepts only `V1_0` or `V1_1` in `protocol_id`, and the supplied string does not determine the version.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, enum `Version` (variants `V1_0` and `V1_1`) and `ConfigBuilder::protocol_id`; master branch, accessed 1 October 2026.] A custom identifier ending in `1.2.0` with `V1_1` set therefore leaves IDONTWANT silently off. A custom identifier with v1.2 behaviour would need a source change that adds `Version::V1_2`, and it would not interoperate with standard-only peers. The proof of concept therefore negotiates `/meshsub/1.2.0`, the profile the specification requires, in every run.

The fourth is limits and lifetimes. Sending a message despite a notice must not be penalised. The specification leaves the per-heartbeat IDONTWANT limit undefined, and Rust's cap of 10,000 remembered identifiers per peer is a memory bound, not that limit, so the release profile has to agree a per-peer, per-heartbeat limit before any excess penalty applies. Suppression lasts 3 s plus heartbeat cleanup in Rust and three heartbeats in Go. It is recorded separately from the seen-cache lifetime.

An "on" run that has silently negotiated v1.1 measures the "off" case. Every run will therefore record, on each connection, the negotiated protocol identifier and the internal peer kind, the library's record of which protocol version the peer speaks; the library sends IDONTWANT only to peers of kind v1.2 or later. A run whose negotiated version differs from its configuration is invalid.

Q6 tests the censorship path that motivated the full-Envelope message identifier. The GossipSub message identifier is the 32-byte value SHA-256(`mpe/v1/msgid` ‖ envelope bytes). The envelope bytes are the complete, immutable MPE Envelope carried as the pubsub `Message.data`, Admission Slot included. They exclude protobuf framing, the GossipSub topic, RPC batching, Noise and Yamux. The identifier is distinct from the EID, which excludes the Admission Slot and serves admission, inventories, application deduplication and Anchors. With the EID as GossipSub identifier, the attack at a single Bus Node runs as follows. The attacker sees an honest MPE Envelope E, alters one byte of its 512-byte slot to make E′, and sends E′ to a Bus Node before E arrives. E and E′ share an EID, because the EID leaves the slot out. The Bus Node rejects E′ for its bad proof and records the identifier as seen; when E arrives a moment later, the library drops it as a copy of something already handled, and the honest Envelope stops at that Bus Node. With the full-Envelope identifier the two copies have different identifiers.

The library has a second path to check. A Bus Node sends IDONTWANT on receipt, inside the handler for received messages, before the application has validated the message.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, function `handle_received_message` (IDONTWANT broadcast); master branch, accessed 1 October 2026.] The specification permits this: the notice announces possession of an identifier, not validity. An invalid copy can therefore suppress forwarding of a valid one for the IDONTWANT lifetime, 3 s in Rust, if the two copies share an identifier, and the seen cache does the same for its 60 s. The full-Envelope identifier rules this out for corrupted slots, subject to the collision resistance of SHA-256. It does not guarantee delivery against other attacks. One such path is known. rust-libp2p inserts the identifier into its duplicate cache before it checks that the Bus Node subscribes to the message's GossipSub topic, so an unchanged valid MPE Envelope sent first on an unsubscribed topic, or on another Shard's topic, can suppress the copy on the right Shard for the 60 s cache lifetime. The identifier excludes the topic, so Q6 runs that case too.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, function `handle_received_message` (duplicate-cache insert before the subscription check); master branch, accessed 1 October 2026.] The specification therefore requires a Bus Node to discard a message on a GossipSub topic it does not subscribe to before it records the message's identifier; the stock router does not, so this needs a router change and a recorded conformance test. Identifier collisions from other causes, implementation defects and data transforms remain open risks. Q6 checks that no loss appears with the full-Envelope identifier. The EID arm is a positive control: it should reproduce the attack.

Q7 checks a rule that unit tests cover but a running overlay may not. A GossipSub validator returns one of three outcomes for each message: Accept forwards it, Reject drops it and counts against the peer that sent it, and Ignore drops it without blame. While a Bus Node's chain view is stale, a check that depends on the chain returns Ignore rather than Reject, so the Bus Node does not penalise honest peers for its own lag. Ignore applies no P4 penalty. It also earns no delivery reward, and where P3 is on it can still leave a delivery deficit. The standard profile turns P3 off, so Q7 isolates P4. The test is whether any honest peer's P4 (invalid-message) score moves during a freeze, since a movement would mean some chain- or clock-dependent check escaped the conversion. A related risk is outside Q7's reach. P4 penalises the forwarding peer, not the party that constructed an invalid admission, so an honest relay that forwards a copy its own stale view accepted can be penalised by a Bus Node with a fresher view. The boundary between Reject and Ignore must stay conservative for this reason.

### Restart barrier and equivocation

Q8 measures what the 140 s restart barrier costs when relays come and go. The barrier exists because of how the quota is enforced. A Bus Node enforces each membership's limit by remembering the admission nullifiers it has accepted in the current admission windows; the same membership, admission window, class and credit index always produce the same admission nullifier, so a second use of a credit shows up as a repeat. A restarted Bus Node does not know which admission nullifiers it accepted before it stopped. Were it to accept admissions at once, a membership could spend again a credit it had used before the restart, and the Bus Node would have no record to detect it. It therefore Ignores new admissions for 140 s, which covers two 60 s admission windows plus the 20 s tolerance of `P-ECO-6`. GossipSub provides no recovery of allowance state. The barrier is an application construction and is valid only under its stated eligibility bounds: an allowance is eligible for at most 20 + 60 + 20 = 100 s, and the 140 s restart barrier (two admission windows plus the tolerance) exceeds that bound (`MPE-ECO-021`, `P-ECO-7`).

The churn scenario is a severe test of this rule. Departures are drawn at random from all current relays, and 10 percent leave every 10 s. One barrier period holds 140 / 10 = 14 waves, and each wave spares a given relay with probability 0.9, so the share of relays that have survived the 14 waves inside one barrier period is 0.9^14 = 0.23. In steady state, about 77 percent of relays are inside their barrier at any moment. That steady state is reached only in the 240 s runs. In the 60 s window there are six waves, so at most 60 percent of the original relays have been replaced by the end.

The repair share decides Q8, not delivery alone. Delivery can reach 1.0 because Subscribers retrieve everything from a second Store Node while the overlay itself delivers little. The 2 percent and 10 percent bounds in the rule are bounds on that share. Barrier occupancy will be recorded each second, so that delivery loss can be set against the share of relays that could not forward.

The scenario also exposes how a Bus Node inside the barrier answers a publish request. Under the publication rule of Chapter 8, it answers `Busy` when it Ignores for the barrier, a full queue, the rate limit or a stale view, and `Refused` for other refusals. The variant answers nothing instead. Busy and Refused are replies of the Midnight Express publish service, not GossipSub validator outcomes. With a Busy reply the client retries at another Bus Node at once; with silence it waits for its timeout. The two behaviours will therefore run as paired variants, so that Q8 does not answer two questions at once.

The publish service sends one response per request. `Accepted{eid}` means that the named ingress completed application acceptance, committed its acceptance state and queued the MPE Envelope for sending; `PublishFailed{eid}` means that acceptance was committed but the GossipSub `publish` call failed, and the client retries the identical bytes through another Bus Node. It does not prove that a mesh peer received the MPE Envelope.

An identical gossip copy ignored inside the barrier stays suppressed at that Bus Node while its identifier is in the seen cache, 60 s under the Rust default, because Reject and Ignore do not remove the cache entry. The loss is bounded by that lifetime. Recovery comes through the client's retrieval path, another application path, or a later retransmission that is still eligible after the cache entry expires.

Q9 measures how far one membership can exceed its quota when it injects at several Bus Nodes at once. Equivocation here means using one credit index, and therefore one admission nullifier, for two different MPE Envelopes. Each Bus Node enforces the quota with its own acceptance state. Two Bus Nodes that each see one MPE Envelope under an admission nullifier both accept, and evidence of the conflict appears only when the copies meet. The evidence is the pair itself: two shares under one admission nullifier let anyone solve for the member's secret, which is what revocation checks. No network-wide admission bound follows from mesh connectivity. The question is how many conflicting MPE Envelopes reach Subscribers before the evidence spreads.

The run uses 200 Bus Nodes as well as 50, because the time for evidence to reach every Bus Node grows with the mesh diameter. It counts acceptance and delivery separately, and it counts delivery per Subscriber as the distinct conflicting EIDs that reach the application. The specified client deduplicates by EID and by Publisher and Logical Message Identifier, never by admission nullifier, so an equivocator that varies the Logical Message Identifier can deliver both MPE Envelopes to one Subscriber. A client rule that drops the second MPE Envelope per admission nullifier is a candidate, not part of version 1; Q9 runs with it on and off, and the rule becomes a requirement only if Q9 shows more than one delivery per admission nullifier without it.

### Retention, download, size classes and repair

Q10 and Q11 rest on simple arithmetic, and the measurement exists to test the multipliers. Raw retention for one Shard at the byte cap over 48 h is 65,536 × 172,800 = 11,324,620,800 B, or 10.55 GiB. At an assumed 2x database multiplier that is 21.1 GiB, inside the 32 GiB allocation of `P-STO-3`. The multiplier is the ratio of bytes a store occupies to the MPE Envelope bytes it holds; indexes, logs and unused space inside the database files all add to it. The optional 7-day archive is 65,536 × 604,800 = 39.6 GB raw (36.9 GiB).

The in-memory store cannot measure the multiplier. It counts MPE Envelope bytes plus a fixed 72 B per index entry, so its multiplier is (776 + 72) / 776 = 1.093 at class 0 and (16,904 + 72) / 16,904 = 1.004 at class 3, by definition. The standard runs bound only the index and Envelope part. Q10 needs a store with a real database, filled to 48 h of identifiers at 10 per second (10 × 172,860 = 1.73 million entries per Shard), with resident and on-disk size measured. Retention is an application rule; GossipSub keeps messages only in its bounded caches. Expiry on an honest Store Node also cannot delete copies that an adversarial store keeps.

Q11's expected value at baseline is 10 × 2,158.4 B × 86,400 s = 1.86 GB per day of MPE Envelope bytes per Subscriber. One Shard of eight is 1.86 / 8 = 233 MB per day. Both exceed the stated bounds before any protocol overhead is counted, so the measurement mainly tests the overhead. The figure is large because every Subscriber downloads the whole Shard, its own Messages and everyone else's, so that its download reveals nothing about which streams it follows. What a Subscriber actually downloads also includes feed framing, cursor overlap between polls, reconciliation and receipts, and the download will therefore be measured at the Subscriber's own byte counters, not computed from Envelope counts. A selective profile would trade interest privacy for volume. It would resemble the topic filtering that MPS-0005 plans at the Indexer for on-chain private events, a reduced-privacy profile under `MPE-PUB-016` and `MPE-PRV-013` [@midnight-mps-0005].

Q12 tests whether each size class holds enough MPE Envelopes to hide in. An observer sees an Envelope's size class, so a Message hides only among the Envelopes of its own class in the same period; a class that carries one Envelope a minute hides nothing. At 10 per second the baseline mix gives 600 Envelopes per minute. Class 3, at 5 percent, gives 30 per minute, exactly the floor. Counts per window are close to Poisson, with a standard deviation of √30 ≈ 5.5, so about half of all windows will fall below 30 by chance even if the mean is exactly 30. The rule is applied to the median over windows and seeds, and the share of windows below the floor is reported beside it. At the 50-per-second weights class 3 receives 3,000 × 0.001 = 3 Envelopes per minute, so that mix tests whether class 3 can stay in the default table at all.

The stand-in fixes the Admission Slot at 512 of class 0's 776 B. The decision register's rule to drop class 0 if a real slot exceeds 1,024 B waits for a real proof system. For scale, the circuit model of experiment L1 below gives proofs of 2,800 B or 4,368 B for the compiled Compact circuits, more than five times the 512 B slot. A production slot is `W = roundUp64(104 + proof length)`, capped at 4,096 B (P-ECO-11), so the largest admissible proof is 3,992 B. A 2,800 B proof gives `W = 2,944 B`, inside the cap but above 1,024 B, so class 0 would leave the production table (`DEC-013`); a 4,368 B proof gives `W = 4,480 B`, above the cap. No admission circuit is written, so which applies is open.

Q13 and Q14 price the two background protocols that give a Subscriber assurance. Reconciliation catches what the feed missed. Once per interval the Subscriber obtains the list of EIDs a second source holds for each Shard window, checks it against what it received, and retrieves the difference. A reconciliation inventory at 10 per second is 600 identifiers × 32 B = 19,200 B per minute. The feed in the same minute is 600 × 2,158.4 = 1,295,040 B, so the inventory is 19,200 / 1,295,040 = 1.5 percent of the feed at the baseline mix, close to the 2 percent bound, and the measurement decides the question. Repair retrieves every Shard window that differs, in full and independent of recognition, because a request for only the identifiers a Subscriber recognised would reveal its interest.

Receipts are more expensive by arithmetic. A receipt is a Bus Operator's signed statement about one EID that it holds. 600 receipts of about 105 B per minute per Bus Operator come to 63,000 B per minute. That is 63,000 × 1,440 = about 91 MB per day per Bus Operator and 272 MB per day for three, near 15 percent of a 1.86 GB per day feed and above the 10 percent trigger. Q14 therefore tests whether the arithmetic holds, and the expected outcome is a signed window root per Bus Operator. Both measurements count only bytes exchanged inside the publish window, by protocol. A receipt request made after the window closes would fall outside the byte counters and make the cost look zero.

### Anchors, the ledger lane and idle Shards

Q15's timing chain has five parts:

- The wait for the Anchor window to close: a Message waits between 0 and 60 s, depending on where in the window it falls.
- The grace period: the anchorer waits 20 s after the Anchor window closes before it posts. This wait equals the admission tolerance of `P-ECO-6` in length but is a separate rule of the anchorer.
- Proving the Anchor transaction: `postAnchor` is a k = 18 circuit (experiment L1). Its proving time has not been measured, and the mock contract will charge none.
- Inclusion: one 6 s block.
- Finality: about 18 s.

Without proving, the wait to `final` is between 20 + 6 + 18 = 44 s and 104 s, with a median near 74 s, plus up to 1 s of polling. A Message published at the very end of a window waits the minimum of 44 s, and one published at its start waits 60 s longer; with publications spread evenly over the window, the median sits halfway, at 44 + 30 = 74 s. That is far inside the 300 s of `P-CON-8`, so the timing half of Q15 is expected to pass unless proving takes minutes. `final` means that the MPE Envelope is covered by a Bus Registry Anchor in a finalized block. Anchors are verified against Bus Registry state, and the `Misc` copy of an Anchor is a notification, because events are not consensus state [@midnight-mip-0002]. The open half of Q15 is agreement. A Subscriber that recomputes a window's root from its own inventory must hold exactly the set the anchorer committed to. One EID more or one EID fewer produces a different root, and the Subscriber can no longer show that its Messages are covered. MPE Envelopes that arrive near a window boundary or near their expiry are the likely cause of mismatches, so the run will record each mismatched window and the identifiers that differ.

The `anchor` scenario's mock contract checks an inclusion proof against an Anchor. Experiment L1 shows what such a check proves on Midnight: that some anchored EID exists. It does not bind a consumption nullifier to that Message. A reaction with authority also needs the Publisher's signature (`DEC-022`, option (a)), and that circuit is experiment L5. Even with the signature, the circuit proves who authorized the instruction, not that the overlay admitted or anchored that Message: version 1 specifies no binding between the signed statement and the anchored MPE Envelope. The race of 100 reactors in `anchor` therefore tests the consumption nullifier's uniqueness. It does not test authority.

Q16 has the tightest arithmetic. The ledger lane sends a body of class c as 4^c `Misc` parts of 256 B each, in one transaction: one part for class 0, four for class 1, sixteen for class 2. Each part is a `Misc` event with 288 B of struct data, about 328 B once MIP-0002's `VersionedLogItem` overhead of about 40 B is added [@midnight-mip-0002]. The transaction size comes from experiment L1. A 16-part class-2 call occupies about 12,920 B of block space, including a 4,368 B contract proof, and each part adds about 306 B, so one-call transactions for classes 0, 1 and 2 are about 8,330 B (12,920 − 15 × 306), 9,248 B (8,330 + 3 × 306) and 12,920 B. These sizes take the contract proof at 4,368 B, an upper bound: the ledger-lane circuits' modelled proofs are 2,800 B.

A Midnight block has several budgets at once, and a transaction is included only if it fits within all of them: total block usage in bytes, bytes written to state, bytes churned, and compute time. Capacity is set by whichever budget runs out first, and which per-block limit binds is not settled. Three readings of the cost model charge a lane transaction against different budgets, and each gives a different capacity.

The first reading takes `bytes_written` as MIP-0002 states it. MIP-0002 says a log's `bytes_written` equals its serialized size, so each part is charged 328 B against a budget of 50,000 B per block. A class-1 Message then writes 4 × 328 = 1,312 B, and 50,000 / 1,312 = 38 fit in a block. In the same way class 0 fits 152 per block (25.3 per second for the whole chain), class 1 fits 38 (about 6.3 class-1 Messages per second under MIP-0002's `bytes_written` sizing, 3.5 if `block_usage` is 200,000 B) and class 2 fits 9 (1.5 per second). Inside a 10 percent chain share that is 2.5, 0.63 and 0.15 per second.

The second reading charges each Message its whole transaction size against `block_usage`, the block size. At 1,000,000 B, the value in the Midnight node's network configuration files, the three classes fit 120, 108 and 77 per block: 20.0, 18.0 and 12.8 per second, or 2.0, 1.8 and 1.28 inside a 10 percent share. At 200,000 B, the value in the ledger's initial limits, they fit 24, 21 and 15 per block: 4.0, 3.5 and 2.5 per second, or 0.40, 0.35 and 0.25 inside 10 percent. Which value is live is unmeasured (`MPE-PRF-040`).

The third reading follows churn and compute. The ledger-9 code counts a log's bytes once as written and once as deleted, so they cancel in net `bytes_written` and are charged to `bytes_churned` instead.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, `Log` instruction ("count the entire log as churn"); base-crypto/src/cost_model.rs, `impl From<RunningCost> for SyntheticCost`; ledger/src/structure.rs, constant `INITIAL_LIMITS`; main branch, accessed 1 October 2026.] Under that reading the 50,000 B budget does not bind lane parts. Experiment L1 derives from simulator gas that one 16-part class-2 call churns about 26,931 B and needs about 27.6 ms of compute. The churn limit (1,000,000 B in the initial limits) then admits 1,000,000 / 26,931 = 37 such calls per block, and the per-block compute limit admits 1,000 / 27.6 = 36 or 2,000 / 27.6 = 72, depending on whether 1 s or 2 s is live.

Planning uses the lowest figure for each class: about 4.0 class-0, 3.5 class-1 and 1.5 class-2 Messages per second for the whole chain with no other writers, and 0.40, 0.35 and 0.15 inside the `P-ECO-8` share. Under the first reading class 2 misses the 1-per-second floor by a factor of almost seven, and class 1 misses it as well. Only the most generous `block_usage` reading clears it, by 28 percent. The expected result of Q16 is therefore a failure of the class-2 hypothesis, and the expected outcome is a lane of classes 0 and 1 with `P-FMT-8` at 4 parts. Proving cost points the same way: one part is a k = 18 circuit, four parts are k = 20, and sixteen parts in one call come to k = 22. Experiment L2 decides which limit binds on a ledger-9 network.

By default the mock ledger will enforce only the 1,000,000 B block size. For Q16 it gains two accounting modes. One charges each part's 328 B against a 50,000 B written budget. The other charges churn, compute and block usage at 200,000 B, using the transaction figures of L1. The burst of 1,000 MPE Envelopes runs under both modes. It measures blocks to clear, and it checks that the reader drains every log entry of a block before it reassembles parts. The latency floor is one block plus finality, about 24 s, plus polling and the proving time of the lane transaction. That proving time is unmeasured, so the 60 s p95 bound is tested without it in the harness and with it in L2.

Q17 tests parameters that the design inherits from the library. Topic score P3 penalises mesh peers that deliver too few messages on a GossipSub topic, and on a Shard with no traffic every peer delivers none. P3 penalises idle peers only when its expected-delivery threshold is nonzero and its penalty outweighs the other contributions. With the library defaults (threshold 20, weight −1), an idle peer's P3 is −1 × 20² = −400 before topic weighting. The complete library-default topic profile does not make every idle peer negative. Its time-in-mesh term (P1) can reach 3,600, and at topic weight 0.5 the contribution is 0.5 × (3,600 − 400), so it can stay near +1,600. The Midnight Express profile gives P1 a cap of 10 per topic at topic weight 1, and an idle Shard brings no new first deliveries, so once P2 has decayed, default P3 leaves an idle peer at best 10 − 400 = −390 on that Shard. Default P3 inside the Midnight Express profile is therefore a different configuration, and it can drive scores negative. A negative score would prune honest peers from the mesh of an idle Shard, and the first Message published there after a quiet spell would find the mesh thin or empty. The design turns P3 off and evicts on its own activity-aware rule. Q17 runs all three arms and records each complete profile, and no arm is reported as "the default". If the Midnight Express profile with default P3 does not prune honest peers, the application rule is unnecessary.

Scoring across Shards has a separate risk. Per-topic contributions, P4 penalties included, are summed before the topic cap of 32 applies, so positive contributions on other Shards can offset invalid-delivery penalties on one Shard. With eight Shards the uncapped positive sum can reach 240, and four invalid deliveries on one Shard can leave the capped result at +32. The eight-Shard runs will therefore repeat `malformed` and record the total score of each attacker.

## The ledger interface experiments

The overlay questions run against a mock ledger. The ledger interface needs other instruments: a Compact compiler and circuit model, a ledger-9 network, the public Indexer, wallet tooling and, for one experiment, a Foundation specification that does not yet exist. Eight experiments cover it. L1 has been carried out in a limited sense: the contracts were compiled and costed, although nothing ran on a network. L2 to L8 are designed and have not yet run.

Two facts apply to all of them. Of the Foundation's event documents, only MIP-0002 is Accepted. MIP-0019, MPS-0005, MPS-0007 and MPS-0043 are Proposed, and Part 2 of MPS-0005, which plans on-chain private events, is unpublished [@midnight-mip-0002; @midnight-mip-0019; @midnight-mps-0005]. MIP-0002 and CoIP-0003 govern contract events wherever MPS-0005 differs [@midnight-coip-0003]. On 4 August 2026 mainnet ran ledger 8.0. Contract events arrive with ledger 9, and MIP-0002 is live on Stagenet. Every result below therefore belongs to a ledger generation that mainnet did not run on that date.

### Experiment L1, compiled and costed

**Method.** Three contracts were written in Compact, Midnight's language for contracts whose circuits are proved in zero knowledge: the Bus Registry, the ledger lane contract and a consumer contract. They are exploratory code, and the design does not depend on them being final. They were compiled with toolchain 0.35.0 (language 0.27.0, ledger 9.1 release candidate, compact-runtime 0.20.0) on a 6-core host, and also with 0.31.1, the ledger-8 toolchain, to find their ledger-9 dependencies. Circuit sizes come from the circuit model of the proof system (`zkir mock-compile`), which reports rows, k and proof size. A circuit is laid out as a table of 2^k rows, the smallest power of two that holds its constraints, so k = 13 means a table of 8,192 rows and k = 18 a table of 262,144. The prover's work and memory grow with that table, which is why each step in k matters on a phone. The generated JavaScript ran in the Compact simulator against the Bus Registry and the ledger lane contract; that run supplies the transcript gas used for the fees and the SHA-256 equality noted below. Fees are derived from the ledger-9 cost model at genesis mainnet prices, with the simulator's transcript gas as input. No transaction was constructed, proved, balanced or submitted, and no proof was generated or verified.

**What the contracts do.** The Bus Registry holds one membership tree per membership period, a set of revoked identity commitments, the parameters with a time-locked change procedure, the relay list, a pause flag, and the Anchors. Anchors sit in a ring of 2,940 slots indexed by window mod 2,940, with an Anchor tree that other contracts read through a witness-free circuit. The ring holds 49 h of 60 s windows (49 × 60 = 2,940): the 48 h lifetime plus a 1 h margin, because a contract rejects an expired Message and never needs an older root. The live Anchor records stay at 2,940; the Anchor tree's set of accepted roots still grows by about 1,440 roots (about 46 KB) a day until a reset rule, still open, bounds it. Revocation checks equivocation evidence in circuit: two shares on the member's line under one admission window, class and credit index, with distinct EIDs. The ledger lane contract emits one `Misc` part per call, or a whole class-0, class-1 or class-2 MPE Envelope per call, and has no class-3 circuit. The consumer contract's `react` circuit verifies a private RFC 6962 inclusion path from an EID to an Anchor-tree root. An inclusion path is the list of sibling hashes that leads from one leaf of a Merkle tree to its root; for a window of 600 EIDs it holds at most 10 hashes, because 2^10 = 1,024 is the first power of two at or above 600. The circuit calls the Bus Registry to check that root, checks expiry privately against a coarse public bound, and records a consumption nullifier. The contracts emit `Misc` events under fixed 32-byte names. A name is a compile-time constant, so the specification's names (`mip-xxxx:anchor[v1]` and `mip-xxxx:envelope[v1]`, NUL-padded to 32 bytes) do not change the circuit sizes.

**Compile results.** Each of the three contracts compiles with 0.35.0. With 0.31.1 the Bus Registry and the ledger lane contract fail on `emit`, which arrived with toolchain 0.33. Without its two `emit` statements the Bus Registry compiles with 0.31.1, so `emit` is its only ledger-9 dependency. The consumer also fails with 0.31.1, because the ledger-8 cross-contract model needs the callee's compiled contract information. The circuit model gives the following sizes for the main circuits.

The verifier side stays small. The compiler's cost model gives proofs of 2,800 B or 4,368 B and verifying keys of 1,351 B or 2,119 B: 2,800 B for `activateParams`, `anchorRootValid`, `prunePeriod` and the four ledger-lane circuits, 4,368 B for the other Bus Registry circuits and the consumer's `react`. The k = 18 proving keys are of the same order as the 64.3 MB prover key that MPS-0039 reports for an `emitMisc` circuit [@midnight-mps-0039]. Proving time was not measured for any circuit.

**Fees, derived.** Fees on Midnight are paid in DUST, a resource that cannot be transferred between holders. At genesis mainnet prices the fees come out as follows, without and with the wallet's margin of five blocks.

A registration of about 8.7 KB and 0.25 DUST fits the `P-ECO-13` gate of 16 KiB and 0.5 DUST. An Anchor every 60 s costs 1,440 × 0.195 = about 280 DUST per day per anchorer, and each one needs a k = 18 proof. The 0.195 DUST per Anchor assumes no net state growth; each retained Anchor-tree root adds about 32 B, about 0.006 DUST per Anchor or about 9 DUST per day (derived: 32 × 0.0002; 1,440 × 0.0064), until a reset rule bounds the tree. Sixteen separate part calls cost 4.6 times one 16-part call (0.866 / 0.188 = 4.6), because each call carries its own proof and its own fixed overhead. Transaction sizes and fees are derived with 4,368 B for every contract proof, an upper bound for the ledger lane; with the modelled 2,800 B the sixteen-call shape is about 55,170 B and 0.62 DUST instead of 80,260 B and 0.866 DUST (derived: 80,260 − 16 × 1,568; 0.552 + 0.045 + 0.018), and the one-call shapes keep their compute-bound fees. One call per MPE Envelope is the cheaper shape in fees and the more expensive one to prove. Live prices move each block by up to about 4.6 percent per dimension, and mainnet still runs the ledger-8 parameter schema, so these figures can change before ledger 9 is deployed.

**Limitations found.** Nine limitations of Compact 0.35.0 and ledger 9 shaped the contracts:

- Bytes dominate proving. Turning circuit values into bytes costs about 670 rows per conversion, and `emit` needs bytes. Emitting a constant 256-byte payload costs 23 rows (k = 6). Emitting a 256-byte argument costs 166,241 rows (k = 18). `postAnchor` spends most of its rows on the payload of its single `emit`.
- SHA-256 is affordable only with struct preimages. `persistentHash` over `Bytes` values, and over a struct of `Bytes` fields, equals plain SHA-256 of the concatenated bytes; the simulator checked this against a standard SHA-256. Written with byte spreads, the 19 SHA-256 evaluations of `react` need 703,378 rows (k = 20). Written with struct preimages, they need 77,905 rows (k = 17).
- There is no signer. A Midnight transaction has no sender, so the steward and the anchorer prove knowledge of a secret whose hash is in state.
- A contract can test block time against a bound but cannot read it. Each time-dependent write takes a caller-supplied clock value, checked against block time within a 900 s tolerance. Every such test also discloses its operand, so the consumer discloses only a coarse bound and checks the exact expiry privately.
- Root history has no time bound. A circuit cannot read its own Merkle root, and the historic-root check accepts every past root. The 3,600 s root window of `P-ECO-5` cannot be enforced by the contract, so Bus Nodes enforce it off chain.
- DUST cannot be paid to a contract. The price of a membership is the network fee of the registration transaction. A further price would need NIGHT or another token.
- Inclusion is not authority. `react` proves that some anchored EID exists. Nothing binds the consumption nullifier's secret to that EID.
- Large transcripts leave the guaranteed segment. A Midnight transaction has a guaranteed segment, which pays the fees and cannot fail, and fallible segments, which can fail one at a time and leave the transaction partially applied. A transcript goes into the guaranteed segment only if its modelled cost fits the time-to-dismiss budget, the larger of 2 µs per transaction byte and 15 ms, less a per-transaction reserve; otherwise all of it goes into the fallible segment. The 16-part call (27.6 ms against 25.8 ms), the registration and the Anchor post all exceed it, a placement derived from the gas figures and the partitioning code but not observed. Ledger lane parts therefore share one phase of one intent, which MIP-0019 accepts, but not necessarily the guaranteed phase.
- `transientHash` has no stability promise. The in-circuit revocation relation uses it, and a protocol hash pinned by the specification should be one that Midnight commits to keeping.

**Implications for the requirement set.** Ledger lane parts land in one phase of one intent (`MPE-FMT-042`), not necessarily the guaranteed phase. `P-FMT-8` keeps 16 parts as the fee limit. The 16-part call is a k = 22 circuit, however, which argues for an in-contract limit of 4 parts (k = 20) unless a cheaper `Misc` encoding appears. `DEC-022` keeps option (a), the Publisher signature, as the default for consumption with authority. `MPE-ECO-004` describes a registration transaction, not a paid DUST fee. `MPE-ECO-015` and `P-ECO-5` state that Bus Nodes enforce the root window. `MPE-ECO-049`, `MPE-OPS-046` and `MPE-VER-030` use the inputs above until network measurements exist. Protocol hashes computed in circuit take struct preimages of fixed-width fields.

L2 is the experiment the ledger lane depends on. It measures the serialized size of a `Misc` event, which MIP-0002 gives as about 40 B of `VersionedLogItem` overhead on 288 B of struct data. It records gross and net written bytes, churn and block usage separately, and so settles which of the readings in Q16 is the real one. It also adds the cost the mock cannot charge, the proving time of a lane transaction. The same network run measures the Bus Registry: registration size and fee, the Anchor's fee and proving time per window, and whether large transcripts land in the fallible segment as L1 derives.

L3 tests the reader against the vectors that MIP-0019 makes normative. A test vector is a fixed input published with its exact expected output, so two separately written readers can be checked against each other byte for byte. A reader that passes can be one of the two readers that MIP-0019 needs before it can become Active [@midnight-mip-0019]. The vectors test reconstruction only; phase behaviour needs the publisher tests. These matter here because L1 places large lane transcripts in the fallible segment, and a failed fallible phase must expose no applied parts.

L4 checks the read path that `MPE-CON-053` assumes: a filter on the contract address alone, served by an Indexer that serves finalized blocks only and delivers at least once, through a schema that marks the whole contract-event surface as beta. At-least-once delivery means a reader may see the same part twice, so the reader must discard repeats by position before it reassembles a body. The ledger lane cursor is the Indexer's monotonic `id`, which the Ledger Adapter translates into the client's cursor.

L5 writes the circuit that L1 left out. The inclusion-only `react` circuit is k = 17, and it gives no authority, because nothing binds its consumption nullifier to the Message. MIP-0013 rejects Ed25519 in circuit because emulated field arithmetic needs hundreds of constraints per field operation, while JubJub Schnorr uses native arithmetic [@midnight-mip-0013]. The `ed25519Verify` built-in also needs the toolchain's ZKIR v3 feature. A phone-class proving time is part of the result, because a Consumer that reacts from a wallet proves on the wallet's hardware.

L6 extends a partial result of L1. The simulator showed that `persistentHash` over `Bytes` equals plain SHA-256 for this toolchain, and the inclusion path compiles at k = 17. Two things remain open. The simulator ran JavaScript, not the circuit's constraints, and MPS-0042 documents the encoding under `persistentHash` as unstable [@midnight-mps-0042]. L6 therefore requires a proved execution on fixed vectors under a pinned toolchain. It also measures the cost of recomputing an EID over a whole sealed body, which no circuit has yet attempted.

L7 tests the key derivation that MIP-0015 proposes for wallets [@midnight-mip-0015]. With it, a membership survives the loss of a device: the admission secret is recomputed from the wallet seed the user has already backed up. The method is Proposed and optional in each wallet, so a pass permits derivation but cannot require it.

L8 cannot run until the Foundation publishes Part 2 of MPS-0005. Until then the syntax of `@private`, `@topic`, `encrypt_for` and `proven`, the key types and the size of a private event are unknown. When the text appears, the analysis of Midnight Express against on-chain private events is repeated first, and then one private event is carried as a carried event. The test checks each condition: the bytes exist in the client when the transaction is constructed, the chain keeps the binding, the event fits a size class with its 73 + `e` byte carried-event header (a logged item of up to 781 − `e` B in class 1), recipients can recognise it, Consumers treat it as `gossip` until the finalized transcript matches, nothing is re-typed, and the fee is paid once on chain. A rehearsal with a public `Misc` event can run now on a ledger-9 network. It tests every condition except those that depend on Phase 2.

## Controls and variant runs

A control is a second run that differs from the test run in one respect only, so that a difference between their results can be attributed to that respect. Every attack scenario has a built-in control: the baseline run with the same seed. The honest schedule, identities and stream assignment are the same, so a difference in honest delivery or latency between `spam` at seed 3 and `baseline` at seed 3 is attributable to the attack, apart from timing noise. The spread of the baseline over five seeds shows the scale of that noise.

Variant runs change one flag against the standard configuration and keep the seed set. The pairs are:

- IDONTWANT emission on, off and at 700 B (Q5);
- full-Envelope and EID message identifiers (Q6);
- Recognition Tag and trial recognition (Q1);
- the two mesh profiles (Q3, Q4);
- the three P3 arms (Q17);
- allow-list and open relaying (Q3);
- the three proof costs (Q2);
- a live ledger against a frozen, skewed or paused one (Q7);
- Busy reply and silent Ignore in the restart barrier (Q8);
- seen-cache lifetimes of 60 s and 120 s (`replay`);
- the ledger accounting modes (Q16);
- one Shard and eight Shards under `malformed` (score safety);
- in-memory and TCP transport.

The transport pair tests the harness itself. A result that holds on memory but not on TCP, or the reverse, is an artefact of the transport and is not reported as a property of the design.

A gate that passes may mean the property holds, or that the instrument cannot see a failure. Positive controls separate the two by planting the defect on purpose and checking that the instrument reports it:

- The leakage scanner must find a canary deliberately planted in a frame of each protocol. The scanner matches contiguous byte strings, so a field encoded as an array of integers rather than a byte string hides a key from it. Encoding all RPC byte fields as byte strings is therefore a precondition of the leakage gate, and the planted canary verifies it.
- For message identifiers, the EID arm of Q6 should reproduce the corrupted-slot loss.
- For eclipse attribution, a run with every honest path withheld from the victim, and repair off, should fail the gossip-path gate.
- For eviction, a withholder given an application score of only −20, which leaves its total score at +10 or +12, should be reported as still in the mesh, while the specified −33 with direct pruning should remove it.
- For expiry on the send path, an expired MPE Envelope placed in a Bus Node's message cache and then requested by IWANT should appear in the count of expired sends.
- For version negotiation, a run configured for v1.2 but forced to negotiate v1.1 should be marked invalid by the configuration echo.

## How results are checked

**Implementation defects and design properties.** The proof of concept is one implementation of the specification, so a failed gate can come from a defect in that code as well as from the design. A failure will be attributed to the design only when it reproduces in the deterministic simulator from the same seed and the replayed trace shows the mechanism the specification prescribes producing it. A failure whose trace shows a departure from the specification is an implementation defect; it is fixed and the run repeated, and it is not reported as a property of the design. Two departures are checked for directly because the specification makes them easy to miss: a seen-set capped below the 1.73 million entries that 48 h at 10 per second requires, and a feed cursor that returns overlapping pages and so inflates delivery.

**Isolated runs.** Only one scenario will run on the host at a time, with no compilation, no other scenario and no capture tool running beside it. All swarms share six cores, so a parallel job takes CPU from validation and forwarding. That delays MPE Envelopes past queue limits and timeouts, and the run then reports the delay as a design property. Each result file records host load and wall time, and a run that overlapped another is discarded, not corrected. The same rule holds for the ledger interface experiments: key generation at k = 20 takes about 1,105 s and 7.1 GB and must not share a host with a gated run.

**Repeated seeds.** Each gated result uses seeds 1 to 5, with the median and range reported. The schedule is fixed by the seed, so the five runs differ in workload as well as timing.

The number of seeds follows from the size of the gates. A baseline run has about 1,200 eligible pairs, so a 0.999 gate allows one missing pair per run, and one run with no loss shows little. With zero failures in n trials, the 95 percent upper bound on the failure rate is about 3 / n. The bound comes from asking how large a loss rate p could be while zero losses in n pairs still had at least a 5 percent chance: (1 − p)^n ≥ 0.05 gives p ≤ −ln(0.05) / n, and −ln(0.05) ≈ 3.0. For n = 1,200, the bound is 3 / 1,200 = 0.25 percent, worse than the gate's 0.1 percent. Five seeds give about 6,000 pairs, and zero losses then bound the loss rate at 3 / 6,000 = 0.05 percent, inside the gate. The bound is optimistic, because pairs are not independent. A lost MPE Envelope usually loses both of its pairs, and runs with different seeds share the same topology rules.

**Attribution of delivery.** Every received pair will record the path by which the Subscriber first authenticated it:

- the gossip path, through the mesh to the Subscriber's Bus Node and its feed;
- reconciliation from the second source;
- back-fill from a Store Node;
- the ledger lane.

Delivery ratios are reported per path as well as in total. Three results depend on this:

- The victim's ratio in `eclipse` counts only MPE Envelopes its Bus Node accepted from gossip.
- Recovery in `backfill` counts only pages retrieved by the late Subscriber.
- The repair share under churn is the deciding metric of Q8.

Reconciliation will run in the client library and not in the harness, so measured repair is what a deployed client would do. Retention, receipts, Anchors, replay protection, whole-Shard feeds and reconciliation are application mechanisms of Midnight Express. A result about them is attributed to the application and never to GossipSub, whose bounded caches and dissemination establish none of these guarantees.

**Run length against time constants.** A run must last longer than the time constant of the rule it tests. A 60 s window cannot show eviction (90 loaded heartbeats), barrier exit (140 s), seen-set growth towards its 1.73 million entries, or store pruning at expiry (48 h). Questions that depend on these rules use their own longer runs.

**Configuration echo.** Each result file records the parameters the run actually used. These include the negotiated GossipSub protocol identifier and internal peer kind on each connection, the mesh profile, and the IDONTWANT threshold, size predicate and switched-off behaviour. They also include the complete topic-score profile, the seen-cache and IDONTWANT lifetimes, whether Identify is enabled and which fields it exports, the gossipsub version and decoder, the proof cost, the ledger accounting mode and the drain. Results will be grouped by recorded configuration, not by the command line.

## Threats to validity

A threat to validity is a way in which a result could be produced by the set-up and not by the design.

### Internal validity

The largest internal threat is CPU contention. Fifty to two hundred swarms, a synthetic proof loop and the leakage scanner will share six cores. Instrumentation can itself become load: a frame scanner that searches every canary in every frame costs as much as the protocol it watches. The synthetic proof cost is a busy loop, so it consumes CPU as a real verifier would, but it does not reproduce a real verifier's memory traffic or cache behaviour. The 200-Bus-Node runs are restricted to baseline, churn and spam part B for this reason, and their latency results will carry the host's load as well as the overlay's.

The second threat is the drain. A pair delivered during the drain counts as received, while one that would arrive a second after the drain ends counts as lost. A change in the drain length can therefore move delivery, so each scenario's drain is fixed in advance and recorded.

The third threat is timing that depends on library constants. The replay fixture, the IDONTWANT arms and the barrier variants all depend on cache and suppression lifetimes. A result read without the recorded lifetimes can be attributed to the wrong mechanism.

### Construct validity

Several metrics measure something close to the property but not the property itself:

- Storage: `store.max_bytes` measures a definition, not a database.
- Admission: the Admission Proof is a stand-in. Its secrets are visible to every Bus Node, its verification cost is synthetic, and no admission privacy can be inferred from any run.
- Recognition: the 32-key fixture is the expected key count, not the worst case, which is why Q1 is evaluated at 256 keys.
- Circuit cost: L1's row counts come from the circuit model, not from proving. Its fees are derived, and its segment placement is derived from gas figures.

The leak count covers the secrets the harness knows, as contiguous byte strings. It does not cover a value derived from a secret, or a pattern in timing or volume. Nor does it cover what the transport discloses by design. GossipSub topic names reveal the network prefix, the major version and Shard membership. Size class, message timing, volume and the full connection transcript stay observable. Identify, if enabled, exposes keys, addresses, protocols and implementation metadata.

The scenarios do not test the interest-privacy property as a game over complete transcripts. In such a game an observer sees everything a Subscriber sends and receives and must decide whether it holds a given stream key, and the property holds if the observer does no better than guessing. That property holds only if recognition changes none of the Subscriber's subscriptions, requests, acknowledgments, retries, errors, repairs, receipts or diagnostics. Whether the proof of concept's client library meets it will stay unknown until paired transcripts that include repair and error paths have been checked against each other.

The interest-privacy property has a concrete form. Suppose a Subscriber recognises one MPE Envelope and, because of that match, sends one extra repair request a few seconds later. A Bus Node that sees the request learns that this Subscriber follows the stream of that Envelope, even though every byte of the request is encrypted. The paired-transcript test runs one Subscriber twice, once holding the stream key and once without it, under the same seed, connection schedule and active probes, and compares everything it sends and when: `/feed` pulls and their cursors, `/inventory`, `/backfill` and `/receipts` requests, any `/inclusion` request, retries, error replies, acknowledgments and diagnostics. Any difference is a failure (`MPE-VER-028`). No standard scenario runs this test, so no gate above covers interest privacy.

### External validity

The harness has no wide-area latency, no packet loss, no bandwidth limit, no NAT and no IP diversity. Its latencies will be optimistic against the 100 ms per-hop reference of `P-PRF-9`. Its eclipse results will understate attacks that depend on time, and it cannot test defences that depend on addresses.

The sizes are 50 and 200 Bus Nodes, while the requirement set also names 1,000. The published GossipSub evaluation needed thousands of containers on a cloud platform to study attacks at that scale [@2020-vyzovitis-gossipsub].

The proof of concept uses rust-libp2p only, so it will not establish compatibility with other GossipSub implementations. Four differences are already known from the source. The Rust and Go IDONTWANT predicates differ, as do the default version lists, and Go's PX handling differs from Rust's. Go's parameter validation also requires D_out < D/2, so it rejects the specified (8, 6, 12, 4) tuple, which the GossipSub specification allows: with D = 8, D/2 is 4, and D_out = 4 is not less than 4.^[libp2p/go-libp2p-pubsub, gossipsub.go, function `GossipSubParams.validate`; master branch, accessed 1 October 2026.]

The ledger, Indexer and contract in the harness are mocks. They copy Midnight's published limits: 6 s blocks, finality about 18 s, 1,000,000 B blocks, the 256-byte `Misc` payload and the 1 KiB log limit. They do not reproduce fees, proving time, contention for inclusion, segment placement or the behaviour of a real Indexer under load. The ledger's initial limits set `block_usage` at 200,000 B, not 1,000,000 B, and which value is live is unknown. The limits come from ledger 9, the generation pinned by the current node code. Mainnet ran ledger 8.0 on 4 August 2026, and a later ledger generation may change any of these values; L1 used release candidates of the ledger-9 toolchain for the same reason.

All CPU figures will come from a desktop host and do not transfer to phones.

### Statistical validity

Five seeds give about 6,000 pairs at baseline. That is enough to support a 0.999 gate when losses are near zero. It is not enough to estimate a rare tail, such as one loss in 10,000, or to separate two variants whose difference is smaller than the spread across seeds: zero losses in 6,000 pairs bound the rate only at 3 / 6,000 = 5 in 10,000, five times the rate in question. Paired variants on the same seeds reduce this problem, because the schedule cancels and only timing noise remains. A difference between variants is reported as a difference only when it exceeds the range of both variants over the five seeds.

## What the set-up cannot show

Some properties are outside what a single host with mock components can establish, however the runs are arranged:

- unlinkability of a publication to its Bus Node, and the cost of a real Admission Proof, because the stand-in reveals the member;
- source anonymity against relays that observe the first hop or the spread of a message, where estimators of the source from observed spread are well studied [@2015-fanti-spyvsspy]. The ingress sees the submitting connection directly, whatever the configuration. StrictNoSign, disabled flood publishing and separate sidecar keys remove neither that observation nor host correlation;
- any timing, volume, relationship or global-observer privacy; none is claimed at launch (`MPE-PRV-024`, `MPE-PRV-026`, `MPE-PRV-027`);
- behaviour at wide-area latency, under bandwidth limits, behind NAT, or at 1,000 Bus Nodes;
- resistance to a determined Sybil adversary under open admission in production. The closure of CVE-2022-47547 for the pinned library release and the complete scoring profile is also unknown until evidence specific to that configuration exists;
- interoperation with GossipSub implementations other than rust-libp2p;
- anything about Midnight's real ledger, Indexer, fees or DUST beyond the compiled and costed results of L1, and the proving time of any Bus Registry, ledger lane or consumption circuit;
- the carriage of an on-chain private event, until MPS-0005 Part 2 is published;
- Store Node durability across real crashes, the 72-hour soak, and the 24-hour run at 50 per second;
- recognition and download cost on phone hardware.

Passing every gate would not establish release security either. Regression closure (evidence that each known vulnerability, such as CVE-2022-47547, is fixed in the pinned release and covered by a test), complete privacy-game evidence, sustained resource behaviour, wide-area performance and resilience at production scale are separate acceptance obligations. Each needs a different instrument: a measured proof system, a distributed test network with injected latency and address diversity, a ledger-9 devnet or Stagenet, a second GossipSub implementation, or devices. Chapter 11 orders those experiments.
