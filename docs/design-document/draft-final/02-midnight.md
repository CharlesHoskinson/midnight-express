# Midnight in brief {#ch2}

Midnight is a blockchain whose contracts keep some of their data private and prove facts about it in zero knowledge, while the rest of their state stays public and is agreed by consensus. A zero-knowledge proof is a short piece of data that convinces anyone who checks it that a computation on hidden inputs produced a stated public result, without revealing the inputs. Contracts are written in Compact. A *circuit* is a Compact function whose execution the user proves in this way.

The Foundation's documents come in three numbered series. Midnight Problem Statements (MPS) state problems, Midnight Improvement Proposals (MIP) propose changes, and Compact Improvement Proposals (CoIP) propose changes to Compact. Each document carries a status such as Draft, Proposed or Accepted.

Two words keep the Foundation's meanings throughout. An *event* is a contract event: a Compact circuit emits it during transaction execution, and the transaction records it [@midnight-mip-0002; @midnight-coip-0003]. A *private event* is a contract event some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment that the proof checks. It is planned as Phase 2 of MPS-0005, the events problem statement, after public events in Phase 1, and is not yet specified [@midnight-mps-0005]. Midnight Express carries *Messages*, which are application messages and not contract events (Chapter 4), and a *Confidential Message* is one that holds the four properties defined there. Before sending a Message, Midnight Express seals it into a fixed-size MPE Envelope (Chapter 8).

## Two generations of the code

Contract events need ledger 9. The published documentation describes the ledger 8 generation of Midnight and the current code the ledger 9 generation, where a generation is a version of the ledger: the rules that apply transactions and the format of the state they change. A statement about Midnight can be checked only once its generation is named. Compact contract events arrived with toolchain 0.33.0 (language 0.25.0), which targets ledger 9.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.33.0.md, header ("This release works with a Midnight ledger 9 blockchain") and section on events ("Compact now supports _events_"); main branch, accessed 1 October 2026.] The ledger 8 branch has the virtual machine's `log` instruction but not the decoding and size cap that turn a log into a typed event.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, constant `MAX_LOG_SIZE` (present) and `MAX_LOG_EMITTED` (absent); branch `ledger-8`, version 8.2.0-rc.1, accessed 1 October 2026.]

Every source that describes mainnet, the latest dated 28 September 2026, places it on ledger 8. The release support matrix lists the mainnet deployment as node 1.0.300, Compact toolchain 0.31.1 and on-chain runtime 3.0.0.^[midnightntwrk/midnight-docs, docs/relnotes/support-matrix.json, entries `node`, `compactc` and `onchain-runtime` for `mainnet`; main branch, accessed 1 October 2026.] The Compact multi-target proposal, dated 4 August 2026, lists mainnet on ledger 8.0 with on-chain runtime 3.0 [@midnight-coip-0005]. The Compact 0.35.0 release notes, dated 28 September 2026, say that ledger 9 "is not yet deployed on Midnight Mainnet" and tell mainnet developers to keep using toolchain 0.31.x, the ledger 8 toolchain.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, section "High-level summary"; main branch, accessed 1 October 2026.]

The test networks and the code are on ledger 9 or later. The multi-target proposal lists preprod on ledger 9.1, and preview on 9.1 in its abstract but 10.0 in its table [@midnight-coip-0005]. MIP-0018 reports that MIP-0002 events are live on Stagenet, where its reference contracts were compiled with Compact 0.34.0 (language 0.26.0, runtime 0.19.0) on ledger 9 [@midnight-mip-0018]. On its main branch the node pins ledger 9 (crate tag `ledger-9.1.0.0-rc.5`) and wires a state translation from ledger 8 to ledger 9 into its runtime migrations.^[midnightntwrk/midnight-node, Cargo.toml, dependency `mn-ledger-9` (package `midnight-ledger-v9`, tag `crate-ledger-9.1.0.0-rc.5` in Cargo.lock); runtime/src/lib.rs, runtime migrations; main branch at commit 887348f9, accessed 1 October 2026.]

This document therefore treats ledger 9, Compact 0.33 or later and version 4 of the API of the Indexer (the chain-data service described below) as the generation that any design for events targets. Where a statement holds only for that generation it says so, and Table 2.1 marks the generation of each limit.

Two parts of Midnight Express rest on contract events. The Bus Registry is its Compact contract for Bus Operators, memberships and Anchors. An Anchor is an authorized anchorer's commitment, kept as a Bus Registry record, to one 60-second window: the window number, a count of MPE Envelopes per Shard, and the window root, a SHA-256 Merkle root over the MPE Envelope identifiers (the hashes that name the Envelopes) it accepted in that window. The Bus Registry checks the anchorer's authority, the window's timing bounds and the record's form, not the identifiers or counts, so the chain establishes only that the commitment existed at the finalized block that includes it. The Bus Registry adds a hash of each Anchor to its Anchor tree, a Merkle tree against which other contracts check inclusion, and emits each Anchor as an event (Chapter 8). The ledger lane is the path on which a Publisher posts a sealed Message on chain as a series of contract events. Until ledger 9 is activated on mainnet, contract events should not be assumed live there, and neither should the Anchors or the ledger lane. Whether activation has happened since 28 September 2026 is unknown; `MPE-OPS-043` records the target network's ledger version and runtime `spec_version` when the Stage 0 exit review starts.

## The five layers

Figure 2.1 shows the five layers a protocol engineer touches. Wallets and dapps sit at the top. They hold keys and private state, assemble and prove transactions, and read the chain through the Indexer, which is, in the Foundation's definition, "a service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]. Midnight's Indexer follows finalized blocks, re-executes them and serves a GraphQL API, a query interface in which the client names the fields it wants returned. The node runs consensus and applies transactions to the ledger. Beneath it, the Cardano partner-chain machinery chooses the block producers and feeds Cardano observations into each block. At the bottom is the libp2p network that carries blocks, transactions and consensus votes between nodes.

{{fig:2-1}}

Contract events cross the figure indirectly. The node does not keep them; about 18 s after inclusion, once the block is final, the Indexer recomputes them by re-applying the block and serves them in the clear. No layer carries a private event or offers publish/subscribe to applications.

## Partner chain and consensus

Consensus settles two questions on which any posting to the chain depends: who may add the next block, and when a block can no longer be undone. Midnight is a partner chain of Cardano, based on the Polkadot SDK (Substrate) with the Partner Chains toolkit: it runs its own blocks and consensus but takes the choice of its block producers, and some of its inputs, from Cardano. Blocks are produced by Aura, a slot scheme in which committee members author in fixed turn. The slot is 6,000 ms, one committee member authors in each slot, and two thirds of the slot are allotted to assembling the block proposal.^[midnightntwrk/midnight-node, runtime/src/lib.rs, constant `SLOT_DURATION`; node/src/service.rs, `block_proposal_slot_portion`; main branch, accessed 1 October 2026.] Finality comes from GRANDPA, which runs in every full node with a gossip duration of 333 ms, although only the votes of the authorities, the committee members, count.^[midnightntwrk/midnight-node, node/src/service.rs, GRANDPA configuration field `gossip_duration`; main branch, accessed 1 October 2026.] Once more than two thirds of the authorities have voted for a block, that block and all its ancestors are final. BEEFY with a Merkle Mountain Range, an append-only Merkle structure, runs beside it to give bridges and light clients compact finality proofs, with a minimum block delta of 8.^[midnightntwrk/midnight-node, node/src/service.rs, BEEFY parameter `min_block_delta`; main branch, accessed 1 October 2026.] The code has no finality constant. MPS-0028 states that blocks usually finalize within about 3 blocks, or about 18 s, and later under stress.^[midnightntwrk/midnight-improvement-proposals, mps/mps-0028-pre-finality-state-visibility.md, problem statement; status Proposed; main branch, accessed 1 October 2026.]

BABE code is present, together with a pallet that would switch from Aura to BABE, but it is not active, and the proposal for the switch is Proposed.^[midnightntwrk/midnight-node, pallets/consensus-engine/src/lib.rs; midnightntwrk/midnight-improvement-proposals, mips/mip-0010-aura-to-babe-migration.md, status Proposed; main branch, accessed 1 October 2026.] Under BABE several validators can win one slot, "producing short-lived forks resolved by fork choice" [@midnight-mip-0010], so a reader that acted on an abandoned block would have to undo it. Midnight Express takes no value from an unfinalized block and so never has to roll one back (Chapter 8).

The committee is chosen each partner-chain epoch of 300 slots, which is 30 minutes at 6 s per slot. Selection uses the Ariadne algorithm, which mixes permissioned candidates and candidates registered from Cardano stake pools in a ratio set by the D-parameter.^[midnightntwrk/midnight-node, res/mainnet/chain-spec.json, `slotsPerEpoch`; midnightntwrk/partner-chains, toolkit/committee-selection/selection/src/ariadne_v2.rs; main branch, accessed 1 October 2026.] Mainnet sets 10 permissioned candidates and 0 registered ones.^[midnightntwrk/midnight-node, res/mainnet/system-parameters-config.json, `d_parameter`; main branch, accessed 1 October 2026.] Each block also carries inherent data, inputs that the block author inserts and every other node checks: the referenced main-chain block hash, observations of NIGHT held on Cardano, governance membership and bridge transfers.^[midnightntwrk/midnight-node, node/src/inherent_data.rs, `ProposalCIDP` and `VerifierCIDP`; main branch, accessed 1 October 2026.] Governance can also pause user transactions through a safe mode that deliberately does not whitelist the user transaction call.^[midnightntwrk/midnight-node, runtime/src/check_call_filter.rs, safe-mode and tx-pause filters; main branch, accessed 1 October 2026.] A posting reaches the chain only if a committee member puts it in a block, so any design that posts to the chain has the censorship resistance of a ten-member committee and inherits the chance that posting is paused.

## The node and its peer-to-peer layer

The node uses the libp2p backend of Substrate's networking crate; libp2p is a networking library assembled from separate protocols. The alternative litep2p backend is in the dependency tree but not selected.^[midnightntwrk/midnight-node, node/src/command.rs, `service::new_full::<sc_network::NetworkWorker<_, _>>`; main branch, accessed 1 October 2026.] The lockfile carries rust-libp2p 0.54.1 with TCP, WebSocket, DNS, Noise, Yamux, Kademlia and mDNS, and Yamux is patched to a Midnight branch.^[midnightntwrk/midnight-node, Cargo.lock, packages `libp2p` 0.54.1 and `yamux` 0.12.2; Cargo.toml, `[patch]` entry for `midnightntwrk/rust-yamux`; main branch, accessed 1 October 2026.] Mainnet bootnodes listen on WebSocket over TCP port 30333.^[midnightntwrk/midnight-node, res/mainnet/bootnodes-config.json; main branch, accessed 1 October 2026.]

The protocols on that network are Substrate's: block announcements, block and state sync, warp sync, the transactions protocol, and the GRANDPA and BEEFY notification protocols. Warp sync lets a new node reach a recent finalized state by checking a chain of finality proofs instead of replaying every block. Midnight adds one protocol of its own, a request-response protocol named `midnight-ledger-sync/2` that restores the ledger store after warp sync, with chunks of at most 1 MiB.^[midnightntwrk/midnight-node, node/src/warp_ledger_sync/protocol.rs, constants `PROTOCOL_NAME_SUFFIX` and `MAX_LEDGER_SYNC_CHUNK`; node/src/service.rs, `add_request_response_protocol`; main branch, accessed 1 October 2026.] Every protocol name embeds the genesis hash, so peer sets are scoped to one chain.

Publish/subscribe is a messaging pattern in which publishers send to a named channel and the network delivers each message to every subscriber of that channel. GossipSub is libp2p's publish/subscribe protocol: for each GossipSub topic, a peer forwards full messages to a small mesh of peers and tells some others only which messages it holds [@2020-vyzovitis-gossipsub]. Two absences in the node shape the design space. First, the node has no GossipSub and no floodsub, its predecessor; neither crate appears in the lockfile.^[midnightntwrk/midnight-node, Cargo.lock, no `libp2p-gossipsub` or `libp2p-floodsub` package; main branch, accessed 1 October 2026.] The only gossip is Substrate's gossip engine, `sc-network-gossip`, which the GRANDPA and BEEFY gadgets use with a validator per protocol and which no application can reach. Second, there is no plugin point. A new protocol has to be registered when the node's networking service is set up, so for the protocol to span the network every node operator must run a modified node binary, the route Chapter 6 evaluates as Option 3.

A protocol that runs beside the node brings its own libp2p stack, and the node's lack of GossipSub does not constrain it. Midnight Express takes this route. Its Bus Nodes, the relays of its overlay, run GossipSub with v1.2 behaviour (the v1.1 scoring and mesh rules plus IDONTWANT, a control message by which a peer asks its mesh peers not to send a message it already has) on rust-libp2p 0.57 with gossipsub 0.50, separate from the node's 0.54.1 (Chapter 8). The overlay divides its traffic into Shards, each one GossipSub topic. Scoping by genesis hash has a weaker counterpart there. Shard topics and request-response protocols are named `/mpe/<g>/1`, where `g` is the first eight bytes of the genesis hash in lowercase hexadecimal. Such a name is only a routing label and authenticates nothing, and two genesis hashes can share an eight-byte prefix, so admission binds the full genesis hash. Separate libp2p keys for a Bus Node avoid key reuse with the Midnight node on the same host, but they do not prevent co-location, addresses and traffic from linking the two processes.

An extrinsic is Substrate's name for anything a block carries from outside the chain's own logic. User transactions travel as bare (unsigned) extrinsics that call `send_mn_transaction` with the serialized Midnight transaction, and the runtime validates them through `ValidateUnsigned`.^[midnightntwrk/midnight-node, pallets/midnight/src/lib.rs, `send_mn_transaction` and `impl ValidateUnsigned for Pallet<T>`; main branch, accessed 1 October 2026.] The pool tags each transaction with its hash and a longevity of 600 blocks, about one hour. It sets no priority. The ordering therefore has no fee market, and a transaction cannot pay more to be included sooner. With no signer on the extrinsic, the node has no notion of a sender to throttle: its per-account throttle applies only to signed extrinsics, and only governance calls may be signed.^[midnightntwrk/midnight-node, pallets/midnight/src/lib.rs, `validate_unsigned` (`longevity(600)`, no priority); runtime/src/lib.rs, `pallet_throttle::Config`; runtime/src/check_call_filter.rs, signed governance calls; main branch, accessed 1 October 2026.]

The node also exposes the usual Substrate RPC subscriptions (finalized heads, storage changes, extrinsic status and GRANDPA and BEEFY justifications). None of them carries application messages or ledger events. MPS-0007 asks for ledger events to reach the node's event, RPC and subscription surface; it is Proposed and has no MIP [@midnight-mps-0007].

## The ledger

The ledger applies transactions to the state that consensus agrees on, and its cost model prices each of them.

### Shielded and unshielded state

The ledger 9 state holds a Zswap state for shielded coins (a commitment tree and a set of Zswap nullifiers), a map from contract address to contract state, an unshielded UTXO set (a UTXO, or unspent transaction output, is a coin record that can be spent exactly once), a DUST state, replay protection, and the treasury and reward pools.^[midnightntwrk/midnight-ledger, ledger/src/structure.rs, `struct LedgerState`; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.]

Shielded coins follow Zswap, a Zerocash-style scheme with multiple asset types and atomic swaps [@iog-zswap-zk-snark-based-non-interactive-multi-asset-swaps; @2014-bensasson-zerocash]. Three objects do the hiding. A coin commitment stands in for a coin and binds its contents without revealing them. A Pedersen value commitment hides an amount but still lets anyone check that a transaction balances. A Zswap nullifier is derived from a coin and a secret only its owner holds; publishing it marks the coin as spent, and a second spend would publish the same Zswap nullifier and be rejected. A Zswap output publishes a coin commitment, a Pedersen value commitment and optionally a ciphertext for the recipient, encrypted by Diffie-Hellman on the embedded curve with Poseidon, a hash function designed to be cheap inside proofs, used as a counter-mode cipher [@2024-midnight-zswap-spec]. An input publishes a Zswap nullifier, a value commitment and the Merkle root it proves against. An observer sees commitments, Zswap nullifiers and the net imbalance per token type, but not owners, individual values or which commitment a Zswap nullifier spends. The recipient finds a coin by trying to decrypt every output. Chapter 5 traces this recipient-ambiguity mechanism back to Bitmessage; its cost grows with the whole chain's output rate. Contract-initiated outputs carry no coin ciphertext at all. MIP-0011 therefore says that the returned coin information "is the recipient's only copy" and that callers "SHOULD deliver it out of band" [@midnight-mip-0011].

Unshielded outputs carry owner, value and token type in the clear and are spent with Schnorr signatures over secp256k1.^[midnightntwrk/midnight-ledger, ledger/src/structure.rs, `struct UtxoOutput`; base-crypto/src/schnorr.rs; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.]

A transaction is split into a guaranteed segment, which pays the fees and cannot fail, and fallible segments, which can fail one at a time and leave the transaction partially applied. A caller whose fallible segment fails has still paid the fee and loses that segment's events. A node validates a transaction and applies its guaranteed segment before it knows that the fee is paid, so the ledger caps that unpaid work, the time to dismiss, at the larger of 2 µs per transaction byte and 15 ms. A contract call enters a segment as its transcript, the public list of ledger operations the call performs, with their values, which every node re-runs. Checkpoints, VM operations that end one section of a transcript, let its sections go into different segments. A transcript without them goes wholly into one segment, chosen by the ledger code that constructs the transaction and not by the caller: the guaranteed segment if its modelled cost fits the time to dismiss less a per-transaction reserve, the fallible segment otherwise.^[midnightntwrk/midnight-ledger, ledger/src/construct.rs, segment partitioning of contract transcripts; ledger/src/structure.rs, `time_to_dismiss`; ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c; midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, `time_to_dismiss_per_byte` and `min_time_to_dismiss`; main branch, accessed 1 October 2026.]

On the ledger lane a Message travels as parts, each one `Misc` event with a 256-byte payload. A sixteen-part call is about 12,920 B (estimated: 7,280 B of proofs, about 306 B per part and about 744 B for the rest of the transaction), so its time to dismiss is 2 µs × 12,920 ≈ 25.8 ms before the reserve. Simulator gas, the compute and read time that the Compact simulator models for a transcript, puts the call at about 27.6 ms. Its transcript, events included, therefore lands in the fallible segment. A Bus Registry registration (the transaction that records a new membership) and an Anchor post (the transaction that writes one Anchor) also exceed their budgets (derived; Chapter 10).

Contract state is public. Compact's model separates a public ledger state, agreed on chain, from private state that each user holds locally, and transitions are proven in zero knowledge against both. This is the Kachina model of private smart contracts [@iog-kachina-foundations-of-private-smart-contracts]. A contract call publishes the contract address, the entry point, its transcript, its declared effects and a proof. The caller's identity is not part of it, because there is no signer. Whatever reveals the caller is in the payload or in the fee inputs.

Compact 0.35.0 adds `kernel.caller()`, which for a top-level call names the user who owns every unshielded input of the intent (the part of a transaction that groups contract calls with their coin transfers and DUST spends). A top-level user call that reads it fails. The wallet adds those inputs when it balances the transaction, after the proof is generated, so the transcript records that `kernel.caller()` returned nothing. The ledger re-runs the transcript on the balanced transaction and reads the user who owns those inputs; when they all belong to one user, the recorded value and the ledger's value differ, and the call fails on that mismatch. The release notes advise reading `kernel.caller()` only where the caller is known to be a contract.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, section "The caller of a circuit is available to the circuit"; main branch, accessed 1 October 2026.] A contract that needs an authority, such as a steward or an anchorer, therefore checks in circuit that the caller knows a secret whose hash is in contract state.

### NIGHT, DUST and fees

NIGHT is the native token. It exists on Cardano as cNIGHT, which the node observes through an inherent, and on Midnight as an unshielded token. Holding NIGHT generates DUST, the resource that pays fees. DUST is shielded and non-transferable; in MIP-0018's words, "DUST is not a token" [@midnight-mip-0018]. Its value grows towards a cap while the backing NIGHT is unspent and decays to zero after it is spent.^[midnightntwrk/midnight-docs, docs/concepts/dust-architecture.mdx, section "Shielded and non-transferable"; main branch, accessed 1 October 2026.] The mainnet parameters set the cap at 5 DUST per NIGHT (`night_dust_ratio` 5,000,000,000 Specks per Star, with 10^15 Specks to a DUST and 10^6 Stars to a NIGHT), a generation rate of 8,267 Specks per Star per second, and a grace period of 10,800 s.^[midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, object `dust`; midnightntwrk/midnight-docs, docs/concepts/dust-architecture.mdx, `STARS_PER_NIGHT` and `SPECKS_PER_DUST`; main branch, accessed 1 October 2026.] Dividing the cap by the rate gives about 604,800 s, one week, to fill an unspent UTXO from empty (derived). One NIGHT generates 8,267 × 10^6 Specks per second, about 0.714 DUST per day (8.267 × 10^-6 × 86,400, derived).

A fee is paid by a `DustSpend` inside the transaction, which carries a public fee value, a DUST nullifier, a new commitment and a proof.^[midnightntwrk/midnight-ledger, ledger/src/dust.rs, `struct DustSpend`; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.] No path in the ledger 9 code credits the fee to a block producer, the treasury or a pool, so fees are burned. Block rewards exist in the ledger state, but the node's reward hook returns zero.^[midnightntwrk/midnight-ledger, ledger/src/semantics.rs, handling of the `DustSpend` fee value; ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c; midnightntwrk/midnight-node, runtime/src/lib.rs, `LedgerBlockReward`; main branch, accessed 1 October 2026.]

Three facts follow for Midnight Express. DUST cannot pay a Bus Operator, the party that runs Bus Nodes, because it cannot be transferred. Nor can it be paid to a contract, so a Bus Registry cannot charge or even observe a registration price in DUST; the only price of a registration is the network fee of its transaction, and a price set by the Bus Registry would need NIGHT or another token. And nothing in the protocol pays Indexer, RPC or proof-server operators. MPS-0004 leaves payment of proof servers as an open question [@midnight-mps-0004]. Payment of Bus Operators is decision `DEC-001` (Chapter 7). Bonds in Midnight Express are Bus Registry contract balances and have no relation to the planned NIGHT staking of MIP-0016 (a Draft), under which stake is liquid and "carries no consensus weight" [@midnight-mip-0016].

The cost model prices five dimensions against per-block limits: read time, compute time, block usage in bytes, persistent bytes written and temporary bytes churned. Each term is the transaction's use of a dimension as a fraction of its per-block limit, times a dimension factor, and the fee is

```
fee = overall price × (max(read, compute, block usage) + write + churn)
```

so a transaction pays only for whichever of read time, compute time and block bytes it uses up fastest, plus its write and churn terms.^[midnightntwrk/midnight-ledger, spec/cost-model.md, fee formula (`utilization_cost + write_cost + churn_cost`); base-crypto/src/cost_model.rs; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.] The write term counts net bytes. The model subtracts bytes deleted from bytes written and counts the rest of the written bytes as churn.^[midnightntwrk/midnight-ledger, base-crypto/src/cost_model.rs, conversion from `RunningCost` to `SyntheticCost` ("net bytes written"); ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c, accessed 1 October 2026.] A transaction that writes 300 bytes and deletes 100 thus pays the write price for 200 net bytes and the churn price for the other 100.

The node's mainnet parameter file sets per-block limits of 1,000,000 B of block usage, 50,000 B of net persistent writes, 50,000,000 B of churn and 2 s each of read and compute time. One transaction may be at most 1,048,576 B.^[midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, `limits.block_limits` and `limits.transaction_byte_limit`; main branch, accessed 1 October 2026.] The ledger's own initial limits differ: 200,000 B of block usage and 1,000,000 B of churn, with the same 50,000 B of writes.^[midnightntwrk/midnight-ledger, ledger/src/structure.rs, constant `INITIAL_LIMITS`; ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c, and branch `ledger-8`, accessed 1 October 2026.] Which block-usage value is live on a ledger 9 network is unknown. `MPE-PRF-040` requires the ledger-lane ceiling to be measured under both values on a running ledger 9 chain.

Separately, the runtime caps a block at 1 MiB of encoded length, and 75 percent of that (786,432 B) is available to ordinary calls. User transactions are ordinary calls, because `send_mn_transaction` declares no dispatch class, so none can exceed 786,432 B.^[midnightntwrk/midnight-node, runtime/src/lib.rs, `BlockLength` and `NORMAL_DISPATCH_RATIO`; pallets/midnight/src/lib.rs, weight of `send_mn_transaction` (no `DispatchClass`); main branch, accessed 1 October 2026.] If encoded length and block usage count about the same bytes, which has not been measured, the capacities below that assume 1,000,000 B are about a fifth too high (786,432 / 1,000,000 ≈ 0.79, derived).

Prices move every block towards 50 percent fullness, by at most about 4.6 percent per block: a block more than half full in a dimension raises that dimension's price, and one less than half full lowers it. The genesis overall price is 10.0 and all dimension factors are 1.0.^[midnightntwrk/midnight-ledger, base-crypto/src/cost_model.rs, `price_adjustment_function`; ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c; midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, overall price and dimension factors; main branch, accessed 1 October 2026.] At those values a transmitted byte costs 10 / 1,000,000 = 0.00001 DUST, or 0.01 DUST per kilobyte. A byte kept in contract state costs 10 / 50,000 = 0.0002 DUST, twenty times as much, and a churned byte costs 10 / 50,000,000 = 0.0000002 DUST. A millisecond of compute or read time costs 0.005 DUST (derived; live prices differ). Wallets pay with a margin of five blocks of price movement, a factor of 1.2519, which is five of the largest rises in a row (1.046^5 ≈ 1.252). There is no state rent, and nothing prunes contract state. A byte written into a contract stays there and is paid for once.

The ledger interface contracts of Chapter 10, a Bus Registry, a ledger-lane contract and a consuming contract, are exploratory Compact code that has been compiled but is not final, and the design does not depend on their exact form. Their fees are derived from the cost model at genesis prices and the mainnet limits, including 1,000,000 B of block usage, with circuit sizes from the compiler's circuit model and gas from the Compact simulator. Nothing was run on a Midnight network, no transaction was submitted and no fee was observed. A Bus Registry registration comes to about 8.7 KB of block usage and 0.246 DUST (0.308 DUST with the wallet margin). An Anchor post costs 0.195 DUST (0.244 DUST), so one Anchor per 60 s costs about 280.8 DUST per day. Generating that much needs about 393 NIGHT (derived: 1,440 × 0.195 = 280.8 DUST per day; 280.8 / 0.714 DUST per NIGHT per day = 393), assuming generation runs at the full rate while the balance stays below the cap. The 0.195 DUST per Anchor assumes no net state growth; each retained Anchor-tree root adds about 32 B, about 0.006 DUST per Anchor or about 9 DUST per day (derived: 32 × 0.0002; 1,440 × 0.0064), until a reset rule bounds the tree. One `Misc` part in its own transaction costs 0.129 DUST (0.161). Sixteen parts cost 0.188 DUST (0.236) in one call but 0.866 DUST (1.084) as sixteen separate calls, because every call adds its own proof and block bytes. These sizes and fees use 4,368 B for every contract proof, an upper bound for the ledger lane; with the modelled 2,800 B the sixteen-call shape is about 55,170 B and 0.62 DUST instead of 80,260 B and 0.866 DUST (derived: 80,260 − 16 × 1,568; 0.552 + 0.045 + 0.018), and the one-call shapes keep their compute-bound fees. With that block-usage limit, compute dominates every one of these fees except the separate calls, where block usage dominates. At 200,000 B, block usage would dominate all of them, and a registration's block term alone would be 8,670 × 10 / 200,000 = 0.434 DUST (derived).

## Compact and the proofs

A Compact circuit runs on the user's machine, takes private inputs from *witnesses* (TypeScript callbacks that read local private state), and produces a public transcript and a proof. The compiler tracks every value derived from a witness. It rejects the program if such a value reaches a ledger write, an exported circuit's return value or a branch that affects either, unless the code marks the flow with `disclose()`.^[LFDT-Minokawa/compact, doc/compact-reference.mdx, section "Explicit disclosure"; compiler/analysis-passes/track-witness-data.ss; main branch, accessed 1 October 2026.] So a circuit that reads a bid from a witness and writes it to a ledger field is rejected. With the bid wrapped in `disclose()` it compiles, and the write places the bid in the public transcript. `disclose()` is a permission marker and does not publish anything by itself.^[LFDT-Minokawa/compact, doc/explicit-disclosure.mdx ("Placing a `disclose()` wrapper does not cause disclosure in itself"); main branch, accessed 1 October 2026.] Privacy in a Compact contract is therefore explicit and checked at compile time: a value is private only because it was never disclosed, and Compact applies no encryption to it on chain.

The virtual machine that applies transcripts, the Impact VM, has stack, map, arithmetic, checkpoint and `log` operations and no input or output. A contract cannot call out to a network or read anything but ledger state. Since Compact 0.33 a contract can call another contract's circuits, but only if the callee has no witnesses.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.33.0.md, section "Runtime support for cross-contract calls"; main branch, accessed 1 October 2026.]

The proof system is PLONK with KZG commitments over BLS12-381, with JubJub, a curve whose arithmetic is cheap inside these circuits, as the embedded curve.^[midnightntwrk/midnight-zk, README.md, repository structure (`curves`, `proofs`); main branch, accessed 1 October 2026.] Zswap input and output proofs are 4,832 B each and a DUST spend proof is 2,912 B. The ledger estimates a contract call proof at 4,832 B when it sizes an unproven transaction.^[midnightntwrk/midnight-ledger, zswap/src/structure.rs, constants `INPUT_PROOF_SIZE` and `OUTPUT_PROOF_SIZE`; ledger/src/dust.rs, `DUST_SPEND_PROOF_SIZE`; ledger/src/structure.rs, `PROOF_SIZE`; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.] The compiler's cost model gives proofs of 2,800 B or 4,368 B and verifying keys of 1,351 B or 2,119 B: 2,800 B for `activateParams`, `anchorRootValid`, `prunePeriod` and the four ledger-lane circuits, 4,368 B for the other Bus Registry circuits and the consumer's `react`. The genesis cost model charges about 3.27 ms per proof verification plus about 4.56 µs per public input, and validation compute is discounted by a parallelism factor of 4.^[midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, `proof_verify_constant`, `proof_verify_coeff_size` and `parallelism_factor`; main branch, accessed 1 October 2026.] A transaction that carries one contract call and pays its fee therefore needs two proofs, 5,712 to 7,744 B before any transcript or payload (2,912 + 2,800, 2,912 + 4,368 and 2,912 + 4,832, derived). Proving is slow on user hardware. MPS-0004 records about 190 ms for a Zswap spend proof on a 32-core server and 5 to 30 s on a consumer laptop, and the tutorials warn that a transaction can take over a minute while the proof server works.^[midnightntwrk/midnight-improvement-proposals, mps/mps-0004-trusted-proof-serving.md, problem statement; status Proposed; midnightntwrk/midnight-docs, docs/tutorials/zk-loan/cli.mdx; main branch, accessed 1 October 2026.] Wallets usually delegate proving to a separate proof server over HTTP, which sees the witnesses it is asked to prove.

The compiled contracts show where the size of a circuit comes from. They were compiled with toolchain 0.35.0 (language 0.27.0, runtime 0.20.0), which uses ledger 9.1.0.0-rc.3, and sized with the ZKIR circuit model; no proof was generated. A circuit is laid out as a table of 2^k rows. A circuit of 166,241 rows does not fit in 2^17 = 131,072 but fits in 2^18 = 262,144, so it needs k = 18, and each step in k doubles the table the prover must fill. The model also reserves rows for blinding values, lookup tables and public inputs, so a small circuit can need a larger k than its counted rows suggest.^[midnightntwrk/midnight-zk, proofs/src/dev/cost_model.rs, `min_k`; main branch, accessed 1 October 2026.] Compact packs a `Bytes<n>` value into field elements of at most 31 bytes each. Every operation that needs individual bytes (a spread, an index, a cast from `Uint` to `Bytes`, or the encoding of an `emit` payload that is not a constant) therefore adds an internal division step of about 670 rows. Emitting a constant 256-byte payload needs no such step and costs 23 rows, yet needs k = 6. Emitting a 256-byte circuit argument needs 247 steps, about one per byte, and 247 × 670 ≈ 165,500 rows is nearly all of its 166,241 rows (k = 18, derived). The rows grow with the number of parts: four in one call need 663,950 rows (k = 20) and sixteen about 2.65 million (about k = 22, from the circuit model alone; no keys were generated).

A consuming contract meets the same cost when it hashes. An Anchor's window root is a SHA-256 Merkle tree over MPE Envelope identifiers, so a contract that checks a Message's Anchor inclusion must recompute in circuit the SHA-256 path from the Message's identifier to an Anchor. Three chained SHA-256 hashes cost 133,922 rows (k = 18) when the preimage is formed by byte concatenation and 12,674 rows (k = 14) when it is a struct of `Bytes` fields, with identical digests. In the Compact simulator, `persistentHash` over such a struct is plain SHA-256 of the concatenated bytes. A contract can therefore check SHA-256 Merkle paths if its preimages are structs, and the consuming contract's 19 SHA-256 evaluations then need 77,905 rows (k = 17) instead of 703,378 (k = 20). The verifier side does not grow with the circuit; the prover side does. The k = 18 proving keys are 67 to 76 MB, and key generation for one ledger-lane part took 264 s and 1.8 GB of memory. Proving time for these circuits was not measured.

The language has further limits that bind any contract-side design. A contract can compare the block time with a value (`blockTimeLt`, `blockTimeGte`) but cannot read it, and each comparison puts its operand in the public transcript.^[LFDT-Minokawa/compact, doc/api/CompactStandardLibrary/exports.md, `blockTimeLt` and `blockTimeGte`; main branch, accessed 1 October 2026.] A circuit cannot read the root of its own Merkle tree, because `root()` is callable only from TypeScript. Nor can a contract bound the age of a root: a historic Merkle tree, which keeps accepting proofs made against earlier roots, accepts every past root until its history is reset.^[LFDT-Minokawa/compact, doc/ledger-adt.mdx, MerkleTree `root` ("callable only from TypeScript") and HistoricMerkleTree `checkRoot`; main branch, accessed 1 October 2026.] A rule such as "accept only roots from the last hour" must be enforced outside the contract. Compact has no division, modulo or bitwise operators and cannot iterate over ledger collections. `transientHash` is "not guaranteed to persist between upgrades", unlike `persistentHash`.^[LFDT-Minokawa/compact, doc/api/CompactStandardLibrary/exports.md, `transientHash` and `persistentHash`; main branch, accessed 1 October 2026.] Ed25519 verification, added in 0.35.0, requires the `--feature-zkir-v3` flag.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, section "High-level summary"; main branch, accessed 1 October 2026.] Compiled with 0.31.1, the ledger 8 toolchain, the Bus Registry and the ledger-lane contract fail only on `emit` (`unbound identifier emit`), and the consuming contract fails because the ledger 8 cross-contract model needs the callee's compiled contract information.

## Indexer, wallet and dapp connector

Wallets and dapps read the chain through the Indexer, and a browser dapp reaches the user's wallet through the dapp connector.

### The Indexer

The node keeps blocks and state, not history in a form applications can query; the Indexer supplies that. Its chain-indexer, the single writer, subscribes to the node for finalized blocks only, applies each block to its own copy of the ledger, checks the resulting Merkle roots against the node's, and writes blocks, transactions and ledger state to PostgreSQL or SQLite.^[midnightntwrk/midnight-indexer, docs/architecture.md, section "Data flow"; chain-indexer/src/infra/subxt_node.rs, `subscribe_finalized_blocks`; main branch, version 4.4.0-rc.5, accessed 1 October 2026.] Because it re-executes, it can recover the ledger events that the node throws away. Its ledger 8 adapter drops contract logs; its ledger 9 adapter maps them, including `Misc` events.^[midnightntwrk/midnight-indexer, indexer-common/src/domain/ledger/ledger_state.rs, handling of `ContractLog` in the ledger 8 and ledger 9 adapters; main branch, version 4.4.0-rc.5, accessed 1 October 2026.] An Indexer API serves GraphQL queries and WebSocket subscriptions (API v4). A NATS bus, or an in-memory bus in standalone mode, carries only small signals that tell the API new data exists.

The subscriptions that matter here are `contractEvents` (by contract address, marked beta), `zswapLedgerEvents` and `dustLedgerEvents` (global streams of every shielded event), `unshieldedTransactions` (by address), `shieldedTransactions` (by session, after the client has handed over a viewing key, which finds and reads the wallet's shielded transactions but cannot spend) and subscriptions by Zswap nullifier prefix. Each of them tells the Indexer operator something about the client, except the global streams and the prefix queries, which were designed to leak little: a short prefix matches the Zswap nullifiers of many wallets. The default API configuration allows 20 subscriptions per WebSocket connection and drains 20 rows per batch.^[midnightntwrk/midnight-indexer, indexer-api/config.yaml, subscription and connection limits; main branch, version 4.4.0-rc.5, accessed 1 October 2026.] Each deployed environment runs its public Indexer as two instances behind one host name. Anyone can run their own, and standalone mode makes that cheap.

### The wallet

The current wallet SDK syncs shielded coins without giving the Indexer its keys. It subscribes to the global `zswapLedgerEvents` stream and trial-decrypts every Zswap event locally.^[midnightntwrk/midnight-wallet, packages/shielded-wallet/src/v1/Sync.ts, subscription `zswapLedgerEvents`; main branch, accessed 1 October 2026.] The older path, in which the Indexer holds the viewing key and does the trial decryption itself, still exists in the Indexer API; MPS-0043 notes that "the indexer already accepts this key to filter a wallet's transactions" [@midnight-mps-0043]. The first path costs the wallet a decryption attempt for every event. The second saves that work by letting the Indexer operator see the wallet's transactions. The DUST wallet uses `dustLedgerEvents` and the unshielded wallet queries by its own address. The wallet SDK's sync code does not consume contract events.

### The dapp connector

A browser dapp reaches the user's wallet through the dapp connector API. It can read balances and addresses, ask the wallet to balance and submit a transaction, sign data, obtain a proving provider and read the wallet's configuration, which includes the Indexer and node URIs.^[midnightntwrk/midnight-dapp-connector-api, src/api.ts, interface `WalletConnectedAPI` and type `Configuration`; main branch, accessed 1 October 2026.] There is no event or subscription method. A dapp that wants events opens its own connection to the Indexer, usually through the midnight-js `PublicDataProvider`, which exposes `queryContractEvents` and `contractEventsObservable`, resumable from an event identifier or a block.^[midnightntwrk/midnight-js, packages/types/src/public-data-provider.ts, `contractEventsObservable`; main branch, version 5.0.0-rc.3, accessed 1 October 2026.]

## What the chain offers for events

Ledger 9 has three kinds of record called events, and only one of them carries data a contract chooses. The node's pallet emits Substrate events such as `ContractCall`, `TxApplied` and `UnshieldedTokens`, which carry transaction hashes and addresses but no contract data. The ledger produces `EventDetails` while it applies a transaction: Zswap inputs and outputs, contract deployments, DUST events and contract logs. And Compact exposes the contract log to programmers as `emit`. Only the last is an event in the Foundation's sense.

The Foundation's event documents have different standing. MIP-0002, which connects `emit` to the ledger and the Indexer, is the only one Accepted [@midnight-mip-0002]. CoIP-0003, which specifies `emit`, is a Draft, although it describes a facility released in language 0.25 [@midnight-coip-0003]. These two match the shipped compiler and Indexer, and the text follows them wherever another document differs. The rest are Proposed: MPS-0005, the events problem statement, which predates the current proposal process [@midnight-mps-0005]; MIP-0018 (token metadata events); MIP-0019 (multipart events); MPS-0007 (node-side event visibility); and MPS-0028 (pre-finality visibility).

MPS-0005 differs from MIP-0002 and CoIP-0003 in three places on Phase 1 events. It names `event` and `public` keywords, and Compact implements neither. It says no protocol changes are required, whereas MIP-0002 bumps the `EventDetails` serialization tag and calls the change "effectively a hard fork". And it lists new base and data fees, where MIP-0002 states that "no new fee metering is needed", because `Log` gas already has a base and a per-byte part.

A Compact program emits an event with `emit(e)`, where `e` must be one of the standard event structs. Emitting any other type is a static error, and so is emitting from the constructor.^[LFDT-Minokawa/compact, doc/compact-reference.mdx, section "Emitting events"; main branch, accessed 1 October 2026.] Ten of the standard structs describe token movements and pausing. The only one for application data is `Misc`, with tag 10, a 32-byte `name` and a 256-byte `payload`: 288 bytes of struct data.^[LFDT-Minokawa/compact, compiler/midnight-events.ss, `(declare-event-type Misc 10 288 ...)`; main branch, accessed 1 October 2026.] Serialized, a `Misc` event is larger. MIP-0002 gives about 40 bytes of `VersionedLogItem` overhead per event, which puts a `Misc` event at about 328 B (288 + 40, derived); its exact serialized size on a ledger 9 network has not been measured. MIP-0018 makes the name carry the layout version: lowercase, colon-separated, with a bracketed version and NUL padding to 32 bytes, as in `mip-0018:token-metadata[v1]` [@midnight-mip-0018]. Midnight Express follows that convention and names its Anchors and ledger-lane parts `mip-xxxx:anchor[v1]` and `mip-xxxx:envelope[v1]`, where `xxxx` is the proposal's number once the editors assign it.

The compiler treats `emit` as a disclosure site. Every field must already be disclosed, so an event can carry nothing the transaction does not already make public.^[LFDT-Minokawa/compact, compiler/analysis-passes/track-witness-data.ss, case `emit` ("performing this emit operation"); coips/coip-0003.md, Rationale ("Why disclosure enforcement?"); main branch, accessed 1 October 2026.] CoIP-0003 says that emitting private data "is a different problem with different tradeoffs (encryption, topic-based filtering, recipient key management)" and leaves it out of scope [@midnight-coip-0003]. Proving an `emit` costs one public input per 31 payload bytes, paid even when the branch that emits is not taken [@midnight-coip-0003].

The compiler lowers `emit` to the VM's `log` instruction with a three-field value: version 1, the event tag and the encoded struct. The VM accepts a log argument of up to 512 KiB (`MAX_LOG_SIZE`). It decodes the value as a `VersionedLogItem`, and if the data exceeds `MAX_LOG_EMITTED`, 1 KiB, it drops the event without error. The source calls this the limit "over which `log` events are silently swallowed".^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, constants `MAX_LOG_SIZE` and `MAX_LOG_EMITTED`, function `decode_event`; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.] The call that emitted an oversized event still succeeds, and no reader ever receives the event. Because the 1 KiB is measured over the serialized storage nodes, including a 32-byte hash per node, it is not 1,024 bytes of payload. MIP-0002 caps a single event at "1 KB serialized" and uncompressed, and CoIP-0003 states the same 1 KB limit at the language level, about double the largest standard event (`ShieldedReceive`, 578 B) [@midnight-mip-0002; @midnight-coip-0003]. The Compact compiler's own maximum event size is 512 KiB, set to match `MAX_LOG_SIZE`, so the ledger is the layer that enforces the 1 KiB.^[LFDT-Minokawa/compact, compiler/events.ss, `max-emit-size` ("Must match MAX_LOG_SIZE"); main branch, accessed 1 October 2026.] With the standard structs, the binding limit in practice is the 256-byte `Misc` payload.

MIP-0019 defines how to concatenate several `Misc` events into one longer message and is Proposed. All parts must sit in one execution phase of one physical intent, because events in a fallible phase that fails are discarded; a phase in MIP-0019 is a segment in the sense above. MIP-0019 recommends the guaranteed phase but allows the fallible phase, provided the caller confirms inclusion and the success of that phase [@midnight-mip-0019]. Large transcripts leave the guaranteed segment, so the ledger lane of Midnight Express places all parts of a Message in one phase of one intent, not necessarily the guaranteed one.

A log costs gas, and the ledger 9 code counts its whole size as both written and deleted, so the cost model treats it as churn rather than net persistent growth: an event of about 328 B adds no net writes and about 328 B of churn.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, gas of the `log` operation (`bytes_written: size`, `bytes_deleted: size`); ledger 9 source, version 9.1.0.0-rc.4, commit 9a8777c, accessed 1 October 2026.] MIP-0002 states the same metering ("counted as churn") and gives the shared per-block budgets as 50 KB of `bytes_written` and 1 MB of churn. Yet it also says that events "compete with state writes for the shared per-block `bytes_written` budget (50 KB)" and sizes event capacity against that budget [@midnight-mip-0002].

The two readings differ in what an event costs and in which budget caps how many fit. Under the churn reading, which the code implements and the fees above use, an event at genesis weights costs about as much per byte as the transaction bytes that carry it and twenty times less than bytes written into contract state, and block usage caps capacity at whichever of its two values is live. Under the `bytes_written` reading, which MIP-0002's capacity figures use, an event byte is priced like a byte of contract state, and the 50,000 B write budget caps capacity.

Midnight Express seals each Message into an MPE Envelope of one of four size classes, numbered 0 to 3, and on the ledger lane a sealed body of class c travels as 4^c parts (Chapter 8): a class-1 Message is four parts and a class-2 Message sixteen. Under the `bytes_written` reading a part takes about 328 B, so the budget admits about 152 parts per block. That is about 38 class-1 Messages (50,000 / 1,312) or 9 class-2 Messages (50,000 / 5,248) per block: about 6.3 class-1 Messages per second under MIP-0002's `bytes_written` sizing (3.5 if `block_usage` is 200,000 B) and 1.5 class-2 Messages per second, for the whole chain with no other writers (derived). Under the churn reading block usage sets the count. With the same 744 B for the rest of the transaction, a class-0 call is about 8,330 B (7,280 + 306 + 744) and a class-1 call about 9,248 B (7,280 + 4 × 306 + 744), so 200,000 B of block usage holds about 24 class-0, 21 class-1 or 15 sixteen-part calls per block, and 1,000,000 B about 120, 108 and 77 (derived, with 4,368 B contract proofs, an upper bound). Planning uses the lowest figure for each class: about 4.0 class-0, 3.5 class-1 and 1.5 class-2 Messages per second for the whole chain with no other writers, and 0.40, 0.35 and 0.15 inside a 10 percent share (`P-ECO-8`). `MPE-PRF-040` requires a measurement on a ledger 9 network of which reading and which block-usage value hold.

Events reach readers by a route that bypasses the node. The node's interface to the ledger, which MPS-0007 calls the ledger bridge, returns a state root, the transaction hash, the touched addresses and the UTXO deltas, and discards the ledger events.^[midnightntwrk/midnight-node, ledger/src/ledger_9/mod.rs, construction of `TransactionAppliedStateRoot`; main branch, accessed 1 October 2026.] MIP-0002 states that "events are not consensus state" and leaves retention to downstream systems.^[midnightntwrk/midnight-improvement-proposals, mips/mip-0002-public-contract-log-emission.md, status Accepted, section "Event Lifetime"; main branch, accessed 1 October 2026.] It also states that events "represent the contract author's claim about what happened, not independently verifiable facts" [@midnight-mip-0002], and MPS-0043 adds that a public event is authenticated to the contract and entry point that emitted it, "not to the user who triggered the call" [@midnight-mps-0043].

The Indexer recovers events by re-execution and serves them through `contractEvents`. The shipped filter requires a contract address and accepts optional event `types`, `fieldPrefixes`, `fromBlock`, `toBlock` and `transactionHash`; MIP-0002's single `eventType` field is not what shipped.^[midnightntwrk/midnight-indexer, indexer-api/graphql/schema-v4.graphql, input `ContractEventFilter` and type `MiscContractEvent`; main branch, version 4.4.0-rc.5, accessed 1 October 2026.] Prefix filters work only for the standard token events, and MIP-0002 calls them a way for the dapp to "choose the level of disclosure at the cost of the data returned". `Misc` has no indexed fields unless indexing is "configured by policy" [@midnight-mip-0002], and no shipped filter selects by `name` or `payload`. A client that wants one `name` receives every `Misc` event of the contract and discards the rest itself.

Events are ordered by an identifier the Indexer assigns, which grows monotonically, and within a transaction by emission order. Delivery across reconnects is at least once, and midnight-js tells consumers to deduplicate by identifier.^[midnightntwrk/midnight-js, packages/types/src/public-data-provider.ts, documentation of `contractEventsObservable` ("Delivery is at-least-once"); main branch, version 5.0.0-rc.3, accessed 1 October 2026.] Because the Indexer reads only finalized blocks, an event is never retracted, and it cannot be read through the Indexer before finality, about 18 s after inclusion, plus indexing time. The transcript that holds it is public from the moment its block is seen, so observers of included but unfinalized blocks can read it earlier. MIP-0018 requires consumers to "verify indexer-supplied metadata against authenticated on-chain data before treating it as authoritative" [@midnight-mip-0018]. Node-side event visibility (MPS-0007) would let a reader do that without trusting one Indexer, but Midnight Express does not depend on it.

Midnight therefore gives a design for events a public, ordered, final, at-least-once broadcast channel of 256-byte payloads, scoped to a contract, paid for in DUST and asserted by the contract author. Midnight Express uses that channel for exactly the traffic it suits: Anchors, Bus Registry membership changes and the ledger lane (Chapter 8). Because events are not consensus state, it keeps Anchors as records in Bus Registry state, checks there the anchorer's authority and each record's form, and treats the `Misc` copy of an Anchor only as a notification.

## What the chain lacks

Midnight has no publish/subscribe layer for applications. The Indexer's subscriptions come closest, but they are a read API over one operator's database: the operator sees which contract or address each client watches, and nothing is delivered until a block is final.

Midnight has no private event primitive yet. MPS-0005 plans private events as Phase 2: `@private` field annotations, `@topic` annotations for filtering, client SDK encryption and decryption, `encrypt_for` for encrypted delivery, `proven` blocks for commitment binding, an Indexer topics column with "wallet-specific decryption with session isolation", and an encryption fee [@midnight-mps-0005]. MPS-0005 says that Phase 2 "is scoped in Part 2 of this document", and Part 2 was not published as of 1 October 2026. The key types, the encryption scheme, the topic derivation, the size limit and what the filtering Indexer learns are therefore unknown until Part 2 is published. A private event will still be a contract event, produced by a proved transaction and authenticated to the contract and entry point that emitted it.

Until then every emitted field is public by construction. A contract that wants to hide event content today can only emit ciphertext it computed itself in a `Misc` payload. That hides the plaintext but, as MIP-0019 notes, not the contract, entry point, transaction, time or size [@midnight-mip-0019; @midnight-mps-0043]. Every reader can list every ciphertext for the contract, and every recipient must trial-decrypt all of them. MPS-0005 calls this the scanning problem: "Fully encrypted events without metadata force wallets to download and trial-decrypt every event on chain." It is the Zswap recipient-discovery cost again, now capped at 256 B per part and emitted inside proven transactions, whose overhead several parts can share while each logged byte pays `Log` gas.

Midnight Express does not supply this primitive. It is a complement to on-chain private events and, under conditions stated in Chapter 4, a transport for them: a Message can be a *carried event*, whose payload is the unchanged bytes of a contract event, public or private, together with the hash of the transaction that recorded it and its position there, which locate the event on chain. Midnight Express is not an alternative to on-chain private events and does not replace MPS-0005 Part 2. The Foundation's own documents ask for an off-chain channel of this kind. MIP-0011 asks callers to deliver coin information out of band, and MPS-0043 assigns "choosing how the data travels" for confidential data to a pending problem statement, Confidential Contract Notifications (PR #271), whose text is not published [@midnight-mps-0043]. Where discovery and recovery must work from chain data alone, as in the custody inbox of MIP-0012, an off-chain channel is not a substitute [@midnight-mip-0012].

Contracts cannot consume events. No on-chain primitive reads an event or subscribes to one, and events are not stored in contract or ledger state. A contract learns that something happened only when an off-chain party submits a transaction that calls it, and such a transaction can prove facts about an off-chain Message against contract state. The exploratory consuming contract of Chapter 10 proves that an MPE Envelope identifier is covered by an Anchor through a witness-free cross-contract read of the Bus Registry's Anchor tree, so a reaction carries two contract calls and two proofs. Inclusion alone gives no authority. The contract records a consumption nullifier, a value derived from a secret of the Message, and refuses one it has already recorded, so that one Message cannot make it act twice. Nothing in the circuit checks, however, that the secret, which the caller supplies privately, belongs to the included Message, so a caller with one inclusion proof could supply several secrets and make the contract act several times. A Publisher signature checked in circuit binds the secret to a signed instruction (Chapter 8), and that signature circuit has not been compiled. Even then the contract learns who authorized the instruction, not that the overlay admitted or anchored the Message: proving that by a deadline needs a binding between the signed statement and the anchored Envelope that version 1 does not specify.

Midnight has no per-sender rate limit and no way to pay infrastructure: transactions have no signer, the pool has no priority, and DUST cannot be transferred or paid to a contract. A design that needs per-sender quotas on the ledger must enforce them in contract logic. Midnight Express enforces its overlay quotas off chain instead, with admission nullifiers. Each MPE Envelope carries one, derived from the Publisher's admission secret together with the genesis hash, the Bus Registry address, the admission window, the size class and a counter, and it marks one use of the membership's allowance; Bus Nodes refuse a repeated one and count the rest against the membership's quota (Chapter 8). A Bus Node counts only the MPE Envelopes that reach it, so Bus Nodes acting alone cannot enforce a network-wide quota; whether that gap matters at the load of Chapter 7 is a hypothesis the proof of concept must test (Chapter 9). Paid Bus Operators would have to be paid in NIGHT or by some other mechanism.

## Limits that bind any event design

Table 2.1 lists the Midnight limits that any design using Midnight to carry contract events or Messages must respect. "Node main" is midnight-node at commit 887348f9 (runtime spec version 3,000,000), which pins ledger 9.1.0.0-rc.5. "Mainnet parameters" are the genesis values in that node's mainnet configuration, which governance can change. The ledger can carry a few hundred bytes per message, publicly, at block and finality pace, for the price of a proven transaction whose prover cost grows with every non-constant byte. Chapter 3 shows why Confidential Messages need both their privacy and the rate set by Chapter 7's load parameters, 10 MPE Envelopes per second per Shard, and Chapter 6 compares the ways to provide them. Under MIP-0002's `bytes_written` accounting the ledger cannot carry that rate: one Shard at class 1 needs 60 Messages per block, 78,720 B (60 × 1,312, derived), more than the whole chain's budget of 50,000 B. Under the ledger-9 code's churn accounting block usage binds instead: 60 class-1 calls of about 9,248 B take about 554,880 B per block, 2.8 times a 200,000 B limit and 55 percent of a 1,000,000 B one (derived).
