## Path to Active

Under MIP-0001, a proposal becomes Active once the improvement is deployed in a Midnight network upgrade, and the MIP Editors note that upgrade. Midnight Express needs no network upgrade of its own. It changes nothing in the Midnight node, the ledger or the Compact compiler (see Backwards Compatibility Assessment). It does depend on the ledger-9 upgrade that introduces contract events, because Anchors, governance events and the ledger lane all use `emit`, the Compact statement with which a circuit writes a contract event into its transaction. Deploying Midnight Express therefore means deploying the Bus Registry and the ledger-lane contract on a mainnet that runs ledger 9, publishing the consumption module for contracts that react to Messages, and publishing a Bus Node release whose transport profile, admission profile (how each MPE Envelope is admitted; see Dependencies) and parameters match this Specification.

The upgrade noted at activation is the one that activates ledger 9 on mainnet. At the start of the exit review of Stage 0, the first rollout stage, the proposal records the target network's ledger version, the runtime `spec_version` and the pinned revision of every Midnight component that Midnight Express depends on (`MPE-OPS-043`). The same record is taken again at activation.

Before activation, the proposal passes the earlier steps of MIP-0001: the editors mark it Proposed when the authors file it and, after a commentary period of usually at least two weeks, vote it Accepted. This proposal asks the editors to mark it Implemented once criteria 1 to 9 below have passed.

Active means permissioned production: the Bus Nodes that relay MPE Envelopes are those on the allow-list that the Bus Registry holds. It does not mean open relay admission, and it does not permit any claim about the size of an anonymity set, the number of Publishers among whom an observer cannot tell which one sent a given Message. Each of those has its own later gate under Implementation Plan. Active also adds nothing to on-chain private events: a contract event whose fields are encrypted for chosen recipients remains the subject of MPS-0005 Part 2, which is planned and unpublished. Midnight Express complements that route and, under the conditions in the Specification, carries such events as carried events, but does not replace it.

### Acceptance Criteria

A criterion is met only by a published, reproducible run that names its acceptance profile: source revisions, lockfile, hardware, topology, parameters and seeds (`MPE-VER-001`). A missing, skipped or timed-out check counts as a failure (`MPE-VER-003`). A result from an exploratory run, from the mock Ledger Adapter, from a compiled circuit that was never proved, from a run of the Compact simulator or from a fee derived from the cost model cannot satisfy a criterion that names a real network.

The latency, delivery and resource thresholds below are acceptance targets for Midnight Express. GossipSub does not guarantee them.

On a ledger-9 devnet:

1. **Bus Registry costs.** The compiled Bus Registry is deployed, and ten registration transactions and ten Anchor transactions are submitted. For each one the run records the serialized bytes, every cost dimension and the DUST fee (taken from the block's `ledgerParameters`), and the proving, submission, inclusion, finality and indexing times (`MPE-VER-030`, which owns the obligation that `MPE-OPS-046` restates). The run must show:
   - A registration costs at most 16 KiB and 0.5 DUST (`MPE-ECO-049`, P-ECO-13).
   - Over 100 Anchors, proving one Anchor transaction on the anchorer reference host takes less than one 60 s window (`MPE-PRF-043`).
   - A time-dependent Bus Registry write whose caller clock (a time the caller supplies, since a circuit cannot read block time) is more than 900 s from block time fails (`MPE-NET-069`).
   - The run records whether each transcript landed in the guaranteed section or a fallible segment (see The compiled ledger interface).
2. **Ledger lane.** An MPE Envelope's class (0 to 3) fixes its Sealed Body at 256, 1,024, 4,096 or 16,384 B; a `Misc` part carries 256 bytes. MPE Envelopes of classes 0 to 2 make a byte-exact round trip. Each travels as 1, 4 or 16 `Misc` parts named `mip-xxxx:envelope[v1]`, all in one execution phase of one intent and grouped by the MIP-0019 rule (`MPE-FMT-040` to `MPE-FMT-043`, `MPE-FMT-045`). The run must show:
   - A transaction whose fallible segment fails applies no part of its MPE Envelope (`MPE-FMT-042`).
   - A class-3 request, which would need 64 parts against a limit of 16 (P-FMT-8), returns `TooLarge` before any transaction is constructed (`MPE-FMT-044`).
   - The run measures the serialized size and `bytes_written` of one `Misc` event and of groups of 1, 4 and 16 parts, the DUST fee of each, which block limit binds, and which `block_usage` value (200,000 B or 1,000,000 B of block bytes) is live (`MPE-PRF-040`).
   - Proving keys are generated for the k = 18, 20 and 22 circuits, and proving time and prover memory are recorded for each. Here k is the base-2 logarithm of the domain that holds a circuit's rows and the proof system's overhead (`publishClass0` uses 166,241 of the 2^18 = 262,144 rows at k = 18); each step of k doubles the domain and roughly doubles the proving key.
   - A burst of 1,000 Messages records how many blocks it takes to clear and how many Messages fit in each block, per class.
3. **Ledger-lane reader.** The ledger-lane reader reproduces every normative vector of MIP-0019: package groups, part counts, part order, lengths and bytes. It is offered to MIP-0019 as one of the two separately written readers that MIP-0019's own acceptance criteria require. This check needs no network, and it belongs to the devnet stage.
4. **Contract consumption.** The consumption circuit that checks a publisher signature (`DEC-022` option (a)) is compiled and measured under both signature profiles, Ed25519 and JubJub Schnorr. For both, the run reports rows, proving time and prover-key size. A wrong key, target (the destination contract), action (the circuit's effect) or genesis (the genesis block hash of the network the reaction runs on, signed by the publisher with the target and action) fails proof generation (`MPE-CON-043`, `MPE-CRY-043`). The remaining thresholds are:
   - A consumer contract accepts a valid reaction against an eligible Anchor (its root still inside the acceptance window) even after later Anchors are inserted (`MPE-VER-031`).
   - With 100 concurrent reactors there is exactly one effect (`MPE-VER-032`).
   - The hostile ledger-input suite produces zero unauthorized effects (`MPE-VER-033`). The suite includes a holder of a valid inclusion path who supplies another Message secret or no signature (`MPE-CON-060`).
   - Each Ledger Adapter failure mode produces its defined degraded result (`MPE-VER-035`).
5. **Admission profile.** Over 10,000 proofs, the selected zero-knowledge admission profile needs at most 4,096 B of proof fields (the production Admission Slot ceiling; see Dependencies) and at most 10 ms of verification on one core of a 4-vCPU machine (`MPE-ECO-048`). Proof generation is reported on server, laptop and mobile hardware, with a statement for each hardware class of whether generation runs locally (`MPE-PRF-018`). A client configured with an unattested remote prover fails before any admission witness leaves it (`MPE-ECO-054`). The admission relation uses only hashes that Midnight documents as stable across upgrades (`MPE-ECO-057`).

On a public Midnight test network that runs ledger 9 (Stagenet, where MIP-0002 is live, or preview):

6. **Stagenet Indexer read.** A client reads the `MiscContractEvent` records of the deployed contracts from the public Stagenet Indexer. Its filter holds only the contract address and the `MISC` type (`MPE-CON-053`). For every emitted event, the name and payload bytes equal the emitted bytes. Repeated deliveries are deduplicated, and resuming from the Indexer `id`, as translated by the Ledger Adapter, loses no event.
7. **Permissioned overlay.** A permissioned overlay runs with the selected admission profile and without the stand-in (the placeholder admission check; see Dependencies). It completes 72 h at 10 MPE Envelopes/s per Shard without an unplanned termination (`MPE-VER-012`). It delivers at least 99.9 percent of eligible pairs of MPE Envelope and Subscriber within 10 s of admission (`MPE-VER-013`, `MPE-VER-014`; P-VER-6, P-VER-7).
8. **Scoring regression and pause drill.** A reproduction of the CVE-2022-47547 score-manipulation attack fails against the pinned GossipSub version and the complete scoring configuration (`MPE-VER-026`, which owns `MPE-OPS-047`) [@2022-kumar-gossipsub-formal; @2023-kumar-gossipsub-acl2s]. The run covers every supported Shard configuration, because the topic-score cap applies after positive and negative contributions from all Shards are summed, so credit earned on other Shards can hide misbehaviour on one. A pause-to-resume drill of the Bus Registry completes within 1 h (`MPE-OPS-041`, `MPE-VER-039`).
9. **Conformance and review.** At least two implementations of the MPE Envelope codec and the Bus Node validator, written separately from this Specification, reproduce every published conformance vector (`MPE-VER-004`, `MPE-FMT-049`). Each records the GossipSub protocol identifier it negotiated. Under StrictNoSign (no author fields; see Dependencies), each rejects a message that carries any of `from`, `seqno`, `signature` or `key`. External review of the admission binding, cryptography, parsing, persistent state and ledger-interface authorization closes with no open critical or high finding (`MPE-VER-037`).

On mainnet:

10. **Ledger generation.** Ledger 9 is active. The exact Bus Registry, Anchor, ledger-lane and consumer-contract operations run against the mainnet runtime and Indexer schema, with finalized results (`MPE-OPS-044`, `MPE-VER-034`).
11. **Bus Operators and funding.** The Bus Operator roster lists at least 8 independent organizations, and none runs more than 20 percent of the listed Bus Nodes (`MPE-OPS-009`, `MPE-OPS-010`). Written funding commitments cover every launch Bus Operator role for 12 months, including the anchorer's DUST (`MPE-OPS-051`).
12. **Canary delivery.** Canary Publishers in every Shard achieve at least 99.9 percent timely delivery within 5 s for 30 consecutive days (`MPE-VER-038`, `MPE-OPS-049`). Criterion 7 allows 10 s because its admission cost is not yet measured.

As of 2 October 2026 none of the twelve criteria has been met. Exploratory runs guided the design, and the next step is the proof of concept, a single reference implementation with a deterministic simulator, which has not been built. The ledger interface (Bus Registry, ledger-lane contract and inclusion-only reference consumer contract) has been compiled with Compact and costed from the ledger-9 cost model; none of it has run on a Midnight network, and the contracts are exploratory code on whose final form the Specification does not depend. ### Implementation Plan

The plan has five rollout stages, Stage 0 to Stage 4, as the requirement set numbers them (`DEC-028`). They are not the phases of MPS-0005, where Phase 1 means public contract events and Phase 2 means private contract events. No stage starts until every exit gate of the stage before it has passed with published evidence (`MPE-OPS-042`). An admission profile selected before criteria 1 to 4 have passed on the devnet therefore still waits for them, because those criteria close Stage 0. Stage 0 has two parts, local measurement and the ledger interface on a devnet, and its exit review closes the second part.

The local part of Stage 0 begins with the proof of concept: a single reference implementation of the Bus Node, Store Node and client library against the mock Ledger Adapter, a deterministic simulator that reproduces any run from its seed, and a runnable harness that executes every scenario below against that one implementation. Fourteen experiments then run on it, and all fourteen gate the stage. Two settle decisions that its exit names, three run acceptance criteria locally, two check feasibility and seven test the overlay:

- trial decryption at 1, 32 and 256 keys against the salted Recognition Tag (by which a Subscriber recognizes its Messages), which decides whether the Tag stays (`DEC-003`);
- one Bus Node per host at 10, 20 and 50 MPE Envelopes/s (`DEC-005`);
- the ledger-lane reader against the MIP-0019 vectors (criterion 3);
- the consumption circuit under both signature profiles (criterion 4);
- scoring across every supported Shard configuration (criterion 8);
- whether a circuit can recompute the MPE Envelope Identifier and its RFC 6962 path byte for byte;
- recovery of an admission membership from a wallet seed through a `deriveSecret` stub standing in for the wallet's key derivation (`MPE-CRY-027`);
- a fully poisoned eclipse run of at least 180 s, with all the victim's dial sources and bootstrappers hostile;
- IDONTWANT thresholds at 500, 700 and 1,000 B, recording the size predicate that rust-libp2p applies and stating whether emission or receipt is disabled in the control run;
- a churn matrix that sets the restart-barrier `Busy` reply (after each start a Bus Node answers publication requests with `Busy` for 140 s) against reconciliation (window-by-window comparison with a second Bus Operator's inventory) at 5, 15 and 60 s;
- a stale-chain overlay run, checking that a stale Ledger Adapter view penalizes no honest peer (`MPE-NET-018`);
- idle Shards, whose peers must not be pruned for lack of traffic;
- the withholding-eviction rule, which prunes a mesh peer that delivers nothing or only Rejected MPE Envelopes, over at least 90 loaded heartbeats with asymmetric latency;
- a 48 h full-retention soak, holding every accepted identifier until expiry.

The stages move from a mock Ledger Adapter on local hosts through a ledger-9 devnet and a public test network to mainnet.

The ledger interface is tested on a devnet before the overlay pilot because only a ledger-9 network can host Anchors and the ledger lane; the ledger-8 toolchain rejects `emit`. If ledger 9 has no mainnet activation date before Stage 1 starts, Stage 1 runs as a permissioned overlay whose Ledger Adapter targets a ledger-9 devnet (`MPE-OPS-054`).

The protocol pays no Bus Operator in any stage. DUST, the resource that pays Midnight transaction fees, is generated from registered NIGHT and pays only fees: it cannot be transferred, a contract cannot receive it, and the runtime credits fees to no one. Launch Bus Operators are therefore funded by written commitments outside the protocol (`DEC-001`). Those commitments also cover the anchorer's fees. At genesis prices one Anchor per 60 s costs about 280 DUST a day (1,440 × 0.195 DUST, derived). Registration has no price beyond the network fee. If a token price is added later, this proposal must name the token and the receive path, with shielded NIGHT as the default (`MPE-ECO-056`). Any bond is a Bus Registry contract balance and has nothing to do with NIGHT staking, which locks nothing and carries no consensus weight.

A treasury that pays only for work a contract can check, such as Anchors and passed retention challenges, remains an optional later feature. Paying Bus Operators on probe scores is rejected: in Nym's reputation system, scoring attacks cut the cost of dominating a paid active set by over 99 percent [@2026-cao-nymreputation].

Strong anonymity costs either bandwidth overhead or latency [@2017-das-trilemma], and a broadcast overlay hides only as much as its traffic allows. No claim about the size of a broadcast anonymity set is therefore published while organic load is below 20 Messages/s or fewer than 1,000 distinct publisher admissions are active (`MPE-OPS-052`). Every course-change trigger, such as a failed admission-cost gate, a failed Anchor proving gate or a failed red team, is entered in advance with a numeric threshold and a named response (`MPE-OPS-053`).

Carried private events come later and do not gate Active. Once MPS-0005 Part 2 is published, its private events are compared with the carried-event schema, and one Phase 2 private event is then carried end to end under the conditions in the Specification.

## Implementation

Midnight Express is a set of programs, two contracts and a Compact module that run beside Midnight, plus a reference consumer contract (a Consumer written in Compact) that uses the module. None of it changes Midnight. Retention, receipts, Anchors, replay protection, whole-Shard feeds and reconciliation are all mechanisms of Midnight Express itself; GossipSub's bounded message caches and its dissemination provide none of them.

The path of one Message crosses every component. A Publisher's client library seals it, fills the 512-byte Admission Slot and submits the MPE Envelope to a Bus Node, which validates it and forwards it on its Shard. A Store Node keeps it until expiry, and a Subscriber's client library recognizes it by its salted Recognition Tag. The Anchor that the anchorer posts for its 60-second window commits to its MPE Envelope Identifier, across all Shards. A contract that reacts to the Message runs the consumption module, which checks the publisher signature and can check inclusion against that Anchor. Four of the seven components are Rust code and three are Compact.

| Component | Form | Role |
|---|---|---|
| Bus Node | Rust binary on rust-libp2p | Joins one GossipSub topic per Shard, runs the validator of the Overlay protocol section before forwarding, and serves the publish and feed protocols. Optional roles are bootstrapper, gateway and anchorer. In the proof of concept a bootstrapper also relays, and neither a zero-degree bootstrapper nor Peer Exchange with signed peer records is in its scope. |
| Store Node | The same binary with the store role | Keeps every MPE Envelope it accepts until expiry, and answers back-fill, inventory and receipt requests. It stores no chain history. |
| Client library | Rust crate with a TypeScript binding | Publisher: seal, admit, submit, retry. Subscriber: recognition, deduplication, gap detection, labels, second-source reconciliation. Also carried-event sealing and verification, consumer adapters for agents, wallets and contract reactions, and the explicitly selected ledger lane. |
| Bus Registry | Compact contract, ledger 9 | Holds one membership tree per membership period, the revoked set, parameters with a time-locked change path, the relay list, the pause flag, and Anchors in a ring of 2,940 slots indexed by `window mod 2940` with a matching historic Anchor tree (2,940 × 60 s = 49 h, an hour past the 48 h MPE Envelope lifetime). It emits only `mip-xxxx:anchor[v1]` and `mip-xxxx:governance[v1]` events (`MPE-NET-040`). It never stores a Message or a Sealed Body (`MPE-STO-001`). |
| Ledger-lane contract | Compact contract, ledger 9 | Emits the Sealed Body of one MPE Envelope as 1, 4 or 16 `mip-xxxx:envelope[v1]` parts in one call. It writes no ledger state, and it has no circuit for class 3. |
| Consumption module | Compact circuits that a consuming contract includes | Checks the publisher signature, the expiry against a coarse bound, an optional Anchor inclusion path through a witness-free Bus Registry read, and the consumption nullifier, all in one transition. |
| Ledger Adapter | Module of the client library and the Bus Node | Reads finalized Bus Registry state, Anchors, ledger-lane parts and carried-event transcripts, and takes no value from an unfinalized block (`MPE-NET-068`). Submits registration, Anchor, ledger-lane and reaction transactions through the wallet's existing balancing path. |

Code is not part of this proposal. The proof of concept has not been written; once it exists, it will be linked from the resource directory `mips/mip-xxxx/` together with the three Compact contracts and the conformance vectors. Criterion 9 also needs a second implementation written separately from this Specification, and it cannot be met until both implementations and the vectors are public.

### The compiled ledger interface

The Bus Registry, ledger-lane and reference consumer contracts compile with Compact compiler 0.35.0 (language 0.27.0, compact-runtime 0.20.0), which targets the ledger-9 release candidate 9.1.0.0-rc.3. They use the default proof backend. Compact gained `emit` in toolchain 0.33.0, and toolchain 0.35.0 states that ledger 9 is not yet deployed on mainnet.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.33.0.md (contract events) and doc/release-notes/toolchain-0.35.0.md (ledger-9 target); main branch, accessed 1 October 2026.] The contracts are exploratory code. The Specification does not depend on their final form; their circuit sizes and derived fees show what the ledger-9 toolchain and cost model imply for circuits that do this work.

The ledger-8 toolchain, 0.31.1, rejects both the Bus Registry and the ledger-lane contract with `unbound identifier emit`. With its two `emit` statements removed, the Bus Registry does compile with 0.31.1, so `emit` is its only dependency on ledger 9. The consumer contract does not compile with 0.31.1, because the ledger-8 model of cross-contract calls needs the callee's compiled artifacts. Midnight Express therefore requires a released toolchain at 0.33.0 or later (`MPE-NET-070`). The contracts' generated JavaScript was exercised in the Compact simulator for registration, relay management, Anchor posting with five refusal cases, the historic Anchor-root check, revocation, pause, the 16-part call with its emission order, and refusal of a foreign `Misc` name. The simulator runs that JavaScript, not the circuits, so it does not show that the circuits accept the same executions, and it does not run the cross-contract call of `react`.

On the verifier side every proof is at most 4,368 B and every verifying key at most 2,119 B. The prover side is far larger. Compact packs `Bytes<n>` into field elements, so every byte that an `emit` payload takes from a circuit argument must be split out of a field element, and each split adds decomposition rows. Emitting a constant 256-byte payload costs 23 rows; emitting a 256-byte argument costs 166,241 rows (k = 18). Hashes inside circuits are likewise affordable only over struct preimages (structs of fixed-width `Bytes` fields, not concatenated bytes): three chained SHA-256 node hashes take 12,674 rows that way, against 133,922 rows with byte concatenation, for the same digests (`MPE-CRY-046`).

Every Anchor therefore needs a k = 18 proof, one per minute per anchorer. That cost is the reason for the proving gate of criterion 1, and for the rule that the Bus Registry emits at most 72 non-constant bytes per Anchor and 35 per governance event (`MPE-FMT-059`). Every ledger-lane MPE Envelope needs a proof of k = 18 to k = 22. On one host, key generation took 195 s for `publishClass0` and 264 s for `publishPart` at k = 18, with at most 1.8 GB of memory, and 1,105 s and 7.1 GB for `publishClass1` at k = 20. Keys at k = 22 were not generated, and proving time was not measured at any size. If criterion 2 shows that the 16-part call cannot be proved on the reference host, the limit on parts per call drops to 4 (P-FMT-8).

A Midnight transaction holds intents, each under a nonzero segment number, because segment 0 is reserved for the guaranteed section. Each contract call declares two transcripts, the lists of its visible effects with events included. The guaranteed transcripts of all intents run first, together, in the guaranteed section; each intent's fallible transcript then runs in that intent's own segment, a fallible segment. A failed fallible segment is discarded without undoing the guaranteed section, and the transaction's fees, collected in the guaranteed section, are still spent.^[midnightntwrk/midnight-docs, docs/concepts/how-midnight-works/building-blocks.mdx (guaranteed section and segment order) and docs/guides/dust-sponsorship.mdx (fees collected in the guaranteed phase); main branch, accessed 2 October 2026.] MIP-0019 calls an intent a physical intent and its two parts its execution phases.

The compiled contracts also mark the limits of what Compact can express:

- A Midnight transaction has no signer. The steward and the anchorer therefore authorize by proving, inside the circuit, knowledge of a secret whose hash is in state.
- A circuit can compare block time but not read it. Each time-dependent write takes a caller clock checked within 900 s of block time, and every comparison discloses its operand. The consumer contract therefore discloses only a coarse bound that the prover chooses (`MPE-CON-061`).
- A circuit cannot read its own Merkle root, and a historic-root check has no time bound. The 3,600 s membership-root window is therefore enforced by Bus Nodes, not by the Bus Registry.
- The transcripts of `register` and `postAnchor`, and of the 16-part call, exceed the guaranteed-section budget (derived from simulator gas, not observed). Their events land in a fallible segment. Ledger-lane parts are therefore required to sit in one execution phase of one intent, not necessarily in the guaranteed phase that MIP-0019 recommends.
- The inclusion-only `react` proves that some anchored identifier exists, but it does not bind the consumption nullifier to that Message. Authority needs the publisher signature (`MPE-CON-060`).
- The compiled revocation circuit computes the rate-limiting relation with `transientHash`, which carries no stability guarantee across upgrades. The selected admission profile must use a stable hash instead (`MPE-ECO-057`).

Fees derived from the ledger-9 cost model at genesis mainnet prices, with estimated block bytes, range from 0.129 DUST for one `Misc` part to 0.866 DUST for 16 single-part calls. None was measured on a network, and mainnet still runs the ledger-8 parameter schema. The second figure in each fee cell includes the wallet's five-block margin: live prices move by up to about 4.6 percent per dimension per block, and 1.046^5 ≈ 1.252, so 0.246 DUST becomes 0.308.

| Transaction | Block bytes | Dominant term | Fee (DUST) |
|---|---|---|---|
| One registration | about 8,670 | compute | 0.246 / 0.308 |
| One Anchor | about 10,340 | compute | 0.195 / 0.244 |
| One `Misc` part alone (`publishClass0`) | not estimated | not stated | 0.129 / 0.161 |
| 16 parts in one call | about 12,920 | compute | 0.188 / 0.236 |
| 16 single-part calls in one intent | about 80,260 | block bytes | 0.866 / 1.084 |

A block arrives every 6 s and must stay within several limits at once; whichever fills first binds. The ledger lane meets three of them: `bytes_written` (bytes written persistently, 50,000 B per block), `block_usage` (block bytes) and `bytes_churned` (bytes written temporarily or overwritten). MIP-0002 and the cost code charge a `Misc` part to different ones. MIP-0002 counts each event's serialized size against `bytes_written`, which then binds. With its 40-byte overhead per event, one part is about 328 B, so a block holds about 38 class-1 groups of four parts (50,000 / 1,312 B), about 6.3 per second for the whole chain, or about 9 class-2 groups of sixteen (50,000 / 5,248 B), about 1.5 per second, with no other writers (derived).

The ledger-9 cost code charges only the net figure, written minus deleted bytes, against `bytes_written`.^[midnightntwrk/midnight-ledger, base-crypto/src/cost_model.rs, struct `SyntheticCost`, field `bytes_written` ("net bytes written ... `max(0, r.bytes_written - r.bytes_deleted)`"); version 9.1.0.0-rc.4, accessed 1 October 2026.] It counts a logged value as both written and deleted, so a part adds instead to `bytes_churned` and to block bytes. Under the block-bytes limit, one 16-part call of about 12,920 B fits 15 times in a 200,000 B block (about 2.5 per second) or 77 times in a 1,000,000 B block (about 12.8 per second; 12.9 at the unrounded 77.4) (derived). Which `block_usage` value is live is unknown. Criterion 2 settles the counting rule and the live value by measurement.

Two further capabilities would help, and neither is required. A cheaper way to emit public byte payloads in `Misc` would lower the cost of the ledger interface, and a way to read block time or a contract's own Merkle root inside a circuit would remove the caller clock and the enforcement of the root window by Bus Nodes.

### Changes and non-changes in Midnight

Nothing in the Midnight node changes. The Midnight node carries no GossipSub.^[midnightntwrk/midnight-node, Cargo.lock, no `libp2p-gossipsub` package among the libp2p crates; main branch at commit 887348f9, accessed 1 October 2026.] The Bus Node runs as a separate process with its own libp2p identity, so no fork of the Midnight node is needed. Separate keys avoid reusing the Midnight node's identity, but they do not hide that two processes share a host: co-location, addresses and traffic can still link them.

The ledger and the Compact compiler do not change either. The contracts use existing Compact types and the existing `Misc` event, which has a 32-byte name and a 256-byte payload.^[LFDT-Minokawa/compact, compiler/midnight-events.ss, standard event `Misc`; main branch, accessed 1 October 2026.] The 288 bytes of a `Misc` event are its struct data. Its serialized size is larger, about 40 B more by MIP-0002's estimate, and criterion 2 measures it.

The Indexer, which reads chain data and serves it to wallets and DApps, needs no change. Its `contractEvents` subscription already replays and follows the `Misc` events of one contract address from finalized blocks, with an inclusive, monotonic `id`.^[midnightntwrk/midnight-indexer, indexer-api/graphql/schema-v4.graphql, subscription `contractEvents`; main branch, accessed 1 October 2026.] The shipped filter takes `contractAddress` with optional `types`, `fromBlock`, `toBlock` and `transactionHash`, and the whole surface is marked `@beta`. The ledger-lane cursor is that `id`, which the Ledger Adapter translates into the client's cursor (`MPE-CON-053`). Four Indexer additions are recommended:

- a segment-number field and an emission position on each contract event;
- documentation that `id` order matches ledger emission order within a transaction;
- `Misc` indexing by name, which MIP-0002 already allows to "be configured by policy" and which therefore needs no API change;
- a documented retention for contract events of at least 176,400 s, the live Anchor history.

midnight-js needs no change, because the TypeScript binding uses its existing `contractEventsObservable`. The wallet and the DApp connector need no change for agent or service consumers. The DApp connector exposes no event or subscription method.^[midnightntwrk/midnight-dapp-connector-api, src/api.ts, interface `ConnectedAPI`; main branch, accessed 1 October 2026.] Wallet-held Subscriber keys, and a grant that lets a DApp read one stream, would therefore be a separate, optional proposal to those two repositories.

### Dependencies

Midnight Express depends on rust-libp2p, MIP-0002 and MIP-0019, and on an admission profile that has not been selected. MPS-0007 and MPS-0005 Part 2 bear on it without being dependencies.

The overlay is specified on rust-libp2p (libp2p 0.57, `libp2p-gossipsub` 0.50) with GossipSub v1.2: the v1.1 scoring and mesh rules plus IDONTWANT, a control message with which a Bus Node tells its mesh peers not to send a message it already holds. The v1.2 specification is a Working Draft (r2, dated 30 August 2026), and a v1.2 node talking to a v1.1 peer gets no IDONTWANT on that link.

The transport profile requires the standard GossipSub identifier `/meshsub/1.2.0`, so a conforming implementation offers it. The strings under `/mpe/<g>/1`, where `g` is the first eight bytes of the genesis hash in lowercase hexadecimal, name Shard topics and request-response protocols; they are not GossipSub identifiers. Upstream, `protocol_id` takes a custom string but selects only `Version::V1_0` or `Version::V1_1`, and the string does not set the internal version.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, enum `Version` (variants `V1_0`, `V1_1`) and `ConfigBuilder::protocol_id`; master branch, accessed 1 October 2026.] Stock `libp2p-gossipsub` 0.50 therefore cannot pin v1.2 on a custom identifier, while its default `/meshsub/1.2.0` meets the profile, and the proof of concept will negotiate that default. A patch adding `Version::V1_2` could negotiate a custom identifier such as `/mpe/<g>/1/gossipsub/1.2.0`, but no standard-only peer would accept it without configuration changes, so the profile excludes one.

The default offer lists of the Rust and Go libraries also include v1.3 and older versions, so a default offer does not guarantee that v1.2 is negotiated. A conforming Bus Node records the negotiated identifier and enforces the version policy, and a strict v1.2 offer needs a negotiation test.

Under StrictNoSign a message carries no author fields. The 0.50 decoder does not reject a message that carries only `key`. Version 0.51 adds that rejection,^[libp2p/rust-libp2p, protocols/gossipsub/CHANGELOG.md, entry 0.51.0 ("Reject messages carrying a `key` field in `ValidationMode::Anonymous`"); master branch, accessed 1 October 2026.] so the proof of concept will use 0.51 or carry the fix.

The parameter check of go-libp2p-pubsub requires `Dout < D/2` and so rejects the profile's mesh tuple of (8, 6, 12, 4), which the specification allows.^[libp2p/go-libp2p-pubsub, gossipsub.go, parameter validation of `Dout`; master branch, accessed 1 October 2026.] Go interoperability under this profile stays unestablished until that is resolved and tested.

Partial messages and other extensions that change behaviour are outside the launch profile. Topic names are routing labels and authenticate no network: admission binds the full genesis hash, and Bus Nodes filter subscriptions to supported names under `/mpe/`. Per-class egress counters that the proof of concept adds for measurement are test instrumentation and need not go upstream.

MIP-0002 (Accepted) supplies `emit`, `Misc` and the Indexer's contract-event surface, all of which belong to the ledger-9 generation. On 4 August 2026, mainnet ran ledger 8.0, preview ran ledger 9.1, and MIP-0002 was live on Stagenet. Whether mainnet has moved since then is unknown; the `spec_version` query of the evidence freeze settles it, and criterion 10 waits for activation. CoIP-0003, a Draft, is the language-level reference. It dates `emit` to language 0.25, the language of toolchain 0.33.0 (toolchain 0.31.1 carries language 0.23.0).

MIP-0019 (Proposed) is the source of the rule that groups the parts of one ledger-lane MPE Envelope by transaction and intent, in emission order, within one execution phase. The Specification states this rule itself and cites MIP-0019 as its source, so Active does not wait for MIP-0019 to be accepted. The ledger-lane reader is offered as one of the two separately written readers that MIP-0019 needs (criterion 3).

MPS-0007 (Proposed, with no MIP) is not a dependency. Today ledger events reach a Bus Node only through an Indexer, which re-executes every transaction, so Anchor reads and ledger-lane reads trust the Indexer's availability and correctness. Until node-side events exist, Anchors are verified against Bus Registry state, not against their `Misc` copies. Ledger-lane bodies are labelled `final` only after verification against authenticated on-chain data from P-NET-14 = 2 independent sources (`MPE-CON-016`, `MPE-SEC-022`). A MIP that answers MPS-0007 would let a Bus Operator read the same events from its own Midnight node and take the Indexer out of its trust path.

MPS-0005 Part 2 (planned, text unpublished) is not a dependency either. Midnight Express can carry its private events once it is specified, but it does not stand in for them. None of these Foundation documents gives the overlay a delivery or privacy property: MIP-0002, MIP-0019, MPS-0005 and MPS-0007 concern contract events, multipart reconstruction and node-side visibility.

Several transport risks stay open after these dependencies are met:

- Scoring safety across several Shards is unknown, for the reason given under criterion 8.
- Compatibility between the Rust and Go GossipSub libraries is unestablished, because protocol identifiers, default version lists, IDONTWANT size predicates and Peer Exchange support all differ.
- The ingress Bus Node sees the submitting connection directly, and neighbours see forwarding paths and timing. No GossipSub configuration removes these observations.
- No compliance result for the transport (conformance to the GossipSub specifications) establishes release security. Criteria 7 to 9 and 12 are separate obligations.

The open dependency is the zero-knowledge admission profile. The proof of concept will use a stand-in admission check that keeps the relation of an RLN membership proof [@2022-vac-rln-v1-spec; @2024-vac-rln-v2-spec] and every check a relay performs. In that relation a Publisher proves membership in a tree that the Bus Registry holds and a credit index below its class quota, and derives one admission nullifier per MPE Envelope from its admission secret, the admission window, the class and the credit index. A relay that sees the same admission nullifier twice knows that a credit was spent twice; a zero-knowledge proof of the relation is meant to reveal nothing more. The stand-in's secrets are visible to every Bus Node, so it links each MPE Envelope to its membership and is acceptable on devnets and public test networks only. A follow-up must select a profile that meets three conditions:

- it meets `MPE-ECO-048`, with a verifier that runs outside the Midnight node;
- it states for each hardware class whether proofs are generated locally;
- it never sends the admission secret to an unattested prover (`MPE-ECO-054`), the risk that MPS-0004 describes for delegated proving.

Midnight's own proof system does not fit the Admission Slot as it stands. The Admission Slot has one fixed width per MPE Envelope version, 512 B in this one; a production version sets it to the measured proof fields rounded up to a multiple of 64 B, which P-ECO-11 caps at 4,096 B. The ledger estimates a contract-call proof at 4,832 B,^[midnightntwrk/midnight-ledger, ledger/src/structure.rs, constant `PROOF_SIZE`; tag ledger-9.1.0.0-rc.5, accessed 1 October 2026.] and the compiled circuits above produce proofs of 2,800 to 4,368 B in the circuit model. All of these exceed the 512-byte Admission Slot, and the larger two exceed the 4,096 B ceiling. A Midnight-native profile would therefore need either a smaller proof or a new MPE Envelope version with a wider slot (`DEC-013`, `DEC-015`). If no profile passes, `DEC-007` selects object-bound blind-RSA stamps of 354 B instead [@2023-rfc9474-rsablind]. A blind signature lets the issuer sign a stamp without seeing it, so a spent stamp cannot be matched to its signing. The issuer still learns which customers buy admission, and the leakage table records that. Criterion 5 and Stage 1 both wait on which profile, if any, meets all three conditions.

## Versioning

This Specification is versioned so that a change never reinterprets data already on the overlay or in chain history. Store Nodes keep MPE Envelopes for 48 hours (172,800 s) and chain history keeps every event as written, so a reader must be able to tell from the data alone which rules produced it. Each versioned surface therefore carries its version in its own name, and old and new versions can run side by side without coordination. A change that the rules below cannot express is made by a superseding MIP.

1. **MPE Envelope format.** The `version` field of the 8-byte visible header is bound to the major version in the GossipSub topic `/mpe/<g>/<major>/shard/<i>` and in the request-response protocol identifiers. The Bus Registry's `maxVersion` names the highest version that Bus Nodes accept (`MPE-NET-039`). A Bus Node Rejects an MPE Envelope whose version is inconsistent with the supported topic it arrived on (`MPE-FMT-023`). It Ignores one whose protocol context it does not support, and it does not subscribe to unsupported versions. Both are GossipSub validation verdicts, and only Reject penalizes the peer that forwarded the message. When a new version activates, Bus Nodes relay the GossipSub topics of both versions for at least P-FMT-9 (34 days) (`MPE-FMT-024`).
2. **Ledger event names.** Following MIP-0018, the version is part of the event name. The bracketed suffix is the layout version: `mip-xxxx:anchor[v1]`, `mip-xxxx:envelope[v1]` and `mip-xxxx:governance[v1]`, in ASCII and NUL-padded to 32 bytes (P-FMT-10). An incompatible layout always takes a new name. An amendment within this MIP increments the bracket (`[v2]`), a superseding MIP takes a fresh name, and no existing name is ever reinterpreted. A reader that knows only `[v1]` ignores other names, and a reader that knows several keeps them apart. MIP-0019 warns that opting an existing name into the multipart rule would reinterpret that name's history. `mip-xxxx:envelope[v1]` is therefore opted into the rule from its first use, by declaring the opt-in label that MIP-0019 defines (written `mip-xxxx:multipart[v1]` in its current text).
3. **Domain-separation labels.** Every label takes the form `mpe:<purpose>[v1]`; the MPE Envelope Identifier, for example, uses `mpe:envelope-id[v1]` (P-FMT-11). A changed hash input takes a new bracket. The complete table of labels and `Misc` names is published in this MIP in a form ready for registration under the registry that MPS-0027 recommends (`MPE-CRY-042`).
4. **Contracts and toolchain.** Each version of this MIP names the Compact toolchain, language, runtime and ledger versions used to compile the Bus Registry, ledger-lane and consumer circuits (`MPE-OPS-056`). This version uses compiler 0.35.0, language 0.27.0, compact-runtime 0.20.0 and ledger 9.1.0.0-rc.3. A changed circuit is either a verifier-key update under the Bus Registry's maintenance authority, subject to the delay that `MPE-OPS-017` must establish, or a new deployment. Either way its emitted names follow rule 2, so a reader never needs a contract version to decode an event.
5. **Parameters.** Bus Registry parameters change through the time-locked propose-and-activate path (`MPE-OPS-012`), not through a new Specification version.
6. **Transport profile.** The profile is GossipSub v1.2 negotiated as `/meshsub/1.2.0`, the identifier that Dependencies requires. Moving to another GossipSub version, or enabling an extension such as partial messages, is a new Specification version.
