None of the evidence for the contracts comes from a network. Sizes come from compilation: every circuit's size (`k` and rows), proof size and key sizes are the compiler's output under its circuit cost model. Behaviour was exercised only in Compact's local simulator, which runs the generated JavaScript, over registration, relay management, Anchor posting and its refusal cases, the historic Anchor-root check, revocation with its refusals, pause and unpause, a 16-part ledger-lane call in emission order and refusal of a foreign `Misc` name. For `persistentHash` over a byte value or a struct of byte fields, the simulator returned plain SHA-256 of the concatenated bytes. The simulator does not show that the circuits accept the same executions, and it does not run cross-contract calls.

Fees are derived. Every fee given here is computed from the ledger-9 cost model at genesis mainnet prices, using estimated transaction sizes. No transaction was constructed, proved, balanced or submitted, and no proof was generated or verified.

Fees are paid in DUST, a non-transferable resource that holding NIGHT, Midnight's native token, generates and that only pays transaction fees. Genesis mainnet prices are the starting prices in the Midnight node's mainnet ledger parameters. A wallet adds a margin of about 1.25 times, covering five blocks of price movement, and each fee below is given without and with that margin.

A Compact circuit is a function whose execution the caller proves in zero knowledge. The ledger checks the proof against the circuit's verifying key and then applies the public effects. Private inputs, called witnesses, come from the caller's own code. A private value that reaches contract state, an event or a block-time comparison must be disclosed, and so enters the public transcript the proof is checked against. A circuit of size `k` has 2^k rows of capacity, so each step in `k` roughly doubles it and its proving key.

`persistentHash` is SHA-256 and is guaranteed to stay the same across upgrades, but is costly in a circuit; `transientHash` works natively on field elements and is cheap, but Compact does not guarantee that it stays the same.^[LFDT-Minokawa/compact, doc/api/CompactStandardLibrary/exports.md, `persistentHash` and `transientHash`; main branch, accessed 1 October 2026.] In the formulas below, `SHA-256(a || b)` is `persistentHash` over a struct of the fixed-width fields `a` and `b`. In the simulator this gave the digest of SHA-256 over their concatenated bytes; the proof of concept must confirm the same digest from a proved circuit before any external verifier relies on it.

The proof of concept will test the overlay against a mock Bus Registry with a single maintainer key that implements the semantics below. The contract sources, their compile and cost scripts and the simulator test are exploratory code. This specification states the interface they implement and does not depend on them being final; it shows only short signatures, and the Implementation section names where the sources will be published.

#### Bus Registry state

The Bus Registry's membership trees and its Anchor tree are of Compact's `HistoricMerkleTree` kind, which remembers earlier roots, so a proof made against a root that a later insertion replaced still checks. The fields of the Bus Registry's public ledger state, and their meanings, are normative; the types shown are those of the compiled contract.

The slot count follows from the Anchor history. Dividing 176,400 s by the 60 s window gives 2,940 windows, so a slot is reused exactly when its record leaves the live history, and the other 1,156 leaves of the Anchor tree (2^12 - 2,940) are never written.

The Message lifetime is not a Bus Registry parameter. Version 1 of the MPE Envelope fixes it at 172,800 s, and P-FMT-3 allows a later version at most 1,209,600 s. The compiled `params` carry one limit vector, for the lowest tier. Further tiers need a tier table that replaces that vector, and the registration circuit would then read the tier from it. The Shard count that a change replaces is not stored, because readers take it from the parameter set that was in force before the change in the finalized history.

A `RelayEntry` holds the following:

- a 32-byte Bus Operator organization identifier;
- five role flags as Booleans: relay, Store Node, bootstrapper, gateway and anchorer;
- an anchor-key commitment;
- a dialable address.

Role flags are Booleans because Compact has no bitwise operators. The compiled `RelayEntry` holds the first three items and has no address field. The address is specified because clients must find replacement Bus Nodes and Store Nodes in the finalized relay list and refresh it when it changes, which a static list cannot do. Its fixed-width encoding is not yet defined. The Bus Registry and the authenticated bootstrap records together are the authoritative source of identities and addresses.

The map key is the raw 32-byte Ed25519 public key. A Bus Node MUST derive the libp2p PeerId from that key with libp2p's key encoding and MUST NOT treat the 32 bytes as a serialized PeerId, which for Ed25519 is a 38-byte multihash.^[libp2p/specs, peer-ids/peer-ids.md, sections "Keys" and "Peer Ids"; master branch, accessed 2 October 2026.] The compiled contract keys entries by SHA-256 of the PeerId bytes instead. That key is also 32 bytes, but a PeerId cannot be recovered from it, so a conforming deployment uses the raw public key.

A libp2p identity authenticates a connected endpoint, not the Publisher sealed inside an MPE Envelope. A listed relay key says which Bus Operator runs an endpoint and nothing about who published through it. At launch there is no bond, deposit or treasury field (DEC-001, DEC-007). If bonds are added later, they are Bus Registry contract balances and have no relation to NIGHT staking, which "carries no consensus weight" [@midnight-mip-0016].

A membership leaf is computed as follows. The identity commitment of admission secret `a0` is `SHA-256(pad32("mpe/v1/idc") || a0)`. The leaf value is `persistentHash` over the struct (`pad32("mpe/v1/leaf")`, identity commitment, limit vector). Because the registration circuit computes the leaf from the current `params`, a registrant cannot commit a larger limit (DEC-016). The committed vector is the per-member limit of RLN-Diff [@2024-vac-rln-v2-spec], a variant of the Rate-Limiting Nullifier (RLN) construction whose mechanism Revocation evidence under Circuits sets out. The tree then hashes the leaf: its leaf hash is SHA-256 over a domain separator and the value, and its inner nodes use Midnight's transient (Poseidon) hash.^[midnightntwrk/midnight-ledger, transient-crypto/src/merkle_tree.rs, function `leaf_hash` (`persistent_hash`) and `MerklePath::root` (`transient_hash`); branch ledger-8 at 9f9842eb, a crate the Indexer's code describes as shared by ledger 8 and ledger 9; accessed 1 October 2026.]

This version of the specification does not fix the zero-knowledge proof system behind the Admission Proof; a separate proposal that follows this one selects it as an admission proof profile, and until then the proof of concept will use the stand-in described under Binding admission to Bus Registry roots. Bus Nodes compare the root in an Admission Proof with a root of the period's tree, so the admission proof profile that the later proposal selects MUST prove membership under this exact construction. That profile also depends on the pinned toolchain, because the leaf value hashes a vector of `Uint` fields through Compact's serialization.

Every compiled circuit has a proof of at most 4,368 B and a verifying key of at most 2,119 B. The verifier side stays small, but the prover side does not: the proving keys of the k = 18 circuits are 67 to 76 MB, and key generation for one k = 18 ledger-lane circuit took 264 s and 1.8 GB of memory on a 6-core host. Proving time and prover memory are unknown at every size.

**Revocation evidence.** Revocation rests on the rate limit committed in the leaf. For each admission window, class and credit index, the secret `a0` and a derived value `a1` define a line `y = a0 + a1 × x`, and each MPE Envelope admitted under that credit reveals one point on it, with `x` derived from its Envelope Identifier. One point says nothing about `a0`. Two points with different `x` fix the line, whose value at `x = 0` is `a0`. A member that spends one credit twice has therefore published the evidence for its own revocation. The circuit takes that evidence as private witnesses:

- the recovered admission secret `a0`;
- the admission window, class and credit index;
- the limit vector committed in the member's leaf;
- two shares `(EID_i, y_i)`;
- the member's Merkle path.

The circuit computes `a1 = H(a0, window, class, credit)` and `x_i = H(EID_i)` with `transientHash` over the native field. It checks `y_i = a0 + a1 × x_i` for both shares and checks that `EID_1 ≠ EID_2`. It then recomputes the identity commitment from `a0` and the leaf from that commitment and the committed limit vector, and checks the path from that leaf against a historic root of the period's tree. The circuit discloses the period, that root, the leaf index, the identity commitment and a reason code. No steward action is involved.

The RLN relation uses `transientHash` because an in-circuit Admission Proof on Midnight would use it, although that hash may change across upgrades. The admission relation that the later admission-profile proposal pins MUST use a hash that Midnight commits to keeping stable.

**Authority without a signer.** Every authorization in the table is knowledge of a secret, proved in the circuit, because no transaction carries a signer: off chain, `kernel.caller()` returns no caller for a top-level call.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, section "The caller of a circuit"; main branch, accessed 1 October 2026.] The circuit hashes a secret supplied as a witness and asserts that the result equals a commitment held by the Bus Registry: `SHA-256(pad32("mpe/v1/steward") || secret)` for the steward and `SHA-256(pad32("mpe/v1/relaykey") || secret)` for an anchorer. The Midnight documentation describes the same hash-authentication pattern.^[midnightntwrk/midnight-docs, docs/concepts/how-midnight-works/keeping-data-private.mdx, section "Making use of Merkle trees" (circuits `publicKey` and `increment`); main branch, accessed 1 October 2026.]

The hash check itself is cheap: `register` computes two SHA-256 hashes in 6,305 rows. The steward circuits are large (k = 15 to 17) because of the byte work of their governance payloads and `Bytes<32>` arguments.

**Time.** A contract can compare block time with a value but cannot read it.^[LFDT-Minokawa/compact, doc/api/CompactStandardLibrary/exports.md, circuits `blockTimeLt`, `blockTimeLte`, `blockTimeGt` and `blockTimeGte`; test-center/compact/block-time.compact passes `disclose(time)`; main branch, accessed 1 October 2026.] Two uses of time must therefore be kept apart. A comparison needs only a bound: `register`, `prunePeriod`, `activateParams` and `postAnchor` compare block time with bounds computed from their arguments or from stored state, so they take no clock value. Storing a time is different. `proposeParams` must store the effective time `now + paramsDelay`, and since the contract cannot obtain `now`, the caller supplies it. A write depends on time when it stores a time value that the contract cannot compute from its arguments or its state; a circuit that only compares block time with a bound computed from its arguments or its state is not such a write. Every Bus Registry write that depends on time MUST take a caller-supplied clock value and check it against block time within a stated tolerance, 900 s in the compiled contract. In that contract, `proposeParams` is the only circuit that takes such a value. A transaction that waits in the pool longer than the tolerance fails.

A circuit also cannot read its own Merkle root: `root()`, `firstFree()` and `pathForLeaf()` are available to off-chain code only.^[LFDT-Minokawa/compact, doc/ledger-adt.mdx, sections `MerkleTree` and `HistoricMerkleTree`; main branch, accessed 1 October 2026.] The Bus Registry therefore keeps no map from root to publication or supersession time. The Ledger Adapter derives both from the timestamps of the finalized blocks whose transactions changed a period's tree (`MPE-ECO-027`, `MPE-NET-055`).

**Arithmetic.** Compact has no division, modulo or bitwise operators. For the Anchor slot, the caller supplies the quotient `q` and the circuit checks `q × 2,940 + slot = window`. For window 29,833,333, the minute that begins at Unix time 1,789,999,980, the caller supplies `q` = 10,147 and `slot` = 1,153, and the circuit checks 10,147 × 2,940 + 1,153 = 29,833,333. Compact casts `Uint` values to bytes in little-endian order, so the big-endian fields of a `Misc` payload are byte-reversed in the circuit.

**Governance.** In the compiled contract one steward commitment governs the Bus Registry, and the parameter time-lock is deployed with a delay of 0 (DEC-019). Only parameter changes go through the time-lock there; relay-list changes take effect at once.

The steward's powers end at the circuits in the table. Midnight's ledger also keeps with each contract a **contract maintenance authority**, a committee of keys with a signature threshold that can insert and remove the verifying keys of the contract's circuits.^[midnightntwrk/midnight-ledger, onchain-state/src/state.rs, struct `ContractMaintenanceAuthority` (`committee`, `threshold`); ledger-wasm/src/contract.rs, `VerifierKeyInsert`, `VerifierKeyRemove` and `ReplaceAuthority`; accessed 1 October 2026.] Replacing a verifying key replaces the circuit, so this authority can change or remove any check in the table, the steward's included. Who holds it for the Bus Registry until open admission ends is not yet decided. Production requires the following:

- a relay-list or parameter change takes effect no earlier than P-OPS-6 after approval;
- an unratified emergency action lapses after P-OPS-7;
- a steward set with time locks governs the Bus Registry;
- before open admission ends, the Bus Registry's contract maintenance authority is transferred to Midnight federated governance or removed (`MPE-OPS-012`, `MPE-OPS-013`, `MPE-OPS-020`, `MPE-OPS-023`).

Ratification and lapse are not yet compiled, and it is not known whether a ledger-9 contract maintenance authority can be made to wait before it replaces a verifying key. A devnet test must settle this (`MPE-OPS-017`).

While the pause flag is set, `register` and `postAnchor` fail. Revocation and pruning stay open, so exits and evidence survive a pause. If bonds are ever enabled, withdrawal and slashing calls also keep working (`MPE-OPS-014`).

**Why emitting bytes is expensive.** Compact packs a `Bytes<n>` value into field elements. Every operation that needs individual bytes adds division instructions of about 670 rows each: a byte spread, an index, a `Uint`-to-bytes cast, or the encoding of an `emit` payload that is not a constant. Emitting a constant 256-byte payload costs 23 rows (k = 6). Emitting a 256-byte circuit argument costs 166,241 rows (k = 18). Three chained SHA-256 node hashes cost 133,922 rows when the preimage is assembled by byte concatenation and 12,674 rows when it is a struct of byte fields, with identical digests.

Protocol hashes that a circuit computes MUST therefore take struct preimages of fixed-width fields, never byte-level concatenation. Each version MUST keep the non-constant bytes a circuit emits as few as the protocol allows: 72 B of fields for an Anchor and 35 B for a governance event. Two Midnight capabilities would lower these costs, and the Rationale states them: a cheaper `emit` path for public byte payloads, and a way to read block time or a contract's own Merkle root inside a circuit.

**Segment placement.** A transaction carries one or more intents. An intent is a sealed bundle of contract calls, numbered within its transaction; MIP-0019 calls it the physical intent [@midnight-mip-0019], and each event's source records its number in the field `physical_segment`. The guaranteed segment, holding the guaranteed part of every intent, runs first, and each intent's fallible segment runs after it. A fallible segment that fails has its state changes and events discarded, while the guaranteed segment stays applied and the fee stays paid.

The ledger divides a call's transcript between the two segments only at checkpoints. A checkpoint is a `kernel.checkpoint()` call inside a circuit. It marks all execution before it as one atomic unit, so the ledger may place the transcript up to a checkpoint in the guaranteed segment and the rest in the fallible segment.^[LFDT-Minokawa/compact, doc/ledger-adt.mdx, section `checkpoint`; main branch, accessed 1 October 2026.] None of the three contracts calls it, so each of their transcripts is one unit and lands whole in one segment. A transcript without a checkpoint goes whole into the guaranteed segment only if its modelled cost fits the time-to-dismiss budget, which bounds the work a Midnight node spends before it can reject a transaction: `max(2 µs × transaction bytes, 15 ms)` less a per-transaction reserve. Otherwise all of it goes into the fallible segment.^[midnightntwrk/midnight-ledger, ledger/src/construct.rs, guaranteed and fallible segment partitioning; tag ledger-9.1.0.0-rc.4, accessed 1 October 2026.] By the derived gas, `register`, `postAnchor` and the 16-part ledger-lane call all exceed that budget, so their effects and events land in the fallible segment. This placement is derived, not observed. Each call's events still share one segment of one intent, but a caller MUST confirm that the transaction was included and that its fallible segment succeeded before treating the effect as done [@midnight-mip-0019].

#### Binding admission to Bus Registry roots

Suppose a client proves membership against root `R` and another registration replaces `R` ten seconds later. A Bus Node that accepted only the newest root would drop that client's MPE Envelope. One that accepted every past root would let a revoked member keep publishing under a root that still contains its leaf.

The Admission Slot, laid out with the MPE Envelope in the Specification, names a membership root. A Bus Node MUST treat that root as valid only if it is a root of the current period's tree in finalized Bus Registry state, or was such a root and was superseded less than P-ECO-5 (3,600 s) before, where its supersession time is the timestamp of the finalized block whose transaction replaced it (`MPE-ECO-015`).

Keeping a window of recent roots follows RLN relay, where routing peers accept a window of past roots so that proofs made just before an update still verify [@2021-vac-waku2-rln-relay-spec]. The contract cannot enforce this window, because `HistoricMerkleTree.checkRoot` accepts every past root until the history is reset, so Bus Nodes enforce it off chain. Every registration changes the root, and the set of roots valid inside the window can be large. The Ledger Adapter keeps it in full.

A Bus Node MUST Ignore an MPE Envelope whose root serves a membership period that ended more than P-ECO-5 before the Bus Node's clock (`MPE-ECO-051`). This caps forwarding under a cached root at 86,400 + 3,600 = 90,000 s, or 25 h, and matches `prunePeriod`, which may remove the tree at the same moment. Ignore drops an MPE Envelope without penalizing the Bus Node that forwarded it; Reject drops it and lowers that Bus Node's score. While the Ledger Adapter view is stale, every check that depends on chain state or the clock therefore returns Ignore, never Reject (`MPE-NET-018`).

A Store Node that validates a back-filled MPE Envelope looks up the historic root and its period. It accepts roots published within the last 172,800 + 3,600 = 176,400 s (`MPE-NET-056`, `MPE-SEC-013`).

The membership leaf commits the per-class limits. The Admission Proof shows three things:

- a credit index below the limit for the MPE Envelope's class (`MPE-ECO-016`);
- an admission nullifier derived from the secret, admission window, class and index (`MPE-ECO-017`);
- a share bound to the Envelope Identifier (`MPE-ECO-018`).

Revocation takes effect at Bus Nodes once the revoking transaction is in a finalized block and every root of that period's tree that still contains the leaf has left the P-ECO-5 window, at most 3,600 s after the revoking block (`MPE-ECO-029`).

The binding is only as private as the Admission Proof. In the proof of concept the admission check will be a stand-in that lets every Bus Node learn every admission secret and link each MPE Envelope to its membership. Because revocation evidence proves only knowledge of `a0`, the stand-in also lets every Bus Node revoke any member; Security Considerations states the consequences. The stand-in is acceptable on devnet and testnet only.

#### Anchors

The overlay leaves no public record that the network accepted a Message by a given time. An Anchor is that record. A Subscriber compares its counts with what it holds, and a Consumer can later prove to a contract that a Message existed by a deadline.

In version 1, an MPE Envelope belongs to window `w = floor((expiry - 172,800) / 60)`, the minute in which it was created. Every Bus Node, Store Node and client library computes `w` from the visible header, so all of them put an MPE Envelope in the same window. The batch root of a Shard is the RFC 6962 Merkle tree hash over the window's Accepted Envelope Identifiers, sorted in ascending byte order (`MPE-NET-051`):

- a leaf is `SHA-256(0x00 || EID)`;
- a node is `SHA-256(0x01 || left || right)`;
- the empty tree is the SHA-256 of the empty string;
- the left subtree holds the largest power of two smaller than the leaf count.

For three identifiers the left subtree holds the first two, so the batch root is `SHA-256(0x01 || SHA-256(0x01 || leaf_1 || leaf_2) || leaf_3)`. The prefixes 0x00 and 0x01 keep a leaf from passing as an inner node.

The window root applies the same construction to the per-Shard batch roots, in Shard order. An anchorer MUST wait 20 s after a window closes, because Bus Nodes accept a window's MPE Envelopes for up to P-ECO-6 = 20 s after it ends. It MUST submit at most one Anchor per non-empty window, covering every Shard, and none for an empty window (`MPE-NET-041`).

Continuing the example under Arithmetic, an MPE Envelope created at Unix time 1,790,000,030 has expiry 1,790,172,830 and falls in window 29,833,333, which closes at 1,790,000,040. Its Anchor can be posted no earlier than 1,790,000,060, into slot 1,153.

The Anchor's authoritative form is its record in Bus Registry state. The copy that travels as the payload of one `Misc` event named `mip-xxxx:anchor[v1]` (`MPE-FMT-047`, `MPE-NET-050`) is a notification: contract events are not consensus state [@midnight-mip-0002], so the event alone never makes a Message `final`. The payload layout does not depend on the Shard count.

| Offset | Length (B) | Field |
|---|---|---|
| 0 | 8 | Window number, unsigned, big-endian |
| 8 | 32 | Window root |
| 40 | 32 | Eight Envelope counts, unsigned 32-bit big-endian, in Shard order. Zero for Shards at or above the Shard count |
| 72 | 184 | Zero |

A reader MUST reject an Anchor whose fill is not zero or whose count for an inactive Shard is not zero. The payload does not say where the active counts end, so the reader takes the Shard count from the Bus Registry's parameters. At one Shard the seven unused counts, 28 bytes at offsets 44 to 71, must be zero just as the fill must. All 212 bytes after the first count must then be zero, and a non-zero byte there is rejected whether it is a bad count or bad fill. An Anchor decoder MUST therefore accept the full 256-byte payload and check the fill; a decoder that reads only the first 72 bytes cannot apply this rule.

`postAnchor` runs these checks:

1. The Bus Registry is not paused.
2. `peer` is listed with the anchorer role, and the caller knows the preimage of its anchor-key commitment (`MPE-NET-053`).
3. `slot < 2,940` and `q × 2,940 + slot = window`.
4. The window closed at least 20 s ago: `blockTimeGte(60 × (w + 1) + 20)`.
5. The window is younger than the live history: `blockTimeLt(60 × (w + 1) + 176,400)`.
6. At least one count is non-zero, and every count for an inactive Shard is zero.
7. The slot holds no record for the same or a newer window. The first valid Anchor for a window wins, and a later, different one is refused.

On success the circuit writes the record over the record 2,940 windows older in the same slot, writes the Anchor-tree leaf at the slot and emits the event. `pruneAnchor` lets anyone remove a record older than P-STO-9 (176,400 s) that no later Anchor has replaced. The slot rule makes the bound of 2,940 live records structural (`MPE-STO-028`, `MPE-STO-029`).

A record holds the window, the root and eight counts: 8 + 32 + 32 = 72 B. So 2,940 records take 211,680 B before the ledger's storage overhead and the Anchor tree (derived). The Anchor tree keeps every past root until its history is reset, and the compiled contract never resets it. The set of accepted Anchor-tree roots therefore grows by one root per Anchor, 1,440 a day, which at 32 B per root is about 46 KB a day before overhead (derived). A periodic reset would bound it but would invalidate reaction proofs made against older roots. The reset rule and the age limit it puts on reactions are open.

One Anchor transaction is about 10,340 B, and its fee is 0.195 DUST, or 0.244 DUST with the wallet margin (derived). At 1,440 Anchors a day the cost is about 280 DUST a day at genesis prices (1,440 × 0.195). The bytes come to 14.9 MB a day, 0.10 percent of a 14.4 GB daily block-usage budget at 1,000,000 B per 6 s block.^[midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, `blockUsage: 1000000`; main branch at 887348f9, accessed 1 October 2026.] If the live block-usage limit is the ledger's initial 200,000 B, the share is 0.52 percent. Which value is live is unknown until it is measured on a ledger-9 network.

Every Anchor is a k = 18 proof, so each anchorer proves once a minute, and the payload bytes take most of its rows. Verifiers that need an Anchor older than the live history use its `Misc` copy to locate it (DEC-024). They then confirm it against Bus Registry state read at a finalized block inside its live period, a read that needs a source keeping historic contract state. Per-Shard counts are public and appear in the ledger leakage declaration (`MPE-PRV-038`).

For P-STO-9 after anchoring, the anchorer MUST serve the full leaf list of each window and Shard and, on request, the inclusion path of an anchored identifier: its leaf index and count, the path to the batch root, the batch root, and the path from the batch root to the window root (`MPE-NET-052`). At 600 leaves and 8 Shards a path is 13 × 32 = 416 B (derived). Subscribers use leaf lists only. A per-identifier path is requested only by a Consumer that has decided to react.

#### Ledger Adapter

The Ledger Adapter is the only component that reads Midnight or submits to it. It exposes one interface, which a mock can implement for testing (`MPE-NET-035`). It returns only state from finalized blocks and never acts on unfinalized state, so no rollback is ever needed (`MPE-NET-036`). Admission roots and parameters come from contract state, not from `contractEvents` (`MPE-NET-037`). Every read has a fixed source on Midnight and serves a named requirement.

| Read | Source on Midnight | Requirements |
|---|---|---|
| Finalized head: height, hash, block time | `chain_getFinalizedHead` and the header | `MPE-NET-019` |
| Current membership root of each period's tree, relay list, parameters, pause flag, live Anchors | `midnight_contractState` at the finalized hash, or the Indexer's contract state when confirmed | `MPE-NET-055` |
| Publication and supersession time of each membership root | Timestamp of the finalized block whose transaction changed the tree (`register`, `revoke`) | `MPE-ECO-027`, `MPE-NET-055` |
| Historic root with its period | The same root history, kept for 176,400 s | `MPE-NET-056` |
| Anchors older than the live history | `contractEvents` with the Bus Registry address and type `MISC`, name `mip-xxxx:anchor[v1]`, confirmed against historic Bus Registry state | DEC-024 |
| Ledger-lane parts | `contractEvents` with the ledger-lane contract address and type `MISC` only | `MPE-CON-053` |
| `ledgerParameters` | Indexer `Block.ledgerParameters` of the latest finalized block | `MPE-ECO-008` |
| Submission and status | The wallet's existing balancing and submission path | `MPE-NET-035` |

A deployment fixes two contract addresses, the Bus Registry and the ledger-lane contract. Clients are configured with both, as they are with the Network Identifier.

`midnight_contractState` reads the best block unless it is given a block hash, so the adapter MUST pass the finalized hash.^[midnightntwrk/midnight-node, docs/openrpc.json, method `midnight_contractState`, parameter `at` ("defaults to best block"); main branch at 887348f9, accessed 1 October 2026.] Here the Indexer is the Foundation's: "a service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]. Its chain indexer follows finalized blocks only.^[midnightntwrk/midnight-indexer, chain-indexer/src/infra/subxt_node.rs, function `subscribe_finalized_blocks`; main branch at 7842950e, accessed 1 October 2026.]

In production the adapter reads P-NET-14 = 2 independent chain sources. It MUST mark its view stale if they report different admission roots for the same finalized block (`MPE-NET-020`). An Indexer result that these sources do not confirm never authorizes admission, an Anchor or a `final` label (`MPE-SEC-022`). This follows MIP-0018, which requires consumers to verify Indexer-supplied data "against authenticated on-chain data before treating it as authoritative" [@midnight-mip-0018]. The view is also stale when the local clock and the finalized block time differ by more than 60 s (`MPE-NET-019`). Each adapter outcome maps to one client outcome, except a successful read, which maps to none.

| Adapter outcome | Meaning | Client outcome |
|---|---|---|
| `Ok(value, block)` | Value read at a finalized block | none |
| `Stale` | Sources disagree, or the clock and finality differ by more than 60 s | Chain-dependent checks Ignore; no new `final` label |
| `Unavailable` | No source answers | `LedgerUnavailable` |
| `Paused` | Midnight rejects user transactions (safe mode or transaction pause) | `LedgerPaused` |
| `BusPaused` | The Bus Registry pause flag is set | `BusPaused` |
| `Limit` | The transaction would exceed the transaction or block limits | `ResourceExhausted` |
| `InsufficientDust` | The quoted fee exceeds the balance (detected before proving) | `InsufficientDust` |
| `Invalid` | The ledger rejected the transaction | `Refused` |

A submitted transaction is `Pending`, `Included(height)`, `Final(height)` or `Failed(reason)`. A transaction whose effects lie in the fallible segment is `Final` only if that segment succeeded. The Midnight node's call filter puts all user traffic behind safe mode and the transaction pause.^[midnightntwrk/midnight-node, runtime/src/lib.rs, `type BaseCallFilter = InsideBoth<SafeMode, TxPause>`; main branch at 887348f9, accessed 1 October 2026.] While either is active:

- Bus Nodes keep relaying MPE Envelopes admitted under previously accepted roots until those admissions expire (`MPE-NET-038`);
- clients keep delivering `gossip` Messages (`MPE-CON-051`);
- reaction and ledger-lane calls return `LedgerPaused` (`MPE-CON-050`).

A block is final when GRANDPA, the voting protocol that runs beside block production, finalizes it. Midnight documents this as about 3 blocks, or about 18 s [@midnight-mps-0028]; no code constant fixes it. A Message created at the start of a window therefore waits at least 60 + 20 + 6 + 18 = 104 s for its Anchor to become final, plus the anchorer's proving time and the polling time (derived). The four terms are the rest of the window, the anchorer's wait, one 6 s block to include the Anchor transaction, and finality. The proving time of the k = 18 Anchor circuit is not measured, and the unanchored notice threshold P-CON-8 = 300 s leaves a margin only if proving takes well under 196 s (300 - 104). The time from publication to `final` has not been measured.

A deferred `in-block` label, with rollback of values from blocks that a reorganization removes as MIP-0018 requires [@midnight-mip-0018], is reserved for use if MPS-0028 produces a best-chain Indexer view [@midnight-mps-0028]. It is not part of this version.

#### Ledger lane

The ledger lane is a last resort. An application MUST select it explicitly, and the library MUST NOT switch to it automatically (`MPE-PRV-013`, DEC-008). The ledger-lane contract does not read the Bus Registry's pause flag, because that would add a cross-contract call and a second proof to every publication. While the flag is set, the library refuses ledger-lane publication with `BusPaused`.

A `Misc` payload holds 256 bytes, the size of a class-0 Sealed Body. A class-1 body of 1,024 B therefore travels as 4 parts, a class-2 body of 4,096 B as 16, and a class-3 body of 16,384 B would need 64.

**Publisher rules.** A Publisher MUST place exactly one MPE Envelope in one intent of one transaction, with every part in the same segment of that intent, guaranteed or fallible (`MPE-FMT-042`). It SHOULD emit the whole Sealed Body with one call to the class circuit. It MAY instead use one `publishPart` call per part within that intent. The intent emits the Sealed Body as consecutive 256-byte parts, in order, each in its own `Misc` event named `mip-xxxx:envelope[v1]`, with 288 bytes of struct data (`MPE-FMT-040`, `MPE-FMT-041`, `MPE-FMT-043`).

The guaranteed segment is preferred, but the 16-part call exceeds its budget and lands in the fallible segment. The Publisher MUST therefore confirm inclusion and success of the fallible segment before it reports `final`. No Admission Slot travels on the ledger lane: the transaction fee, paid in DUST, is the only rate limit.

**MIP-0019 opt-in.** Midnight Express adopts the MIP-0019 multipart rule [@midnight-mip-0019] for the event name `mip-xxxx:envelope[v1]`, NUL-padded to 32 bytes and emitted by the deployment's ledger-lane contract. Its declared multipart rule is `mip-xxxx:multipart[v1]`, the rule label as MIP-0019 writes it. No other name used by Midnight Express opts in. MIP-0019 is Proposed, not Accepted. If a Proposed prerequisite is not accepted, the reconstruction rule below stands on its own text, and MIP-0019 remains its source.

On the transport side, a reader groups the matching applied events of one included transaction and one intent and concatenates their full 256-byte payloads in ledger emission order. The rule has no boundary inside an intent, so one MPE Envelope per intent is required. Above the transport, Midnight Express adds an application validity rule. MIP-0019 accepts every non-empty group as a package, but an MPE package is valid only if it has 1, 4 or 16 parts, for classes 0, 1 and 2. A class-3 MPE Envelope would need 64 parts, more than P-FMT-8 = 16. The library MUST return `TooLarge` for it before constructing any transaction (`MPE-FMT-044`).

**Reader rules.** A reader MUST apply these rules:

1. Query `contractEvents` with the ledger-lane contract address and `types: [MISC]` only. The shipped filter field is `types`, not MIP-0002's `eventType`. Within one Indexer instance, resume from the Indexer's monotonic `id`, which the Ledger Adapter translates to the MPE cursor. Across instances, resume by block height, because nothing documents whether `id` values agree between instances. Drain every event up to the finalized head before closing any group, because a burst cut by pagination would lose parts.
2. Keep only events whose name is `mip-xxxx:envelope[v1]`.
3. Group by transaction and intent, the intent being read from the `physical_segment` field, in emission order, counting only applied events. The GraphQL `ContractEvent` type exposes neither the intent nor a position.^[midnightntwrk/midnight-indexer, indexer-api/graphql/schema-v4.graphql, `interface ContractEvent` and `type MiscContractEvent`; main branch at 7842950e, accessed 1 October 2026.] The reader therefore decodes the `raw` field, which holds the whole tagged ledger `Event` including its `EventSource`.^[midnightntwrk/midnight-indexer, indexer-common/src/domain/ledger/ledger_state.rs, function `make_ledger_events_v9`; midnightntwrk/midnight-ledger, ledger/src/events.rs, struct `EventSource` (`transaction_hash`, `logical_segment`, `physical_segment`); accessed 1 October 2026.]
4. Apply the validity rule. Discard and count any group with a part count other than 1, 4 or 16, or with a payload that is not 256 bytes. Then continue: one malformed group must not block the others (`MPE-FMT-046`).
5. Reconstruct the header bytes that the associated data covers. The version comes from the name, the class from the part count, the Shard from the stream secret, and the reserved byte is zero. Expiry is the signed creation time plus 172,800 s, checked after opening. Then run the same Recognition Tag test and opening as on the overlay (`MPE-FMT-037`, `MPE-FMT-045`).
6. Before labelling the Message `final`, verify the group against authenticated on-chain data: the part bytes, the emitting contract, inclusion in a finalized block and success of the segment that emitted the parts. The data must be confirmed by P-NET-14 independent sources or by replaying the block (`MPE-CON-016`, `MPE-SEC-022`) [@midnight-mip-0018]. An Indexer response alone establishes none of these facts.
7. Deduplicate against overlay copies by Envelope Identifier and logical identifier. Deliver with carrier `ledger`, and with label `final` only after step 6. Before that the label is `gossip`.

**Fees and proving.** Derived fees at genesis mainnet prices depend on the shape of the ledger-lane transaction.

| Transaction | Block bytes (estimated) | Dominant cost | Fee, DUST (with wallet margin) |
|---|---|---|---|
| One part alone (`publishClass0`) | about 8,330 | compute | 0.129 (0.161) |
| 16 parts in one call (`publishClass2`) | about 12,920 | compute | 0.188 (0.236) |
| 16 `publishPart` calls in one intent | about 80,260 | block bytes | 0.866 (1.084) |
| Each further part inside one call | +306 | block bytes or compute | +0.0032 to +0.0068 (+0.0040 to +0.0085) |

The fee is `overall_price × (max(read, compute, block bytes) + net bytes written + bytes churned)`, with each dimension divided by its block limit and an overall price of 10 DUST.^[midnightntwrk/midnight-ledger, base-crypto/src/cost_model.rs, fee computation and `impl From<RunningCost> for SyntheticCost`; tag ledger-9.1.0.0-rc.4, accessed 1 October 2026; midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json; main branch at 887348f9, accessed 1 October 2026.] Contract proofs are 4,368 B and the DUST spend proof is 2,912 B. The class-0 block-byte figure is the 16-part figure less 15 parts of 306 B. Live prices move by up to about 4.6 percent per dimension per block, and mainnet still runs the ledger-8 parameter schema.

One call per MPE Envelope costs 4.6 times less in fees than 16 separate calls (0.188 against 0.866 DUST), but the single call is the more expensive shape to prove: about k = 22 for 16 parts against k = 18 for each separate part. P-FMT-8 stays at 16 parts as the fee limit. Whether to lower the in-contract limit to 4 parts (k = 20) is open until proving time is measured or a cheaper `Misc` encoding exists.

**Capacity.** Two block limits can bind the ledger lane, and they count different bytes. The `block_usage` limit counts the transaction's bytes in the block, which grow by 306 B of call arguments per part. The `bytes_written` limit counts the event bytes that execution produces. MIP-0002 states that an event's serialized size counts as both written and deleted bytes, with about 40 bytes of overhead per event [@midnight-mip-0002], which gives 288 + 40 = 328 B per part. At that size the 50,000 B `bytes_written` budget per block binds before a block-usage budget of 1,000,000 B for classes 1 and 2.

Chain-wide capacity of the ledger lane depends on which of these limits binds, and only a tenth of it falls inside the production chain-share budget. The `bytes_written` column divides 50,000 B by the serialized group size. The `block_usage` columns divide each limit by the estimated transaction size from the fee table: about 8,330 B for one part, 8,330 + 3 × 306 = 9,248 B for four parts in one call, and about 12,920 B for sixteen.

| Class | Parts | Struct data (B) | Serialized at 328 B per part (B) | Per block, `bytes_written` 50,000 B | Per block, `block_usage` 1,000,000 B | Per block, `block_usage` 200,000 B | Chain-wide per second (1,000,000 B to 200,000 B) | Within a 10% share (P-ECO-8) |
|---|---|---|---|---|---|---|---|---|
| 0 | 1 | 288 | 328 | 152 | 120 | 24 | 20.0 to 4.0 | 2.0 to 0.40 |
| 1 | 4 | 1,152 | 1,312 | 38 | 108 | 21 | 6.3 to 3.5 | 0.63 to 0.35 |
| 2 | 16 | 4,608 | 5,248 | 9 | 77 | 15 | 1.5 | 0.15 |
| 3 | 64 | refused | none | none | none | none | none | none |

Each chain-wide range runs from the 1,000,000 B case to the 200,000 B case, and its lower end is the lowest figure for that class. In each case the per-second figure takes the smaller of the `bytes_written` count and that case's `block_usage` count, the limit that binds, and divides it by one block every 6 s. For class 1, 50,000 B admits 38 groups of 1,312 B per block. With 1,000,000 B of block usage 108 transactions would fit, so `bytes_written` binds at 38 / 6 = 6.3 per second; with 200,000 B only 21 fit, and `block_usage` binds at 21 / 6 = 3.5. For class 2, `bytes_written` binds in both cases.

The last column applies P-ECO-8, the production chain-share budget, whose decision is still open. Under it, registrations, Anchors and ledger-lane parts together are to use no more than 10 percent of either the `block_usage` or the `bytes_written` limit, averaged over 24 h (`MPE-ECO-011`). Each figure in the column is one tenth of the chain-wide figure beside it. Because registrations and Anchors draw on the same share, these figures bound the ledger lane's production allowance from above, and the ledger lane cannot count on reaching them.

Three quantities are not yet established:

- which `block_usage` value is live;
- the serialized size per part;
- whether event bytes count against `bytes_written` at all.

Compact's local simulator counts 693 B for each additional part (414 B for a one-part call), which would roughly halve the `bytes_written` figures. The ledger-9 cost code converts event bytes into churn, so net bytes written would stay near zero, and compute and block usage would then bind first. The 16-part call needs 27.6 ms of compute, and the 2 s compute limit of one 6 s block admits 72 such calls (2,000 / 27.6, derived). One measurement on a ledger-9 devnet or Stagenet, of one part and of 1, 4 and 16-part groups, would settle all three. Until it exists, this specification plans with the lowest chain-wide figure in each row, the 200,000 B end of each range: 4.0 class-0, 3.5 class-1 and 1.5 class-2 Messages per second for the whole chain (`MPE-PRF-040`, `MPE-ECO-011`). These are ceilings of the chain itself, which the measurement of `MPE-PRF-040` reports. Inside the P-ECO-8 share the ledger lane's production allowance is at most a tenth of them: 0.40, 0.35 and 0.15 Messages per second.

Each part is below the 1 KiB limit above which the ledger-9 virtual machine drops an event without error.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, constant `MAX_LOG_EMITTED`; tag ledger-9.1.0.0-rc.5, the generation the node pins, accessed 1 October 2026.] Ledger-lane delivery latency, which includes the Publisher's proving time and finality, has not been measured.

The ledger lane makes public the ledger-lane contract, the time, the part count and therefore the class, the fee and the ciphertext. All of these stay in chain history for good. As MIP-0019 states, application encryption "does not hide that metadata or retract disclosed data" [@midnight-mip-0019].

#### What changes in Midnight

Nothing changes in the Midnight node, the ledger, the virtual machine or the Compact compiler. The Bus Registry, the ledger-lane contract and the consumer pattern are new contracts written with existing types and a released toolchain. They are implementable today at the costs stated above, compiled for ledger 9, which mainnet does not yet run. The wallet changes are listed under Consumer interface.

The Indexer needs no change for Midnight Express to work, because readers can decode `raw`. Five Indexer additions are recommended:

- expose the intent and an emission position on each contract event;
- document that `id` order matches ledger emission order within a transaction;
- index `Misc` names for the two Midnight Express contracts. This uses MIP-0002's allowance that `Misc` indexing may be "configured by policy" [@midnight-mip-0002] and is not an API change;
- document a contract-event retention of at least 176,400 s, the live Anchor history;
- document whether `id` values agree across Indexer instances.

MPS-0007 [@midnight-mps-0007] is Proposed and has no MIP, and it is not a dependency. A MIP answering it would let lane readers and Bus Operators verify event bytes from their own Midnight node instead of an Indexer, which is the verification MIP-0018 asks for.

### Consumer interface

Every Consumer reaches Midnight Express through one client library: autonomous agents, contracts through reaction transactions, and wallets. The operations below are language-neutral, and the proof of concept will provide them in Rust. Overlay, gateway and ledger-lane deliveries come through the same subscription call as the same item type (`MPE-CON-019`), so an application can act on a Message without knowing which carrier delivered it.

Retention, receipts, Anchors, replay protection, whole-Shard feeds, historical retrieval, reconciliation, delivery deduplication and processing semantics are Midnight Express application mechanisms. GossipSub's bounded caches and dissemination do not provide them.

#### Subscription without revealing interest

A client that asks a server for the Messages matching a filter tells it which stream it follows. A Midnight Express client instead receives every MPE Envelope of a Shard and decides locally which are its own. It pays in bandwidth for requests that do not depend on its interest.

A Subscriber obtains stream keys only by importing an invitation received outside Midnight Express (`MPE-PUB-008`). It never sends an audience key, recognition key or Recognition Tag filter to a Bus Node, Store Node or Indexer (`MPE-PUB-010`). In the default mode it retrieves every unexpired MPE Envelope of each Shard it follows (`MPE-PUB-011`) and tests every one locally. The content, size and timing of its requests MUST NOT depend on which MPE Envelopes match (`MPE-PUB-012`). Four further rules follow:

- receipts and Anchor checks are requested per window, never per recognized Message;
- repair retrieves complete differing Shard windows, never only recognized or missing identifiers;
- recognizing a Message triggers no message, acknowledgement, retry, error report or transaction (`MPE-CON-039`);
- a ledger-lane reader's Indexer queries name only the ledger-lane contract address and the `MISC` type (`MPE-CON-053`).

These rules exclude by design the relevance model planned for MPS-0005 Phase 2, in which an Indexer keeps a per-wallet table of relevant events and decrypts per wallet session [@midnight-mps-0005]. Topic filtering at the Indexer, as MPS-0005 plans it, and MIP-0002's prefix filters [@midnight-mip-0002] correspond to reduced-privacy selective profiles in this design. They are not the default.

A reduced-privacy retrieval mode MUST be enabled only by explicit opt-in for each subscription (`MPE-PUB-016`). If the active mode cannot be sustained, the library reports `Degraded` and does not switch modes (`MPE-PRV-013`).

These rules hide interest within a fixed set of received Shards, but they do not hide participation. A Bus Node still sees the following:

- the client's connection identity and address;
- the Shards it follows, which the GossipSub topic names disclose together with the network prefix and major version;
- its online schedule and traffic volume.

With one Shard at launch, the Shards a client follows reveal nothing, but participation and traffic remain visible. The property holds only if every client behaviour, including repair, retries, errors and diagnostics, stays independent of recognition. Whether a complete client meets that condition stays unknown until paired transcripts that include repair and error paths are compared.

At the baseline mix, the class and rate mix that Chapter 9 defines, a Shard carries 21,584 B/s of MPE Envelope bytes, so whole-Shard reception costs about 1.86 GB per day before transport framing (derived: 21,584 × 86,400 = 1,864,857,600 B). That fits a desktop or service host but not a mobile budget of 56 to 60 MB per day.

A stream secret handed to an auditor is a coarse, irrevocable viewing capability over the whole stream, comparable to the custody viewing capability of MIP-0012 [@midnight-mip-0012].

| `capabilities()` | Reports carriers, Shard count, active profile, and the back-fill window as the minimum of source retention and local key retention | `MPE-CON-030` |
| `importInvitation(inv)` | Installs a stream's keys, up to 256 recognition keys | `MPE-PUB-008`, `MPE-CRY-016` |
| `subscribe(from?)` | One stream of items for all followed Shards and installed keys, from an optional committed cursor | `MPE-CON-019`, `MPE-CON-028` |
| `processOnce(item, handler, store)` | Commits the handler's effect, the cursor and the deduplication state in one atomic write | `MPE-CON-033` |
| `publish(message, class?)` | Seals, admits and submits with retries. Returns exactly one of `accepted`, `final` or `failed{reason}` | `MPE-CON-026` |
| `selectProfile(profile)` | Explicit opt-in to the ledger lane or a reduced-privacy mode | `MPE-PRV-013`, `MPE-PUB-016` |
| `publishOnLedger(message)` | Ledger-lane publication through one class circuit call | `MPE-FMT-040` to `MPE-FMT-044` |
| `carryEvent(tx, position, stream)` | Publishes a carried event (see Carried events) | Carried events |
| `fetch(reference)` | Fetches an object referenced inside a Message, only when called | `MPE-FMT-038` |
| `inclusionProof(eid)` | Fetches a per-identifier Anchor path. Only for a reaction | `MPE-NET-052` |
| `buildReaction(item, target, options)`, `submitReaction(tx)` | Prepares and submits a contract reaction | `MPE-CON-042`, `MPE-PUB-047` |
| `meter()` | Bytes received per Shard per UTC day | `MPE-CON-054` |

`accepted` means that the named ingress Bus Node completed Midnight Express application acceptance and committed its acceptance state. It does not prove remote mesh receipt, delivery, storage durability or finality. A failure to enqueue the MPE Envelope for publication is reported separately. `Busy` and `Refused` are Midnight Express service replies, not GossipSub validation outcomes.

#### Items, labels and guarantees

A subscription delivers eleven kinds of item.

| Item | Meaning | Requirements |
|---|---|---|
| `message` | Authenticated Message: identifier, publisher, logical identifier, sequence number, schema, payload, attributes | `MPE-PUB-036` |
| `late` | Message whose sequence number lies in an open gap | `MPE-PUB-040` |
| `undecodable` | Authenticated Message with an unregistered schema | `MPE-PUB-049` |
| `finalised{eid}` | A `gossip` Message is now `final` | `MPE-CON-017` |
| `unanchored{eid}` | No covering Anchor within P-CON-8 (300 s) | `MPE-CON-018` |
| `unmatched{eid}` | A carried event did not match a finalized transaction within P-CON-8 | Carried events |
| `stored{eid}` | Retention receipts completed after delivery | `MPE-STO-012` |
| `incomplete{window}` | An Anchor covers identifiers the client never received | `MPE-CON-038` |
| `gap{publisher, range, reason}` | `sequence` after P-PUB-7 (120 s), `overflow` beyond P-CON-9, `retention-exceeded` or `key-erased` | `MPE-PUB-039`, `MPE-PUB-045`, `MPE-PUB-046`, `MPE-CON-023` |
| `lost` | Gap still open 172,800 + 60 s after it was reported | `MPE-PUB-041` |
| `head{cursor}` | Back-fill has reached the newest MPE Envelope held | `MPE-PUB-042` |

Every `message` carries three independent attributes (DEC-026):

- **Finality.** Exactly one of `gossip` or `final` (`MPE-CON-015`). `final` means one of two things (`MPE-CON-016`). Either the Envelope Identifier is under an Anchor verified against Bus Registry state read at a finalized block, or the Message arrived as a ledger-lane group verified against authenticated on-chain data in a finalized block. The `Misc` copy of an Anchor never sets `final` on its own. For a carried event, `final` also requires the transcript match described under Carried events.
- **Carrier.** Exactly one of `overlay`, `gateway` or `ledger` (`MPE-CON-057`).
- **Storage.** `stored` is set only after the library holds receipts from P-STO-5 = 3 distinct Bus Operator organizations naming the same identifier and deadline (`MPE-STO-012`). Anchor inclusion never implies `stored` (`MPE-STO-039`).

None of these attributes implies another. A `final` Message may not be `stored`, because an Anchor commits to an identifier and says nothing about who holds the bytes.

The library decides `final` one window at a time. It recomputes the window's batch root from its own inventory, and if the count and the root match the Anchor in Bus Registry state, every Message in that window is `final`. Otherwise it fetches the anchorer's leaf list for the whole window and Shard, verifies the list against the Anchor, and labels the Messages it holds that appear in the list.

The library MUST deliver each unexpired MPE Envelope at least once while at least one configured source that retains it answers (`MPE-PUB-035`). It MUST deliver each Envelope Identifier, and each authenticated pair of publisher and logical identifier, at most once per subscription store (`MPE-PUB-036`, `MPE-PUB-037`). It delivers in authentication order and holds nothing back to restore sequence order (`MPE-PUB-038`). A handler run through `processOnce` therefore commits each Message's effect exactly once per store, even across crashes.

The client library and its sources must meet these targets; GossipSub provides none of them. No guarantee extends past the 48-hour retention or holds if every source withholds an MPE Envelope. Two checks expose withholding but do not prevent it: reconciliation against a second Bus Operator every P-PUB-3 (`MPE-PUB-014`), and the Anchor count check. The default P-PUB-3 is 60 s; whether a shorter interval repairs faster, and at what cost in requests, is open. Neither check proves that every MPE Envelope existed or reached a Store Node.

#### Carried events

Midnight's events are contract events. A Compact circuit emits one with `emit`, the transaction records it, and the Indexer serves it [@midnight-mip-0002; @midnight-coip-0003]. A private event, in the Foundation's sense, is a contract event some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment that the proof checks. It is planned for MPS-0005 Phase 2, whose Part 2 text is not published [@midnight-mps-0005]. Midnight Express redefines neither.

A Message is not a contract event: it is authenticated by its Publisher's signature and committed by an Anchor, and no contract executed it. Midnight Express complements on-chain events and does not replace them. It acts as a transport for a contract event only when the Message carries that event's bytes unchanged, and such a Message is a **carried event**. The event's authority stays with the transaction. The Publisher's signature adds only who forwarded it.

Suppose a contract emits a public event when an order fills. A party that asked the Indexer for it would reveal which contract it watches. If one party forwards the event as a carried event on a stream the others follow, they receive it within seconds without such a query, and each still waits for the chain to confirm it before treating it as `final`.

**Schema.** A carried event uses the reserved schema identifier `636576656e743031` (ASCII `cevent01`), schema version 1. Its payload has this fixed layout.

| Offset | Length (B) | Field |
|---|---|---|
| 0 | 32 | Transaction hash |
| 32 | 2 | Logical segment, big-endian |
| 34 | 2 | Physical segment, big-endian |
| 36 | 2 | Emission index of the event among the transaction's applied events, zero-based, big-endian |
| 38 | 32 | Emitting contract address |
| 70 | 1 | Entry-point name length `e` |
| 71 | `e` | Entry-point name |
| 71 + `e` | 2 | Length `L` of the logged item, big-endian |
| 73 + `e` | `L` | The ledger's serialized logged item (`VersionedLogItem`) for this event, unchanged |

The fields at offsets 0 to 36 locate the event in the chain. The address and entry point are what the event is authenticated to [@midnight-mps-0043]. A single event is at most 1 KB serialized [@midnight-mip-0002]. The payload capacity of each class, which the Specification fixes with the MPE Envelope, is the Sealed Body less 170 B of fixed fields under the default cryptographic profile: 86, 854, 3,926 and 16,214 B for classes 0 to 3. The layout spends 73 + `e` bytes before the logged item, so class 1 holds `L ≤ 781 - e` within its 854-byte payload, since 854 - 73 = 781. Class 2 holds every event: even with a 255-byte entry-point name, 3,926 - 73 - 255 = 3,598 B remain. The Publisher MUST choose the smallest class that holds the whole payload.

**Conditions.** A contract event, public or private, flows through Midnight Express unchanged only under the following conditions.

1. **The bytes exist off chain when the transaction is constructed.** compact-runtime captures emitted events during local circuit execution [@midnight-coip-0003], so the client can forward the logged item exactly as the ledger will record it. Whether Phase 2 ciphertext is formed in the client SDK, and so is available there, is unknown. MPS-0005 lists "client SDK encryption/decryption", which suggests it is.
2. **The chain keeps the binding.** Either the ciphertext stays in the transcript, so Midnight Express only accelerates delivery and hides interest, or the transcript holds a commitment to it, so Midnight Express carries the body. Which of these Phase 2 allows is unknown. The second needs the Phase 2 specification to allow a committed field whose body is not emitted.
3. **The size fits a class** (see Schema).
4. **Recipients recognize it.** Recipients and Publisher share a stream secret by invitation. A Recognition Tag profile derived from the recipient key of Phase 2's `encrypt_for` does not exist and depends on a key type that is not yet specified.
5. **Consumers treat it as unconfirmed until the chain agrees.** The library labels a carried event `gossip` until three checks have succeeded: the transaction is finalized, the bytes match the transcript at the stated position, and that match is verified against authenticated on-chain data [@midnight-mip-0018]. An event emitted in a fallible segment counts only if that segment succeeded [@midnight-mip-0019]. If no match is established within P-CON-8, the library reports `unmatched{eid}` and never labels the event `final`.
6. **No new meaning is added.** The library MUST NOT re-type, re-order or truncate the event. It MUST decode the logged item only with Midnight's decoder for its event type and schema version and never with a Midnight Express schema decoder. The event remains the contract author's claim [@midnight-mip-0002].
7. **The fee is paid once.** The event pays `Log` gas on chain, and any future Phase 2 encryption fee. Carrying it adds no protocol fee. The base, data and encryption fees of MPS-0005 apply to contract events, not to overlay Messages.
8. **Topic values stay sealed.** Any `@topic` value of a carried event travels only inside the Sealed Body and never in a request, a filter or a cleartext field.

Public (Phase 1) contract events can be carried under these conditions today. Carrying a Phase 2 private event is specified only up to conditions 1, 2 and 4. A test of one carried Phase 2 event follows the publication of MPS-0005 Part 2. Where discovery and recovery must work "from chain data alone", as MIP-0012 requires for custody [@midnight-mip-0012], off-chain carriage is not a substitute for the on-chain event.

#### Resume and back-fill

A cursor is the pair (expiry, Envelope Identifier). It is formed from header fields only, so it means the same thing at every Store Node (`MPE-PUB-043`). A client resumes inclusively from (cursor expiry minus 60 s, zero identifier) and drops repeats. The 60 s overlap covers MPE Envelopes accepted out of expiry order (`MPE-CON-028`).

Back-fill requests name complete Shard intervals and carry no Recognition Tag, stream identifier or Envelope Identifier list (`MPE-STO-017`). Responses arrive in pages of 64, each followed by a continuation cursor or `head`. A Store Node that cannot serve a request in full answers `Refused`, `ResourceExhausted` or `RetentionGap`, never an empty page. An empty page would look like an interval in which nothing was published, so a Store Node could use one to hide MPE Envelopes unnoticed.

On the ledger lane, resume follows reader rule 1 under Ledger lane.

#### Agents

An agent runs the library as a long-lived service and handles each item through `processOnce` against its own store. A `gossip` Message lets an agent act within seconds, but an agent that would put value at risk SHOULD wait for `final`. Labels describe what the library has verified; a contract effect rests on its circuit checks, not on any label.

An agent that registers a membership proves locally. The admission secret MUST NOT be sent to a prover outside the client's trust boundary unless that prover is attested, because a remote prover receives the private witness [@midnight-mps-0004].

#### Contracts

A contract cannot subscribe or read the overlay. It consumes a Message only through a later transaction that a Consumer constructs (`MPE-CON-042`). The target contract holds three items:

- a committed publisher set: one key, or a Merkle tree of keys that hides which key signed;
- an action identifier;
- a set of consumption nullifiers. The compiled pattern keeps them as `Map<Bytes<32>, Bytes<32>>`, from consumption nullifier to action.

The consumption circuit takes as private witnesses the signed statement, the signature, the stream secret and the payload fields it uses. The Specification defines the statement layout with the MPE Envelope. The circuit MUST assert each of the following:

1. The signature verifies under a committed key. The statement binds the network, the sealed context, the stream identifier, the logical identifier, the sequence number, the schema, the creation time, the expiry, the payload digest, the destination contract and the action (`MPE-CON-043`).^[LFDT-Minokawa/compact, doc/api/CompactStandardLibrary/exports.md, circuits `ed25519Verify`, `jubjubSchnorrVerify` and `merkleTreePathRoot`; main branch, accessed 1 October 2026.]
2. The statement's destination is this contract and its action is this circuit's action.
3. The stream secret hashes to the stream identifier in the statement. The Message secret is derived from the stream secret and the logical identifier. The consumption nullifier is `SHA-256(pad32("mpe/v1/consume") || N || contract || Message secret)`, a struct of four 32-byte fields. It is disclosed, absent from the set and inserted in the same transaction and segment as the effect (`MPE-CRY-025`, `MPE-CON-044`).
4. The Message has not expired. The Consumer discloses a bound `t` that lies after the expected inclusion time and no later than the expiry, for example the expiry rounded down to the hour. The circuit asserts `t ≤ expiry` privately and `blockTimeLt(t)` publicly (`MPE-CON-046`). Only `t` becomes public. The Message's creation time does not.

For a Message that expires at 14:37 UTC, a Consumer that expects inclusion well before 14:00 can disclose `t` = 14:00 that day. Observers learn only that the expiry is no earlier than 14:00.

Every reactor that holds the stream derives the same consumption nullifier, and the circuit refuses a nullifier already in the set and inserts it in the same transition as the effect, so concurrent reactions commit one effect. The library MUST NOT accept output from a Bus Node, Store Node or Indexer as evidence of publisher authorization (`MPE-CON-048`).

**Signature profiles.** In toolchain 0.35.0, `ed25519Verify` requires the ZKIR version 3 compiler feature and a proof server that supports it.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, Ed25519 signature verification ("requires the flag `--feature-zkir-v3`"); main branch, accessed 1 October 2026.] MIP-0013 rejects in-circuit Ed25519 because emulated field arithmetic needs "hundreds of constraints per field operation" [@midnight-mip-0013]. `jubjubSchnorrVerify` uses native arithmetic but signs a vector of field elements, so it needs a field encoding of the statement. Midnight Express therefore defines an optional JubJub Schnorr publisher-signature profile beside plain Ed25519. Measuring both, by rows, proving time and prover-key size, decides which one serves in-circuit consumption. Neither signature circuit has been written or compiled, and their cost is unknown.

**Anchor inclusion.** The compiled consumer circuit, `react(notAfter, action)`, proves inclusion instead of authorization. Its private witnesses are:

- the Envelope Identifier and window;
- a 12-step RFC 6962 path to the Shard batch root (up to 4,096 MPE Envelopes per Shard per window);
- a 3-step path to the window root (up to 8 Shards);
- the Anchor-tree path;
- the Message secret.

Each path step carries a skip flag, so trees whose size is not a power of two fit the fixed depth. The circuit checks the chain from Envelope Identifier to Anchor-tree root and calls the Bus Registry's witness-free `anchorRootValid`. Because that is a historic-root check, later Anchors do not invalidate the proof. The circuit then checks `window × 60 + 172,800 ≥ notAfter` privately and `blockTimeLt(notAfter)` publicly. It derives the consumption nullifier, refuses a known one, and records the nullifier and action in the same transition. It discloses the Anchor-tree root, `notAfter`, the consumption nullifier and the action. The Envelope Identifier, window, Shard, paths and secret stay private.

Its 19 SHA-256 evaluations need 77,905 rows (k = 17) with struct preimages. Written with byte concatenation they needed 703,378 rows (k = 20), and key generation did not finish in 25 minutes. A reaction carries two contract calls and two proofs. Compact 0.33 rejects a cross-contract call whose callee invokes a witness, so the Bus Registry read must stay witness-free.^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.33.0.md, section "Runtime support for cross-contract calls", guard 4; main branch, accessed 1 October 2026.] The compiled circuit was not executed, and its fee is not derived.

Inclusion is not authority. Nothing in `react` binds the Message secret to the anchored identifier, so a holder of one inclusion proof could react several times with different secrets. A consumption circuit that uses Anchor inclusion MUST therefore also perform checks 1 to 3 above, which bind the consumption nullifier to the signed Message (DEC-022). Inclusion alone serves only as proof of publication by a deadline, which is optional (`MPE-CON-047`).

That proof discloses the Anchor-tree root, not the window. A prover that uses the newest root containing the leaf reveals only that the window lies within the live history at that time.

DEC-022 keeps this proof out of the default because a link is missing: nothing binds the signed statement of checks 1 to 3 to the Envelope Identifier that the inclusion path proves. Making that link in the circuit would mean hashing the Sealed Body to recompute the Envelope Identifier and proving that the same body decrypts to the signed statement. Nobody has measured that cost, and whether a circuit can recompute the Envelope Identifier byte for byte over a 16 KiB body is unknown.

A reaction transaction reveals its target and its public effect, and must keep the Message and everything that identifies it private, except fields the effect discloses by design.

| A reaction reveals | A reaction must not reveal |
|---|---|
| Target contract and circuit; the consumption nullifier; the bound `t`; the contract's public state changes; the DUST fee and the block; with the inclusion option, the Anchor-tree root and a call to the Bus Registry | Payload (except fields the contract's effect discloses by design), statement, signature, publisher key when the set has more than one key, stream secret, Message secret, Sealed Body, Envelope Identifier, Recognition Tag, inclusion path, window |

Observers still learn that some Message caused this effect at this time. The optional random delay before submission is still an open decision (`MPE-CON-040`).

#### Wallets

Today the wallet SDK consumes no contract events. It synchronizes coins from the global Zswap stream.^[midnightntwrk/midnight-wallet, packages/shielded-wallet/src/v1/Sync.ts, subscription `zswapLedgerEvents`; main branch at 4628d984, accessed 1 October 2026.] The DApp connector has no event or subscription method.^[midnightntwrk/midnight-dapp-connector-api, src/api.ts, interface `ConnectedAPI`; main branch at 612db2b, accessed 1 October 2026.] Agents and services need no wallet change: the library prepares registration, Anchor, reaction and ledger-lane transactions and balances them through the wallet's existing path.

Fees come from DUST (`MPE-ECO-007`). They are quoted from the latest finalized `ledgerParameters`, and a shortfall returns `InsufficientDust` before any proving (`MPE-ECO-008`, `MPE-ECO-009`). Because DUST cannot be transferred, a contract can neither receive nor observe a registration price. The cost of a membership is the network fee of the registration transaction (`MPE-ECO-004`). One registration is about 8.7 KB and costs 0.246 DUST, or 0.308 DUST with the wallet margin (derived), inside the P-ECO-13 gate of 16 KiB and 0.5 DUST. A price beyond the network fee would need NIGHT or another token, with its receive path named. Shielded receipt is preferred, and `MPE-ECO-036` covers the unshielded case.

Hosting subscriptions in a wallet is optional. It needs four changes to the wallet SDK and the connector:

- storage for the dedicated admission secret (`MPE-ECO-006`), invitations and recognition keys;
- a grant per stream, so that a DApp receives only the streams its user granted (`MPE-CON-052`, open);
- connector methods to import an invitation, subscribe under a grant and prepare a reaction;
- for phones, a reduced-privacy profile chosen by opt-in, given the derived cost of about 1.86 GB per day for whole-Shard reception at the baseline mix.

Where a wallet offers `deriveSecret` [@midnight-mip-0015], the admission secret MAY instead be derived under a fixed domain such as `mpe:admission:v1` with the membership period as context, so that a membership survives device loss. That method is Proposed and optional per wallet, so DApps must detect it. The derived secret stays separate from spending and encryption keys.

#### Error cases

The library MUST report every refusal or failure as exactly one outcome from a closed set (`MPE-CON-056`). The set has nineteen outcomes.

| Outcome | Raised when |
|---|---|
| `TooLarge` | The payload exceeds its class capacity, or ledger-lane carriage needs more than 16 parts |
| `NotReady` | A precondition is unmet: restart barrier, admission-window allowance spent, profile not selected |
| `NotAccepted` | No Bus Node accepted the MPE Envelope after 3 attempts of 5 s each |
| `Busy` | A Bus Node refused for a local reason. The library retries at another listed Bus Node (`MPE-PUB-034`) |
| `Refused` | A source or the ledger refused a request or a transaction |
| `ResourceExhausted` | A rate, queue or ledger size limit was reached |
| `StorageExhausted` | Local or Store Node storage is full |
| `KeyLimit` | Installing the key would exceed 256 recognition keys |
| `Degraded` | The active reception mode cannot be sustained |
| `SourceFailed` | A source connection failed. The subscription stays open (`MPE-CON-025`) |
| `Unresolved` | Inventory comparison or repair failed for an interval |
| `RetentionGap` | The cursor is older than every source's oldest MPE Envelope |
| `KeyGap` | The interval predates the keys the client still retains |
| `CorruptRecord` | A received or stored record is malformed |
| `LedgerUnavailable`, `LedgerPaused`, `BusPaused` | As in the Ledger Adapter outcome table |
| `InsufficientDust` | The quoted fee exceeds the DUST balance |
| `SessionUpdateRequired` | A ratcheted session needs a key update before this publication |

A ledger rejection maps to `Refused`, not `CorruptRecord`, because the transaction was well formed and the ledger declined it.
