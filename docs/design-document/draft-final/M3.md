### Overlay protocol

Bus Nodes MUST run as sidecar processes whose libp2p identities are distinct from those of any co-located Midnight node. They MUST support TCP, Noise encryption (which authenticates each end by its identity key) and Yamux, which multiplexes many streams over one connection. The overlay requires no change to the Midnight node binary, runtime or pallets (`MPE-NET-001`, `MPE-NET-003`, `MPE-NET-005`, `MPE-NET-007`). The Midnight node carries its consensus gossip through the Substrate gossip engine and contains no GossipSub, so the overlay is a separate network that the Midnight node does not see. MPE Envelope construction and cryptographic binding follow "Event envelope and sealing"; Bus Registry reads, Anchors and the ledger lane follow "Ledger interface".

Bus Nodes form a GossipSub network [@2020-gossipsub-v11-spec]. On each GossipSub topic, a peer forwards every message it accepts to a few mesh peers, and GRAFT and PRUNE control messages add peers to that mesh and remove them. At each heartbeat, the periodic maintenance tick, the peer also announces recent message identifiers to some peers outside its mesh (IHAVE), and a peer that lacks one of those messages asks for it (IWANT).

**Carried events and contract events.** A carried event is a Message whose payload is the unchanged bytes of a contract event, public or private, with the hash of its transaction and its position there. Bus Nodes relay MPE Envelopes without opening them, so they cannot tell a carried event from any other Message. The overlay adds early, confidential delivery and interest-hiding to such an event. It adds no authority. The event remains the contract author's claim, bound by its transaction [@midnight-mip-0002], and the Consumer confirms it against the chain as "Consumer interface" specifies. A Message carrying a trade-settlement event may reach the counterparty before the Indexer serves the event, but until the Consumer finds the transaction on the chain it is only a claim that the event exists. Any `@topic` value that a future private event carries [@midnight-mps-0005] travels only inside the Sealed Body, and no Bus Node or gateway filters on it. Every property in this subsection (delivery, retention, replay protection and privacy) is a Midnight Express mechanism that neither GossipSub nor Midnight's event proposals provide. MIP-0002, MIP-0019, MPS-0005 and MPS-0007 concern contract events, multipart interpretation and Midnight node visibility, and they give no transport guarantee [@midnight-mip-0002; @midnight-mip-0019; @midnight-mps-0005; @midnight-mps-0007].

**Shards and names.** Let `N` be the full Midnight genesis hash and `g` its first eight bytes encoded as sixteen lowercase hexadecimal characters. Version 1 uses the prefix `/mpe/<g>/1` for every Midnight Express GossipSub topic name and every request-response protocol identifier (`MPE-NET-006`). A Shard is a GossipSub topic named `/mpe/<g>/1/shard/<i>`, where `i` is a decimal integer without leading zeros. Bus Nodes MUST subscribe to the GossipSub topics that the Bus Registry's Shard count defines for the Shards they serve (`MPE-NET-031`). They MUST refuse a subscription to any GossipSub topic outside the supported major versions, the configured genesis prefix and the Shards the Bus Registry currently authorizes or keeps in transition, and MUST also apply subscription-count limits (`MPE-NET-066`). The default rust-libp2p filter limits the number of subscriptions but admits any name, so it does not meet this rule on its own.^[libp2p/rust-libp2p, protocols/gossipsub/src/subscription_filter.rs, `MaxCountSubscriptionFilter` and `AllowAllSubscriptionFilter`; master branch, accessed 1 October 2026.] Bus Nodes MUST NOT subscribe to an unsupported major version. GossipSub topic names are routing labels, not authenticated network identifiers. Because the eight-byte prefix does not guarantee collision-free separation of networks, admission binds and checks the full genesis hash `N`.

The initial Shard count is one; the benchmark profile has eight. Placement uses the stream's 32-byte `audience_key`, which its Publisher and Subscribers hold. Publishers MUST derive placement as follows:

```text
h = SHA-256("mpe:shard[v1]" || audience_key)
shard = unsigned_big_endian_u64(h[0..8]) mod shard_count
```

The label `mpe:shard[v1]`, like `mpe:msgid[v1]` and `mpe:receipt[v1]` below, belongs to the MIP's table of domain-separation labels (`MPE-CRY-006`, `MPE-CRY-042`). Bus Nodes MUST check that the visible Shard matches the GossipSub topic. After a Bus Registry activation changes the count, Bus Nodes and clients MUST support placements under both counts for 172,860 s, the 172,800 s lifetime of an MPE Envelope placed under the old count plus 60 s of clock tolerance (`MPE-PUB-002`, `MPE-PUB-003`, `MPE-PUB-004`, `MPE-FMT-052`). Connected infrastructure still sees Shard membership.

**GossipSub profile.** The transport profile requires GossipSub v1.2 behaviour: the v1.1 peer-score, extended-validation and mesh rules, plus the v1.2 `IDONTWANT` extension, with which a peer that has just received a message tells its mesh peers not to send it that message (`MPE-NET-008`). The v1.2 specification is a Working Draft (r2, 30 August 2026).^[libp2p/specs, pubsub/gossipsub/gossipsub-v1.2.md, lifecycle table; master branch, accessed 1 October 2026.] A v1.2 Bus Node can talk to a v1.1 peer, but that link carries no `IDONTWANT`.

The transport name, the protocol identifier that two peers negotiate for the pubsub stream itself, is specified separately from the `/mpe/<g>/1` application names. The profile requires that mesh links negotiate the standard identifier `/meshsub/1.2.0`, and a default offer list does not meet this requirement: the inspected rust-libp2p and go-libp2p-pubsub defaults also offer v1.3 and older versions, so a successful default negotiation can settle on another version. Each Bus Node MUST therefore record the negotiated protocol identifier and internal peer kind of every pubsub connection (`MPE-NET-057`), and MUST refuse a mesh slot to any peer whose negotiated protocol is not the v1.2 profile identifier (`MPE-NET-058`). Pinning the version takes more than a name. In the unpatched rust-libp2p API, `ConfigBuilder::protocol_id` accepts only `Version::V1_0` or `Version::V1_1`, and the supplied string does not select the internal version. A custom name ending in `1.2.0` set with `V1_1` therefore leaves `IDONTWANT` disabled.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, `Version` and `ConfigBuilder::protocol_id`; protocols/gossipsub/src/protocol.rs, `ProtocolConfig::default`; master branch, accessed 1 October 2026.]

With unpatched gossipsub 0.50.0, only the standard identifier reaches v1.2 behaviour. A custom transport name such as `/mpe/<g>/1/gossipsub/1.2.0` would need a source change that adds `Version::V1_2`, and would not interoperate with standard-only peers unless their configuration changed. The proof of concept will therefore use the standard identifier and apply `MPE-NET-058` to what each connection negotiates. Releasing the standard profile requires a negotiation test with a v1.1-only peer and with a peer that also offers v1.3.

Bus Nodes MUST negotiate no GossipSub extension that changes message behaviour, partial messages included, unless the release profile specifies it and has reviewed it for privacy (`MPE-NET-067`).

Bus Nodes MUST apply the following router settings. The timing settings follow `MPE-NET-012`, and the others satisfy `MPE-NET-009`, `MPE-NET-010`, `MPE-NET-011`, `MPE-NET-013`, `MPE-NET-014`, `MPE-NET-015` and `MPE-NET-047`.

| Setting | Initial value |
|---|---|
| Target mesh degree `D` | 8 |
| Lower and upper mesh bounds `D_low`, `D_high` | 6, 12 |
| Minimum outbound mesh peers `D_out` | 4 |
| Heartbeat | 1 s |
| Gossip factor | 0.25 |
| PRUNE backoff | 60 s |
| Flood publish | Disabled |
| Maximum encoded RPC size | 65,536 B |
| `IDONTWANT` emission threshold | Serialized pubsub message longer than 1,000 B |
| Message history / gossip history | 5 / 3 heartbeats |
| Router duplicate-cache retention | 60 s |
| Publication authenticity / validation mode | `Anonymous` / `Anonymous` (StrictNoSign) |
| Application validation | Enabled |

At each heartbeat, a Bus Node grafts peers onto a Shard's mesh when it has fewer than `D_low` and prunes when it has more than `D_high`, in both cases back to `D`. `D_out` counts the mesh peers that the Bus Node dialled itself, so peers that connected to it cannot fill its mesh by themselves. Configurations MUST satisfy `D_low ≤ D ≤ D_high`, `D_out < D_low` and `D_out ≤ D/2`; the zero-degree bootstrapper profile is the only exception (`MPE-NET-011`, `MPE-NET-024`). The tuple `(D, D_low, D_high, D_out)` = `(8, 6, 12, 4)` satisfies the specification. The inspected Go validator instead requires `D_out < D/2` and rejects that tuple, so Go interoperability under this profile is not established until the mismatch is resolved and tested.^[libp2p/go-libp2p-pubsub, gossipsub.go, `GossipSubParams.validate`; master branch, accessed 1 October 2026.] The tuple `(6, 5, 12, 2)` passes both validators. Mesh bounds are maintenance targets. They guarantee neither a minimum degree nor a ceiling on the set of peers that receive a message, since gossip, explicit peers, publication replenishment, outbound-quota repair and opportunistic grafting all add recipients.

Flood publishing is disabled. With it, the Bus Node that first publishes a message would send it to every peer on the GossipSub topic above the publish threshold, not only to its mesh. Disabling it reduces initial dissemination and egress, and gives up part of the publication resilience that v1.1 recommends against eclipse attacks, in which an attacker surrounds a peer with its own peers.

Disabling flood publishing does not hide the Publisher from its ingress, the Bus Node that takes the Publisher's submission into GossipSub, and does not provide source anonymity. Receiving peers see the ingress's transmission whether or not flood publishing is enabled.

**Publication without origin fields.** Bus Nodes MUST publish under StrictNoSign and MUST drop any received message that carries a `from`, `seqno`, `signature` or `key` protobuf field, including an explicitly empty one, applying P4 (the invalid-delivery penalty below) to the forwarding peer (`MPE-NET-009`). In Rust, publication uses `MessageAuthenticity::Anonymous` and receipt uses `ValidationMode::Anonymous`, with a decoder that enforces all four absences. The gossipsub 0.50.0 decoder does not check `key`. The 0.51.0 source adds that check, so a Rust Bus Node complies only with 0.51.0 or an equivalent change.^[libp2p/rust-libp2p, protocols/gossipsub/src/protocol.rs, `ValidationMode::Anonymous` branch of the decoder, and protocols/gossipsub/CHANGELOG.md, 0.51.0; master branch, accessed 1 October 2026.] A Go configuration MUST omit authorship as well as set StrictNoSign.

Under StrictSign, the Bus Node that first publishes a message would be stamped as its author, and later relays would keep that author. StrictNoSign removes the stamp. It authenticates no Publisher and gives no replay protection: Publisher authentication stays inside the sealed Message, and replay protection is application state, the seen-set and admission nullifiers that each Bus Node records.

**Message identifiers.** The GossipSub message identifier MUST be the 32-byte value `SHA-256("mpe:msgid[v1]" || envelope_bytes)`. Here `envelope_bytes` is the complete, immutable MPE Envelope carried as `Message.data`, Admission Slot included (`MPE-NET-010`). The input excludes GossipSub protobuf framing, the GossipSub topic, RPC batching, and Noise and Yamux framing. Every Bus Node MUST hash identical bytes and encode the output identically, and the transport MUST use no data transform that changes this input. Without a custom function, rust-libp2p would substitute fixed values for the absent source and sequence fields, and anonymous messages would collide. The GossipSub identifier differs from the MPE Envelope Identifier (EID). The Admission Slot is the fixed 512 B region of the Visible Header that carries the admission nullifier, the Admission Proof and the other admission fields; it is attached after sealing, and the EID excludes it. The EID keys admission binding, inventories, application deduplication and Anchors (`MPE-SEC-014`). A router cache keyed by EID would let a copy whose slot was corrupted in transit, arriving first, take the honest copy's entry. Because the GossipSub identifier covers the Admission Slot, a copy with a corrupted slot cannot suppress an honest copy through the router's duplicate cache, given a collision-resistant hash (`MPE-SEC-042`). The guarantee covers that one cache path and does not extend to delivery under other attacks.

**Peer scores.** Bus Nodes MUST enable the following score profile (`MPE-NET-008`, `MPE-NET-021`, `MPE-NET-022`). The terms and thresholds keep GossipSub's meanings [@2020-gossipsub-v11-spec].

| Parameter | Value |
|---|---|
| Per-topic weight / topic-score cap | 1 / 32, applied to the weighted sum of P1 to P4 |
| P1 time in mesh | Weight `1/360`; quantum 1 s; counter cap 3,600 |
| P2 first accepted deliveries | Weight 1; decay 0.99; counter cap 20 |
| P3 mesh-delivery deficit / P3b failure penalty | Both weights 0 |
| P4 invalid deliveries | Weight −10 on the squared counter; decay 0.99 |
| P5 application weight | 1 |
| Bootstrapper application contribution | +200 |
| Listed relay application contribution | 0 |
| Unlisted peer while the relay allow-list applies | −33 |
| Evicted peer application contribution | −33 throughout its 60 s backoff |
| P6 IP colocation | Weight −10; threshold 10 |
| P7 behavioural penalty | Weight −10; threshold 6; decay 0.9 |
| Score decay interval / zero cutoff / disconnected retention | 1 s / 0.01 / 3,600 s |
| Gossip / publish / graylist thresholds | −10 / −50 / −80 |
| Peer Exchange acceptance threshold | 100 |
| Opportunistic graft threshold | 5 |

Each Bus Node computes these scores locally, keeping P1 to P4 for each Shard as a separate GossipSub topic. A peer whose total score falls below the gossip threshold is left out of IHAVE and IWANT exchange. Below the publish threshold it receives none of the Bus Node's own publications, and below the graylist threshold the Bus Node ignores all its RPCs. A threshold applies only when the total score falls strictly below it.

Per-topic contributions, P4 penalties included, are weighted and summed before the cap of 32 applies. P5, P6 and P7 are added afterwards. The cap therefore does not limit accumulated positive credit before penalties, and it sets no universal count of invalid messages that leads to graylisting. With one GossipSub topic, P1 contributes at most 10 (3,600 × 1/360) and P2 at most 20, so a topic's positive maximum is 30. Across eight maximally rewarded Shards the uncapped sum can reach 8 × 30 = 240. Four undecayed invalid deliveries on one Shard, a penalty of −10 × 4² = −160, reduce that sum to 80, which can then still leave the capped topic contribution at 32.

The isolated P4 term is `−10 × counter²`. Its counter decays by 0.99 per second, a half-life of about 69 s, so the squared penalty halves in about 34.5 s. The isolated rust-libp2p P7 term is `−10 × max(counter − 6, 0)²`.

The opportunistic graft threshold of 5 concerns the median total score of mesh peers: when that median falls below 5, a Bus Node grafts extra peers that score above the median. P2 can reach it well before 30 minutes of clean mesh time. Retained scores decay over the 3,600 s retention period and do not stop an attacker from returning under fresh identities.

P6 counts peers that share an IP address, which can penalize honest peers behind NAT, hosting providers or proxies. Colocation exemptions are confined to development networking. A production policy for shared addresses is still open.

The relay allow-list is the Bus Registry relay list used as a mesh filter. The P5 value of −33 exceeds in magnitude the largest capped positive topic contribution, 32. It makes the total negative whenever P6 and P7 are not positive. Score alone still does not enforce relay exclusion or eviction. A Bus Node MUST refuse GRAFT from a peer missing from the Bus Registry relay list while the allow-list applies, MUST stop meshing with a removed relay within P-OPS-11, and MUST prune an evicted peer, whatever that peer's total score (`MPE-OPS-007`, `MPE-OPS-023`, `MPE-NET-022`). Bus Nodes MUST check the resulting total score and keep the exclusion for the whole backoff. P5 is global to a peer and affects every Shard's mesh, so a per-Shard exclusion needs per-Shard enforcement.

A P5 contribution of −20 would not meet this rule through the GossipSub total score alone: with a +30 topic contribution the total is +10, so the peer would be neither refused nor pruned.

**Pruning without P3.** Setting P3 and P3b to zero removes GossipSub's own defence against withholding, and the following eviction rule replaces it. Its safety is not yet established. For each peer and Shard, a loaded heartbeat is one in which the Bus Node accepts at least one MPE Envelope on that Shard. The rule counts deliveries within the mesh-delivery window, the interval GossipSub's P3 uses: a mesh peer's copy counts if it is the first copy of the message or arrives within the window after the first copy has been validated. GossipSub v1.1 asks for a window of the order of milliseconds [@2020-gossipsub-v11-spec]. A Bus Node MUST prune a mesh peer after 90 consecutive loaded heartbeats without an accepted delivery within the mesh-delivery window, including a peer that delivers only rejected traffic. An accepted qualifying delivery resets the counter, and idle heartbeats do not advance it (`MPE-NET-022`). Idle-heartbeat handling MUST NOT prevent pruning for invalid behaviour that has been established by other means. With a 1 s heartbeat on a Shard loaded in every heartbeat, a mesh peer that never delivers in the window is pruned after about 90 s. On an idle Shard this rule never prunes it.

Tracking first deliveries only approximates the mesh-delivery-window rule and is not its equivalent. Ordinary rust-libp2p message events expose first deliveries only. The `with_peer_score_and_message_delivery_time_callback` constructor reports peer, GossipSub topic and relative delivery time, but the report carries no message identifier and can arrive before application acceptance. Exact tracking of accepted near-first deliveries therefore needs its own correlation.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, `Behaviour::with_peer_score_and_message_delivery_time_callback`; master branch, accessed 1 October 2026.] Honest forwarding does not guarantee an equal share of first deliveries, since topology, latency and scheduling can consistently favour other peers. Verification of this rule MUST cover asymmetric latency and topology, slow honest peers, every supported Shard and at least 90 loaded heartbeats.

Scoring helps resist attacks but limits neither identity creation nor Sybil attacks on its own [@2020-leastauthority-gossipsub-audit]. CVE-2022-47547 is a score-manipulation attack in which some configurations let a peer misbehave without its score falling [@2022-kumar-gossipsub-formal]. With the topic cap applied after mixed contributions across several Shards, the safety of this profile is unknown. The release gate `MPE-VER-026` requires the registered CVE-2022-47547 attack traces and multi-Shard score counterexamples to fail against the pinned release and complete profile. Whether that vulnerability is closed in the pinned release is unknown until that evidence exists.

**Validation and admission.** Bus Nodes MUST validate before forwarding a payload. They MUST run the cheap framing, eligibility and duplicate checks before proof verification (`MPE-NET-015`, `MPE-PUB-051`, `MPE-ECO-013`, `MPE-SEC-005`). They hash the Sealed Body but do not decrypt it. Some transport work comes before application acceptance: identifier calculation, the router's seen-cache entry, `IDONTWANT` emission and delivery bookkeeping. Only payload forwarding waits for Accept. A Message submitted by a local client MUST pass the same application checks before the Bus Node calls GossipSub `publish` (`MPE-NET-059`).

Validation MUST complete while the pending message is still in the GossipSub message cache; with 5 heartbeats of history at 1 s, that leaves 4 to 5 s. The Bus Node MUST check the result of `report_message_validation_result` and record a message that has left the cache as not propagated (`MPE-NET-060`). A cache miss, an absence of recipients or a failed publication queue MUST NOT be reported as propagation.

Validation ends in one of GossipSub's three extended-validator outcomes [@2020-gossipsub-v11-spec]. Reject suppresses delivery and forwarding and applies P4, the invalid-delivery counter whose contribution is −10 times its square, to the forwarding peer and to any tracked duplicate forwarders. Ignore suppresses delivery and forwarding without P4; it earns no accepted-delivery reward and promises no retry. Accept permits forwarding and the normal accepted-delivery rewards. The forwarding peer is a Bus Node, not necessarily the Publisher. An honest relay that forwards an invalid MPE Envelope it had no means to assess would itself be penalized, so the boundary between Reject and Ignore stays conservative: Reject applies only where the Bus Node can establish invalidity from information it holds.

Each check below has a fixed position in the validator order, a failure reason, an outcome and a score effect.

These outcomes satisfy `MPE-NET-014` to `MPE-NET-019`, `MPE-NET-023`, `MPE-FMT-023`, `MPE-PUB-028`, `MPE-SEC-018`, `MPE-SEC-041` and the admission requirements `MPE-ECO-012` to `MPE-ECO-020`. Row 3 applies only to a GossipSub topic version the Bus Node supports. If validity cannot be determined because the Bus Node lacks support for an MPE Envelope's protocol context, the outcome is Ignore, so that valid traffic of a future profile is never penalized.

The encoded-RPC cap and the MPE Envelope length check are separate checks on different objects. The MPE Envelope lengths exclude pubsub and transport framing, and several individually valid MPE Envelopes batched in one RPC must still fit 65,536 B. Go peers MUST set this limit explicitly, because go-libp2p-pubsub defaults to 1 MiB.

For admission window `a`, live admission MUST satisfy `60a − 20 ≤ now < 60(a + 1) + 20`, with times in seconds (`MPE-ECO-014`). The window covers the 60 s from `60a` to `60(a + 1)`, and the tolerance adds 20 s at each end, so live admission for one window lasts 100 s. Roots MUST come from finalized Bus Registry state, and the Ledger Adapter MUST take no value from a block that is not finalized, so no rollback is ever needed (`MPE-NET-036`, `MPE-NET-068`). A root is eligible if it is current or was superseded less than 3,600 s earlier, and if `now` is less than the start of its membership period plus 90,000 s. The 90,000 s figure is the 25-hour bound: a membership period of 86,400 s plus the 3,600 s root window (`MPE-ECO-015`, `MPE-ECO-051`).

The Bus Registry cannot enforce the root window itself. Its historic-root check accepts every past root of a membership tree, and a Compact circuit can check the block time against a supplied value but can neither read the block time nor read its own Merkle root. Bus Nodes therefore enforce the 3,600 s window off chain. The Ledger Adapter takes each root's publication and supersession times from the timestamps of the finalized blocks that include the transactions that change it (`MPE-NET-055`). An exploratory Bus Registry contract of the form "Ledger interface" describes, with one membership tree per membership period, compiles with Compact 0.35.0 (language 0.27.0, against a ledger-9 release candidate). Its circuit sizes come from the compiler's circuit model and its fees are derived from the ledger cost model. It has not run on any Midnight network, and the design does not depend on that contract being final. Bus Nodes in the proof of concept will read a mock Bus Registry. The Ledger Adapter MUST mark its view stale when local time differs from the latest finalized block timestamp by more than 60 s. In production, disagreement between configured chain sources also makes the view stale (`MPE-NET-019`, `MPE-NET-020`, `MPE-SEC-022`). Cached-valid admissions continue. Missing context, or a failed check that depends on the chain or the clock, produces Ignore, never P4 (`MPE-NET-018`).

The Admission Proof MUST establish membership and bind the EID and the visible context. It MUST also prove a credit index below the class quota committed in the membership leaf: `(64, 16, 4, 1)` for classes 0 to 3 per 60 s admission window. A credit, the allowance of "Event envelope and sealing", is one (admission window, class, credit index) triple of a membership. One MPE Envelope consumes one credit and uses one admission nullifier, derived from the admission secret, admission window, class and credit index (`MPE-SEC-005`, `MPE-ECO-016`, `MPE-ECO-017`, `MPE-ECO-018`). Two MPE Envelopes that consume one credit therefore carry the same admission nullifier, which is how a Bus Node detects the second use. This follows the rate-limit relation of RLN-v2 [@2024-vac-rln-v2-spec]. The production zero-knowledge proof profile is chosen separately, and its unknowns are its proof system, its binding and its operating cost. That profile MUST use a hash that Midnight commits to keeping stable. `transientHash`, which the exploratory revocation circuit uses for the same relation, carries no such guarantee.

The stand-in admission proof that the proof of concept will use exposes admission secrets to relays and maps every MPE Envelope to its membership. It provides no admission unlinkability and is limited to devnet and testnet.

A Bus Node MUST verify a conflicting Admission Proof before it keeps both MPE Envelopes and emits `AdmissionConflict`. It MUST NOT penalize the forwarding peer (`MPE-SEC-018`, `MPE-SEC-019`, `MPE-ECO-020`). The verified conflict evidence is retained and handled by the separately specified evidence and revocation policy.

Each Bus Node accepts at most one EID per live credit under its local acceptance state (`MPE-ECO-022`). Two Bus Nodes can each accept a different first use of the same credit before either has seen the other's, so no network-wide quota follows from mesh connectivity.

**Publication and restart.** The client SHOULD choose one ingress uniformly from at least two Bus Nodes it dialled itself (`MPE-NET-033`). The ingress MUST return `Accepted{eid}` only after it has completed application acceptance and committed its acceptance state. The client MUST match that identifier before it reports publication success (`MPE-NET-049`, `MPE-PUB-022`). `Accepted{eid}` says what the ingress did. It does not prove that a mesh peer received the MPE Envelope, that any Subscriber got it, that a Store Node holds it, or that it is final. If the ingress's GossipSub `publish` call then fails, for example with no mesh or fanout peers or a full publication queue, the ingress MUST send `PublishFailed{eid}` on the same exchange (`MPE-NET-061`). The publish service MUST return an explicit `Busy` for transient local unavailability: the restart barrier, rate limiting, queue saturation, or chain context that is required but unavailable. It MUST return `Refused` for other refusals. `Accepted`, `PublishFailed`, `Busy` and `Refused` are Midnight Express service replies, not GossipSub validator outcomes, and none of them changes a GossipSub score (`MPE-NET-049`, `MPE-PUB-025`, `MPE-SEC-009`). A stale chain view need not refuse admissions that are valid from cache.

If no acceptance arrives within 5 s, the Publisher MUST retry the identical wire bytes through a different Bus Node, using at most three Bus Nodes. It MUST stop at expiry, or 20 s after the admission window ends, and return `NotAccepted` if no attempt succeeds (`MPE-PUB-023`, `MPE-PUB-024`, `MPE-PUB-053`). GossipSub deduplication can suppress these copies at Bus Nodes that already hold the message. Each retry is a separate application request to a different ingress.

After every process start, a Bus Node MUST withhold live admission for 140 s and answer publication requests with `Busy` during that barrier. The 140 s exceeds the 100 s for which one admission window's credits stay live, so no credit accepted before a restart is still live when the barrier ends. Historical retrieval does not consume live credits (`MPE-STO-015`, `MPE-SEC-013`). The barrier restores replay protection only within the stated eligibility bounds, and GossipSub recovers no record of consumed credits. An explicit `Busy` lets the Publisher retry at another Bus Node at once instead of waiting out the 5 s acceptance timeout. That this reply keeps delivery complete through a restart is a hypothesis the proof of concept will test (Testing). A production configuration MAY use durable replay protection; consumed credits MUST then be committed before forwarding (`MPE-SEC-015`).

Production ingress SHOULD also wait until four outbound mesh peers have stayed present continuously for 600 s, returning `Refused` with a client-side `NotReady` outcome meanwhile (`MPE-NET-030`). Readiness shows only that the Bus Node is connected; it proves neither the honesty of those peers nor immunity from eclipse.

**Duplicate and replay state.** Acceptance MUST atomically record the EID and the admission nullifier before forwarding. EIDs remain in the application seen-set until expiry plus 60 s (P-FMT-4). Admission nullifiers remain for at least 140 s after acceptance, the restart-barrier bound. Failed validation MUST NOT insert an application seen-set entry (`MPE-PUB-027`, `MPE-ECO-021`, `MPE-SEC-041`). The application seen-set is separate from the GossipSub seen cache. When capacity cannot preserve every unexpired protection record, the Bus Node MUST refuse new admission rather than evict a record. Concurrent verification completions MUST recheck eligibility and replay state before acceptance (`MPE-SEC-005`, `MPE-SEC-018`). Verification-cache entries MUST be invalidated when the proof bytes, the verifier version or the Bus Registry context change (`MPE-STO-040`). The router, for its part, records a GossipSub message identifier before application validation, and neither Reject nor Ignore removes that entry. A valid MPE Envelope ignored as Busy during local overload (row 16) therefore stays suppressed at that Bus Node while the identifier remains in the seen cache: every later identical copy, however honest its sender, is dropped before validation. The configured rust-libp2p lifetime is 60 s, and the go-libp2p-pubsub default is 120 s.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, `handle_received_message` and `report_message_validation_result`; libp2p/go-libp2p-pubsub, pubsub.go, `TimeCacheDuration`; master branch, accessed 1 October 2026.] Recovery uses the Midnight Express retrieval services or another application path. A later retransmission still within its admission bounds succeeds after the cache entry expires.

Clients MUST deduplicate across live delivery, back-fill and repair, first by EID and then by authenticated Publisher and Logical Message Identifier (`MPE-PUB-036`, `MPE-PUB-037`). Collisions of other identifiers, handling across GossipSub topics and software defects can still let prevalidation state suppress later traffic; hashing the whole MPE Envelope closes only the corrupted-slot path.

**Expiry on the transport.** Once an MPE Envelope's `expiry` passes, a Bus Node MUST stop sending it to peers, including IWANT responses and sends already queued (`MPE-FMT-032`). GossipSub does not read the expiry field, and the inspected stock IWANT handlers serve validated cached messages without any expiry check. Bus Nodes therefore need expiry-aware cache and send handling, with a conformance test recorded for each libp2p library used. No send path has yet been shown to conform, and the proof of concept must include that test. Expiry is a rule for honest Bus Nodes. It deletes no copy an adversary has kept, and later compromise of a key can expose archived content under a profile without forward secrecy.

**`IDONTWANT`.** Bus Nodes MUST send and honour `IDONTWANT` on every link that negotiated v1.2 and send none on v1.1 links (`MPE-NET-062`). A Bus Node MUST emit `IDONTWANT` only for a message whose serialized pubsub-message length exceeds 1,000 B (P-NET-18), a strict comparison (`MPE-NET-063`). With that threshold, classes 1 to 3 trigger notices and the 776 B class 0 does not. Go evaluates payload length, sends at equality and defaults to 1,024 B, so interoperability reports MUST record each library's predicate.

Notices may be sent before validation; they announce possession of an identifier, not accepted validity. A peer that sends a message after receiving a notice for it MUST NOT be penalized (`MPE-NET-064`).

The v1.2 specification leaves the per-heartbeat limit on notices undefined. Any excess-notice penalty therefore applies only above a per-peer, per-heartbeat limit stated in the release profile (`MPE-NET-065`). The 10,000 identifiers that rust-libp2p remembers per peer are a storage cap, not that limit. Suppression lifetimes are recorded separately from the seen cache: 3 s in rust-libp2p and three heartbeats in go-libp2p-pubsub. Setting the Rust emission threshold to 65,537 B suppresses emission under the 65,536 B cap. It does not stop the Bus Node receiving or honouring notices, and on/off measurements state which behaviour was disabled (`MPE-NET-047`).

The bandwidth that `IDONTWANT` saves under this profile is unknown, in deployment and at a threshold below class 0. The proof of concept will measure ingress amplification, the number of copies a Bus Node receives per MPE Envelope, and per-class egress with emission on and off (Testing).

**Request-response services.** Each request and response MUST use a four-byte big-endian length prefix followed by one CBOR (Concise Binary Object Representation) map, capped at 65,536 B of CBOR. A text `type` field names the variant below, and the named fields sit in the same map. Integers are unsigned, byte fields are CBOR byte strings, and absent continuation values are CBOR null. Receivers MUST check the cap before allocating a frame (`MPE-NET-014`, `MPE-SEC-011`). These services are Midnight Express protocols carried over libp2p request-response, not GossipSub subscriptions: a client sends one request to one chosen peer and reads its reply.

Midnight Express has seven request-response protocols, all listed below. Paged responses MUST obey both the frame cap and the 64-entry maximum (`MPE-PUB-031`, `MPE-STO-041`).

| Identifier | Request | Successful response |
|---|---|---|
| `/mpe/<g>/1/publish` | `Publish{envelope}` | `Accepted{eid}`, followed by `PublishFailed{eid}` if publication fails |
| `/mpe/<g>/1/feed` | `Feed{shard, after}` | `Feed{cursor, envelopes}` |
| `/mpe/<g>/1/backfill` | `Backfill{shard, from, until}` | `Backfill{envelopes, next, head, roots}` |
| `/mpe/<g>/1/inventory` | `Inventory{shard, window, after}` | `Inventory{eids, next}` |
| `/mpe/<g>/1/receipts` | `Receipts{shard, window, after}` | `Receipts{receipts, next}` |
| `/mpe/<g>/1/anchor-leaves` | `AnchorLeaves{window, shard, after}` | `AnchorLeaves{eids, next}` |
| `/mpe/<g>/1/inclusion` | `Inclusion{eid}` | `Inclusion{window, shard, leaf_index, batch_path, shard_path}` |

`eid` is 32 B. A back-fill cursor is `{expiry, eid}`. A retrieval window is `{from, until}` in inclusive Unix seconds. Inventory, receipt and leaf-list continuations are exclusive EIDs. The `window` of an Anchor service is a 60 s window number. A root record contains `{root, period_start, published_at, superseded_at}`, with both times taken from the timestamps of including finalized blocks. Services MUST distinguish `Busy`, `Refused`, `ResourceExhausted`, `RetentionGap{from, to}` and `CorruptRecord{eid}` from successful empty results where they apply (`MPE-PUB-032`, `MPE-STO-019`, `MPE-STO-020`, `MPE-SEC-011`).

**Retention, back-fill and reconciliation.** Retention, receipts, Anchors, whole-Shard feeds, historical retrieval and reconciliation are Midnight Express services. GossipSub's bounded caches provide none of them. Store Nodes MUST retain complete accepted verification material until visible expiry, MUST NOT extend that deadline on replay or retrieval, and MUST prune managed live records within 60 s after it (`MPE-STO-004` to `MPE-STO-007`). The ordinary lifetime is 48 hours. A separately agreed paid archive MAY keep copies for seven days, but it does not extend a Message's execution deadline (`MPE-STO-021`). Back-fill MUST return every retained MPE Envelope in cursor order, selecting only by Shard, time and cursor. `from` is inclusive, and `next` identifies the first record omitted. Fail-over resumes at `(previous_cursor.expiry − 60 s, zero_EID)` and deduplicates the overlap (`MPE-PUB-030`, `MPE-PUB-031`, `MPE-PUB-043`). Version 1 derives creation time as expiry minus 172,800 s. Historical validation MUST use the original Bus Registry context and consume no new credit. Root lookup covers 176,400 s, the lifetime plus the root window (`MPE-STO-016`, `MPE-NET-056`, `MPE-SEC-013`).

Reconciliation MUST run in the client library from the start of a subscription. It checks every received EID, unmatched MPE Envelopes included, against inventories from a different Bus Operator. The initial interval is 60 s. Whether a shorter interval repairs gaps sooner at an acceptable request cost is a hypothesis for the proof of concept (Testing). Recognition is the Subscriber's local matching of MPE Envelopes to its streams. Every window that differs MUST be back-filled in full, whether or not recognition matched anything in it. The client MUST NOT request only recognized or missing identifiers, since such a request would show the Store Node which MPE Envelopes concern the client. When no second inventory is available or repair fails, the result is `Unresolved` (`MPE-PUB-012`, `MPE-PUB-014`, `MPE-PUB-015`, `MPE-SEC-024`).

Inventories and Anchors expose some omissions. They do not prove that every MPE Envelope existed, reached a Store Node or can still be retrieved.

The gateway MUST serve every accepted MPE Envelope on each requested Shard. It MUST refuse filters on streams, Recognition Tags or identifiers (`MPE-NET-043`, `MPE-NET-048`). The indexer-side relevance filtering that MPS-0005 plans for private events, in which the filtering party learns which events concern a wallet, is therefore left out by design [@midnight-mps-0005]. Pull clients SHOULD poll every 1 s and MUST fail over after `Busy` (`MPE-PUB-013`, `MPE-PUB-034`). Feed cursors are exclusive acceptance-sequence positions scoped to one serving instance, and they are not portable back-fill cursors.

A retention receipt is a Store Node's signed commitment to retain an MPE Envelope until a deadline. Receipt requests cover whole windows. Each receipt names `{operator, eid, shard, deadline, signature}` and signs `"mpe:receipt[v1]" || N || eid || shard || deadline`, with a one-byte Shard and a four-byte big-endian deadline. Store Nodes MUST issue durable retention receipts only after recoverable persistence. A Message is `stored` only with compatible receipts from three distinct Bus Operators (`MPE-STO-011`, `MPE-STO-012`, `MPE-STO-042`). Receipts are compatible when they name the same EID, Shard and deadline and their signatures verify under the keys of distinct Bus Operators. A store that holds MPE Envelopes only in memory, as the proof of concept's store will, does not meet the durability obligation.

Anchor leaf lists and inclusion paths stay available for 49 hours, the 2,940 windows of live Anchor history. Subscribers obtain leaf lists by window. Per-EID inclusion requests belong to an explicit Consumer reaction (`MPE-NET-052`, `MPE-PUB-012`).

**Discovery and resource limits.** Clients and Bus Nodes MUST obtain peer identities, Bus Operator identities and roles from the finalized Bus Registry relay list and refresh replacements (`MPE-NET-054`, `MPE-NET-055`). The relay list is keyed by SHA-256 of each relay's serialized libp2p PeerId. A 32-byte key is never a PeerId, since an Ed25519 PeerId serializes to a 38-byte multihash. The compiled relay entry holds an organization identifier, role flags and an anchorer key commitment, but no address. Dialable addresses come from the authenticated bootstrap list, whose hash the Bus Registry holds, and from Peer Exchange suggestions, the peer lists carried on PRUNE, checked against the relay list (`MPE-NET-026`, `MPE-NET-027`). Every address, whatever its source, MUST pass the same authentication and address policy. Outbound mesh slots MUST be filled only from the bootstrap list, trusted-bootstrapper Peer Exchange or the Bus Registry relay list (`MPE-NET-028`). Peer Exchange is accepted only above score 100, which only the bootstrapper application contribution can reach, so the bootstrapper role is itself taken from the Bus Registry. The inspected rust-libp2p Peer Exchange supplies peer identifiers but does not process addresses in signed peer records. With the default of zero `prune_peers` it supplies no candidates, so enabling `do_px` alone does not give self-sufficient discovery.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, `make_prune`, `handle_prune` and `px_connect`; protocols/gossipsub/src/config.rs, `prune_peers`; master branch, accessed 1 October 2026.] Bootstrappers SHOULD run with zero mesh degree and return at least one Peer Exchange candidate on every PRUNE (`MPE-NET-024`).

Zero-degree bootstrapper operation and signed-record Peer Exchange are claimed for no Bus Node until a test demonstrates them. Production requires four bootstrappers run by distinct Bus Operators. Outside development, discovery or dialling of private, link-local and loopback addresses is forbidden (`MPE-NET-025` to `MPE-NET-029`). Outbound quotas resist capture of a mesh by inbound connections alone when honest dial sources exist. Poisoned discovery, compromised Bus Registry governance and colluding outbound peers can still isolate a Bus Node.

Bus Nodes MUST enforce a token bucket of 20 MPE Envelopes/s per peer per Shard, with burst 20. They MUST allow at most eight outstanding verification jobs per peer and 128 per Bus Node, counting executing work, and MUST dispatch round-robin among nonempty peer queues (`MPE-NET-023`, `MPE-SEC-009`, `MPE-SEC-010`). The initial capacity profile is 10 MPE Envelopes/s and 64 KiB/s per Shard. Resource allocations are 2 GiB of resident memory, 1 GiB of application caches, four full-Shard client streams per Bus Node, and 32 GiB per retained Shard. The proof of concept's memory store will be capped at 256 MiB per Shard. Retrieval byte, request and concurrency budgets MUST refuse excess work before committing to it. Storage exhaustion MUST preserve existing commitments and return `StorageExhausted` (`MPE-SEC-011`, `MPE-STO-008` to `MPE-STO-010`, `MPE-PRF-041`). The seen-set needs room for about 1.73 million identifiers per Shard, derived as `10 × 172,860`, and unexpired protection records MUST NOT be evicted to make room (`MPE-PUB-027`, `MPE-STO-010`). Edge bandwidth is budgeted at 6 Mbit/s per direction per Shard, which rounds up a planning model of mesh egress at the byte cap, 1.25 × D × 64 KiB/s ≈ 5.24 Mbit/s. A four-Shard full Bus Node therefore has 24 Mbit/s per direction. Feed and repair traffic are accounted separately (`MPE-PRF-013`, `MPE-PRF-014`).

These latency, throughput and resource values are Midnight Express acceptance targets, not GossipSub guarantees. The planning model counts a full copy to every mesh peer and subtracts none of the copies that `IDONTWANT` suppresses, so it is an upper estimate for forwarding. The proof of concept will measure egress per Shard against the 6 Mbit/s budget, and deployment latency, bandwidth, address diversity and failure behaviour need runs across machines (Testing).

**What the overlay reveals.** Sealing protects content under the chosen cryptographic assumptions. Equal lengths hide payload length within a size class, but the class, timing, volume and complete connection transcripts stay observable. GossipSub topic names disclose the network prefix, the major version and Shard membership. One launch Shard removes the differences between Shards, but it still reveals participation and traffic. A libp2p identity authenticates a connected endpoint, not the Publisher sealed inside the MPE Envelope. The ingress sees the submitting connection and can link an MPE Envelope to that endpoint's identity and address. Later relays see the identities and timing of forwarding peers: a relay that forwards a class-3 MPE Envelope on Shard 0 learns the class, the Shard, the visible expiry, the moment of arrival and the peer that sent it, but not the sealed content. Subscriptions, IHAVE, IWANT and `IDONTWANT` messages show possession and missing-message patterns to neighbours. Local scoring keeps observations per peer and per GossipSub topic even when persistent logs omit them (`MPE-SEC-027`). If Identify, libp2p's peer self-description protocol, is enabled, its public key, addresses, supported protocols and implementation fields are further permitted leakage, and its enablement and exported fields MUST be recorded. Separate sidecar keys prevent direct key reuse, not correlation with a co-located Midnight node through host, address or traffic. Subscriber-interest privacy is conditional on a fixed set of received Shards, the incoming traffic, the online schedule and public application actions. GossipSub itself proves none of these properties, and Security Considerations states the adversary classes and residual risks. Recognition MUST NOT change subscriptions, requests, acknowledgements, retries, errors, repair, receipts or diagnostics (`MPE-PUB-012`).

**Open transport risks.** Several questions about the overlay remain open, and release depends on evidence for each:

- the safety of the score profile across several Shards, and of the eviction rule that replaces P3;
- the missing `key` check in the gossipsub 0.50.0 decoder;
- interoperability between rust-libp2p and go-libp2p-pubsub, where standard and custom identifiers, default version lists, Go's outbound-quota check, `IDONTWANT` predicates and Peer Exchange capabilities differ;
- losses under overload that a local `Busy` does not repair for every Subscriber;
- the conformance of every send path to the expiry rule.

Compliance of the transport with GossipSub does not establish that a release is secure. Closure of the scoring vulnerability, complete privacy-game evidence, sustained resource behaviour, wide-area performance and resilience at production scale are separate acceptance obligations, defined in Path to Active and Testing.
