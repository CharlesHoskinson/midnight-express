### Midnight Problem Statement: Confidential Message and Private Event Delivery

```text
MPS: "xxxx"
Title: Confidential Message and Private Event Delivery for Contracts, Agents and Wallets
Authors: Charles Hoskinson <CharlesHoskinson>
Status: Proposed
Category: Standards
Created: 02-Oct-2026
Requires: MIP-0002
Replaces: none
MIP: MIP-xxxx (Midnight Express: Confidential Message and Private Event Delivery over a GossipSub Overlay with Ledger Anchoring)
```

#### Abstract

Midnight lets a contract prove facts about private data, but it gives contracts, agents and wallets no private way to tell each other that something happened. The only notification mechanism is the contract event. Compact's `emit` (MIP-0002, the only Accepted event proposal) writes every field in the clear into a transaction that every chain observer can read. A custom event has a 32-byte name and a 256-byte payload, and the ledger silently drops any event whose data exceeds 1 KiB. Clients receive the event after finality, from an Indexer that sees which contract each client watches. MPS-0005 plans private events in an unpublished Part 2: encrypted fields, commitment binding and topic filtering. Planned private events would still travel inside transactions, with block and finality latency and the chain's shared budgets. The Midnight Foundation's own proposals already send coin information, transfer context and offer notes outside the chain. None of them specifies a confidential channel for that data. This MPS states the gap for confidential messages between parties and for early, private delivery of contract events, sets measurable goals and lists the non-claims that any answer must state. It complements MPS-0005 Part 2 without asking to replace it, and proposes no design.

#### Vision

A Message is an application message, not a contract event. Its Publisher seals it and sends it to the parties entitled to read it. A Subscriber takes in Messages and recognizes those meant for it. A Consumer acts on one, and for an agent or a wallet the two are one process. A contract learns of a Message only when someone presents it in a transaction.

Only the entitled parties can read a Message's content; relays, the Indexer and chain observers cannot. A Subscriber learns of the Messages meant for it within seconds, and the infrastructure that delivers them cannot tell which Messages the Subscriber was looking for. A contract event, public today or private once MPS-0005 Part 2 defines it, can reach its recipients the same way, unaltered, before finality (the point after which a block can no longer be reverted). The chain then confirms the event, and its authority stays with the transaction that recorded it. Relays admit a Message only if its Publisher proves, without saying which, that it holds a rate-limited right to publish. Who grants that right is open question 9. A contract can act on a signed instruction carried in a Message without learning who published it. An auditor can be shown one Message, or one period of Messages, check it against the chain and tell who disclosed it, without receiving a key that opens everything else. The volume and per-Message cost suit routine agent traffic, and the chain's capacity is left for transactions; data that must be recoverable from chain data alone stays on chain. Every privacy claim names its adversary and states its limits.

#### Problem

Two kinds of traffic need a private route between parties on Midnight: application Messages, for which Midnight specifies no confidential channel, and contract events, which the chain records in public and delivers only after finality. For both, an answer must hide content from everyone not entitled to it, let a receiver find its own traffic without telling the infrastructure what it looks for, arrive within seconds, and leave the authority of any contract event with the transaction that recorded it. MPS-0005's planned private events would still fail the third condition, because they travel inside transactions.

**What Midnight offers today.** In the Foundation's terms, an event is a contract event: a Compact circuit emits it with `emit`, and the transaction records it [@midnight-mip-0002; @midnight-coip-0003]. The node code pins the ledger-9 generation. In that generation Compact accepts only the standard event structs, and the only one that carries custom data is `Misc`, made of `name: Bytes<32>` and `payload: Bytes<256>`.^[LFDT-Minokawa/compact, compiler/midnight-events.ss, definition of the `Misc` standard event; main branch, accessed 1 October 2026.] `emit` is a disclosure site. Any value derived from a circuit's private inputs must pass through `disclose()` before it reaches such a site, or the compiler rejects the contract, so every field is already disclosed and the events of this generation "carry values that are already public" [@midnight-mip-0002]. The ledger wraps the value in a `VersionedLogItem` inside a `ContractLog` record and silently drops any event whose data exceeds `MAX_LOG_EMITTED`, which is 1,024 bytes.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, constants MAX_LOG_EMITTED and MAX_LOG_SIZE; tag ledger-9.1.0.0-rc.5, accessed 1 October 2026.] CoIP-0003 sets the same 1 KB limit at the language level [@midnight-coip-0003]. The node discards ledger events once it has applied a transaction [@midnight-mps-0007], so clients recover them from the Indexer, which the Foundation defines as "a service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]. The Indexer re-executes finalized blocks and serves a `contractEvents` subscription, which requires a contract address as its filter and delivers each event at least once.^[midnightntwrk/midnight-indexer, indexer-api/graphql/schema-v4.graphql, subscription `contractEvents`; main branch, accessed 1 October 2026.]

The published documentation describes the earlier ledger generation, which has no contract events. Events arrive with ledger 9: as of 4 August 2026 mainnet ran ledger 8.0, and MIP-0002 was live on Stagenet [@midnight-mip-0018; @midnight-coip-0005]. Of the Foundation's documents on events, only MIP-0002 is Accepted. MPS-0005, MPS-0007, MPS-0043 and MIP-0019 are Proposed, and CoIP-0003 is a Draft that the Compact compiler implements. MPS-0005 differs from MIP-0002 and CoIP-0003 on keywords, on fees and on whether the protocol changes. Where it does, this statement follows MIP-0002 and CoIP-0003, because the first is Accepted and the second is implemented.

**What a public event leaks.** A chain observer learns each event's name, payload, emitting contract, entry point, transaction and block time, together with the public fee fields of the transaction that carried it. The Indexer also learns which contract addresses and event types each client subscribes to, from which connection and on what schedule. Encrypting the payload does not hide that a contract emitted something, when it did so, or the reaction transaction that follows. Together these reveal who reacted, when and to what. If a contract emits an encrypted `Misc` when it approves a loan and the borrower's wallet withdraws the funds two blocks later, an observer who cannot read the payload can still pair the event with the withdrawal. MIP-0019 agrees: "Application encryption may hide payload plaintext but does not hide that metadata or retract disclosed data" [@midnight-mip-0019]. A public event is authenticated to the contract and entry point that emitted it, not to the user who triggered the call [@midnight-mps-0043]. Midnight transactions carry no signer, but the missing signer does not make them unlinkable. Each call leaves a public transcript (the record of the reads and writes its proof attests to), and transcripts, fee fields and timing remain visible.

**What private events under MPS-0005 Part 2 would cover, and what they leave.** For a later phase, MPS-0005 lists private fields (`@private`, `encrypt_for`), commitment binding (`proven` blocks), topic annotations (`@topic`) with an Indexer topics column, a per-wallet relevance table (`RelevantContractEvent`), wallet-specific decryption with session isolation, and an encryption fee [@midnight-mps-0005]. A topic is a value attached to an event, so that a client can ask for the events that carry it instead of every event of a contract. The published text says this phase "is scoped in Part 2 of this document", but the Foundation's repository does not contain that Part 2. Its syntax, key types, encryption scheme, size limits, fee formula and Indexer leakage are therefore unknown. Every listed item sits in the compiler, the client SDK, the Indexer or the fee model, and the only carrier named is the transaction. A private event would still be a contract event, and that is the source of its authority. Part 2 would hide field content from chain observers. If private events keep the transaction as their carrier, as every listed item assumes, each event stays in a transaction that every chain observer sees, with its contract, entry point and time, arrives with block and finality latency, and shares the chain's per-block budgets. Their size limits and cost are unknown until Part 2 is published, and a mechanism in Part 2 that hides further metadata would change this assessment.

MIP-0002 sizes event capacity against the 50,000 B per-block `bytes_written` budget, which the state writes of every contract share, at an event's serialized size [@midnight-mip-0002]. A `Misc` event has 288 bytes of struct data; with the `VersionedLogItem` overhead of about 40 bytes it counts about 328 B. The whole chain then admits about 50,000 / 328 ≈ 152 such events per 6 s block, about 25 per second, before any other write. A payload of up to 1 KiB in four parts takes about 1,312 B, so about 38 fit in a block (about 6.3 per second on this sizing; about 3.5 if block usage binds at 200,000 B, as the next paragraph explains); one of up to 4 KiB in sixteen parts takes about 5,248 B, about 9 per block (about 1.5 per second). Routine agent traffic needs a carrier for about 10 Messages and 64 KiB per second in each partition of the traffic, whichever binds first. Carried as 256-byte event payloads, 64 KiB per second is 256 parts per second, or 256 × 328 ≈ 84,000 B of writes per second. The whole chain's write budget is 50,000 / 6 ≈ 8,333 B per second, so one partition would need about ten times the write budget of the entire chain.

The ledger-9 code reads the same bytes differently. It charges a logged event as both written and deleted, and the block limit applies to net written bytes, so under the code an event adds nothing to `bytes_written`, its bytes count as churn, and block usage (the bytes of the transactions in a block) binds instead.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, opcode `Log` ("count the entire log as churn"), and base-crypto/src/cost_model.rs, conversion from `RunningCost` to `SyntheticCost`; tag ledger-9.1.0.0-rc.5, accessed 1 October 2026.] The node's mainnet parameter file allows 50,000,000 B of churn per block. `block_usage` is 1,000,000 B in the Midnight node's network configuration files and 200,000 B in the ledger's initial limits.^[midnightntwrk/midnight-node, res/mainnet/ledger-parameters-config.json, `block_limits`; midnightntwrk/midnight-ledger, ledger/src/structure.rs, `INITIAL_LIMITS`; main branch, accessed 1 October 2026.] Under this reading the ledger-9 cost model puts a transaction that emits sixteen parts in one call at about 12,920 block bytes. Which reading governs a live ledger-9 network is unmeasured (open question 7). The Compact simulator records 693 B written and 693 B deleted for each further `Misc` inside one call (414 B each for a one-part call): gross bytes with no net growth, which the fee model books as about 832 B of churn per part. Only a gross reading of `bytes_written` would count the 693 B, and it would roughly halve the MIP-0002 figures.

No reading admits 256 parts per second.

| Reading | Binding limit per block | Whole-chain rate | 256 parts per second needs |
|---|---|---|---|
| MIP-0002 | `bytes_written`, 50,000 B | 50,000 / 328 ≈ 152 parts per block, about 25 per second | about 10 times the budget (84,000 / 8,333) |
| Ledger-9 code, parameter file | block usage, 1,000,000 B | 1,000,000 / 12,920 ≈ 77 sixteen-part transactions per block, about 12.8 per second or 205 parts per second | about 1.25 times (256 / 205) |
| Ledger-9 code, `INITIAL_LIMITS` | block usage, 200,000 B | 200,000 / 12,920 ≈ 15 sixteen-part transactions per block, about 2.5 per second or 40 parts per second | about 6.4 times (256 / 40) |

At the message rate instead, ten Messages of up to 4 KiB per second need 160 parts per second. Only the ledger-9 code's reading at 1,000,000 B admits that, at about 12.8 sixteen-part transactions per second, and only if they take about 78 percent of every block (60 × 12,920 / 1,000,000); the other readings carry about 1.5 to 2.5 such Messages per second for the whole chain.

The Indexer's contract-event subscription serves events from finalized blocks, about three blocks (about 18 s) after inclusion, plus indexing delay [@midnight-mps-0028]. The transcript that holds an event is public from the moment its block is seen, so observers of included but unfinalized blocks can read it earlier. Submission, inclusion and finality are distinct moments.

The `Misc` payload field holds 256 bytes, and the ledger drops any event above 1 KiB without an error. A larger payload must therefore be split, and MIP-0019 proposes multipart `Misc` events in one phase of one intent [@midnight-mip-0019]. An intent groups circuit calls within a transaction so that no third party can add calls to it. An intent runs a guaranteed phase, which must succeed for the transaction to succeed, and then a fallible phase, which can fail on its own. The ledger places a transcript too large for the guaranteed phase's budget in the fallible phase, where the fee is paid even if the call fails. The estimate for the sixteen-part call exceeds that budget.^[midnightntwrk/midnight-ledger, ledger/src/construct.rs, transcript partitioning into guaranteed and fallible segments (`partition_transcripts`); tag ledger-9.1.0.0-rc.5, accessed 1 October 2026.]

An event is emitted inside a proved transaction that pays a fee in DUST, the non-transferable resource generated by holding NIGHT, Midnight's native token; one call can emit several events and one transaction can hold several calls, so transaction and proof overhead can be shared, while each logged byte pays `Log` gas. Proving cost grows faster than the fee. Exploratory contracts reported with MIP-xxxx (a registry, a contract that emits a sealed payload as events, and a consumer contract) were compiled with Compact 0.35.0 (language 0.27.0, for a ledger-9 release candidate).^[LFDT-Minokawa/compact, doc/release-notes/toolchain-0.35.0.md, which states that the toolchain targets ledger 9, not yet deployed on Midnight Mainnet; accessed 1 October 2026.] The contracts are not final, and nothing below depends on their exact form. The fees derived from the ledger-9 cost model at genesis prices are about 0.129 DUST (0.161 with the wallet's fee margin) for a transaction that emits one 256-byte `Misc`. Sixteen parts emitted in one call cost about 0.188 DUST, under 1.5 times the one-part fee, and sixteen separate calls in one intent cost about 0.866 DUST, derived with 4,368 B for every contract proof, an upper bound (about 0.62 DUST with the modelled 2,800 B). The circuit must turn a non-constant payload into bytes before it can emit it, and that conversion sets its size: emitting one 256-byte circuit argument needs 166,241 rows (k = 18), against 23 rows for a constant payload. Here k is the base-2 logarithm of the circuit's row capacity, so k = 18 allows 262,144 rows. Four parts need k = 20 and sixteen parts about k = 22. The proof does not grow with the circuit. The compiler's cost model gives proofs of 2,800 B or 4,368 B and verifying keys of 1,351 B or 2,119 B, so the added cost falls on the prover. These figures come from compilation, circuit models and the cost model; nothing was run on a network.

**What the filtering party learns.** Topic filtering has a sixth effect, on the party that evaluates the filter. An Indexer that evaluates topics learns which topics each wallet asks for, unless the topic values are hidden from it. MPS-0005 claims "99%+ scanning reduction" for topic filtering and does not state what the filtering party then learns [@midnight-mps-0005]. MIP-0002's prefix filters state the same trade openly: the client chooses "the level of disclosure at the cost of the data returned" [@midnight-mip-0002].

**What a contract can check today.** A contract that must act on something published outside its own call has to check admission, expiry and authority, and Compact 0.35.0 constrains each check. Authority cannot come from a signer, because none exists, so it must be a secret or a signature proved inside the circuit. A circuit can compare block time but cannot read it, and each comparison puts its operand in the public transcript, so checking an exact expiry publishes it. An offer that expires at 12:00 is checked by asserting that block time is less than 12:00, and the accepting transaction shows 12:00 to every observer. Admission is checked against a Merkle tree, whose single root commits to every admitted item, so a holder can prove admission without revealing which item it holds. A circuit cannot read the root of its own Merkle tree. A historic-root check accepts every past root: it answers whether a value was ever a root, not when, so a contract cannot bound a root's age by time. A proof that an item is included under a stored root does not bind the item to the party that reacts to it. That binding needs a publisher signature or the full item inside the circuit.

The compiled contracts show what these checks cost. In those contracts a registry commits the admitted items and a separate consumer contract checks them, so every reaction carries two contract calls. The consumer circuit that checks an inclusion against the registry's roots compiles at k = 17 (77,905 rows). That size comes from the compiler; the circuit was not executed.

**Delivery the Foundation's proposals already need outside the chain.** Four Foundation proposals move data outside the chain, and none specifies how it travels confidentially. MIP-0011 notes that contract-initiated outputs carry no coin ciphertext, so "the returned coin info is the recipient's only copy; callers SHOULD deliver it out of band" [@midnight-mip-0011]. MPS-0025 asks whether source-of-funds evidence should be "encrypted to the recipient, provided out-of-band, selectively disclosed, or issued as a verifiable attestation", and names "encrypted transfer context" as a target for future MIPs [@midnight-mps-0025]. MIP-0005 records that a maker's note is needed but that "no part of the Transaction can hold this", so "offer files carry no messages" [@midnight-mip-0005]. MIP-0006 publishes swap offers to a shared off-chain data-availability namespace that every indexer reads [@midnight-mip-0006]. Those offers are public by design.

MIP-0012 rejects off-chain delivery for asset custody because it "breaks the 'chain data is sufficient' property" and adds a liveness dependency between depositor and owner. For custody, "discovery and total-loss reconstruction are requirements, not conveniences" [@midnight-mip-0012]. An answer to this problem must not be offered where that property is required.

**The receiver's dilemma.** Midnight's shielded wallet receives payments through Zswap, Midnight's shielded-token protocol, whose outputs carry ciphertexts that only the receiving wallet's key opens. The wallet learns what it has received in one of two ways. The current wallet SDK downloads every Zswap ledger event and trial-decrypts each one locally, which hides interest at the cost of a full scan. The older server-assisted path sends the wallet's viewing key to the Indexer, which can then read every incoming payment.^[midnightntwrk/midnight-indexer, docs/architecture.md, wallet-indexer description of `connect(viewingKey)`; main branch, accessed 1 October 2026.]

Bitmessage has every receiver download and scan everything, which hides interest [@2012-warren-bitmessage-whitepaper]. Oblivious message retrieval starts from that baseline, whose "communication and computation costs are excessive at scale" [@2021-liu-omr, p. 1]. Detection keys move the scan to a server at a tunable false-positive rate, and that rate sets what the server learns [@2022-penumbra-fmd]. A higher rate hides the receiver's true matches among more cover but enlarges its download. Strong anonymity against a global observer requires high bandwidth or high latency [@2017-das-trilemma], and gossip alone gives the source only bounded anonymity [@2023-guerraoui-inherent-anonymity-gossiping]. Take, for example, a carrier with four fixed wire lengths of 776, 1,544, 4,616 and 16,904 B, those of MIP-xxxx. At a nominal 10 messages per second, 60, 25, 10 and 5 percent of them in the four sizes, the mean is 0.60 × 776 + 0.25 × 1,544 + 0.10 × 4,616 + 0.05 × 16,904 = 2,158.4 B. A receiver that takes in one whole partition of that traffic therefore downloads 10 × 2,158.4 B × 86,400 s ≈ 1.86 GB per day, before any protocol overhead. That is about 31 to 33 times (1,865 / 60 and 1,865 / 56) the mobile budgets of 56 to 60 MB per day in the requirement set published with MIP-xxxx. Per-Message follow-up requests, such as asking for a receipt for each recognized Message, reveal interest even when content stays sealed. Interest-hiding holds only within the set of traffic a receiver takes in, and subscriptions, connections and online schedules stay visible to the infrastructure.

Each mechanism fails at least one condition or leaves it unspecified, meaning that no Foundation document defines it.

| Mechanism | Content hidden | Interest hidden | Within seconds | Authority kept |
|---|---|---|---|---|
| Public `emit` (MIP-0002) | No | No | No | Yes |
| Private event (MPS-0005 Part 2, planned) | Field content only | Unknown | No | Yes |
| Shared namespace (MIP-0006) | No | Not specified | Not specified | Not applicable |
| Off-chain delivery (MIP-0011, MPS-0025, MIP-0005) | Not specified | Not specified | Not specified | Not specified |
| Server-assisted wallet | No | No | No | Yes |

**Selective disclosure.** MPS-0043 records that a shielded wallet has one viewing key, which covers the whole wallet, cannot be revoked and shows incoming activity only. MPS-0043 also records that a contract value is either private to its holder or public to all [@midnight-mps-0043]. No mechanism lets a Publisher or Consumer reveal one Message, or one period of Messages, to a chosen party who can verify it against the chain and tell who disclosed it.

**Relation to Confidential Contract Notifications.** MPS-0043 calls itself "the access-control slice of Confidential Contract Notifications (`mps-xxxx`, PR #271)" and assigns to that statement "concealing that a disclosure happened, letting a reader find what was granted without being told, and choosing how the data travels" [@midnight-mps-0043]. That statement's text is not in the Foundation's repository, so its scope beyond those words is unknown. The transport and discovery of confidential data described here fall within that assignment. The Foundation will decide whether this MPS is that statement, a replacement for it or a companion to it (open question 6).

#### Use Cases

**An agent reacting to a private offer.** Midnight City runs AI agents in a simulation [@midnight-mps-0015]. Suppose that an agent with a shielded wallet receives an offer from another agent and must accept it within seconds or lose it. As a public `emit`, the offer exposes its terms, both contracts and its timing to every observer, and the acceptance transaction links the two parties. An offer posted to a shared namespace, as MIP-0006 does for swap offers, is public by design, and the offer file can carry no note (MIP-0005). Sent off chain, the offer travels through a channel that Midnight neither specifies nor anchors. The agent needs to learn of the offer quickly, read it privately and react, without the network learning which offers it watches.

**A contract reacting without learning the producer.** A settlement contract must release funds when an authorized oracle or member publishes a condition. It must first check that the condition was admitted and has not expired, and it must not learn which member produced it. Today the contract can read only a public event or public state, so the condition is visible to all, and the carrying transaction's transcript, fee fields and timing can often link the condition to its producer.

**A wallet learning about incoming payments or messages.** A mobile wallet must learn about incoming payments and application Messages without downloading everything and without giving its viewing key to a service. Today it can scan every Zswap event, at a cost that grows with total chain activity, or hand the Indexer a key that reveals every amount it has received. Coins minted by a contract carry no ciphertext at all, so their coin information must reach the wallet out of band (MIP-0011). Receiving one whole partition of the traffic would add about 1.86 GB per day by the arithmetic under the receiver's dilemma, against a budget of about 60 MB.

**An auditor or relay operator needing selective disclosure.** A regulated business must show an auditor every Message it received from one counterparty in one quarter, and nothing else. A relay operator must show that it carried traffic as agreed, without being able to read that traffic. Today the business can disclose only a whole-wallet viewing key, or plaintext that the auditor cannot check. A secret that opens every Message of that relationship is no better, since it cannot be withdrawn once handed over. The relay operator has no anchored record against which to prove service.

**A contract's event reaching its recipients early.** A contract emits an event, public today or private once MPS-0005 Part 2 is published, and its recipients must act on it quickly. Today they learn of it only after finality, through an Indexer that sees which contract they watch. They need to receive it privately within seconds, act provisionally, and confirm the exact bytes against the transaction once it is final, while the event keeps the contract's authority.

#### Goals

The goals are in priority order. Each states an outcome and, where one exists, a measurable threshold; identifiers name the requirement set published with MIP-xxxx.

1. **Content confidentiality.** Message content and logical labels (stream, recipient, session) are hidden from relays, storage services, the Indexer, chain observers and colluding infrastructure that lack the decryption secrets (`MPE-PRV-002`, `MPE-PRV-003`). A stream is a sealed channel between a Publisher and its audience.
2. **Interest-hiding.** Within the fixed set of traffic a Subscriber receives, its selection of Messages does not change any subscription, request, acknowledgment, retry, error, repair or schedule that infrastructure can observe (`MPE-PRV-006`, `MPE-PRV-008`). No per-Message request reveals which Messages a Subscriber recognized. The claim is conditional: participation, connection identity, online schedule and traffic volume remain visible.
3. **Length concealment.** Message length is hidden within a small, fixed set of size classes. The test passes when every sealed object extracted from captured traffic has one of the allowed lengths and no captured frame contains plaintext. Transport frame sizes, which batching and control traffic vary, are analysed separately against their permitted leakage. The size class itself, Message timing and the transport transcript remain observable.
4. **Latency.** Warm propagation is timed from a publication request with admission complete to validated receipt at a relay that should carry the Message. Its p50 is at most 1.5 s and its p99 at most 3 s under the reference conditions of the requirement set. Separately, at least 99.9 percent of canary deliveries (scheduled test Messages to known recipients) arrive within 5 s over 30 consecutive days.
5. **Volume and size.** An answer sustains at least 10 Messages and 64 KiB per second in each partition of the traffic, whichever binds first, without depending on the chain's per-block budgets. Payloads range from under 100 bytes to at least 16 KiB, and a payload that cannot be carried is refused, never truncated, so no loss is silent.
6. **Chain footprint.** The total on-chain share stays at or below 10 percent of either the `block_usage` or the `bytes_written` block limit over a 24 h mean, and periodic commitments use under 1 percent.
7. **Spam resistance without identification.** Publication is rate-limited per membership without revealing which member published. Each party that admits traffic enforces the limit on what it sees. Independent admitting parties can accept conflicting uses of one membership's limit before they exchange state, so a double use must be detectable as evidence that leads to revocation.
8. **Receiver cost.** A path exists for constrained receivers within about 60 MB per day, and its leakage is stated before it ships.
9. **Selective disclosure.** One Message, or a defined period of Messages, can be disclosed to a chosen party who can verify it against the chain and tell who disclosed it, without receiving a long-term key. Each goal of MPS-0043 is met or declared unmet.
10. **Composition with contract events.** A contract event, public or private, can be delivered early and privately with its bytes unchanged, together with what a Consumer needs to confirm it against its transaction. The event counts as unconfirmed until the transaction is final and the bytes match, and an event from a fallible phase counts only if that phase succeeded. Delivery adds no meaning and no fee, and the event's authority stays with the transaction. Private events depend on the publication of MPS-0005 Part 2.
11. **No change to block validity.** The answer requires no new consensus rules and no change to the node. A path that uses only the ledger exists for parties that accept its cost and latency.
12. **Stated non-claims.** The following are declared unclaimed until evidence supports them (`MPE-PRV-024`): Publisher unlinkability (the first relay observes the submitting connection), relationship privacy, timing and volume privacy, hidden participation, protection against a global passive observer, and deletion of copies that dishonest stores keep after expiry. The terms follow the standard privacy notions for anonymous communication [@2019-kuhn-privacynotions].

#### Expected Outcomes

An answer would give agents and DApps a confidential channel for application Messages at interactive speed and outside public transactions. It would also give a specified route for the coin information, transfer context and offer notes that Foundation standards send out of band. Contract events, including private events once they exist, could reach their recipients before finality and keep the authority of the transaction that records them. Once a proof system that runs on the client is chosen (open question 1), relays could admit Messages without learning which member published them, and contracts could act on signed instructions that Messages carry. If a receiver-privacy technique meets the mobile budget (open question 3), wallets could learn of incoming activity without a full scan or a handed-over key. Relay and storage operators would get a defined role, an anchored record of service and a stated leakage profile once the unit that pays them is chosen (open question 4). Verifiable scoped disclosure for auditors needs its own MIP (goal 9).

#### Open Questions

1. Which zero-knowledge proof system will admit Messages, and does it run locally on the client's hardware, so that the admission secret never reaches an unattested prover (MPS-0004 [@midnight-mps-0004])? Until one is chosen, the proof of concept will charge a synthetic 4.5 ms per verification. Midnight's cost model charges 3.27 ms plus 4.56 µs per public input to verify a contract proof, and a Compact proof is up to 4,368 B. Until a system is chosen, any admission stand-in exposes members to the relays.
2. How can a per-membership limit be enforced when independent admitting parties cannot see each other's state? Each party checks only the uses of a membership's limit that it has seen, so two parties that have not yet exchanged state can each accept a different use beyond the limit. What evidence, dissemination and revocation policy closes that gap?
3. Which receiver-privacy technique meets the mobile budget, and at what leakage? The candidates are detection keys; oblivious message retrieval, where untrusted servers return a compact digest of a receiver's messages without learning which are its own [@2021-liu-omr]; and private information retrieval, where a client fetches an item without the server learning which [@1998-chor-pir].
4. Which unit pays relays and storage? DUST cannot be transferred and cannot be paid to a contract, so a price beyond the network fee needs NIGHT or another token.
5. How does this problem compose with MPS-0005 Part 2? When should an event be carried on the chain, and when off it? Will Part 2 allow a committed field whose body is not emitted? Which key type will `encrypt_for` target? What does its topic filter reveal to the party that evaluates it?
6. Is this MPS the pending Confidential Contract Notifications statement (`mps-xxxx`, PR #271), a replacement for it or a companion to it? Which parts belong there, and which to MPS-0043?
7. Which per-block limit binds events on a ledger-9 network: `bytes_written`, churn or block usage? Is the live block usage limit 200,000 B or 1,000,000 B? Measuring one event and 4-part and 16-part groups on a ledger-9 devnet or Stagenet would answer both.
8. Can Midnight offer a cheaper emission path for public byte payloads, and circuit access to block time or a contract's own Merkle root? Byte encoding dominates the proving cost of ledger-carried messages (k = 18 for one 256-byte part).
9. Who operates the infrastructure at launch, and what governance applies to admission and removal?
10. How much timing and source privacy can be achieved at acceptable cost, given the trilemma bound and the first-hop exposure of any relay network?

#### Recommended MIPs

- **Midnight Express: Confidential Message and Private Event Delivery over a GossipSub Overlay with Ledger Anchoring (MIP-xxxx, filed with this statement).** It specifies sealed, fixed-size MPE Envelopes, each carrying one Message, delivered over a relay overlay that runs beside the node and uses GossipSub, the publish-subscribe protocol of libp2p. It adds Anchors (an authorized anchorer's commitments to the Envelope Identifiers it accepted in one 60-second window) in a Bus Registry contract, admission, the Consumer interface, the carriage of contract events under stated conditions and a ledger lane that carries an Envelope as `Misc` events. Its largest size class holds 16,214 B of payload, 170 B short of 16 KiB; a larger payload is refused, not truncated, and a full 16 KiB needs the optional sealed fragmentation that its requirement set leaves open (`MPE-FMT-039`). One Anchor per minute of about 10,340 block bytes uses about 0.1 percent of a 1,000,000 B block-usage limit (10,340 / (10 × 1,000,000)), or about 0.5 percent at 200,000 B, and costs about 0.195 DUST (0.244 with the wallet's fee margin), about 280 DUST per day at genesis prices (1,440 × 0.195), derived from the cost model of a compiled exploratory contract and not measured on a network. The 0.195 DUST assumes no net state growth; each retained Anchor-tree root adds about 32 B, about 0.006 DUST per Anchor or about 9 DUST per day (derived: 32 × 0.0002; 1,440 × 0.0064), until a reset rule bounds the tree. A contract can act on a signed instruction carried in a Message; proving to a contract that the Message was admitted and anchored by a deadline needs a binding between the signed statement and the anchored Envelope that version 1 does not specify. The proposal addresses goals 1 to 7 and 10 to 12: goal 5 up to 16,214 B in one MPE Envelope, goal 7 without identification only once an admission proof system is chosen (open question 1), and goal 10 for private events only once MPS-0005 Part 2 is published. It does not address goal 8, which the receiver-privacy profile below covers, or goal 9, which the scoped-disclosure MIP below covers. It complements MPS-0005 Part 2 without replacing it.
- **Private events (MPS-0005 Part 2).** This MIP should be the Foundation's own specification of private fields, commitment binding, topic filtering and the encryption fee. It is not proposed here; goal 10 for private events and open question 5 depend on it.
- **Node-side event interface.** This follows MPS-0007, which is Proposed and has no MIP. Ledger events, including `ContractLog`, would become visible from the node, so clients could verify event bytes and commitments without relying on one Indexer. It is not a prerequisite for the others.
- **Proving-system profile for admission.** This selects the proof system, the slot size, the verification cost, the membership circuit and the hash Midnight commits to keeping stable inside circuits. It answers open question 1.
- **Scoped message disclosure.** This defines per-Message and per-period disclosure objects with a discloser signature, verifiable against commitments and mapped to the goals of MPS-0043. It addresses goal 9.
- **Receiver-privacy profile.** This specifies a path for constrained clients with a stated leakage, once measurements settle open question 3.
- **Circuit capabilities for ledger interfaces.** This answers open question 8.
