## Motivation

Parties coordinating through Midnight exchange many short messages that never enter any contract's state: an offer, a fill, a price signal, a key rotation, an instruction to an agent, or a receipt that a contract should act on. This proposal calls such an application message, sent from one party to others, a Message. A Message is not a contract event: no contract emits it and no transaction records it. Three kinds of Consumer act on Messages. Autonomous agents react to them in seconds, wallets learn from them about payments, invitations and state changes that concern their keys, and Compact contracts take some of them as authorized inputs to a later transaction.

MPS-xxxx (Confidential Message and Private Event Delivery for Contracts, Agents and Wallets) states the problem in full. Its working figures are a sustained load of 10 MPE Envelopes per second and 64 KiB per second per Shard (one partition of the relay network), payloads of up to 16,214 bytes, and delivery in seconds. Its privacy demand is that neither the relays nor the Indexer learn the content of a Message or which Subscriber it concerns.

The Foundation's own proposals already defer to out-of-band delivery. MIP-0011 notes that contract-initiated outputs carry no coin ciphertext, so "callers SHOULD deliver it out of band" [@midnight-mip-0011]. MPS-0025 asks whether provenance evidence should be "provided out-of-band" [@midnight-mps-0025]. MIP-0005 records that offer files "carry no messages" [@midnight-mip-0005], and MIP-0006 shares offers through an off-chain namespace [@midnight-mip-0006]. MPS-0043 assigns "choosing how the data travels" to a pending problem statement, Confidential Contract Notifications (PR #271), whose text is not published [@midnight-mps-0043]; the MIP editors must decide whether MPS-xxxx is that statement, a companion or a replacement.

Custody is the counter-case. MIP-0012 requires that discovery and total-loss recovery work "from chain data alone" and rejects out-of-band delivery for that reason [@midnight-mip-0012], so Midnight Express is not offered where that property is required.

A carrier must meet three demands together: the rates and sizes above, delivery in seconds, and confidentiality of both content and interest against its own infrastructure. Each existing Midnight capability fails at least one.

**Public contract events (MIP-0002).** MIP-0002 is the one Accepted event proposal [@midnight-mip-0002]. In Compact, a witness is a private input that the caller's client supplies to a circuit, and a disclosure site is where data can leave the circuit in public form, such as a ledger write or an event. Compact's `emit` makes a contract event a disclosure site, and the compiler rejects any field derived from a witness unless it is disclosed, so every field of an event is public by construction.^[LFDT-Minokawa/compact, compiler/analysis-passes/track-witness-data.ss, case `emit`; main branch, accessed 1 October 2026.] The only standard event for application data is `Misc`, with a 32-byte name and a 256-byte payload.^[LFDT-Minokawa/compact, compiler/midnight-events.ss, `declare-event-type Misc`; main branch, accessed 1 October 2026.] The virtual machine drops without error any event whose serialized form exceeds 1 KiB.^[midnightntwrk/midnight-ledger, onchain-vm/src/vm.rs, constant `MAX_LOG_EMITTED`, function `decode_event`; tag `ledger-9.1.0.0-rc.5`, accessed 1 October 2026.] An application could encrypt a payload before emitting it, but the contract address, entry point, transaction, time, size and frequency would stay public.

Each emission also needs a whole proven transaction, with a fee in DUST, Midnight's fee resource, which cannot be transferred and whose price moves every block. The fee payment carries a DUST spend proof of 2,912 bytes, and one contract call a proof of up to 4,368 bytes for the circuits compiled for this proposal: together 2,912 + 4,368 = 7,280 bytes, about 7.3 KB, before any payload. A Bus Registry registration, a single-call transaction, comes to about 8,670 bytes of block usage (derived). The node's mainnet parameter file sets a block-usage budget of 1,000,000 B per 6-second block. At that budget the whole chain carries about 115 such transactions per block, or about 19 per second, shared with all other traffic (1,000,000 / 8,670 / 6, derived). The ledger's initial limits set 200,000 B instead.^[midnightntwrk/midnight-ledger, ledger/src/structure.rs, constant `INITIAL_LIMITS`; ledger-9 source, accessed 1 October 2026.] Which value is live on a ledger-9 network is unknown until measured. Events also compete with state writes for a `bytes_written` budget of 50,000 B per block [@midnight-mip-0002]. Blocks finalize after about 3 blocks, about 18 s, and only then does the Indexer show the event. Both figures come from MPS-0028, a Proposed problem statement about making results visible before finality [@midnight-mps-0028].

**The Indexer subscription.** The Indexer is "a service that reads chain data and serves it to wallets and DApps" [@midnight-mps-0028]. It recomputes ledger events from finalized blocks and serves them through `contractEvents`. A subscriber must name a contract address; the filter also accepts event types, a block range, a transaction hash and field-prefix matches. Field-prefix matches apply to standard events only,^[midnightntwrk/midnight-indexer, indexer-api/graphql/schema-v4.graphql, `input ContractEventFilter`; main branch, accessed 2 October 2026.] so any filtering of `Misc` happens on the client unless the operator indexes `Misc` "by policy" [@midnight-mip-0002]. The operator therefore learns which contract each client watches, and when. Delivery is at least once and starts only after finality.^[midnightntwrk/midnight-js, packages/types/src/public-data-provider.ts, `contractEventsObservable` ("Delivery is at-least-once"); main branch, version 5.0.0-rc.3, accessed 1 October 2026.] The Indexer is a read API over one operator's database. It has no publish/subscribe layer and can carry only what the chain carried first.

**Wallet scanning.** The shielded wallet subscribes to the global stream of events from Zswap, Midnight's shielded coin protocol, and trial-decrypts every output.^[midnightntwrk/midnight-wallet, packages/shielded-wallet/src/v1/Sync.ts, subscription `zswapLedgerEvents`; main branch, accessed 1 October 2026.] The stream does not depend on the wallet's keys, so requesting it reveals nothing about which outputs are the wallet's. Coins therefore get receiver privacy, and Midnight Express reuses the pattern: whole-Shard reception replaces the global stream, and a local test of the Recognition Tag replaces trial decryption. The wallet, however, scans only what the ledger carries, at ledger cost and pace, and a Zswap ciphertext carries a coin opening, not application data.

**Planned on-chain private events (MPS-0005, Part 2).** In the Foundation's terms, a private event is a contract event, emitted by a Compact circuit during transaction execution, some of whose fields are encrypted for chosen recipients and bound to the transaction by a commitment that the proof checks. MPS-0005, a Proposed problem statement that predates the MPS process, lists the Phase 2 items: `@private` and `@topic` annotations, `encrypt_for` for encrypted delivery, `proven` blocks for commitment binding, an Indexer topics column, wallet-specific decryption and a `RelevantContractEvent` table [@midnight-mps-0005]. It defers their scope to an unpublished Part 2, so key types, the encryption scheme, topic derivation and what a topic filter reveals to the filtering party are unknown. That route will make some contract fields confidential but keeps the ledger's cost structure: one transaction and one fee per emission, with a planned encryption fee on top, block and finality latency, and throughput shared with the chain. MIP-0019 names the remaining exposure: application encryption "does not hide that metadata", meaning the contract, transaction, time and size [@midnight-mip-0019]. On-chain private events therefore suit facts that a contract must attest as part of a state transition. Most high-rate traffic between agents and wallets is never read by any contract.

**Multipart events (MIP-0019).** MIP-0019, which is Proposed, lets a reader join the 256-byte `Misc` payloads of one physical intent (the sealed unit of a transaction that supplies the package boundary) into a longer package [@midnight-mip-0019]. An intent executes in two phases, a guaranteed phase that the ledger applies first and a fallible phase whose events are discarded if it fails, and all parts of a package sit in one phase. MIP-0019 lifts the size limit within one transaction but does not change cost, latency or visibility.

**Node-side event visibility (MPS-0007).** MPS-0007, which is Proposed and has no MIP, asks the node to expose the ledger events it now discards [@midnight-mps-0007]. That would add a second source of event bytes, not a delivery channel. The node has no publish/subscribe layer for applications. Its only topic gossip is the Substrate gossip engine used by GRANDPA, the finality protocol, and BEEFY, which produces compact finality proofs for other chains, and it links no GossipSub crate.^[midnightntwrk/midnight-node, Cargo.lock, no `libp2p-gossipsub` package; node/src/service.rs, GRANDPA and BEEFY gossip; main branch, accessed 1 October 2026.]

Confidential Messages at these rates and latencies therefore need a carrier outside the ledger, tied to it for membership, rate limits and anchoring. The design problem is how that carrier can use the ledger for these records without taking on the ledger's cost, latency and visibility.

This proposal addresses MPS-xxxx, not MPS-0005 or MPS-0007. It specifies no on-chain private event, does not change what the node exposes, and depends on neither.

## Rationale

Five architectures were compared against the same criteria: the privacy properties and adversary classes defined in Chapter 4, fit with Midnight as it exists, performance, storage, the burden on Bus Operators and how they are paid, the upgrade path, and risk. Chapter 6 gives the full comparison.

**Option 1, ledger and Indexer only (rejected as the primary carrier, kept as the ledger lane).** An MPE Envelope has three parts: an 8-byte fixed header; the 512-byte Admission Slot, which holds the Admission Proof and the admission nullifier; and the Sealed Body, a fixed-length clear recognition prefix and authenticated ciphertext. On the ledger, a Sealed Body of class 0, 1 or 2 (256, 1,024 or 4,096 bytes) travels as 1, 4 or 16 `Misc` parts of 256 bytes; class 3 (16,384 bytes) would need 64 and is refused (MPE-FMT-044). A ledger-lane transaction carries the 7,280 bytes of the two proofs above and the rest of the transaction structure. Taking an assumed 8,192 bytes of overhead per transaction plus 288 bytes per part, classes 0, 1 and 2 cost 8,480, 9,344 and 12,800 bytes. The baseline mix of Chapter 9 puts 60, 25, 10 and 5 percent of Messages in classes 0 to 3. Without the refused class 3 the weights are 60, 25 and 10 out of 95, and (60 × 8,480 + 25 × 9,344 + 10 × 12,800) / 95 ≈ 9,160 bytes per Message (derived). A ledger-lane Message reaches readers only after inclusion and finality: one 6 s block plus about 18 s [@midnight-mps-0028], with proving time on top.

Two per-block limits apply, and they count a part differently. `block_usage` counts the whole transaction, each part at its 288 B of struct data; `bytes_written`, 50,000 B per block, counts each event's serialized size, about 328 B per part (288 B plus about 40 B of serialization overhead) [@midnight-mip-0002]. Under `block_usage` at 1,000,000 B, a block holds 117 class-0 transactions of 8,480 B or 78 class-2 transactions of 12,800 B, so the whole chain could carry between 117 / 6 = 19.5 Messages per second (all of class 0) and 78 / 6 = 13.0 (all of class 2). Counted at 328 B per part, a class-2 transaction is 8,192 + 16 × 328 = 13,440 B, a block holds 74, and the rate is about 12.3 per second. At 200,000 B each figure is one fifth. Under `bytes_written`, a class-1 Message writes 4 × 328 = 1,312 B, so 38 fit in a block, about 38 / 6 ≈ 6.3 per second; a class-2 Message writes 16 × 328 = 5,248 B, so 9 fit, or 9 / 6 = 1.5 per second, with no other writers (derived).

The rate that decides the option is the one inside the share Midnight Express may take. Requirement MPE-ECO-011, a production SHOULD whose decision is still open, caps registrations, Anchors and ledger-lane parts together at a share P-ECO-8 of either limit, averaged over 24 hours, with 10 percent as its proposed value. Within that share the `bytes_written` rates fall to about 0.6 (class 1) and 0.15 (class 2) per second, and the `block_usage` rate at 1,000,000 B to at most 19.5 × 0.1 = 1.95 (derived). Each is more than five times below the target of 10 per second per Shard.

Three questions stay unknown until measured on a ledger-9 network: which limit binds, the live `block_usage` value, and whether `bytes_written` counts gross or net writes. The last is open because the compiled ledger-lane contract counts each part's bytes as both written and deleted.

The ledger-lane contract's fees, derived from the ledger-9 cost model at genesis prices and not run on a network, are:

- A class-0 Message in one call costs 0.129 DUST (0.161 with the wallet's fee margin).
- A class-2 Message in one call costs 0.188 DUST (0.236 with margin).
- Sixteen separate part calls cost 0.866 DUST (1.084 with margin).

The circuit sizes suggest that proving, not the fee, is the larger cost. A circuit with parameter k has room for 2^k rows. Emitting 256 bytes that are not constant takes 166,241 rows (k = 18), because Compact turns field elements into bytes one division at a time. Four parts take k = 20, and sixteen parts about k = 22 (about 2.65 million rows). Proving time for these circuits has not been measured.

Contract events need the ledger-9 generation. As of 4 August 2026, mainnet ran ledger 8.0 and MIP-0002 was live on Stagenet [@midnight-mip-0018; @midnight-coip-0005]; the current mainnet status is unknown. A ledger-only design therefore has no confirmed mainnet to launch on.

**Option 3, in-node protocol (rejected).** The node has no plugin point. A new protocol must be registered in the node's service setup code, and it spans the network only if every node operator runs the modified binary. Every Midnight Express release would then wait on node releases and governance, and the consensus process would carry Message load and a new attack surface. This proposal therefore adds no code to the node binary (MPE-NET-001) and gives block producers no duties (MPE-OPS-001), in keeping with the validator operating limits of MPS-0030 and MPS-0038 [@midnight-mps-0030; @midnight-mps-0038].

**Option 4, mix network or private retrieval as the carrier (rejected for launch, kept as later profiles).** No system gets strong anonymity, low bandwidth overhead and low latency together [@2017-das-trilemma]. Loopix keeps latency in the order of seconds only with continuous loop and drop cover traffic [@2017-piotrowska-loopix], and Vuvuzela reports 37 s end to end [@2015-vandenhooff-vuvuzela]. Receiver-side schemes move the cost: oblivious message retrieval costs its servers about $1 per million messages scanned [@2021-liu-omr], and a SimplePIR server touches every byte of the database per query, after the client downloads a 121 MB hint for a 1 GB database [@2022-henzinger-simplepir]. Midnight has no deployed mix network, and nothing in the protocol pays for one. Mixed ingress and private retrieval stay open as opt-in profiles (DEC-021, DEC-023), each with its own claims.

**Option 5, an external publish/subscribe service (rejected).** Federated brokers see every subscription. A Nostr client sends its relay a filter naming authors, kinds and tags [@nostr-nip-01], and a Waku light node sends a filter node the content topics it wants [@2020-vac-waku2-filter-spec]. Both disclose interest to the infrastructure, the leak this proposal exists to remove. Waku's rate limiting keeps its membership tree in an Ethereum contract [@2022-taheri-waku-rln-relay], so adopting Waku would tie Midnight's admission to another chain and its fee token. A measurement of Nostr finds relay availability limited by relay finances [@2024-wei-nostr-empirical]. Midnight Express must solve that funding problem anyway, and Option 5 would offer no Midnight anchor in exchange.

**Option 2, a GossipSub sidecar overlay with ledger anchoring (chosen).** A separate process leaves the node untouched and uses the ledger only for public, ordered, final records of membership, relay lists and Anchors. An Anchor is a single root, posted to the Bus Registry once per 60-second window, over the Envelope Identifiers of the MPE Envelopes carried in that window; an Envelope Identifier is the commitment to an MPE Envelope's content that excludes the Admission Slot. An Anchor shows that an MPE Envelope existed by a certain time, not who sent it or whether its content is true. In GossipSub, the publish/subscribe protocol of libp2p, a peer forwards every full message of a GossipSub topic to a mesh of a few peers (D = 8 here) and only message identifiers to a few others. GossipSub v1.1 adds peer scores, outbound mesh quotas, adaptive gossip, a publication policy and secure discovery, and was evaluated against Sybil, eclipse and cold-start attacks for Filecoin and Ethereum 2.0 [@2020-vyzovitis-gossipsub; @2020-gossipsub-v11-spec]. A 1,000-node simulation of GossipSub with rate-limit nullifiers delivered messages of 25 KB or less within 1 s [@2024-revuelta-waku-latency]. Whether the specified overlay meets the delivery target of MPS-xxxx is unknown, and the first milestone of the proof of concept tests it (Chapter 9).

On its own, the overlay hides little about sources: gossip offers no meaningful source anonymity over poorly connected graphs [@2023-guerraoui-inherent-anonymity-gossiping]. The ingress Bus Node sees the submitting connection, and neighbors see forwarding times. No GossipSub configuration removes these observations. The privacy claim therefore rests on sealing, fixed sizes and whole-Shard reception, not on the gossip. Equal lengths hide payload length only within a size class, and the payload capacities of classes 0 to 3 are 86, 854, 3,926 and 16,214 bytes. A 300-byte payload goes into class 1 and travels as 1,544 bytes on the wire. When the client takes the default, the smallest class that holds the payload, an observer learns that the payload lies between 87 and 854 bytes (too long for class 0), not that it is 300 bytes. Size class, timing, volume and the full transport transcript stay observable, and the GossipSub topic names of Shards reveal the network prefix, the major version and Shard membership.

**Why GossipSub v1.2.** Midnight Express needs the v1.1 peer scores and mesh rules (MPE-NET-008), and its transport profile needs IDONTWANT, the one control message v1.2 adds, by which a peer tells its mesh peers not to send a message it already holds. A Bus Node sends IDONTWANT only above a size threshold, 1,000 B in this profile, which classes 1 to 3 exceed (1,544, 4,616 and 16,904 B on the wire) and class 0 (776 B) does not. Ingress amplification is the bytes a Bus Node receives per byte of distinct MPE Envelopes. Without IDONTWANT, a Bus Node with D = 8 mesh peers can receive a full copy from each of them, up to eight copies of a 16,904 B class-3 MPE Envelope; with it, the Bus Node names the 32-byte message identifier to the other seven on first receipt, and a peer that has not yet sent skips its copy. The design expects the saving to matter for the large classes, and Q5 of Chapter 9 tests it: a cut of at least 30 percent in class-3 egress, net of control bytes, makes IDONTWANT mandatory on capable links. The libp2p v1.2 specification is at Working Draft maturity (revision r2) and advertises `/meshsub/1.2.0`. A v1.2 peer can talk to a v1.1 peer, but without IDONTWANT on that connection.

A default libp2p offer list does not guarantee that `/meshsub/1.2.0` is negotiated, because the libraries also offer v1.3 and older versions, so a Bus Node records the negotiated identifier and enforces the version policy. In stock rust-libp2p gossipsub 0.50 and its current master, a custom protocol identifier accepts only `V1_0` or `V1_1` as its `Version`, whatever its string says, so an identifier ending in `1.2.0` with `V1_1` leaves IDONTWANT off.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, `enum Version` and method `protocol_id`; protocols/gossipsub/src/protocol.rs, `ProtocolConfig::default` offering `/meshsub/1.3.0`, `/meshsub/1.2.0`, `/meshsub/1.1.0` and `/meshsub/1.0.0`; master branch, accessed 2 October 2026.] The proof of concept is planned to negotiate `/mpe/<g>/1/gossipsub/1.2.0` through a vendored `Version::V1_2` change. A Bus Node configured that way does not interoperate with peers that offer only the standard identifiers unless their configuration changes.

The GossipSub topic names of Shards and the request-response protocols use the prefix `/mpe/<g>/1`, where `g` is the first eight bytes of the genesis hash in lowercase hexadecimal (MPE-NET-006). These names are routing labels, not authenticated network identifiers: admission binds the full genesis hash, and each Bus Node enforces the name policy in its subscription filter.

Interoperability with Go is not established. The mesh tuple (D, D_lo, D_hi, D_out) = (8, 6, 12, 4) gives the target mesh degree, its lower and upper bounds, and the outbound quota, the minimum number of mesh peers a peer must have dialed itself. The GossipSub v1.1 specification requires `D_out < D_lo` and `D_out ≤ D/2`, which this tuple meets, but the go-libp2p-pubsub validator requires the strict `D_out < D/2` and rejects it.^[libp2p/go-libp2p-pubsub, gossipsub.go, `GossipSubParams.validate`; master branch, accessed 2 October 2026.] rust-libp2p and go-libp2p-pubsub also apply different IDONTWANT size tests (Overlay protocol section).

Several decisions inside Option 2 follow from the libp2p code and from arithmetic on the specification, and the Specification states each normatively; where a decision rests on an expectation instead, that expectation is a hypothesis of Chapter 9. The first concerns the GossipSub message identifier, which hashes the complete MPE Envelope carried as the message data, Admission Slot included, and excludes all framing (DEC-010). The Envelope Identifier, by contrast, excludes the slot. rust-libp2p enters a message identifier in its seen cache before it hands the message to the application for validation.^[libp2p/rust-libp2p, protocols/gossipsub/src/behaviour.rs, function `handle_received_message` (`duplicate_cache.insert` before `Event::Message`); master branch, accessed 2 October 2026.] If the message identifier also excluded the slot, a copy with a corrupted slot sent ahead of an honest MPE Envelope would take the shared identifier, fail admission, and leave the honest copy to be dropped as a duplicate. The full hash closes that path only, subject to the collision resistance of SHA-256, and does not guarantee delivery against other attacks. Q6 of Chapter 9 tests it.

No network-wide admission quota is claimed. An allowance is the number of MPE Envelopes one membership may publish in one 60-second admission window: 64, 16, 4 or 1 for classes 0 to 3. Each MPE Envelope carries an admission nullifier derived from the unit of allowance it spends, so two with the same admission nullifier have spent the same unit. Two Bus Nodes that receive conflicting MPE Envelopes under one allowance at about the same time each see a first use and accept it, and GossipSub gives them no step in which to agree before forwarding, so mesh connectivity alone gives no network-wide bound. Each Bus Node therefore enforces quotas locally and keeps equivocation evidence that leads to revocation (DEC-014, DEC-016). Q9 of Chapter 9 tests whether, on average, at most one MPE Envelope per equivocated admission nullifier reaches Subscribers.

A Bus Node keeps admission nullifiers in memory and refuses live admission for 140 s after each start, its restart barrier. An allowance stops being eligible at most 2 × 60 s + 20 s = 140 s after acceptance (two admission windows and a 20 s tolerance), so waiting restores replay protection without a disk write. Inside the barrier the Bus Node answers a publishing client with Busy, a Midnight Express service reply, not a GossipSub validation outcome, and the Publisher retries elsewhere. Q8 of Chapter 9 tests whether delivery under churn stays at or above 0.999 with repair carrying less than 2 percent of pairs; below 0.99, Bus Nodes commit admission nullifiers to disk instead.

Missed Messages come back by repair: each client periodically compares the Envelope Identifiers it holds with the inventory of a Store Node of another Bus Operator and back-fills every 60-second window with a gap (MPE-PUB-014, MPE-PUB-015). A Bus Node also drops later copies of any message identifier in its seen cache, which lasts 60 s by default in rust-libp2p and 120 s in go-libp2p-pubsub.^[libp2p/rust-libp2p, protocols/gossipsub/src/config.rs, default `duplicate_cache_time`; libp2p/go-libp2p-pubsub, pubsub.go, `TimeCacheDuration`; master branches, accessed 2 October 2026.] A copy ignored while overloaded stays suppressed there until the entry expires, and only repair recovers it. The repair interval trades gateway bytes against recovery time, and the churn matrix of Chapter 11 sets it by test at 5, 15 and 60 s, with a pass condition of at least 99.9 percent of pairs delivered within 10 s.

Reception is of the whole Shard, with one Shard at launch (DEC-011, DEC-021). At the baseline mix the mean wire length is 0.60 × 776 + 0.25 × 1,544 + 0.10 × 4,616 + 0.05 × 16,904 ≈ 2,158 B, so at 10 MPE Envelopes per second each Subscriber receives 10 × 2,158 × 86,400 ≈ 1.9 GB per day before transport overhead (derived). Selective reception would lower the cost, and it waits for a profile that keeps the interest hiding. Q11 of Chapter 9 decides whether whole-Shard reception can be the wallet default.

The protocol does not pay relays, because DUST cannot be transferred (DEC-001); proof servers face the same unsolved payment problem [@midnight-mps-0004]. Any bonds are Bus Registry contract balances, unrelated to NIGHT staking, which "carries no consensus weight" [@midnight-mip-0016]. The relay set is an allow-list at launch, because peer scores alone do not limit identity creation (DEC-006): a security review of v1.1 describes Sybil peers that out-score honest ones and replace them in a victim's mesh [@2020-leastauthority-gossipsub-audit]. Peer scores still help when combined with outbound quotas, which resist inbound-only mesh capture where honest dial sources exist. Poisoned discovery and colluding outbound peers remain risks.

**Interest privacy and selective filters.** MPS-0005 plans topic-based filtering that it says achieves "99%+ scanning reduction", and MIP-0002 offers field-prefix filters as a dial between disclosure and returned volume [@midnight-mps-0005; @midnight-mip-0002]. Both are reduced-privacy selective profiles. A Subscriber may enable one only by explicit opt-in per subscription, and doing so changes the leakage contract (MPE-PUB-016, MPE-PRV-013). By default Midnight Express uses the strict profile: Subscribers receive the whole Shard and send no filter, key or topic to infrastructure.

The Recognition Tag is computed from a fresh 16-byte salt and a key that the Publisher shares with the Subscribers of a stream, an application channel set up by an authenticated invitation and identified only inside the Sealed Body. A relay without the key sees 16 bytes that change with every MPE Envelope, even within one stream. Each Subscriber tests every MPE Envelope of the Shard against each of its keys with one keyed computation per key. The design expects interest hiding to cost bandwidth more than computation, and Q1 of Chapter 9 tests that cost against trial decryption.

Interest hiding holds only within the fixed launch Shard set, publication schedule and traffic. It also depends on client behavior: recognition must not change subscriptions, requests, retries, errors, repair or receipts. One launch Shard removes differences between Shards but still reveals participation and traffic. The privacy claim does not cover publisher anonymity, timing, volume, relationships or a global observer. Any `@topic` value of a carried event travels only inside the Sealed Body.

**When the ledger lane is used.** The ledger lane exists for an overlay outage, not as a second mode of operation (DEC-008). A client uses it only when all of these hold:

- No Bus Node gateway can be reached. The client tries the gateway stream service first.
- The application has explicitly selected the ledger profile, because that profile changes the leakage contract (MPE-PRV-013).
- The network runs the ledger-9 generation.
- The MPE Envelope is of class 0, 1 or 2, and it is the only ledger-lane MPE Envelope in its physical intent.

Every delivered Message bears a carrier attribute naming its path, `overlay`, `gateway` or `ledger` (MPE-CON-057). It also bears a finality label: `gossip` until the client library has verified it against finalized chain data, and `final` after (MPE-CON-015, MPE-CON-016). The ledger lane carries the Sealed Body without an Admission Slot, so the ledger fee is its rate limit, and clients keep it inside the chain-share budget for both `block_usage` and `bytes_written`. Readers address the ledger-lane contract by address only, with the Indexer's monotonic event `id` as cursor. Events are not consensus state. A ledger-lane body therefore becomes `final` only after a check against authenticated on-chain data, as MIP-0018 requires of indexer-supplied data [@midnight-mip-0018].

Option 2 would be revisited if the proof of concept fails the Stage 0 gate of Chapter 11, a pass condition not yet settled (delivery of at least 99 percent with p99 of at most 6 s at 200 Bus Nodes), or if a product need arises that the ledger serves better. Passing that gate would not by itself establish release security. CVE-2022-47547 records attacks on GossipSub peer scoring in which, under some configurations, a continuously misbehaving peer can escape pruning [@2023-kumar-gossipsub-acl2s]; whether the pinned GossipSub release fixes it under the selected score profile is unknown. Under StrictNoSign, the libp2p signing policy in which a message carries no author, sequence number, signature or key field, the pinned decoder does not yet reject a lone `key` field. Both items are release gates (Security Considerations).

**Relation to on-chain private events (MPS-0005, Part 2).** Midnight Express complements on-chain private events and, under stated conditions, transports them; it is not an alternative to them. A private event is produced by contract execution inside a proven transaction and authenticated to the contract and entry point that emitted it [@midnight-mps-0043]. A Message is produced by a Publisher's client, authenticated by the Publisher's signature, and committed only through an Anchor over Envelope Identifiers. No contract executed it, and nothing in Midnight Express can stand in for "the contract emitted this field".

The two routes therefore compose. In a trade between two agents, the quotes and offers are Messages on Midnight Express. The settlement is a state transition of the contract, and any event it emits, private or public, is a contract event on chain. A carried event joins the two: it carries the exact bytes of a contract event, with the transaction hash and the event's position, and Midnight Express adds early, private delivery and interest hiding. It flows through unchanged only under these conditions:

- The bytes exist off-chain when the transaction is assembled.
- The chain keeps the binding, by holding either the ciphertext or a commitment to it.
- The event's bytes, with the transaction hash and position, fit the payload capacity of a size class: 854 bytes for class 1 and 3,926 for class 2, so an event near the 1 KiB limit needs class 2.
- Recipients can recognize it.
- Consumers keep its finality label at `gossip` until the transaction is final and the bytes match the transcript. An event emitted in the fallible phase counts only if that phase succeeded [@midnight-mip-0019].
- Midnight Express does not re-type, re-order or truncate it. Its authority stays "the contract author's claim" [@midnight-mip-0002].
- The fee is paid once, on chain.

Whether Phase 2 allows a committed field whose body is not emitted is unknown until Part 2 is published. Until then this proposal standardizes no public-key profile that `encrypt_for` might contradict.

A contract consumes a Message only through a reaction: a later transaction carrying the Publisher's signed statement and a consumption nullifier. Every Consumer holding the stream derives that consumption nullifier identically, so the contract can accept one reaction per Message (DEC-022). Anchors are held in Bus Registry state. The consumer contract proves the path from the Message's Envelope Identifier to an Anchor root and then calls the Bus Registry to check that the root is a past Anchor, so a reaction contains two contract calls, each with its own proof. The consumer contract compiles but has not been executed: with fixed-width struct preimages, the compiler puts its 19 SHA-256 evaluations at 77,905 rows (k = 17), and the Bus Registry side at k = 6. Inclusion alone does not bind the consumption nullifier to the Message. The Publisher's signature, checked in circuit, is required for authority, and that circuit has not yet been compiled.

MPS-0005 Part 2 needs nothing from Midnight Express.

**Category, title and prerequisites.** The proposal is in the Standards category: mostly formats (the MPE Envelope and the `Misc` names), a contract interface (the Bus Registry) and a client and Consumer API. Its networking aspect, in MIP-0001's sense of "network communication, peer discovery", is the peer-to-peer protocol and discovery of the Overlay protocol section, which change nothing in the Midnight node's networking. The proposal addresses MPS-xxxx, and the Confidential Contract Notifications statement if that receives a number. It requires MIP-0002, which is Accepted. The ledger lane follows MIP-0019, which is Proposed and counts as a prerequisite only if the MIP editors accept a Proposed prerequisite; otherwise the Ledger interface section states the multipart rule in full, citing MIP-0019 as its source.

## Backwards Compatibility Assessment

This proposal changes nothing in the Midnight node, runtime, ledger, virtual machine, Compact compiler or consensus. It needs no hard fork or coordinated upgrade. Bus Nodes and Store Nodes are separate processes with their own protocols and connections, outside the Midnight node's peer-to-peer network. Their identity keys are distinct from any Midnight node key (MPE-NET-005), which avoids key reuse, though a co-located process can still be linked by address and traffic. They read the chain through a Ledger Adapter, using unmodified Indexer queries (MPE-NET-045) or node RPC like any client. The Ledger Adapter acts only on finalized data, so no rollback is needed. If MPS-0028 yields an Indexer view of the best chain, unfinalized blocks included [@midnight-mps-0028], the Ledger Adapter could add a labeled pre-finality state, `in-block`, for Messages seen only in unfinalized blocks, with rollback as MIP-0018 requires [@midnight-mip-0018].

Everything the proposal introduces is additive: the Bus Registry and ledger-lane contracts, deployed like any other Compact contract; the Bus Node, Store Node and client library; and Consumer-side additions to wallet and DApp tooling, with the consumption pattern for Compact contracts (Ledger interface and Consumer interface sections).

The Bus Registry, the ledger-lane contract and a consumer contract compile with Compact 0.35.0 (language 0.27.0, ledger-9 release candidate), the toolchain the proposal pins. They are exploratory code, and the design does not depend on them being final. None was run on a network; circuit sizes come from the compiler, and all fees are derived from the ledger-9 cost model at genesis prices. Every circuit's proof is at most 4,368 bytes and every verifying key at most 2,119 bytes. Two roles hold authority over the Bus Registry. The steward is the maintenance authority that changes the relay list and parameters and can pause the contract; the anchorer is the Bus Operator that posts Anchors. Midnight transactions have no signer, so that authority is knowledge of a secret whose hash is in Bus Registry state, proved in the circuit. A contract can compare times with the block time but cannot read it. Each Bus Node, not the contract, therefore enforces the 3,600 s window during which a membership root stays eligible. DUST cannot be paid to a contract, so a membership's price is the network fee of its registration: about 8.7 KB and 0.246 DUST (0.308 with margin). Admission secrets and invitation keys are independent of wallet spending and encryption keys; wallets that offer MIP-0015's `deriveSecret`, which is Proposed and optional for each wallet, may derive them from the seed [@midnight-mip-0015].

One Anchor per 60 s is 1,440 Bus Registry transactions per day; at about 10,340 block bytes each they use 1,440 × 10,340 B ≈ 14.9 MB (derived). A day has 86,400 / 6 = 14,400 blocks, so at 1,000,000 B per block the budget is 14.4 GB per day, of which Anchors take 0.10 percent, or 0.52 percent at 200,000 B per block. Each Anchor post costs about 0.195 DUST (0.244 with margin), 1,440 × 0.195 ≈ 280 DUST per day (derived), and needs a k = 18 proof (152,138 rows) per window from the anchorer, with a proving key of 67 to 76 MB. Each Anchor record replaces the one 2,940 windows (49 hours) older, so the contract's state does not grow. The 49 hours are the 48-hour lifetime of a Message plus one hour of margin. No contract needs an older root, because consumption rejects expired Messages. Registrations, Anchors and any ledger-lane traffic are held to the chain-share budget (P-ECO-8, MPE-ECO-011).

**Interplay with MIP-0002.** Midnight Express uses the `Misc` event exactly as MIP-0002 defines it, with no new `LogEventType` variant and no serialization change. The names follow MIP-0018's convention, lowercase, colon-separated, a version in brackets, NUL-padded to 32 bytes [@midnight-mip-0018]: `mip-xxxx:anchor[v1]` and `mip-xxxx:envelope[v1]`, `xxxx` being this proposal's number once assigned. Consumers verify each Anchor against its record in Bus Registry state. The Bus Registry also emits a single `Misc` copy of the Anchor, with a payload of at most 256 bytes (MPE-FMT-047), but that copy is only a notification, because events are not consensus state. Each ledger-lane part is a `Misc` event with 288 bytes of struct data (MPE-FMT-043). Anchors and ledger-lane parts are public, as every `Misc` event is, and appear in `contractEvents` only for the Bus Registry and ledger-lane contract addresses, so other contracts' queries and subscriptions are unaffected.

Anchors and ledger-lane parts depend on the ledger-9 generation, in which `emit` exists. Toolchain 0.31.1, which the documentation lists for mainnet, rejects `emit`; without its `emit` statements the Bus Registry compiles with 0.31.1, so `emit` is its only ledger-9 dependency (MPE-OPS-044). The consumer contract's cross-contract read also fails to compile with 0.31.1. Midnight Express therefore reaches a network only after the ledger-9 generation is active there.

**Interplay with MIP-0019.** The ledger lane opts in to MIP-0019's multipart rule under a new, dedicated name. MIP-0019 warns that an existing name opting in would be reinterpreted retroactively, and a new name avoids that. All parts of one MPE Envelope sit in one execution phase of one physical intent and are joined in ledger emission order (MPE-FMT-042, MPE-FMT-045). MIP-0019 recommends the guaranteed phase, but the 16-part call, registrations and Anchors exceed the guaranteed-segment budget and land in the fallible phase. That conclusion is derived from the gas the cost model assigns and from the ledger's partitioning code, not observed. MIP-0019 accepts this if the caller confirms inclusion and the success of that phase before treating the package as published. Because MIP-0019 joins every matching part of an intent into one package, each intent carries one ledger-lane MPE Envelope.

Beyond MIP-0019, the ledger lane adds one validity rule: a group whose part count is not 1, 4 or 16 is discarded as malformed (MPE-FMT-046), so one bad group cannot block valid ones. A generic MIP-0019 reader would rebuild the same bytes as an opaque Sealed Body. The ledger-lane reader can therefore serve as one of the two separate readers that MIP-0019's acceptance requires to reproduce its normative vectors. If MIP-0019 changes while it is still Proposed, the grouping rule stands on its own requirements.

**Existing DApps and wallets.** A DApp that does not adopt Midnight Express sees no change: wallet synchronization, the DApp connector and the Indexer API keep their current behavior. An Indexer operator may index the `Misc` names above "by policy", as MIP-0002 allows, a configuration choice rather than an API change. If MPS-0007 is adopted, a Ledger Adapter could read Anchor notifications and ledger-lane parts from the node itself and check them without trusting an Indexer, with no change to this proposal. MPS-0007 is not a dependency.

Within Midnight Express, the GossipSub topic names of Shards carry the MPE Envelope version. A later version runs on new topics beside the old ones for at least 34 days, 2 × 172,800 s + 30 days, so that no unexpired old-version MPE Envelope is lost during an upgrade (MPE-FMT-024). The first term, twice the 48-hour lifetime of a Message, is the lower bound of the overlap parameter P-FMT-9. The further 30 days is a proposed margin above that bound, with no derivation given. On the ledger, the `Misc` name carries the version, and a new layout takes a new name (Versioning section).
