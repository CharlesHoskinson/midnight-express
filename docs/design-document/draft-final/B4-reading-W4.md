## Receiver privacy

@1998-chor-pir :: The founding paper on private information retrieval (PIR): reading one record of a database without the server learning which. With two or more non-colluding replicated servers, a client fetches one bit while each server sees a query independent of that bit; the two-server scheme needs O(n^1/3^) bits of communication for an n-bit database. One server is another matter. For a single server with information-theoretic privacy, the paper proves that n bits must be exchanged, so downloading the whole database is optimal. Since detecting unknown Envelopes is at least as hard as retrieving a known index [@2026-fisch-unifomr], this bound is the formal reason every Subscriber downloads the whole Shard and tests each Envelope locally (`MPE-PUB-011`). Every later scheme escapes the bound by paying in trust (non-colluding servers) or in computation.
@2013-vansaberhagen-cryptonote :: The CryptoNote whitepaper brought one-time stealth keys to ledgers: a fresh public key per payment that only the intended receiver can recognise. The sender publishes R = rG and pays to P = Hs(rA)G + B; the receiver checks every transaction by recomputing P with its view key a. A tracking key (a, B) given to a third party lets it recognise every incoming payment but not spend it. The salted Recognition Tag follows the same scan-everything model, as a 16-byte HMAC of a fresh salt keyed from the 32-byte stream key that a stream's members share. CryptoNote pays two elliptic-curve multiplications per transaction; the reference system pays one HMAC per stream key. Caveats: the circulating copy carries third-party annotations and no scanning benchmarks.
@2014-gervais-bloomfilters :: Measures what Bitcoin SPV clients leak by sending Bloom filters of their addresses to full nodes. A Bloom filter is a compact bit array whose false positives were meant to act as decoys. They give little cover. Testing all 33 million addresses against real filters, the authors find that a 19-address wallet's filter matches only about 6.1 foreign addresses at the default 0.05 % target rate, so the wallet's own addresses stand out. An adversary holding two filters from one client learns a large share of its addresses, whatever the rate. Hence the requirement set allows filter nodes and Recognition Tag indexes only as labelled opt-in profiles (DEC-021). Caveat: Bitcoin as of 2014.
@2021-liu-omr :: Oblivious message retrieval (OMR). Senders attach a 956-byte lattice clue to each message. An untrusted detector tests every clue under homomorphic encryption, which computes on ciphertexts without decrypting them, and returns a digest of about 9 bits per posted message. From that digest the recipient decodes its own payloads, in about 20 ms for 50 out of 500,000. Detection costs about 0.065 s per message on a small cloud VM and needs a 129 MB detection key. Privacy holds even if all parties are malicious and collude; correctness needs an honest detector. The paper calls this design's choice, download-all, "excessive at scale". Caveat: its clue exceeds the 854-byte payload of the 1,024 B class, the second of four Envelope sizes.
@2021-madathil-privatesignaling :: Defines private signaling in the UC framework and builds it either from one SGX enclave (memory the host cannot read) or from two non-colluding servers running garbled circuits. The recipient fetches only its own row, at constant cost. Trial decryption of 500,000 signals at 0.012 s each takes about 100 minutes. Fuzzy message detection, in which a server flags the recipient's messages plus a tunable fraction of others as cover, leaves an anonymity set of only about 15 at false-positive rate 2^-15 (500,000 × 2^-15). A footnote concedes that no server-aided scheme can beat a recipient that stays online and decrypts each signal. Caveats: the baseline uses public-key decryption, and the model rules out the shared keys that invitations supply here.
@2022-henzinger-simplepir :: SimplePIR and DoublePIR make single-server PIR from learning with errors (LWE, a lattice assumption) run near memory bandwidth, at 10 GB/s per core. Before its first query, a client must fetch a hint, a digest of the database. For 1 GB, SimplePIR needs a 121 MB hint and about 242 KB per query; DoublePIR needs 16 MB and about 345 KB. That suits static data. A Store Node's 48 hours of Envelopes change every second, so the hint goes stale, and the client must also know which index to request. PIR therefore suits back-fill of known Envelopes (those missed while offline), not detection of unknown ones.
@2022-monero-pr8061-viewtags :: The Monero change that adds to every output a one-byte view tag, the first byte of a hash of the shared secret between sender and receiver. A receiver skips the costly key derivation for about 99.6 % of outputs (1 − 1/256), and the author measured scanning-time reductions of 30 to 40 %. It is the deployed precedent for a cheap recognition hint beside a sealed payload, though only a filter: the receiver must still compute the shared secret with its view key before testing it. The 16-byte salted Recognition Tag differs in kind. It is a keyed HMAC whose 128-bit width makes false candidates negligible.
@2022-penumbra-fmd-spec :: Penumbra's specification of sender-chosen fuzzy message detection (S-FMD). Each output carries a clue of hashed-ElGamal bits; the sender encrypts n of them, fixing the false-positive rate at 2^-n. A detector holding a recipient's detection key flags true and false matches alike. Consensus fixes n (the clue's precision) and rejects clues not made at the current precision, after a grace period of 10 blocks. It also requires dummy clues up to one per output, so the clue count hides the number of recipients. The specification sets no numeric floor on the rate and leaves open what happens when an adversary inflates traffic. Citing that missing floor, the requirement set keeps S-FMD out of default light reception (reception by a client that cannot take a whole Shard) and allows it only as a labelled opt-in profile (DEC-021).
@2025-goes-multiserverfmd :: Extends fuzzy message detection to several servers, each holding a share of one detection key and seeing a high false-positive rate. With three servers and an honest majority, each server sees rate 2^-6 while the receiver combines their results to about 2^-18. The authors judge safe single-server rates to lie above 2^-6. They also recall an attack that links two messages to the same recipient with probability above 0.5 at rate 2^-8 among a million users. Because these figures come from the technique's own proponents, they support keeping fuzzy clues off the delivery path. Caveats: an honest majority is required, and senders and receivers are assumed to have communicated before.
@2026-fisch-unifomr :: Proves that oblivious message retrieval is at least as hard as PIR over a database of the same size, then builds UnifOMR from additively homomorphic encryption plus batch PIR (several records in one query). At 2^19 messages of 612 bytes it finishes in about 25 s with 4 MB of communication and a 31 MB detection key; an earlier OMR scheme takes more than 1,250 s. The paper's download-all baseline fetches only each message's 48-byte clue, 24,576 KiB in all (2^19 × 48 B), and spends 27.6 s on one key agreement per clue; UnifOMR's detection step needs over 1,000 times less recipient time [@2026-fisch-unifomr, p. 37]. This design also downloads everything. In time it gains on the baseline: 2^19 Recognition Tag tests at 0.2 to 0.5 µs take 0.1 to 0.26 s per stream key, 106 to 276 times less than 27.6 s (derived). In bytes it loses. A Subscriber fetches whole Envelopes, payloads included, and 2^19 of the smallest (776 bytes on the wire, about 16 times a 48-byte clue) come to at least 397,312 KiB (derived). UnifOMR beats this design on both counts, with about 4 MB of communication and about 28 ms of recipient time [@2026-fisch-unifomr, p. 37], while its detector spends 25 s of work and holds a 31 MB key. Caveat: correctness assumes a semi-honest detector. Against the requirement set's mobile budget for light reception, 56 to 60 MB per day (DEC-021), whole-Shard download costs about 1.7 GB per day (measured); whether a measured OMR or PIR profile fits is open.

## Sessions, groups and post-quantum key exchange

@2014-melara-coniks :: CONIKS publishes each epoch a signed, hash-chained root of a Merkle prefix tree of user keys, with names hidden behind a verifiable random function. Clients check their own binding and can catch a provider showing different users different keys. Monitoring costs under 20 kB per user per day and auditing 2.5 kB per provider per day, even at billions of users. On Midnight the ledger already gives the single global view that CONIKS gets by cross-checking roots, so Bus Registry roots need no separate audit. Clients must still monitor their own entries. CONIKS detects equivocation but does not prevent it, and does nothing for compromised endpoints.
@2016-cohngordon-signal :: The first formal analysis of Signal's X3DH handshake and Double Ratchet, as a multi-stage key exchange. Forward secrecy means a key stolen today does not expose earlier messages; post-compromise security means a session heals after a compromise once fresh randomness enters it. Under the Gap Diffie-Hellman assumption, with key derivation functions modelled as random oracles (idealised hashes), each message key is shown to stay secret under freshness conditions that capture both properties; healing comes from fresh Diffie-Hellman entropy at each asymmetric ratchet step. Caveats: the reduction is far from tight, honest key distribution is assumed, and groups, multiple devices and deniability are out of scope. The analysis sets out what the optional pairwise profile of DEC-002 would deliver. A broadcast stream key replaced only on revocation can claim neither property.
@2018-bindel-hybrid-kem-ake :: Defines security for hybrid key encapsulation against an adversary that is classical today and gains quantum power later. A key encapsulation mechanism (KEM) delivers a fresh random key to the holder of a private key; a hybrid KEM runs a classical and a post-quantum KEM together. The paper proves three combiners in the standard model (without random oracles), including XtM, the first proven against fully quantum adversaries, and compiles hybrid KEMs into authenticated key exchange. Its main result is that classical signatures suffice against such an adversary but the KEM must resist quantum attack; otherwise only classical security remains. For invitations this is the record-now, decrypt-later risk. A stream key sent over a classical key agreement could later be recovered by anyone who recorded the invitation, exposing every Envelope they recorded under that key, not only the 48 hours that Store Nodes retain.
@2018-giacon-kem-combiners :: Shows how to combine several KEMs into one that stays secure against chosen-ciphertext attack (CCA) if any one ingredient is. Under CCA, an attacker that can decrypt chosen ciphertexts learns nothing about any other. The naive XOR of the component keys is proved not to preserve CCA security; the secure combiners hash the keys together with the ciphertexts, or apply a pseudorandom function to them. The standard-model versions pass over the whole ciphertext vector n times, a cost that grows with the size of post-quantum ciphertexts, and several proofs rely on random oracles or ideal ciphers. Any hybrid profile for invitations or pairwise sessions must therefore use a proven combiner, never ad hoc XOR or concatenation.
@2018-lund-sealedsender :: Signal's announcement of sealed sender. The sender certificate and message are wrapped in an envelope keyed to an ephemeral key and the recipient's identity key, then handed to the service without authentication. Abuse protection passes to a 96-bit delivery token derived from the recipient's profile key. Only contacts can derive it, so the service learns that a permitted sender wrote, not which one. The service still learns the recipient, the time and the sender's IP address, and the post names traffic correlation as unsolved. It is the closest deployed analogue to this design's one-hop ingress, where the first Bus Node sees the Publisher's connection but nothing in the Envelope names the Publisher. Admission does the token's job here: a Bus Node relays an Envelope only if its admission slot shows a registered membership, and the analogy holds only if the check hides which one. The zero-knowledge proof intended for production would hide it. The prototype's stand-in does not, since relays hold the members' secrets, can link each Envelope to its membership and could forge admission.
@2020-tujner-qsor :: Benchmarks six round-2 NIST KEMs inside a simplified Tor, with post-quantum and hybrid circuit creation. With Kyber512 (800-byte public key, 736-byte ciphertext) the cost that matters is size, not computation. A full circuit build grows from 1,223 bytes in 3 packets to 3,248 bytes in 7, and to 5,774 bytes in 12 for the hybrid. Fixed-size Envelopes meet the same limit: one Kyber512 key and ciphertext take 1,536 bytes, more than the 854-byte payload of the 1,024 B class, so post-quantum key material overflows small cells long before it costs much CPU. Caveats: the measurements leave out network latency, the hybrid combines keys with plain XOR, and its preferred scheme, SIKE, has since been broken.
@2021-len-partitioningoracle :: Shows that AEAD schemes (the standard authenticated symmetric encryption) which are not key-committing, that is, which do not bind each ciphertext to one key, admit splitting ciphertexts. Such a ciphertext decrypts under every key in a chosen set, whose size is its degree, and fails under all others. An attacker who learns whether decryption succeeded thus tests many keys per query and can binary-search the key space; against Shadowsocks this recovered a password 20 % of the time with 124 ciphertexts. The attack needs low-entropy keys, or a setting where recipient anonymity matters. For Poly1305 the authors reached only degree ten, so ChaCha20-Poly1305 is less exposed than AES-GCM. In response, the requirement set draws every stream key as 32 random bytes (`MPE-PUB-006`). A Subscriber opens candidates under up to 256 keys (the cap P-CRY-4), so it must not react visibly to a failed open.
@2022-hashimoto-mls-metadata :: Wraps MLS-style continuous group key agreement (a group secret renewed in numbered epochs as members join, leave or update) so that the server no longer learns who belongs to a group or who sent a message. Each epoch derives a group signature key from the group secret, and members authenticate anonymously over an anonymous channel. The paper gives post-quantum instantiations, and bandwidth at most doubles, on upload only. It lists what standard MLS exposes: group identifier, epoch, member identities and access counts, and group size through Welcome messages, which admit new members. It argues against letting relays see group structure; this design gives them no group identifier and pays with whole-Shard download.
@2022-maram-pq-anonymity-kyber :: Proves that round-3 Kyber, and hybrid encryption built on it, is anonymous under chosen-ciphertext attack (ANO-CCA) in the quantum random-oracle model, assuming module learning-with-errors is hard; the same holds for Saber. Anonymity means a ciphertext does not reveal which public key it was made for, and it needs a strongly pseudorandom DEM (the symmetric half of hybrid encryption). Robustness, meaning that a recipient rejects ciphertexts meant for someone else, needs a robust DEM, because under implicit rejection a wrong secret key yields a pseudorandom key, not an error. A post-quantum first-contact profile (contact without a prior invitation) or pairwise profile needs anonymity so that Envelopes do not reveal their recipient. Caveats: the bound is not tight, the analysis predates FIPS 203, and only classical decapsulation queries are allowed.
@2023-balbas-sender-keys :: The first formal model of Sender Keys, the group scheme of WhatsApp, Signal, Matrix and Session. Each member hash-ratchets a symmetric chain key (replacing it with its hash after each use) and distributes it over pairwise channels. The model finds only limited post-compromise security, since even a manual update need not heal the group, and control messages that require high trust in the server. Its Sender Keys+ restores group-wide healing at O(n) total download, against O(n log n) for TreeKEM, a binary-tree group key agreement. This design's broadcast profile is weaker than plain Sender Keys. One stream key, shared by every holder, is replaced only on revocation and never ratcheted.
@2023-barnes-rfc9420 :: The IETF standard for Messaging Layer Security (MLS). A ratchet tree of HPKE keys and a per-epoch key schedule give a group forward secrecy and post-compromise security; a member re-keys with about log N encryptions instead of N - 1. Section 16.4.1 says the group identifier, the epoch and the message frequency are visible to the Delivery Service, and that a party who sees every commit can reconstruct membership. Forward secrecy holds only once every member has deleted old keys. MLS is a candidate upgrade for private audiences, but its commits and Welcome messages would have to travel inside sealed Envelopes so that relays never see an epoch.
@2024-barbosa-xwing :: X-Wing is a hybrid KEM joining ML-KEM-768 (NIST's post-quantum KEM of FIPS 203, derived from Kyber) and X25519 through SHA3-256. It leaves the ML-KEM ciphertext out of the hash because ML-KEM resists second preimages on ciphertexts. It is IND-CCA secure if either component holds: classically under strong Diffie-Hellman, post-quantum under ML-KEM-768. The public key is 1,216 bytes and the ciphertext 1,120 bytes. X-Wing is the default candidate for a post-quantum invitation or first-contact profile. Its ciphertext exceeds the 854-byte payload of the 1,024 B class, so such a message needs the 4,096 B class, whose 3,926-byte payload holds it. Caveat: the shortcut holds only for these component choices. It remains open whether invitations pay for the larger class or accept the record-now, decrypt-later risk.

## Consumers, edge and IoT publish/subscribe

@2018-arnautov-pubsubsgx :: PubSub-SGX runs content-based matching (subscriptions are conditions on a publication's fields, not topic names) in plaintext inside Intel SGX enclaves, so the broker operator cannot read publications or subscriptions. With 40-attribute subscriptions, throughput peaks near 90 publications per second on 8 instances, and SGX adds about 30 % overhead on average. A Midnight application could run this trusted-hardware broker on its own server. This design does not, because trust moves to the enclave vendor and the paper does not discuss side channels. The host still sees timing and volume, and subscribers authenticate with certificates. Caveat: the workload is synthetic.
@2019-redondi-scalediot :: A position paper on running MQTT brokers on 5G edge servers. MQTT is the common lightweight publish/subscribe protocol for devices, in which a broker forwards messages on named topics; these brokers also filter and aggregate device data. The paper notes that topic bridging between brokers is equivalent to event flooding, "known to not scale well", and calls the broker the component "ultimately controlling all aspects of communication". There is no evaluation. The mainstream IoT answer for constrained consumers is thus a plaintext broker. A sensor cannot download a Shard of 1.7 GB per day, so on Midnight it would need a trusted gateway of this kind.
@2020-vac-waku2-filter-spec :: The Waku v2 filter protocol lets a light node, a client that keeps no mesh and relays nothing, register content topics with a full node. The full node pushes matching messages best-effort, without bundling or retransmission. The specification states the cost: light nodes "need to disclose their liking topics to the full nodes", and anonymous subscription is not supported. Its adversary model leaves out a global observer. It is the libp2p-native form of the unicast filter node, which the requirement set allows only as a labelled opt-in profile (DEC-021). Caveats: it is a living draft, and its suggested remedies (Tor, oblivious transfer, private set intersection) are not specified.
@2021-blazy-iot :: A topic-based MQTT framework built from attribute-based cryptography. It encrypts payloads with ciphertext-policy attribute-based encryption (any key whose attributes satisfy the publisher's policy decrypts) and hides topics with searchable encryption, so the broker matches trapdoors (subscribers' search tokens) without reading topics. Publishers sign with attribute-based signatures. Costs on a Raspberry Pi 3 are heavy: encrypting a topic takes about 1.9 s and signing about 12 s, and each publication carries about 37 kB. The authors concede that full trapdoor privacy is nearly impossible because trapdoors are reused, so the broker still learns which subscriptions match which publications. Broker-side matching on encrypted topics costs that much time and that leakage; a local Recognition Tag test costs 0.2 to 0.5 µs per stream key.
@2024-kotzer-bitcoinlightclients :: Compares the privacy of Bitcoin light clients on April 2023 data: Bloom-filter SPV against Neutrino's compact block filters, which the client tests locally before fetching whole matching blocks. Over 30 days, for a client with 50 addresses, downloading everything costs 12.3 GB (about 410 MB per day, against 1.7 GB per day for one Shard here), PIR 204 MB, and Bloom filters set to 40,000 false positives 2.36 MB. Neutrino leaks through which whole blocks a client fetches. The detection ratio for ten addresses rises from 0.11 after one day to 0.26 after 30 days. Back-fill and second-source reconciliation (a per-window check against a second source's inventory) must avoid such a fetch pattern. Caveats: the wallets are simulated, and the adversary is one passive full node. It leaves open how a Subscriber can fetch missed windows without a request pattern that singles it out over days.
