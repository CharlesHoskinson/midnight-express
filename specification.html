FORMAL SPECIFICATION / MODEL v0.2

Make the rules
precise.

A quote must add up. A payment observation must preserve what its source claimed. An approval must stay bound to the work a person reviewed. The formal model expresses those requirements as mathematical conditions that Lean can check.

Lean is a programming language and proof assistant. It checks that a proof follows from the definitions and assumptions in its source. This specification covers a typed model of the local reference software; a successful validation returns executes:false.

THE AGREEMENT

Choose an exact meaning.

An event names a profile and an exact contract commitment. The receiver uses a reviewed, installed contract to interpret its business data. Unknown contracts are refused.

Profile
A bounded workflow with declared fields and business rules, such as a whole-share USD quote.
Contract commitment
A fingerprint identifying the exact definitions and rules. A version label alone cannot establish that two applications installed the same agreement.
Validation context
Trusted inputs supplied by the application, including current time, source evidence or authority policy. A theorem about those inputs does not establish how they were obtained.
Candidate
The checked interpretation that an application can consider. Execution requires a separate effect boundary and a fresh authority decision.

What enters the mathematical model?

The model starts from typed values. It represents the fields and comparisons needed by each rule. The real reference also checks raw JSON grammar, closed schemas, canonical decimal strings, byte limits and installed bundle resources before constructing a candidate.

That parsing and loading pipeline needs its own assurance. Lean's typed values cannot contain an undeclared profile constructor, but that fact alone does not prove that a JSON parser rejects an unknown field or misspelled profile.

RFQ / EXACT ARITHMETIC

A quote must add up.

A buyer requests 100 shares at $123.45 per share. The contract records price and cash as integer cents, so the cash check has no floating-point rounding step.

Cash in USD cents

cash = quantity × price

1,234,500 = 100 × 12,345

Here, quantity is a positive whole number of Shares and price is a positive number of cents per Share. The cash amount is $12,345.

Translate a declared convention.

A second source format quotes 1,234,500 cents per 100 shares from the dealer's selling perspective. Its reviewed adapter divides the block price by 100 and converts the perspective to the buyer's purchase. The resulting terms agree only when the complete source-bound business meaning agrees.

If the source omits the price basis, the adapter cannot infer it. A quote with cash of 1,234,501 cents also fails: its total differs by one cent from the required product.

Quote validity at the supplied current time

event.time ≤ validFrom ≤ now < validUntil

The opening instant is included. The expiry instant is excluded. At exactly validUntil, the quote is expired. Its record time must also be no later than the opening instant.

How decimal scale relates to the arithmetic

The reference decimal form is coefficient × 10⁻scale. For USD, 12345 × 10⁻² = 123.45. Whole-share quantity uses scale zero; USD amounts use scale two. Canonical coefficient strings are positive and bounded to 18 digits.

The arithmetic theorem applies to the modeled integer quantities after interpretation. It does not prove the decimal parser, adapter implementation or wire encoding correct. Independent RFQ interpreters in Python, Rust and TypeScript provide separate evidence from finite conformance cases.

INVOICE / REPORTED EVIDENCE

Preserve the payment claim.

A source reports a $250 payment against a $500 invoice. The observation identifies the payment, carries its status and matches the complete evidence supplied in the validation context.

Amount admitted for every status

0 < observedAmount ≤ invoicePayable

0 < 25,000 ≤ 50,000 cents

The same amount bound applies to Pending, Final and Reversed. A reversal remains an observation of what the source reported.

Ordered observation clocks

effectiveAt ≤ observedAt
≤ event.time ≤ now

The source says the payment took effect at 10:00; an observer sees it at 10:05 and records the event at 10:06. Validation at 10:07 admits that ordering. A record time before the observation time fails.

Final means that the source asserted final status and the supplied evidence matched. It does not prove bank or blockchain finality, allocate a payment to an invoice or instruct a transfer. Several accepted observations also need separate accounting rules before their amounts can be added.

AGENT / BOUNDED APPROVAL

Keep permission attached
to the reviewed work.

The approval profile covers one sandbox operation: writing a report. The proposal fixes its input and target, with an authority domain, execution scope, budget window, policy and expiry.

Suppose a human approves a report for one sandbox target. Changing the target or input changes the proposal being checked. A matching action label cannot carry that approval to different work. The model compares the approval against the supplied proposal and authority context.

Stable action identity

actionKey =
(authorityDomain, executionScope, actionId)

A new event identifier does not change this key. The consumed action remains the same work even when another delivery asks for it again.

Validation stops at a candidate.

Every successful modeled validation has executes:false. A report-writing host must check current permission again at the effect boundary. Revocation, budget consumption and expiry can change after a message arrives.

The local recovery prototype writes a database report row in a transaction. The formal data model does not prove that Python, JavaScript, PostgreSQL or a remote destination implements the whole authority and recovery contract.

IDENTITY / RETRIES & HISTORY

Know what has repeated.

Occurrence identity
Identifies one event occurrence. Reusing it with changed content must expose a conflict.
Business intent
Includes source, exact profile and contract, and the complete typed business data. Occurrence ID and record time are excluded, so re-emitting the same intent can preserve its candidate fingerprint.
Action identity
Identifies work within an authority domain and execution scope. Once a candidate records this key, later occurrences preserve its intent binding. Execution and budget consumption belong to a separate effect boundary.
Transport EID
Identifies a protocol envelope. It belongs to a different layer from the business intent and the action key.

Intent fingerprint used by the reference

SHA256(JCS({domain, source, type,
profile, contract, data}))

The domain is mpe.model.intent.v0.2. JCS means JSON Canonicalization Scheme: a defined serialization that gives agreed data reproducible bytes.

Preserving the modeled intent under a change of occurrence metadata is a structural statement. The structural journal compares the complete typed event and business intent directly. The Python reference stores JCS/SHA-256 digests, so hash behavior, canonicalization correctness and source authentication remain separate obligations. Two different dealers keep different source identities even if their prices match.

What happens when a contract changes?

A meaning-changing edit creates a new immutable commitment. Historical events retain their original contract. The local reference installs exact reviewed bundles and refuses unknown commitments; it does not fetch a definition from a sender's URL.

The v0.1 release remains historical and read-only. Interpreting old data does not authorize a new effect. Authenticated bundle distribution and live workflow migration remain outside this model's guarantees.

SUBSCRIPTIONS / PROPOSED LOCAL CONTROL PLANE

A watch records what
a consumer wants to receive.

The local subscription demo explores selectors, pauses, cursors and retention gaps. A watch's intent and delivery state are separate from the v0.2 business-event profiles above.

A delivery cursor describes local receipt. A processing cursor describes contiguous decisions about received items, including reviewed or quarantined dispositions. Neither establishes that an action executed. A pause records the consumer's request; permission expiry or revocation still prevents delivery.

Selectors are proposed to run locally after authorized decryption. They cannot restrict what an authorized reader of the whole shard can see. The browser demo uses simulated permissions and tab memory, with no protocol transport or production authority service.

The v0.2 profile proofs below do not establish the subscription demo's behavior. Watch rules require their own explicitly scoped state model and implementation evidence.

PROOF COVERAGE

Read each guarantee
with its assumptions.

A soundness theorem connects a successful modeled check to a stated condition. For example, accepting a modeled quote implies that its cash amount equals quantity multiplied by price.

The shape of a validator guarantee

validate(event, context) = accepted
⇒ requiredConditions(event, context)

This implication quantifies over the typed values in Lean. It depends on the supplied context. Tests against real JSON provide a separate, finite comparison with the reference implementation.

The modules and examples build successfully with Lean 4.34.1 and its bundled standard library. The named theorems below state properties of the definitions in Model.lean Validation.lean and Replay.lean. The project contains no admitted proofs or custom axioms.

  • The executable gates agree with their named mathematical predicates. An accepted result satisfies the common and workflow conditions; rejection means those conditions do not all hold.validation_sound · validation_complete · validation_rejected_iff
  • Dispatch requires the exact release agreement. The reference tag decoders reject unknown profile and operation strings. A complete wire decoder remains outside the proof.dispatch_requires_exact_envelope · unknown_profile_rejected · unknown_operation_rejected
  • An accepted quote carries the exact decimal product as cash and obeys the half-open validity interval. The product must fit the coefficient bound.accepted_quote_exact_decimal_product · accepted_quote_half_open · product_valid_iff_within_bound
  • An accepted payment observation matches the complete supplied evidence, has ordered clocks and stays within the invoice amount. A Final verdict requires Final in that evidence record.accepted_invoice_complete_evidence · accepted_invoice_clocks_and_amount · final_verdict_requires_final_record
  • An approval stays bound to the supplied proposal, policy, human and permitted target. Expiry and a changed policy reject it. Removing authority or reducing the budget cannot turn a rejected event into an accepted one.accepted_approval_authority · expired_approval_rejected · stale_policy_approval_rejected · authority_narrowing_cannot_reauthorize
  • Replay compares event content and structural intent, with no caller-supplied digest token. Changed content under an occurrence key conflicts. A new occurrence with the same action and intent is a duplicate; changed intent under a recorded action conflicts in a reachable journal. Current validation runs first.structural_occurrence_conflict_rejected · structural_same_action_new_occurrence_duplicate · structural_reachable_action_conflict_rejected · structural_invalid_now_cannot_replay
  • A journal built from successful checks has unique keys and consistent occurrence/action bindings. Later checks preserve recorded bindings. Across a sequence with changing contexts, an action key produces at most one fresh candidate.reachable_wellFormed · reachable_unique_keys · run_at_most_one_fresh_candidate · run_preserves_action
  • Occurrence ID and record time are excluded from business intent. Changing an approval target preserves its action key and changes its intent. Results carry executes:false by construction: this model has no effect operation.occurrence_metadata_does_not_refresh_intent · changed_target_keeps_action_key · changed_target_changes_intent · structuralCheck_never_executes
What does the replay proof assume?

The journal is a sequential in-memory model. It stores complete typed events for occurrence identity and structural business intents for action identity. The proofs do not depend on a hash being injective. Starting from an empty journal and threading successful results produces the reachable states used by the coherence theorems.

The supplied context still determines current validity. Remembering an event does not restore an expired or revoked approval. Durable atomic storage, concurrent workers, crashes and external effects need separate implementation evidence.

How are the proofs kept current?

The build uses the pinned Lean compiler, treats warnings as errors and audits dependencies of project-owned declarations. It rejects proof placeholders and custom axioms. Profile checks compare the definitions with the installed release bundles; publication checks keep source downloads and cited theorem names synchronized.

The fixture bridge checks isolated semantic failures and stateful sequences against the Python reference. Its strict translator preserves the typed meaning and refuses unread fields or unsupported fixed tags. Those finite comparisons remain tests of the translator and implementations, separate from the general Lean theorems.

What still needs external evidence

  • The JSON parser, Unicode and decimal grammar, closed schemas, resource bounds and conversion from raw input to Lean's typed values.
  • JCS canonicalization, SHA-256 behavior and collision resistance, signatures, encryption, source authentication and admission to the private protocol.
  • The correctness and freshness of supplied time, source evidence, human identity, policy and revocation information.
  • The running Python and other interpreters, adapters, durable stores, network delivery, concurrency and external effects. The Lean model is not an end-to-end verification of those programs.
  • Bank settlement, blockchain consensus and real partner conventions. A matching fixture cannot establish those facts.

SOURCES & REPRODUCTION

Inspect the definitions.

The equations and examples on this page are readable without repository access. The published Lean source files provide the exact definitions behind the proof claims.

  • Scope and reproduction guide
  • Model.lean: values, profile dispatch, arithmetic and identity
  • Replay.lean: content identity and journal trace proofs
  • ProfilePins.lean: installed release checks
  • Language-neutral event and sequence vectors
  • Semantic condition coverage and exemptions
  • Validation.lean: executable checks, acceptance proofs and replay
  • Examples.lean: concrete accepted and rejected cases
  • Project entry point, build configuration and pinned toolchain

With the files in the same directory layout and Lean's toolchain manager installed, run:

cd formal/lean
lake build

The Python fixture bridge requires the full repository and its model dependencies. The downloaded Lean project builds independently with the pinned toolchain.

A clean build checks the general proofs and the concrete examples. The examples cover selected cases; agreement on a finite corpus is separate from a general proof that the production parser and validator implement this specification.
