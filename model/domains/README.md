# Proposed Ethereum and Solana application domains

[chain-event-catalog.json](chain-event-catalog.json) contains 291 **proposed vocabulary entries** across 20 families for each chain. It covers common chain observations, decoded standard/program semantics, local reconciliation claims, application intents, RPC request/response and subscription controls. It is a bounded design inventory, not an exhaustive list of provider RPCs, program ABIs or future chain features. No entry is an implemented event contract, authenticated evidence or permission to execute.

The accompanying [closed metadata schema](catalog.schema.json) validates this inventory's fields. It deliberately defines no event payload, runtime finality enum, adapter, proof verifier or executable profile. Stable IDs follow `mpe.<chain>.<family>.<semantic-name>.v<version>`; this version names the vocabulary only. Reuse of a family across chains does not imply equivalent semantics or interoperable payloads. A future incompatible meaning requires a new identity/version, not silent reinterpretation.

The design context is the [Ethereum application domain](../../docs/product-requirements/ethereum-application-domain.md), [Solana application domain](../../docs/product-requirements/solana-application-domain.md) and [unified model](../../docs/product-requirements/unified-data-model.md). Detailed native method inventories and dated source captures live in [the Ethereum archive](../../catalog/data-model/ethereum/) and [the Solana archive](../../catalog/data-model/solana/). Catalog sources include additional illustrative program documentation beyond those archives; a primary URL is research provenance, not a pinned deployment or cryptographic trust root. `sourceReviewedOn` records the design review date, not the date every source was last modified.

Every entry records its chain, family, semantic name, source primitive/standard, primary source URL, message kind, scope, evidence kind, qualification, proposed status and `effectAuthority:false`:

- `native`: a chain/RPC/wallet surface, still merely a provider observation until its authenticity is established.
- `decoded`: an interpretation requiring the exact standard, deployment, ABI/program decoder and version.
- `derived`: a local claim requiring inputs, policy and derivation provenance. Cancellation, expiry, replacement, gaps and completed backfill claims never become native consensus facts by naming them.
- `intent`: requested action, query or subscription control; it provides no execution evidence or permission. Generic application intents are explicitly local mappings rather than assertions that every chain exposes the same API.

Queries, simulations, gas/fee estimates, signing, submission of signed bytes, acceptance responses, execution results and finality observations remain separate. Cancelling a local listener or unsubscribing does not cancel a submitted transaction. RPC responses must preserve result/null/error distinctions, method/version, request correlation, endpoint/session, queried network and selectors; provider limits and unsupported methods remain explicit. Local claims retain original transaction identities, nonce/blockhash and expiry evidence, relation to replacement attempts, uncertainty, scope and observation interval.

Ethereum `safe`/`finalized` block selectors and Solana `processed`/`confirmed`/`finalized` commitment reports keep their native names and provenance. There is no shared boolean or blanket `confirmed` enum. Resolve selectors to concrete hashes/heights or slots where available. A finalized report is observational and does not authorize an economic effect. Reorgs, removed logs, dead slots, unavailable history and skipped slots remain different cases. Include invalidation references and replay cursors; backfill completeness is bounded to a stated range, filter, source and commitment.

ERC-20, ERC-721 and ERC-1155 contracts are distinct from SPL Token, Token-2022 extensions, Metaplex Token Metadata and Metaplex Core account/plugin models. Names, tickers and decimals are metadata, not asset identity. Program/account ownership, wallet account exposure, token delegates, operator approval and executor permission have different meanings. Logs, outer instructions, CPI/inner instructions, program return data and account changes require separate evidence paths; logs/instructions from a failed Solana transaction do not establish successful economic effects. Protocol examples such as Uniswap, Aave, Orca, Kamino, Drift, Pyth, Chainlink, Realms and Wormhole require their own deployment/version-specific profiles; a source bridge message does not establish destination settlement.

Future chain contracts must define their own numeric and byte primitives. The existing pilot's positive 18-digit decimal is unsuitable. Ethereum uint256 values and Solana u64 quantities include zero and require full bounded integer precision; signed deltas/exposures require explicit signed ranges. Preserve raw units separately from decimals, prices, fee amounts and human display. Address/hash/signature codecs and decoded byte lengths are chain-specific. Large blocks, batches, logs and account blobs require bounded projections/pages or separately reviewed evidence-reference contracts with content digests and explicit omissions. Catalog source URLs never trigger runtime fetches.

Before a candidate enters the runtime, it needs a complete closed payload schema, exact field meanings and numeric bounds, version/manifest commitment, deployment/decoder binding, source authentication and finality policy, state machine, fixtures and negative cases, two independent adapters and cross-language conformance. Any signing/broadcast/economic effect additionally needs an authenticated current capability, complete immutable proposal, expiry/revocation checks, durable atomic replay/effect state and unknown-outcome reconciliation. That work is deferred; the active [v0.2 model](../README.md) continues to accept only its three pinned pilot profiles.

Run the separate offline metadata checks from the repository root:

```bash
/tmp/mpe-data-model-validation-env/bin/python model/domains/test_catalog.py
```

The script uses the existing pinned `jsonschema` dependency, rejects unknown fields, checks identity uniqueness/namespace agreement, family coverage on each chain, source URI shape, request/evidence separation and proposed/no-authority constraints. Negative tests cover attempted authority/implementation escalation and mistaken promotion of local claims. It does not retrieve URLs, validate chain payloads, verify proofs or demonstrate adapter interoperability. No pinned pilot artifact is modified by these checks.

## Corrected vocabulary release

The original 267-entry catalog is preserved in [releases/0.1.0](releases/0.1.0/chain-event-catalog.json). The current release corrects RPC/instruction and raw/decoded classifications, uses new vocabulary IDs with supersedes for changed meaning, and adds bounded wallet/submission/bridge/token lifecycle candidates. [semantic-index.json](semantic-index.json) checks released classification identity; changing both index and catalog is a new maintainer-reviewed release, not cryptographic installation authority. [support-matrix.json](support-matrix.json) distinguishes typed candidates, raw/generic-only stages and out-of-scope behavior. Narrow read-only fixture projections live in [chains](../chains/observations.py); they do not make the entire catalog executable.
